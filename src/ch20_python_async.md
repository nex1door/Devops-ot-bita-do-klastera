# Глава 20. Асинхронность: asyncio

Сетевой клиент, который опрашивает сотню хостов, почти всё время ждёт: ответа DNS, TLS-рукопожатия, тела ответа. Потоковое ожидание — самая дорогая часть работы, и `asyncio` позволяет ждать тысячу вещей одновременно в одном потоке, не платя за тысячу стеков. Это не «Python стал многопоточным» и не ускорение вычислений: это способ не простаивать на вводе-выводе.

Глава объясняет, как устроен цикл событий ({{L|g37|event loop}}), чем корутина отличается от задачи, как правильно запускать конкурентную работу и ограничивать её, как работают таймауты и отмена, что делать с блокирующими вызовами и почему `asyncio` бесполезен для CPU-bound задач. Отдельный раздел — типичные ошибки, из-за которых асинхронный код работает медленнее синхронного. Примеры проверены на CPython 3.14.9, все замеры времени — реальный вывод на тестовой машине.

## Цикл событий: один поток, много ожиданий

Event loop — планировщик кооперативных задач. Он держит очередь готовых к выполнению корутин и набор файловых дескрипторов с таймерами; когда корутина доходит до `await` на операции ввода-вывода, управление возвращается в цикл, а цикл тем временем запускает другие готовые корутины. Поток всё это время один.

Отсюда два следствия. Хорошее: переключение между задачами стоит сотни наносекунд, а не микросекунды, как переключение потока ОС, и память на задачу — килобайты, а не мегабайт стека. Плохое: любая операция, которая блокирует поток, блокирует **все** задачи. Синхронный `time.sleep(1)` внутри корутины останавливает весь сервис на секунду.

Кооперативность означает, что переключение происходит только в точках `await`. Между ними корутина выполняется непрерывно, и гонок в привычном смысле нет — но и вытеснения тоже: цикл не отнимет управление у корутины, которая считает что-то в цикле `while True`.

## Корутины, `await` и точки приостановки

`async def` создаёт корутину. Вызов такой функции не выполняет тело, а возвращает объект-корутину; тело начнёт выполняться, когда кто-то сделает `await` или обернёт её в задачу.

```python
import asyncio

async def fetch(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return f"{name} ok"
```

`await` означает «приостанови меня здесь, пока результат не готов, и дай поработать другим». `asyncio.sleep` — асинхронный аналог `time.sleep`: он не блокирует поток, а регистрирует таймер в цикле. Всё, что вы ждёте через `await`, должно быть асинхронным: `await httpx.AsyncClient.get(...)`, `await asyncio.open_connection(...)`, `await queue.get()`.

Разница между последовательным и конкурентным ожиданием измерима:

```python
async def main() -> None:
    t0 = time.perf_counter()
    for name in ("a", "b", "c"):
        await fetch(name, 0.2)
    print(f"sequential {time.perf_counter() - t0:.2f}s")

    t0 = time.perf_counter()
    res = await asyncio.gather(fetch("a", 0.2), fetch("b", 0.2), fetch("c", 0.2))
    print(f"gather {time.perf_counter() - t0:.2f}s {res}")

asyncio.run(main())
```

```text
sequential 0.60s
gather 0.20s ['a ok', 'b ok', 'c ok']
```

Три запроса по 0,2 с: последовательно — 0,6 с, конкурентно — 0,2 с. Ускорение равно числу одновременных ожиданий, а не числу ядер, — и на тысяче запросов разница будет тысячекратной по времени ожидания. `asyncio.run()` создаёт цикл, выполняет корутину до конца и закрывает цикл; это единственная точка входа, которую стоит использовать в приложении.

## Задачи: `gather` и `TaskGroup`

`await coro()` выполняет корутину, но не даёт её отменить или запустить отдельно. Для этого нужна задача (Task) — обёртка, зарегистрированная в цикле: `asyncio.create_task(coro)`.

`asyncio.gather` запускает несколько awaitable и возвращает список результатов в порядке аргументов. Важная деталь — обработка ошибок: по умолчанию первое исключение пробрасывается наружу, но остальные задачи **продолжают работать**. С `return_exceptions=True` ошибки возвращаются как значения:

```python
async def boom() -> None:
    raise ValueError("bad response")

res = await asyncio.gather(boom(), asyncio.sleep(0.01, result="ok"), return_exceptions=True)
print(res)
```

```text
[ValueError('bad response'), 'ok']
```

С Python 3.11 предпочтителен `asyncio.TaskGroup` — структурная конкурентность: если одна задача падает, остальные отменяются, а исключения собираются в `ExceptionGroup`.

```python
async def ok(i: int) -> int:
    await asyncio.sleep(0.01 * i)
    return i

async with asyncio.TaskGroup() as tg:
    tasks = [tg.create_task(ok(i)) for i in range(3)]
print([t.result() for t in tasks])
```

```text
[0, 1, 2]
```

Правило выбора: `TaskGroup`, когда нужен «все или никто» (собрать конфиг из трёх источников), `gather(return_exceptions=True)`, когда нужен отчёт по каждому элементу (проверка 50 хостов, где падение одного не должно рушить остальные).

## Таймауты

С Python 3.11 таймаут задаётся контекстным менеджером `asyncio.timeout`, который отменяет всё внутри блока и превращает отмену в `TimeoutError`:

```python
async def slow() -> str:
    await asyncio.sleep(1.0)
    return "late"

t0 = time.perf_counter()
try:
    async with asyncio.timeout(0.2):
        await slow()
except TimeoutError:
    print(f"timed out after {time.perf_counter() - t0:.2f}s")
```

```text
timed out after 0.20s
```

`TimeoutError` здесь — встроенное исключение (в 3.11+ `asyncio.TimeoutError` — его псевдоним), поэтому ловить нужно именно его, а не `asyncio.CancelledError`. Старый `asyncio.wait_for(coro, timeout)` всё ещё работает и полезен, когда нужно обернуть один вызов, но он отменяет корутину и на этом всё.

Таймаут обязателен на каждом сетевом вызове. Без него одна зависшая зависимость останавливает воркер навсегда, а очередь задач растёт. Типичный бюджет: 2–5 с на запрос к внутреннему API, 10–30 с на внешний, и общий дедлайн на весь обработчик, чтобы 10 последовательных вызовов по 3 с не превратились в 30 с.

## Отмена и `CancelledError`

Отмена в asyncio — это исключение `CancelledError`, которое «вбрасывается» в корутину в точке `await`. Перехватывать его можно и нужно для очистки, но нельзя глотать: если не пробросить исключение дальше, задача будет считаться успешно завершённой, а вызывающая сторона не узнает об отмене.

```python
async def worker() -> None:
    try:
        await asyncio.sleep(5)
    except asyncio.CancelledError:
        print("cleanup: releasing lock")
        raise

task = asyncio.create_task(worker())
await asyncio.sleep(0.05)
task.cancel()
try:
    await task
except asyncio.CancelledError:
    print("cancelled", task.cancelled())
```

```text
cleanup: releasing lock
cancelled True
```

Блок `except asyncio.CancelledError` без `raise` — распространённая ошибка: она превращает отмену в «нормальное завершение» и ломает `TaskGroup`, который ждёт, что отменённая задача действительно отменится. Если нужно гарантировать очистку при любой причине выхода, используйте `try/finally`. Если нужно защитить критическую секцию от отмены — `asyncio.shield(coro)`, но помните: `shield` защищает вложенную операцию, а не внешнюю корутину, и после отмены внешней задачи вложенная продолжит работу.

## Ограничение параллелизма

Запустить 10 000 задач разом — верный способ получить `Too many open files` или 429 от API. Ограничитель — `asyncio.Semaphore`: счётчик, который пропускает не больше N одновременных входов.

```python
async def main() -> None:
    sem = asyncio.Semaphore(2)
    active = peak = 0

    async def job(i: int) -> None:
        nonlocal active, peak
        async with sem:
            active += 1
            peak = max(peak, active)
            await asyncio.sleep(0.1)
            active -= 1

    await asyncio.gather(*(job(i) for i in range(6)))
    print("peak concurrency", peak)

asyncio.run(main())
```

```text
peak concurrency 2
```

Шесть задач, максимум две одновременно. Семафор берётся **внутри** задачи, а не вокруг `gather`: иначе вы ограничите создание задач, но не работу. Для потоковой обработки очереди удобнее `asyncio.Queue(maxsize=N)` плюс фиксированное число воркеров — это ещё и даёт {{L|g5|backpressure}}: продюсер засыпает, когда очередь полна.

## Блокирующие вызовы: `to_thread` и `run_in_executor`

`requests`, `psycopg2`, `boto3`, чтение файла, `subprocess.run` — синхронные библиотеки. Вызов такой функции внутри корутины блокирует цикл целиком. Решение — вынести вызов в пул потоков: `await asyncio.to_thread(func, *args)` (3.9+) или `loop.run_in_executor(None, func, *args)`.

```python
def blocking_io() -> str:
    time.sleep(0.2)
    return "file read"

t0 = time.perf_counter()
await asyncio.gather(asyncio.to_thread(blocking_io), asyncio.sleep(0.2))
print(f"to_thread {time.perf_counter() - t0:.2f}s")
```

```text
to_thread 0.20s
```

Два ожидания по 0,2 с заняли 0,2 с: блокирующая функция ушла в поток, цикл продолжил работать. Пул по умолчанию ограничен `min(32, os.cpu_count() + 4)` потоками — это не бесконечный ресурс, и 500 одновременных `to_thread` выстроятся в очередь. Для тяжёлых синхронных драйверов БД пул задают явно, чтобы не упираться в лимит соединений.

`to_thread` — это компромисс, а не решение: потоковое ожидание всё равно расходует память и переключается дороже. Долгосрочно синхронную библиотеку заменяют асинхронной (`httpx` вместо `requests`, `asyncpg` вместо `psycopg2`).

## GIL и почему `asyncio` не про CPU

Глобальная блокировка интерпретатора (GIL) не даёт нескольким потокам одновременно выполнять байткод Python. Для ввода-вывода это неважно: GIL отпускается на время системных вызовов, поэтому потоки и `asyncio` отлично распараллеливают ожидание. Для вычислений — важно.

Замер на CPU-bound функции (два вызова по 3 млн итераций):

```text
serial 0.36s
threads 0.36s
```

Два потока не дали ничего: они по очереди держали GIL. `asyncio` в такой задаче тоже бесполезен — `await` негде поставить, вычисление не приостанавливается. Для CPU-bound работы нужны процессы: `concurrent.futures.ProcessPoolExecutor`, `multiprocessing` или внешний воркер (Celery, RQ). Отдельно стоит знать, что в Python 3.13+ существует экспериментальная сборка без GIL (free-threaded), но по умолчанию интерпретатор по-прежнему с GIL, и полагаться на отсутствие блокировки в общем коде нельзя.

Практический вывод: asyncio выбирают, когда задача — ждать (сеть, диск, внешние API). Когда задача — считать (парсинг гигабайта JSON, ресайз картинок), выбирают процессы или выносят работу из процесса приложения.

## Отладка: кто блокирует цикл

Блокирующий вызов в корутине легко не заметить: код работает, тесты проходят, а под нагрузкой время ответа растёт. У `asyncio` есть встроенный детектор — режим отладки, который замеряет, сколько времени занял каждый колбэк, и печатает предупреждение, если дольше 0,1 с.

```python
async def main() -> None:
    time.sleep(0.6)          # блокирующий вызов вместо await
    await asyncio.sleep(0)

asyncio.run(main(), debug=True)
```

```text
WARNING Executing <Task pending name='Task-1' coro=<main() running at ...> took 0.600 seconds
```

Сообщение прямо указывает на виновника: корутина `main` держала поток 0,6 с. Включать режим стоит в тестах (`asyncio.run(main(), debug=True)`) и на стенде через `PYTHONASYNCIODEBUG=1` или `python -X dev`. Цена — заметное замедление, поэтому в продакшене его держат выключенным, а ловят проблему нагрузочным тестом с включённой отладкой.

## Типичные ошибки

1. **Забытый `await`.** Вызов корутины без `await` ничего не выполняет и возвращает объект-корутину; в логах появляется `RuntimeWarning: coroutine 'fetch' was never awaited`. Механизм — корутина ленива, тело запускается только при `await` или создании задачи.
2. **`time.sleep` вместо `asyncio.sleep`.** Блокирует весь цикл: останавливаются все задачи, включая health-check и таймеры. Механизм — синхронный вызов не возвращает управление планировщику.
3. **Блокирующая библиотека в корутине.** `requests.get` внутри `async def` даёт тот же эффект, что и `time.sleep`, но незаметнее: код «асинхронный», а сервис держит один запрос за раз. Лечение — `to_thread` или асинхронный клиент.
4. **Задача без ссылки.** `asyncio.create_task(coro)` без сохранения ссылки может быть собрана сборщиком мусора до завершения; задача тихо исчезает. Механизм — цикл хранит только слабые ссылки на задачи. Лечение — `TaskGroup`, `asyncio.gather` или именованный набор задач.
5. **`except asyncio.CancelledError: pass`.** Отмена проглатывается, задача считается успешной, `TaskGroup` и таймауты перестают работать. Механизм — отмена реализована исключением, и его нужно пробрасывать.
6. **`gather` без ограничения параллелизма.** 10 000 задач открывают 10 000 соединений и получают отказ от ОС или API. Механизм — `gather` запускает всё сразу, лимит нужно ставить семафором.
7. **Таймаут только на уровне клиента.** Библиотека без таймаута ждёт вечно; общий дедлайн обработчика не задан, и один медленный ответ растягивает весь запрос. Механизм — таймаут по умолчанию часто отсутствует или равен «бесконечности».

## Чек-лист

- [ ] В асинхронном коде нет `time.sleep`, `requests`, `subprocess.run` без `to_thread`.
- [ ] Каждый сетевой вызов имеет таймаут; у обработчика есть общий дедлайн.
- [ ] Параллелизм ограничен `Semaphore` или размером пула; число одновременных соединений известно.
- [ ] Все созданные задачи имеют владельца: `TaskGroup`, `gather` или явный набор с `await`.
- [ ] Обработчики `CancelledError` пробрасывают исключение; очистка — в `finally`.
- [ ] Для CPU-bound работы используются процессы, а не корутины и не потоки.
- [ ] `asyncio.run` вызывается один раз, на верхнем уровне; вложенных циклов нет.
- [ ] Есть тест, который проверяет таймаут и отмену, а не только успешный путь.

## Упражнения

1. **Разминка.** Напишите `async def fetch_all(urls)` через `gather` с таймаутом 2 с на каждый запрос и верните список `(url, ok, elapsed)`. Сравните время с последовательным вариантом на 20 URL.
2. **Таймаут.** Реализуйте функцию с общим дедлайном 5 с, внутри которой три последовательных `await` по 2 с. Добейтесь, чтобы при превышении возвращался частичный результат, а не исключение.
3. **Семафор.** Ограничьте конкурентность до 5 для 100 задач и постройте гистограмму числа одновременно активных задач. Убедитесь, что пик не превышает 5.
4. **Отмена.** Напишите воркер, который держит блокировку и обновляет метрику; отмените его через 100 мс и проверьте, что блокировка освобождена, а метрика не «залипла».
5. **GIL.** Сравните время обработки 10 млн чисел в одном потоке, в четырёх потоках и в четырёх процессах (`ProcessPoolExecutor`). Объясните результат и оцените накладные расходы на передачу данных между процессами.
