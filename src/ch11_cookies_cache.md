# Глава 11. Куки, сессии, кэширование, CDN

HTTP не хранит состояния: каждый запрос самодостаточен, и сервер по умолчанию не знает, что два запроса пришли от одного человека. Куки (cookies) — механизм, который это исправляет, и одновременно главный источник утечек и странных багов. Кэширование — второй механизм, который экономит трафик и деньги, и вторая по частоте причина инцидентов вида «пользователь видит чужой профиль».

После этой главы вы сможете разобрать цепочку «браузер → CDN → балансировщик → приложение» и понять, на каком узле теряется кука или подменяется ответ, объяснить разницу между серверной сессией и JWT, настроить `Cache-Control` так, чтобы кэш не отдавал приватные данные, и проверить всё это через `curl`.

## Куки: как сервер узнаёт клиента

Сервер отправляет заголовок `Set-Cookie`, браузер сохраняет пару «имя=значение» и прикладывает её к последующим запросам через `Cookie`. Больше в протоколе ничего нет: идентификация целиком построена на том, что клиент честно вернёт то, что ему дали.

```
HTTP/1.1 200 OK
Set-Cookie: session_id=8f14e45fceea167a5a36dedd4bea2543; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=604800
Set-Cookie: theme=dark; Path=/; Max-Age=31536000
Content-Type: text/html; charset=utf-8
```

Атрибуты определяют область видимости и защиту. `Domain` задаёт домен: если он не указан, кука становится host-only и уходит только на точное имя, поставившее её. `Path` ограничивает путь. `Max-Age` (в секундах) или `Expires` (дата) делают куку постоянной; без них она сессионная и умирает с браузером.

`HttpOnly` запрещает доступ из JavaScript — это защита от кражи сессии через XSS. `Secure` разрешает передачу только по HTTPS. `SameSite` управляет отправкой при кросс-сайтовых запросах: `Strict` не отправляет куку никогда, `Lax` (по умолчанию в современных браузерах) — только при переходе по ссылке методом GET, `None` — отправляет всегда, но требует `Secure`.

Отдельно стоит запомнить префиксы: `__Host-` требует `Secure`, `Path=/` и отсутствие `Domain`, то есть гарантирует, что куку нельзя подсунуть с поддомена; `__Secure-` требует только `Secure`.

Ограничения жёсткие: одна кука — не больше 4 КБ вместе с атрибутами, на домен браузеры держат порядка 50 кук. Складывать в куку весь профиль пользователя — плохая идея не только из-за размера: она уходит в каждом запросе, включая картинки.

### CSRF и SameSite

Кука уходит с любым запросом к своему домену, включая запрос, инициированный чужой страницей. На этом построена CSRF-атака: сайт злоумышленника содержит форму с `action` на ваш банк, браузер автоматически прикладывает сессионную куку, и перевод выполняется от имени пользователя.

`SameSite=Lax`, ставший поведением по умолчанию в современных браузерах, закрывает основной сценарий: кука не отправляется при кросс-сайтовом POST. Но `Lax` пропускает переход по ссылке методом GET — поэтому изменяющие операции не должны быть GET ни при каких обстоятельствах, а `GET /logout` — плохая идея даже как компромисс.

`SameSite=Strict` надёжнее, но ломает переходы по внешним ссылкам: пользователь приходит из поиска или из письма и видит форму входа, уже имея сессию. Практика — `Lax` плюс CSRF-токен для форм (синхронизирующий токен в скрытом поле или double-submit cookie), плюс проверка `Origin`/`Referer` на стороне сервера для небезопасных методов.

`SameSite=None` нужен только для кросс-сайтовых встраиваний (виджет оплаты в iframe) и обязан идти вместе с `Secure`. Без `Secure` браузер просто отбросит куку, и виджет «сломается» без внятной ошибки в консоли.

## Сессии против JWT

Серверная сессия — самая простая схема: в куке лежит случайный идентификатор, а данные — в Redis или в таблице БД. Плюсы: сервер контролирует срок жизни, может отозвать сессию мгновенно, размер куки минимален. Минусы: состояние нужно хранить и реплицировать, а каждый запрос требует обращения к хранилищу.

JWT (RFC 7519) — самодостаточный токен: полезная нагрузка с утверждениями (`sub`, `exp`, `iat`, `scope`) и подпись. Сервер проверяет подпись и не ходит в хранилище вообще. Плюсы: горизонтальное масштабирование без общего состояния, удобно для межсервисных вызовов. Минусы существеннее, чем кажется на старте: токен нельзя отозвать до истечения срока, он заметно больше идентификатора (легко 500–900 байт) и уходит в каждом запросе, а любая утечка ключа подписи компрометирует всё сразу.

Практический компромисс, который используют чаще всего: короткоживущий access token (5–15 минут) плюс refresh token в `HttpOnly`-куке. Отзыв реализуется через версию пользователя или чёрный список refresh-токенов, а не через отзыв access-токена.

Куку с сессией нельзя хранить в `localStorage`: любой XSS прочитает её. `HttpOnly` — не украшение, а базовая гигиена.

## Кэширование: Cache-Control и валидаторы

Кэш бывает приватным (браузер) и общим (CDN, прокси). Правила задаёт `Cache-Control` (RFC 9111). Ключевые директивы:

| Директива | Смысл |
|---|---|
| `max-age=3600` | свежесть в секундах для любого кэша |
| `s-maxage=600` | то же, но только для общих кэшей |
| `public` / `private` | можно ли кэшировать ответ с авторизацией |
| `no-store` | не сохранять вообще |
| `no-cache` | сохранять, но перепроверять перед каждым использованием |
| `must-revalidate` | после истечения свежести перепроверять, не отдавать устаревшее |

`no-cache` и `no-store` путают чаще всего. `no-store` — «не храни», `no-cache` — «храни, но спрашивай разрешения». Для ответов с персональными данными нужен именно `no-store` (плюс `private`, если ответ всё-таки проходит через CDN).

Валидаторы позволяют не передавать тело повторно. `ETag` — версия ресурса, обычно хеш содержимого; `Last-Modified` — время изменения. Клиент присылает `If-None-Match: "9f2c1ab7e4"` или `If-Modified-Since`, сервер отвечает `304 Not Modified` без тела. Слабый валидатор `W/"9f2c1ab7e4"` означает «семантически то же», сильный — «байт в байт».

`Vary` перечисляет заголовки, влияющие на содержимое. `Vary: Accept-Encoding` обязателен, если сервер отдаёт gzip или brotli; `Vary: Cookie` — если ответ зависит от пользователя. `Vary: *` означает «не кэшировать никогда» и обычно является ошибкой конфигурации.

## Практика: куки и условные запросы через curl

`curl` хранит куки в файле-«банке» и умеет их переиспользовать.

```bash
curl -sS -c /tmp/jar.txt -o /dev/null -w '%{http_code}\n' -X POST -d 'user=alice&pass=secret' https://httpbin.org/cookies/set/session/abc123
grep session /tmp/jar.txt
```

```
200
#HttpOnly_httpbin.org	FALSE	/	FALSE	0	session	abc123
```

Пять полей через табуляцию — домен, флаг для поддоменов, путь, `Secure`, срок, имя, значение. Дальше `-b /tmp/jar.txt` отправит куку обратно, и её видно в `-v` в строке `> Cookie: session=abc123`.

Проверка условного запроса выглядит так:

```bash
curl -sSI https://example.com/ | grep -i etag
curl -sS -o /dev/null -w '%{http_code} %{size_download}\n' -H 'If-None-Match: "9f2c1ab7e4"' https://example.com/
```

```
etag: "9f2c1ab7e4"
304 0
```

Код 304 и ноль байт тела — кэш работает. Если сервер вернул `200` с телом, значит `ETag` не совпал или его нет вовсе.

## Практика: кэш на стороне nginx

Обратный прокси умеет кэшировать ответы бэкенда, и это дешёвый способ снять нагрузку.

```nginx
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api:20m max_size=2g inactive=60m;

server {
    listen 443 ssl;
    http2 on;

    location /api/public/ {
        proxy_pass http://backend;
        proxy_cache api;
        proxy_cache_valid 200 10m;
        proxy_cache_valid 404 1m;
        proxy_cache_key "$scheme$request_method$host$request_uri";
        proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
        proxy_cache_background_update on;
        add_header X-Cache-Status $upstream_cache_status always;
    }

    location /api/private/ {
        proxy_pass http://backend;
        proxy_no_cache 1;
        proxy_cache_bypass 1;
        add_header Cache-Control "no-store" always;
    }
}
```

`X-Cache-Status` показывает `HIT`, `MISS`, `EXPIRED` или `BYPASS` — без него отладка кэша превращается в гадание. `proxy_cache_use_stale` отдаёт устаревший ответ, пока бэкенд недоступен: это лучше, чем 502. Для приватных эндпоинтов кэш отключается полностью, иначе ответ одного пользователя уйдёт другому.

Ключ кэша по умолчанию не включает `Cookie` и `Authorization` — именно поэтому приватные ответы и утекают. Если ответ зависит от пользователя, его нельзя класть в общий кэш ни при каких настройках `max-age`.

## Практика: воспроизводим утечку кэша

Утечка «кэш отдал чужое» воспроизводится двумя запросами с разными куками. Достаточно, чтобы ответ зависел от пользователя, а ключ кэша — нет.

```bash
curl -sS -b 'session=alice-token' -D- -o /dev/null https://shop.example.com/cart | grep -i 'cache-control\|age'
```

```
cache-control: public, max-age=300
age: 0
```

Директива `public` разрешает общему кэшу хранить ответ, хотя он собран под конкретную сессию. Второй запрос с другой кукой получает тот же объект:

```bash
curl -sS -b 'session=bob-token' https://shop.example.com/cart
```

```json
{"items":[{"sku":"A-17","qty":2}],"owner":"alice@example.com"}
```

Боб видит корзину Алисы. Причина не в CDN, а в заголовке: `public` плюс отсутствие `Vary: Cookie` означает, что вариант один на всех. Лечение — `Cache-Control: private, no-store` для всего, что зависит от сессии, и правило на CDN «не кэшировать запросы с `Cookie`», кроме явно публичных путей.

Есть и юридическая деталь: по RFC 9111 общий кэш не должен переиспользовать ответ на запрос с `Authorization`, если в ответе нет `public`, `s-maxage` или `must-revalidate`. Именно поэтому утечки чаще случаются через куки, а не через токены: для `Authorization` защита встроена в стандарт, для `Cookie` — нет.

## CDN: кэш на краю сети

CDN — это сеть кэширующих прокси, расставленных ближе к пользователю. Запрос попадает на ближайший узел (edge); при промахе узел идёт к источнику (origin), забирает ответ и хранит его по правилам `Cache-Control`. Выигрыш двойной: меньше RTT и меньше нагрузки на origin.

Ключ кэша на CDN почти всегда настраиваемый: хост, путь, query-строка (целиком или в виде белого списка параметров), иногда заголовки. Ошибка «кэш отдал чужое» почти всегда означает, что в ключ не попал параметр, влияющий на содержимое: `?lang=en` и `?lang=de` дали один и тот же ключ, или CDN проигнорировал `Vary: Accept-Language`.

Инвалидация — вторая половина задачи. TTL в 24 часа означает, что после деплоя сутки живёт старая версия. Варианты: сократить TTL для HTML и оставить длинный для хешированных статики (`app.9f2c1a.js`), сбрасывать кэш по URL (`purge`) или по тегам (surrogate keys), либо менять имя файла при каждом релизе — самый надёжный подход, потому что не требует инвалидации вообще.

Управлять кэшем CDN отдельно от браузера позволяют `CDN-Cache-Control` (RFC 9213) и `Surrogate-Control`: origin отдаёт браузеру `max-age=60`, а CDN — `max-age=3600`, и оба живут по своим правилам.

`stale-while-revalidate` (RFC 5861) даёт CDN право отдать чуть устаревший ответ, пока он в фоне обновляет его у origin. Для каталогов и лент это ощутимо снижает время ответа при всплесках трафика.

## Сессии в кластере

Как только приложение запущено в двух экземплярах, серверная сессия превращается в распределённую задачу. Три рабочих схемы.

Первая — липкие сессии (sticky sessions): балансировщик по куке направляет клиента на тот же узел. Просто, но хрупко: при деплое или падении узла сессии теряются, а перекос трафика никуда не уходит.

Вторая — общее хранилище: сессии лежат в Redis, идентификатор в куке, любой узел читает любую сессию. Это стандарт для Kubernetes, но добавляет сетевой хоп на каждый запрос (обычно 0,3–1 мс внутри кластера) и точку отказа, которую надо реплицировать.

Третья — подписанные куки (JWT или аналог): состояние у клиента, узлы не общаются. Плата — невозможность отзыва и рост размера куки.

Отдельная ловушка — домен куки. Приложение на `app.example.com` и API на `api.example.com` — это один сайт (same-site) для `SameSite`, но разные хосты для `Domain`. Кука, поставленная без `Domain`, на `api.example.com` не уйдёт, и вход будет «слетать» ровно на кросс-доменных запросах. Лечится либо `Domain=example.com`, либо проксированием API через тот же хост (`/api`), что предпочтительнее: меньше поверхности для подделки кук.

## Типичные ошибки

1. **Кэширование ответа с `Set-Cookie`.** CDN сохраняет ответ вместе с заголовком и отдаёт его следующему пользователю, который получает чужую сессию. Механизм: `Set-Cookie` не входит в ключ кэша и не запрещает кэширование сам по себе; нужен явный `Cache-Control: private` или `no-store`.
2. **Кука «потерялась» на поддомене.** Кука, поставленная на `app.example.com` без `Domain`, не уходит на `api.example.com` — она host-only. Механизм: браузер сравнивает домен строго; чтобы разделить куку между поддоменами, нужен `Domain=example.com`, но тогда её видит и любой другой поддомен, что расширяет поверхность атаки.
3. **`SameSite=Strict` на SSO-переходе.** Пользователь приходит по ссылке с другого сайта, кука не отправляется, и он видит форму логина, уже будучи залогиненным. Механизм: `Strict` блокирует куку при любом кросс-сайтовом переходе, включая обычный клик по ссылке.
4. **`no-cache` вместо `no-store` для приватных данных.** Ответ сохраняется на диск браузера и промежуточных кэшей. Механизм: `no-cache` разрешает хранение, запрещая лишь использование без перепроверки.
5. **Инвалидация «по всем URL» после каждого деплоя.** Origin получает шквал запросов, CDN пуст, latency растёт в разы. Механизм: сброс кэша превращает распределённую систему в один сервер.
6. **`Vary: Accept-Encoding` забыт при сжатии.** Кэш хранит gzip-версию и отдаёт её клиенту без поддержки gzip. Механизм: без `Vary` ключ кэша не различает варианты одного ресурса.
7. **JWT в `localStorage` «потому что удобно».** Любой XSS читает токен и уносит его. Механизм: `localStorage` доступен всему JavaScript на странице, `HttpOnly`-кука — нет.

## Чек-лист

- [ ] Кука сессии имеет `HttpOnly`, `Secure` и осмысленный `SameSite`.
- [ ] Для критичных кук используются префиксы `__Host-` или `__Secure-`.
- [ ] Ответы с персональными данными отдают `Cache-Control: private, no-store`.
- [ ] Статика отдаётся с хешем в имени файла и `max-age` в год, HTML — с коротким TTL.
- [ ] `Vary` содержит `Accept-Encoding`, а при языковой версионности — `Accept-Language`.
- [ ] `X-Cache-Status` (или аналог) есть в ответах и в метриках.
- [ ] Процедура инвалидации описана и проверена на стейдже: по URL, по тегу, через смену имени.
- [ ] Есть алерт на долю промахов кэша (hit ratio) — падение видно раньше, чем пользователи.

## Упражнения

1. Снимите `Set-Cookie` через `curl -i`, разберите все атрибуты и объясните, какие из них защищают от XSS, а какие — от CSRF.
2. Поставьте куку на `app.example.com` без `Domain` и с `Domain=example.com`, затем проверьте `curl -b` к `api.example.com`. Объясните результат.
3. Настройте `proxy_cache` в nginx для публичного эндпоинта и добейтесь последовательности `MISS → HIT → EXPIRED` в `X-Cache-Status`.
4. Возьмите любой публичный сайт и определите, кэшируется ли HTML: сравните `Cache-Control`, `ETag` и ответ на `If-None-Match`. Предложите, что стоит изменить.
5. Включите `SameSite=Strict`, пройдите по внешней ссылке на сайт и объясните, почему кука не отправилась. Затем верните `Lax` и добавьте CSRF-токен в форму.
