# Глава 21. Сеть и API на Python

Почти любой сервис на Python рано или поздно становится HTTP-клиентом: сходить в API облака за списком инстансов, в биллинг за балансом, в чужой сервис за справочником. И почти любой крупный инцидент с такими сервисами выглядит одинаково: не «упал Python», а «мы повесили все воркеры на одном медленном ответе» или «после 503 начали долбить чужой API и получили бан». В этой главе разбирается, как устроен цивилизованный HTTP-клиент: чем `requests` отличается от `httpx`, зачем нужны четыре разных таймаута, как делать ретраи, которые не превращаются в атаку на соседа, и как ограничить параллелизм. В конце мы соберём класс клиента целиком — с джиттером, лимитами и обработкой 429.

## Клиент — это компонент, а не вызов функции

В стандартной библиотеке есть `urllib.request`, в экосистеме — `requests` и `httpx`. Выбор между ними определяется тем, что именно вы строите.

| Возможность | `urllib.request` | `requests` | `httpx` |
|---|---|---|---|
| Синхронный API | да | да | да |
| Асинхронный API | нет | нет | да, `AsyncClient` |
| HTTP/2 | нет | нет | да, `http2=True` |
| Таймауты | один (`timeout=`) | connect + read | connect, read, write, pool |
| Пул соединений | нет | `Session` | `Client` |
| Подмена транспорта в тестах | вручную | через сторонние библиотеки | `MockTransport` из коробки |

Практическое правило: `requests` — для скриптов, миграций и административных утилит. `httpx` — если в проекте уже есть `asyncio` (синхронный клиент внутри {{L|g37|event loop}} останавливает весь цикл) или нужен {{L|g51|HTTP/2}} и единый код для sync и async.

### Почему не голый urlopen

Соблазн велик: `urllib` уже установлен. Но посмотрим, что происходит на реальном запросе.

```python
import json
import urllib.request

with urllib.request.urlopen("https://api.example.internal/v1/services") as resp:
    data = json.load(resp)
print(len(data["items"]))
```

Проблемы начинаются ещё до первого ответа.

1. **Таймаут по умолчанию.** `urlopen` берёт значение из `socket.getdefaulttimeout()`, а оно равно `None` — «ждать столько, сколько ждёт ядро». Установка TCP-соединения в Linux по умолчанию растягивается примерно на две минуты (зависит от `tcp_syn_retries`), чтение ответа не ограничено. Один зависший upstream занимает все воркеры.
2. **Разнородные исключения.** На 4xx/5xx летит `HTTPError`, на проблемы с соединением — `URLError`, на таймаут — `socket.timeout`. Единой ветки обработки нет, и код обрастает `except Exception`.
3. **Нет пула соединений.** Каждый вызов — новый TCP- и TLS-handshake, то есть минимум один лишний round-trip на запрос.
4. **Нет места для политики.** Ретраи, лимиты, разбор JSON и проверка статуса пишутся руками поверх.

Проверим на локальном сервере, который отвечает через три секунды, а на неизвестный путь отдаёт 404:

```python
import urllib.error, urllib.request

urllib.request.urlopen("http://127.0.0.1:8765/slow")          # без timeout
urllib.request.urlopen("http://127.0.0.1:8765/nope", timeout=5)
```

```text
urllib.error.HTTPError: HTTP Error 404: Not Found
```

Первый вызов вернулся через 3.0 с — ровно столько спал сервер.

С сервером, который принял соединение и молчит, тот же код ждёт минутами — обычное поведение балансировщика, потерявшего бэкенд. `urlopen` допустим в одноразовом скрипте с явным таймаутом; в сервисе — нет.

## Таймауты: четыре разных числа

«Поставить таймаут» — недостаточно: в httpx это четыре независимых значения, каждое отвечает за свой этап.

| Параметр | Что ограничивает | Разумное значение |
|---|---|---|
| `connect` | установку TCP+TLS | 2–3 с внутри ДЦ |
| `read` | ожидание следующей порции данных | 5–15 с |
| `write` | отправку тела запроса | 10 с |
| `pool` | ожидание свободного слота в пуле | 1–2 с |

Умолчание httpx — 5 секунд на всё сразу. Явная настройка выглядит так:

```python
import httpx

timeout = httpx.Timeout(10.0, connect=3.0, pool=2.0)
print(timeout)
```

```text
Timeout(connect=3.0, read=10.0, write=10.0, pool=10.0)
```

Первый позиционный аргумент — значение по умолчанию для всех четырёх. `pool=2.0` важен: исчерпанный пул не должен держать запрос в очереди дольше двух секунд, за это время upstream всё равно не уложится в бюджет.

И главное, чего в httpx нет: **общего дедлайна**. `read` сбрасывается на каждой прочитанной порции, поэтому сервер, отдающий по байту в секунду, формально таймаут не нарушает, а запрос может идти час. Дедлайн задаётся снаружи:

```python
import asyncio

async with asyncio.timeout(15):
    data = await client.get_json("/v1/report")
```

Правило бюджета: таймаут клиента меньше таймаута вызывающего. Если {{L|g54|ingress}} рвёт запрос через 30 секунд, клиенту незачем ждать 60 — результат всё равно не успеет, зато соединение и память будут заняты.

## Ретраи: что повторять, когда и сколько раз

Ретрай — компромисс: шанс на успех растёт ценой нагрузки и задержки. Поэтому сначала решается, **что** повторять.

| Код/ситуация | Повторять | Почему |
|---|---|---|
| ошибка соединения, `ReadTimeout` | да | сеть могла моргнуть |
| 408, 425 | да | сервер сам сказал «слишком рано» |
| 429 | да, с `Retry-After` | исчерпана квота, но она восстановится |
| 500, 502, 503, 504 | да | типичные transient-ошибки |
| 400, 401, 403, 404, 409, 422 | нет | результат не изменится |

Повтор 401 — способ получить блокировку учётной записи, повтор 404 — превратить быструю ошибку в медленную.

### Backoff и джиттер

Задержка между попытками растёт экспоненциально и ограничивается сверху:

```python
delay = min(0.5 * 2 ** (attempt - 1), 8.0)   # 0.5, 1, 2, 4, 8, 8...
await asyncio.sleep(random.uniform(0, delay))
```

`random.uniform(0, delay)` — это full jitter: пауза равномерно распределена от нуля до потолка. Без джиттера двести подов одновременно получают 503, одновременно ждут одинаковые 0.5 с и одновременно бьют по восстановившемуся сервису — тот падает снова. С джиттером моменты повторов разные, и нагрузка размазывается. Четыре попытки с базой 0.5 с и потолком 8 с дают около 3.5 с ожидания (0.5 + 1 + 2); дальнейшие попытки почти не повышают шанс, но гарантированно съедают время запроса.

### Идемпотентность

Повтор безопасен, только когда повторное выполнение не меняет результат. По RFC 9110 `GET`, `HEAD`, `OPTIONS` безопасны, `PUT` и `DELETE` идемпотентны, а `POST` — нет: два одинаковых POST создадут две записи или спишут деньги дважды.

Для `POST` идемпотентность делается явно: клиент один раз на операцию генерирует ключ, сервер его запоминает.

```python
import uuid
headers = {"Idempotency-Key": str(uuid.uuid4())}
resp = await client.post("/v1/payments", json=payload, headers=headers)
```

Сервер, увидев знакомый ключ, возвращает сохранённый результат первой операции вместо повторного списания. Без такого контракта `POST` не ретраится — ошибка идёт наверх.

## Ограничение параллелизма

Ретраи и таймауты бесполезны, если клиент запускает тысячу задач разом. Ограничение ставится на двух уровнях: `httpx.Limits` режет число открытых соединений, `asyncio.Semaphore` — число одновременных задач, включая время на ретраи и разбор ответа.

```python
sem = asyncio.Semaphore(4)

async def one(client: httpx.AsyncClient, i: int) -> int:
    async with sem:
        resp = await client.get(f"https://api.example.internal/items/{i}")
        return resp.status_code

async with httpx.AsyncClient(
    transport=transport,
    limits=httpx.Limits(max_connections=4, max_keepalive_connections=4),
) as client:
    codes = await asyncio.gather(*(one(client, i) for i in range(20)))
```

С транспортом, который спит 50 мс на запрос:

```text
20 {200} 0.25s
```

Двадцать запросов по четыре в параллель — пять волн по 50 мс, всего 0.25 с. Без семафора все двадцать уйдут одновременно, и сервер получит всплеск, которого никто не обещал. Нужны оба ограничителя: `Limits` не даёт открыть лишние сокеты, но задачи копятся в очереди пула и занимают дескрипторы; семафор отсекает работу раньше.

## Клиент целиком

Соберём всё в один класс. Первая часть — конструктор: таймауты, лимиты, заголовки, семафор и подменяемый транспорт (пригодится в главе про тесты).

```python
from __future__ import annotations

import asyncio
import random
from typing import Any

import httpx

RETRY_STATUS = {408, 425, 429, 500, 502, 503, 504}
NETWORK_ERRORS = (httpx.ConnectError, httpx.ReadTimeout, httpx.RemoteProtocolError)


class ApiError(RuntimeError):
    pass


class ApiClient:
    def __init__(self, base_url: str, *, token: str, concurrency: int = 8,
                 max_attempts: int = 4,
                 transport: httpx.AsyncBaseTransport | None = None) -> None:
        self._client = httpx.AsyncClient(
            base_url=base_url,
            timeout=httpx.Timeout(10.0, connect=3.0, pool=2.0),
            limits=httpx.Limits(max_connections=concurrency,
                                max_keepalive_connections=concurrency),
            headers={"Authorization": f"Bearer {token}",
                     "User-Agent": "deploy-bot/1.4"},
            transport=transport,
        )
        self._sem = asyncio.Semaphore(concurrency)
        self._max_attempts = max_attempts

    async def __aenter__(self) -> "ApiClient":
        return self

    async def __aexit__(self, *exc: object) -> None:
        await self._client.aclose()
```

Вторая часть — сам запрос с циклом попыток:

```python
    async def get_json(self, path: str, **params: Any) -> dict:
        return await self._request("GET", path, params=params)

    async def _request(self, method: str, path: str, **kw: Any) -> dict:
        last: Exception | None = None
        for attempt in range(1, self._max_attempts + 1):
            async with self._sem:
                try:
                    resp = await self._client.request(method, path, **kw)
                except NETWORK_ERRORS as exc:
                    last = exc
                else:
                    if resp.status_code not in RETRY_STATUS:
                        return self._unwrap(resp)
                    last = ApiError(f"HTTP {resp.status_code} на {path}")
            if attempt == self._max_attempts:
                break
            delay = min(0.5 * 2 ** (attempt - 1), 8.0)
            await asyncio.sleep(random.uniform(0, delay))
        raise ApiError(f"{path}: сдался после {self._max_attempts} попыток") from last

    @staticmethod
    def _unwrap(resp: httpx.Response) -> dict:
        if resp.status_code >= 400:
            raise ApiError(f"HTTP {resp.status_code}: {resp.text[:200]}")
        if resp.status_code == 204 or not resp.content:
            return {}
        return resp.json()
```

Три решения стоит отметить. Семафор берётся **внутри** цикла: иначе клиент, ждущий паузы перед повтором, держал бы слот занятым. Ошибки копятся в `last` и попадают в `raise ... from last`, так что в трейсбеке видна исходная причина. Ответ `204` не разбирается как JSON.

Проверка на подменённом транспорте, где первые два вызова отвечают 503:

```python
calls = {"n": 0}

def handler(request: httpx.Request) -> httpx.Response:
    calls["n"] += 1
    if calls["n"] < 3:
        return httpx.Response(503, headers={"Retry-After": "1"})
    return httpx.Response(200, json={"ok": True, "attempt": calls["n"]})

async def demo() -> None:
    async with ApiClient("https://api.example.internal", token="t",
                         transport=httpx.MockTransport(handler)) as api:
        print(await api.get_json("/v1/services"))
    print("всего вызовов:", calls["n"])

asyncio.run(demo())
```

```text
{'ok': True, 'attempt': 3}
всего вызовов: 3
```

Клиент пережил два 503 и вернул данные с третьей попытки. Тот же транспорт позволяет воспроизводить 429, таймауты и битый JSON в тестах — об этом глава 23.

## JSON: разбор и его пределы

`resp.json()` вызывает `json.loads` и бросает `JSONDecodeError` (подкласс `ValueError`), если тело не JSON. Это происходит чаще, чем кажется: прокси отдаёт HTML с кодом 200, балансировщик — пустое тело, upstream — обрезанный ответ.

```python
try:
    payload = resp.json()
except ValueError:
    raise ApiError(f"не JSON от {resp.request.url}: {resp.text[:200]}") from None
```

Дальше — доверие к структуре. `payload["items"][0]["id"]` упадёт с `KeyError` или `IndexError` при первом изменении контракта, причём в глубине обработчика, где это выглядит как баг вашего кода. Для критичных интеграций схему описывают явно (dataclass или pydantic) и валидируют на границе. Для больших ответов `resp.json()` опасен: он материализует весь документ в памяти, поэтому выгрузки читают потоком:

```python
with client.stream("GET", "/v1/export") as resp:
    for line in resp.iter_lines():
        process(json.loads(line))
```

## 429 и 503: чего хочет сервер

429 означает «превышена квота», 503 — «временно не могу». Оба сопровождаются `Retry-After` и оба требуют, чтобы клиент замедлился. При 429 пауза не меньше указанной в заголовке, иначе — backoff с джиттером; после трёх подряд 429 попытки лучше прекратить: квота обычно считается за минуту и за оставшиеся попытки не восстановится. При 503 помогает размыкание цепи ({{L|g15|circuit breaker}}): после N подряд неудач клиент какое-то время не ходит в сервис вовсе, затем пропускает один пробный запрос и при успехе возвращается в норму. Это дешевле сотен таймаутов, каждый из которых стоит секунды.

## Типичные ошибки

1. **Запрос без таймаута.** `requests` без `timeout=` ждёт бесконечно, `urlopen` наследует `None` из сокета. Один медленный ответ занимает воркер навсегда, очередь растёт, health-check перестаёт отвечать, оркестратор убивает под — и после рестарта всё повторяется.
2. **Ретрай POST без ключа идемпотентности.** Клиент не знает, дошёл ли первый запрос: сеть порвалась после отправки, до ответа. Повтор создаёт вторую запись, деньги списываются дважды.
3. **Ретрай на 4xx.** 401 и 404 детерминированы, повтор даёт тот же результат. Серия 401 приводит к блокировке учётной записи, серия 404 — к штрафу за лишние запросы.
4. **`except Exception` вокруг вызова.** Под него попадают `TypeError` и `AttributeError` из вашего же кода. Ошибка программиста маскируется под сетевую и ретраится четыре раза.
5. **Новый `httpx.get` на каждый вызов.** Модульные функции создают и закрывают клиент, пул не переиспользуется, на каждый запрос — TCP и TLS handshake, а под нагрузкой растёт число сокетов в `TIME_WAIT`.
6. **Игнорирование `Retry-After` и отсутствие джиттера.** Все экземпляры сервиса повторяют синхронно и создают рукотворный всплеск ровно в момент восстановления.
7. **Слепой `resp.json()` без проверки статуса.** На 502 прокси отдаёт HTML, `json.loads` падает, и в логах остаётся «ошибка парсинга» вместо «upstream вернул 502» — диагностика уходит не туда.

## Чек-лист

- [ ] У каждого сетевого вызова задан явный таймаут, включая `pool`, и он меньше таймаута вызывающего.
- [ ] Ретраи включаются только для сетевых ошибок, 408/425/429 и 5xx.
- [ ] Пауза между попытками экспоненциальная, с джиттером и потолком.
- [ ] `POST` ретраится только с `Idempotency-Key`, иначе ошибка идёт наверх.
- [ ] `Retry-After` учитывается как минимальная пауза.
- [ ] Параллелизм ограничен семафором и `httpx.Limits`, числа обоснованы.
- [ ] Клиент один на процесс: создаётся при старте, закрывается при остановке.
- [ ] Статус проверяется до разбора JSON: ошибка парсинга не маскирует 502.
