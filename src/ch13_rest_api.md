# Глава 13. REST и проектирование API

API — контракт, который живёт дольше кода, его реализующего. Клиенты выпускаются реже серверов, мобильные приложения годами остаются на старых версиях, чужие интеграции ломаются молча. Поэтому проектирование API — дисциплина ограничений: какие методы допустимы, что считается ошибкой, как получить следующую страницу, что будет при повторе запроса. Дальше — REST как набор соглашений поверх HTTP, идемпотентность и ключи идемпотентности, пагинация, версионирование, `problem+json`, rate limiting и полный дизайн API сервиса задач.

## Ресурсы, а не глаголы

REST (Representational State Transfer) — архитектурный стиль, описанный Роем Филдингом в 2000 году. В индустрии от него осталась прежде всего одна идея: URL адресует **ресурс** (существительное), а действие выражается HTTP-методом. Сервер не хранит состояние клиента между запросами — каждый запрос несёт всё необходимое для его обработки.

Сравните два подхода к одной операции — отмене заказа:

```http
POST /api/cancelOrder?id=42
POST /api/orders/42/cancel
```

Первый вариант — RPC в обёртке из HTTP: метод всегда POST, действие зашито в путь, кэширование и повторные запросы невозможны осмысленно. Второй лучше, но «отмена» — это не удаление: заказ остаётся в базе с новым статусом. Часто честнее изменить состояние явно:

```http
PATCH /api/orders/42
Content-Type: application/merge-patch+json

{"status": "cancelled"}
```

### Методы и их семантика

Семантика методов зафиксирована в RFC 9110, и от неё зависит поведение посредников: кэшей, прокси, браузеров.

| Метод | Смысл | Безопасный | Идемпотентный | Тело ответа |
|---|---|---|---|---|
| GET | прочитать ресурс | да | да | да |
| POST | создать / выполнить действие | нет | нет | обычно да |
| PUT | заменить ресурс целиком | нет | да | нет |
| PATCH | частично изменить | нет | нет (по умолчанию) | нет |
| DELETE | удалить | нет | да | нет |
| HEAD | заголовки без тела | да | да | нет |

«Безопасный» (safe) значит «не меняет состояние сервера» — по этому признаку роботы и префетчеры решают, можно ли дёргать URL без спроса. «Идемпотентный» — «повторение даёт тот же результат, что один вызов». GET обязан быть и тем, и другим: `GET /orders/42/cancel`, который что-то отменяет, отменит это по вине случайного краулера.

## Идемпотентность и ключи идемпотентности

Идемпотентность — способ выжить в сети, где ответ теряется после того, как сервер уже выполнил работу. По таймауту нельзя отличить «сервер умер до записи» от «сервер записал, но ответ не вернулся». Повтор — единственная разумная стратегия, и она безопасна ровно настолько, насколько операция идемпотентна.

Для PUT и DELETE проблема решена самой семантикой: `PUT /orders/42` с одним и тем же телом десять раз даёт одно состояние, `DELETE` во второй раз вернёт 404 или 204, но состояние не изменится. Для POST так не выйдет: два `POST /orders` создадут два заказа. Здесь вводится **ключ идемпотентности** ({{L|g53|idempotency}} key) — заголовок `Idempotency-Key` с уникальным значением, которое клиент генерирует один раз на логическую операцию.

Сервер хранит таблицу: ключ, хеш тела запроса, код и тело ответа, время жизни (обычно 24 часа). Алгоритм обработки:

1. Ключа `K` нет в таблице — вставить со статусом «в работе», выполнить операцию, сохранить ответ и вернуть его.
2. `K` есть, операция завершена — вернуть сохранённый ответ, не выполняя работу повторно.
3. `K` есть, операция идёт — вернуть `409 Conflict` или `425 Too Early`, чтобы клиент подождал.
4. `K` есть, но хеш тела другой — вернуть `422 Unprocessable Content`: тот же ключ с другим содержимым почти всегда баг клиента.

Ключ должен быть непредсказуемым (годится UUIDv4), а таблица — с уникальным индексом по ключу: без него гонка двух одновременных запросов создаст дубль, потому что между SELECT и INSERT помещается второй запрос.

### Повторные запросы на клиенте

Клиентская сторона тоже требует дисциплины. Повторять имеет смысл только потенциально временные ошибки: таймауты, обрывы, `502`, `503`, `504`, `429`. Повторять `400` или `422` бессмысленно — ответ не изменится. Задержка должна расти экспоненциально и включать случайный разброс (jitter), иначе все клиенты, упавшие одновременно, вернутся одновременно и добьют сервер.

```python
import random, time
import httpx

RETRY_STATUS = {429, 502, 503, 504}

def post_with_retry(url: str, payload: dict, key: str, attempts: int = 4) -> httpx.Response:
    headers = {"Idempotency-Key": key}
    for attempt in range(attempts):
        try:
            r = httpx.post(url, json=payload, headers=headers, timeout=5.0)
        except (httpx.ConnectError, httpx.ReadTimeout):
            r = None
        if r is not None and r.status_code not in RETRY_STATUS:
            return r
        if attempt == attempts - 1:
            break
        delay = min(2 ** attempt, 8) + random.uniform(0, 0.5)
        if r is not None and r.headers.get("Retry-After", "").isdigit():
            delay = max(delay, int(r.headers["Retry-After"]))
        time.sleep(delay)
    raise RuntimeError(f"не удалось выполнить POST после {attempts} попыток")
```

## Пагинация: offset против cursor

Коллекция редко помещается в один ответ. Два канонических способа отдать её частями различаются тем, что именно запоминает клиент.

**Offset-пагинация** (`?limit=50&offset=100` или `?page=3`) опирается на позицию в упорядоченном наборе. Её плюс — возможность прыгнуть на произвольную страницу и простота. Минус — стоимость и нестабильность: `OFFSET 100000` заставляет базу прочитать и выбросить 100 000 строк, а вставка новой записи в начало сдвигает весь набор, поэтому клиент на странице 2 увидит дубль или пропуск.

**Cursor-пагинация** (`?limit=50&cursor=eyJpZCI6MTIzfQ`) передаёт непрозрачный маркер позиции — обычно закодированную пару «значение поля сортировки + id». Сервер читает `WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 50`, что попадает в индекс и не зависит от вставок. Цена — нельзя перескочить на страницу 7 и нельзя посчитать общее число страниц (если не делать отдельный `COUNT(*)`).

| Свойство | offset | cursor |
|---|---|---|
| Прыжок на страницу N | да | нет |
| Стабильность при вставках | низкая | высокая |
| Стоимость глубокой страницы | растёт линейно | постоянная |
| Номер страницы в UI | есть | нет |
| Сложность реализации | минимальная | средняя |

Ответ всегда содержит признак продолжения — иначе клиент не отличит конец данных от забытого курсора:

```json
{
  "items": [{"id": 1042, "title": "Починить CI"}],
  "next_cursor": "eyJ0cyI6IjIwMjYtMTAtMjlUMTA6MDA6MDBaIiwiaWQiOjEwNDJ9",
  "has_more": true
}
```

Курсор непрозрачен для клиента: опубликованную структуру потом нельзя менять. Внутрь стоит класть версию схемы и параметры фильтра, иначе курсор от чужого запроса даст бессмысленный результат.

## Фильтры, сортировка, выбор полей

Правила простые, но нарушаются постоянно. Фильтры — параметры запроса с именами полей: `?status=open&assignee=42`. Значения для «ИЛИ» передаются повтором параметра (`?status=open&status=in_progress`) или через запятую — выберите одно и задокументируйте. Сортировка — `?sort=-created_at,title`, минус означает убывание. Выбор полей — `?fields=id,title,status`; это спасает мобильные клиенты от мегабайтных ответов.

Договоритесь о поведении по умолчанию: без фильтра — все записи или только активные? Без сортировки порядок не определён, и cursor-пагинация невозможна. Правило: **сортировка по умолчанию детерминирована**, всегда с `id` последним ключом.

## Версионирование

Ломающее изменение (breaking change) рано или поздно понадобится, и единственный способ не сломать старых клиентов — выпустить новую версию рядом со старой.

| Подход | Пример | Плюсы | Минусы |
|---|---|---|---|
| URL-префикс | `/v2/orders` | видно в логах и в curl | URL перестаёт быть идентификатором ресурса |
| Свой заголовок | `Accept: application/vnd.api+json;version=2` | чистые URL, версия — часть представления | не видно в логах, сложнее для отладки |
| Параметр | `?version=2` | просто | легко забыть, плохо кэшируется |
| Дата | `Stripe-Version: 2026-10-01` | гранулярность по изменениям | требует инфраструктуры выбора схемы |

Для внутренних и большинства публичных API практичнее URL-префикс: он однозначен при разборе инцидента, работает в любом прокси и не требует объяснений. Заголовочное версионирование выигрывает в чистоте и проигрывает в эксплуатации.

Ломает клиентов удаление или переименование поля, смена типа (`"id": 1` → `"id": "1"`), ужесточение валидации, новые обязательные параметры, изменение кода ответа. Не ломает добавление необязательного поля, нового значения в enum или нового параметра. Явно пропишите в контракте, что клиент игнорирует неизвестные поля, — это разрешает расширять ответы без смены версии.

## Ошибки: коды и problem+json

Клиент должен уметь обработать ошибку, не читая документацию. Для этого есть три уровня информации: HTTP-статус (класс проблемы), машиночитаемый код (конкретная причина) и человекочитаемое сообщение (для логов и разработчика).

Формат `application/problem+json` описан в RFC 9457 (он заменил RFC 7807) и даёт стандартный каркас:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation",
  "title": "Ошибка валидации",
  "status": 422,
  "detail": "Поле due_date не может быть в прошлом",
  "instance": "/v1/tasks/1042",
  "errors": [
    {"field": "due_date", "code": "in_past", "message": "дата уже прошла"}
  ]
}
```

`type` — URI, идентифицирующий **класс** проблемы и ведущий на страницу с описанием; `title` — короткое стабильное название класса; `detail` — конкретика случая; `instance` — путь запроса. Расширения вроде `errors` допустимы и полезны для форм.

Выбор статуса — часть контракта. `400` — битый синтаксис, `401` — не аутентифицирован, `403` — прав нет, `404` — ресурса нет, `409` — конфликт состояния, `422` — синтаксис верный, семантика нет, `429` — слишком много запросов, `500` — баг сервера, `503` — временная недоступность, `504` — не дождались бэкенда. Путать `401` и `403` — классика: клиент с верным токеном получит `401`, пойдёт перелогиниваться и зациклится.

## Rate limiting и заголовки

Ограничение частоты защищает от исчерпания ресурсов, брутфорса и перерасхода квоты. Алгоритмы: фиксированное окно (просто, но пропускает двойной всплеск на границе), скользящее окно (точнее, дороже), {{L|g119|token bucket}} (разрешает короткие всплески — обычно лучший выбор), leaky bucket (сглаживает поток).

Клиенту нужно сообщать не только факт отказа, но и когда возвращаться:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30
Content-Type: application/problem+json

{"type": "https://api.example.com/problems/rate-limit", "title": "Слишком много запросов", "status": 429}
```

`Retry-After` стандартизован в RFC 9110 и принимает либо число секунд, либо HTTP-дату. Поля `RateLimit-*` на момент написания остаются интернет-драфтом IETF, поэтому их стоит дублировать собственными заголовками (`X-RateLimit-*`), если клиенты уже написаны под них. Важнее другое: лимит нужно считать по субъекту (ключ API, пользователь, IP — в таком порядке предпочтения), а не только по IP, иначе за NAT один шумный клиент заблокирует всех.

## Пример: API сервиса задач

Спроектируем контракт для сервиса задач. Ресурсы: `tasks`, `projects`, `comments`.

| Метод и путь | Назначение | Успех | Ошибки |
|---|---|---|---|
| `GET /v1/tasks` | список с фильтрами и курсором | 200 | 400, 429 |
| `POST /v1/tasks` | создать задачу | 201 + `Location` | 409, 422 |
| `GET /v1/tasks/{id}` | одна задача | 200 | 404 |
| `PATCH /v1/tasks/{id}` | частичное изменение | 200 | 404, 409, 422 |
| `DELETE /v1/tasks/{id}` | удалить | 204 | 404 |
| `POST /v1/tasks/{id}/comments` | добавить комментарий | 201 | 404, 422 |
| `GET /v1/tasks/{id}/comments` | комментарии, cursor | 200 | 404 |

Создание задачи с защитой от дублей:

```http
POST /v1/tasks HTTP/1.1
Host: api.example.com
Authorization: Bearer t_9f3c
Content-Type: application/json
Idempotency-Key: 5b1e0f7a-2c4d-4a91-9f60-1d2b3c4e5f60

{"title": "Обновить nginx до 1.29", "project_id": 7, "due_date": "2026-11-15"}
```

```http
HTTP/1.1 201 Created
Location: /v1/tasks/1042
Content-Type: application/json

{"id": 1042, "title": "Обновить nginx до 1.29", "status": "open", "project_id": 7,
 "due_date": "2026-11-15", "created_at": "2026-10-29T12:00:00Z"}
```

Повтор с тем же `Idempotency-Key` вернёт тот же `201` и тот же `id`, а не создаст второй task. Повтор без ключа создаст дубль — поэтому клиентские SDK обязаны подставлять ключ автоматически.

Список запрашивается как `GET /v1/tasks?status=open&assignee=42&sort=-due_date&limit=50&cursor=...` и возвращает `items`, `next_cursor`, `has_more`. При `has_more: false` клиент прекращает цикл; сочетание `has_more: true` с пустым `next_cursor` — баг сервера и нарушение контракта.

## Типичные ошибки

1. **Глаголы в URL.** `POST /getUser`, `POST /updateTask` появляются, когда автор мыслит функциями, а не ресурсами. Следствие: не работает кэш, нельзя отдать `Location`, `PATCH` и `DELETE` неприменимы, а прокси видит только `POST`.
2. **POST без ключа идемпотентности на платёжных и создающих операциях.** Клиент ретраит по таймауту, сервер уже создал заказ — получаются два заказа и два списания. Ошибка проектирования, а не клиента: если операция не идемпотентна по природе, ключ обязателен в контракте.
3. **Offset-пагинация на растущей таблице.** Работает на тестах с 200 записями, разваливается на проде: пользователь листает, видит дубли, база греет диск на `OFFSET 500000`. Проявляется не сразу, поэтому чинить приходится при живых клиентах.
4. **200 OK с `{"success": false}`.** Так делают, чтобы «упростить клиент», и ломают всё: мониторинг не видит ошибок, ретраи не срабатывают, CDN кэширует ошибку как успех. Статус-код — единственный машинно-читаемый сигнал, который видит вся инфраструктура по пути.
5. **Неверсионированный контракт с «мелкими» правками.** Переименование поля кажется безобидным, пока не выясняется, что на нём держится отчёт в чужой системе. Правило: любое изменение, ломающее парсер, — новая версия.
6. **Ошибки без машиночитаемого кода.** `{"message": "Bad request"}` заставляет клиента парсить текст, а тексты меняются. Код ошибки — часть контракта, текст — нет.

## Чек-лист

- [ ] Каждый URL — существительное во множественном числе; действия выражены методами.
- [ ] GET и HEAD не меняют состояние; проверено тестом, который дёргает все GET дважды.
- [ ] Все создающие POST принимают `Idempotency-Key`, таблица ключей имеет уникальный индекс и TTL.
- [ ] Коллекции пагинированы, сортировка детерминирована, cursor непрозрачен, `has_more` присутствует.
- [ ] Версия API зафиксирована в контракте, политика ломающих изменений описана.
- [ ] Ошибки отдаются как `application/problem+json` с полями `type`, `title`, `status`, `detail`.
- [ ] Коды 401/403/409/422/429 используются по назначению, а не «на всякий случай».
- [ ] Для 429 и 503 отдаётся `Retry-After`, лимиты считаются по ключу, а не только по IP.
