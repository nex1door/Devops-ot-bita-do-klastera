# Глава 5. Виртуальная память и файловые системы

Процесс не видит физическую память напрямую — он получает ровное адресное пространство, которого в железе не существует. Файл на диске — тоже не «имя с содержимым», а inode плюс запись в каталоге. Эти две абстракции объясняют большинство загадок эксплуатации: почему контейнер убит с кодом 137, почему `df` показывает 100%, а `du` — 40%, почему `write()` вернул успех, а после отключения питания файла нет. Ниже — страничная адресация, {{L|g83|page fault}}, swap и OOM-killer, затем inode, журнал ext4 и {{L|g43|fsync}}, и в конце — практика с реальными командами.

## Адресное пространство

На x86-64 с четырёхуровневой таблицей страниц пользовательскому коду доступно 128 TiB — адреса от нуля до `0x00007fff_ffff_ffff`; верхняя половина отдана ядру и отображена во всех процессах одинаково, но недоступна из user space. Отсюда два следствия: адрес `0x55d4c2e0d000` в двух процессах указывает на разные физические ячейки, а «память процесса» и «память машины» — разные величины.

Ядро описывает занятые диапазоны структурами VMA (virtual memory areas): отрезок адресов плюс права и то, что под ними лежит.

```bash
cat /proc/self/maps
```

```
55d4c2e0d000-55d4c2e2e000 r--p 00000000 08:11 1310742   /usr/bin/cat
55d4c2e2e000-55d4c2e52000 r-xp 00021000 08:11 1310742   /usr/bin/cat
55d4c2e6b000-55d4c2e6c000 rw-p 00000000 00:00 0         [heap]
7ffd8b3f6000-7ffd8b418000 rw-p 00000000 00:00 0         [stack]
7ffd8b4a1000-7ffd8b4a5000 r--p 00000000 00:00 0         [vvar]
```

Поля слева направо: начало и конец, права (`p` — private, `s` — shared), смещение в файле, устройство, inode, путь. Код отображён как `r-xp`, стек и куча — анонимные (`00:00 0`). Этот файл смотрят, когда процесс «съел гигабайт»: анонимная память — это диапазоны `rw-p` без пути.

## Страничная адресация, MMU и TLB

Память делится на страницы по 4 KiB. Виртуальный адрес режется на две части: младшие 12 бит — смещение внутри страницы (4096 = 2¹²), старшие — номер виртуальной страницы. Переводит его в физический номер аппаратный блок MMU (memory management unit) по таблице страниц, которую строит ядро.

На x86-64 таблица четырёхуровневая: 48 бит адреса — это четыре индекса по 9 бит плюс 12 бит смещения. Каждый уровень — 512 записей по 8 байт, ровно страница 4 KiB. Запись PTE (page table entry) содержит адрес следующей таблицы или страницы и флаги: `P` (present), `RW`, `US` (доступно из user space), `NX` (исполнение запрещено), `A`/`D` (были обращения / изменения — на них завязаны swap и NUMA).

Разберём адрес вручную — лучший способ убедиться, что магии нет:

```python
addr = 0x7ffd8b3f6120
print("offset ", hex(addr & 0xFFF))
print("индексы", [hex((addr >> (12 + 9 * i)) & 0x1FF) for i in range(4)])
```

```
offset  0x120
индексы ['0x1f6', '0x59', '0x1f6', '0xff']
```

Читается справа налево: `0xff` — запись в корневой таблице, дальше уровни вниз, `0x120` — смещение внутри страницы. Четыре обращения к памяти на каждый доступ слишком дорого, поэтому рядом с MMU стоит TLB (translation lookaside buffer) — кэш на несколько сотен готовых переводов. Попадание стоит единицы тактов, промах — обход таблиц, десятки тактов, а если таблиц нет в кэше процессора — сотни.

Отсюда практика: приложение, прыгающее по большому массиву, страдает и от промахов TLB. Лечится huge pages — страницами по 2 MiB, покрывающими тот же объём одной записью:

```bash
grep -i huge /proc/meminfo
```

```
AnonHugePages:     14336 kB
Hugepagesize:       2048 kB
```

Ненулевой `AnonHugePages` означает, что ядро уже склеивает анонимную память (THP, transparent huge pages). У СУБД с собственной работой с памятью THP иногда отключают: фоновый `khugepaged` тратит CPU, а задержки на выделение растут.

## Page fault: minor, major и copy-on-write

Страницы выделяются лениво: `malloc` большого блока превращается в `mmap`, ядро создаёт VMA и ничего не выделяет. Первое обращение вызывает исключение — page fault, — и ядро решает:

- **minor fault** — страница уже в памяти ({{L|g82|page cache}} или свободный фрейм), надо лишь прописать PTE;
- **major fault** — данных нет, нужен ввод-вывод: дочитать с диска или из swap;
- **SIGSEGV** — адреса нет в VMA или идёт запись в страницу только для чтения; это уже падение.

Классический пример ленивости — `fork()`. Копировать гигабайты при каждом форке безумно, поэтому ядро помечает страницы обоих процессов read-only и при записи копирует одну страницу: {{L|g20|copy-on-write}}. Так `fork()` в nginx или gunicorn стоит микросекунды, пока потомок не начнёт писать.

Измерить это можно без профилировщика:

```bash
/usr/bin/time -v python3 -c "import numpy as np; a=np.zeros(10**8); a.sum()"
```

```
	Maximum resident set size (kbytes): 812344
	Minor (reclaiming a frame) page faults: 198432
	Major (requiring I/O) page faults: 0
```

`Maximum resident set size` — пик RSS, реально занятые физические страницы. Сотни тысяч minor fault — норма для выделения 800 МБ: ядро отдаёт заранее обнулённые страницы. Major fault в тысячах означает старт с холодного кэша — первый запуск после деплоя всегда медленнее второго.

## Swap и OOM-killer

Swap — место на диске, куда ядро выгружает давно не используемые страницы. Ядро не «переносит память при заполнении», а держит баланс между анонимными страницами и page cache; агрессивность задаёт `vm.swappiness` (по умолчанию 60, для серверов с БД ставят 1–10).

```
               total        used        free      shared  buff/cache   available
Mem:            7878        4817         148          12        2913        2781
Swap:          10172        7231        2941
```

Смотреть надо на `available`: `buff/cache` — page cache, который отдаётся приложениям мгновенно. `free` в 148 МБ при `available` 2.7 ГБ — нормальное состояние здоровой машины.

Когда кончился и swap, вступает OOM-killer: выбирает процесс с наибольшим `oom_score` и убивает его через SIGKILL, который нельзя перехватить.

```
[41231.882014] python3 invoked oom-killer: gfp_mask=0x140cca(GFP_HIGHUSER_MOVABLE), order=0, oom_score_adj=0
[41231.882102] CPU: 3 PID: 48211 Comm: python3 Not tainted 6.12.0-15-generic #1
[41231.882183] active_anon:412304 inactive_anon:98122 active_file:8120 inactive_file:15231
[41231.883001] oom-kill:constraint=CONSTRAINT_NONE,cpuset=/,mems_allowed=0,global_oom,
             task_memcg=/system.slice/app.service,task=python3,pid=48211,uid=1000
[41231.883044] Out of memory: Killed process 48211 (python3) total-vm:8123456kB, anon-rss:7890120kB,
             file-rss:0kB, shmem-rss:0kB, UID:1000 pgtables:15872kB oom_score_adj:0
```

Ключевые поля: `task_memcg=/system.slice/app.service` — {{L|g13|cgroup}}, в которой жил процесс (именно по ней в Kubernetes выставляется {{L|g79|OOMKilled}}: контейнер убивает контроллер памяти cgroup v2 при исчерпании `memory.max`, а не глобальный OOM); `anon-rss:7890120kB` — почти 8 ГБ анонимной памяти, типичная утечка; `total-vm` в разы больше RSS и о реальном потреблении ничего не говорит.

Снять критичный процесс с первых позиций очереди можно через `oom_score_adj` (от −1000 до 1000). Важно взять ровно один PID: `pgrep -f postgres` на живой базе вернёт и мастер, и воркеров, а путь вида `/proc/123\n456/oom_score_adj` не существует.

```bash
pid=$(pgrep -o -f postgres)     # -o: только самый старый процесс
echo -900 | sudo tee "/proc/$pid/oom_score_adj"
```

Это не бронирует память — при тотальной нехватке кого-то всё равно убьют, — но защищает от «первого кандидата».

## mmap: файл как часть адресного пространства

`mmap` отображает файл в адресное пространство: чтение и запись идут через обычные обращения к памяти, ядро подгружает страницы по требованию. Так работают динамические библиотеки и почти все СУБД.

```python
import mmap

with open("index.bin", "r+b") as f:
    mm = mmap.mmap(f.fileno(), 0)      # 0 — весь файл
    print(mm[0:16])                    # чтение без read()
    mm[0:4] = b"IDX2"                  # запись в page cache
    mm.flush()                         # msync
    mm.close()
```

`flush()` выталкивает грязные страницы, но не гарантирует подтверждения от диска — для durability нужен `os.fsync(f.fileno())`. При `MAP_SHARED` изменения видны другим отображениям, при `MAP_PRIVATE` копируются при записи, и файл не меняется.

## inode

Имя файла — запись в каталоге, ссылающаяся на inode. В inode лежит всё, кроме имени: тип, права, владелец, размер, временные метки, счётчик ссылок, указатели на блоки (в ext4 — extents).

```bash
stat /etc/hosts
```

```
  File: /etc/hosts
  Size: 221       	Blocks: 8          IO Block: 4096   regular file
Device: 8,17	Inode: 1310742     Links: 1
Access: (0644/-rw-r--r--)  Uid: (0/root)   Gid: (0/root)
Modify: 2026-10-20 18:02:44.000000000 +0500
Change: 2026-10-20 18:02:44.000000000 +0500
```

Три времени различаются: `Modify` — содержимое, `Change` — сам inode (права, владелец, переименование), `Access` — чтение (с `relatime` не на каждое). `Links: 1` — жёстких ссылок одна: `ln file hard` создаёт второе имя для того же inode, и данные исчезнут только при `Links: 0`; `ln -s` создаёт отдельный файл с путём.

Inode-ы расходуются отдельно от места:

```bash
df -i /mnt/data
```

```
Filesystem      Inodes  IUsed    IFree IUse% Mounted on
/dev/sda1     61022208 412330 60609878    1% /mnt/data
```

Отсюда классика: «свободно 40 ГБ, а `touch` пишет `No space left on device`» — кончились inode на миллионе мелких файлов (сессии, кэш, `node_modules` в образе).

## ext4: журнал и его гарантии

ext4 журналируемая: перед изменением метаданных она пишет намерение в журнал, затем применяет изменение, затем помечает транзакцию завершённой. Если питание пропадёт посередине, при монтировании журнал «докрутится», и структура останется согласованной — возможно, с потерей последних данных, но без разрушенных каталогов.

| Режим | Что в журнале | Скорость | Риск при сбое |
|---|---|---|---|
| `data=journal` | данные и метаданные | медленно | минимальный |
| `data=ordered` (умолчание) | метаданные, данные — до коммита | средне | старые данные, не мусор |
| `data=writeback` | только метаданные | быстро | в файле могут быть чужие блоки |

```bash
findmnt -no SOURCE,FSTYPE,OPTIONS /
tune2fs -l /dev/sdb1 | grep -E 'Filesystem features|Block size|Journal size'
```

```
/dev/sdb1 ext4 rw,relatime
Filesystem features:  has_journal ext_attr resize_inode dir_index filetype needs_recovery extent 64bit
Block size:           4096
Journal size:         1024M
```

`needs_recovery` означает, что журнал не чист и будет проигран при монтировании — нормальное состояние после жёсткого выключения.

## fsync: почему «запись прошла» ничего не значит

`write()` не пишет на диск. Он копирует данные в page cache и возвращает управление. Долговечными (durable) данные становятся, когда ядро отправит их на устройство и устройство подтвердит запись. Между этими моментами — грязные страницы, которые сбрасываются по таймеру (у ext4 `commit=5` секунд) или при нехватке памяти. Потеря питания в этом окне — потеря записи, причём приложение уже получило «успех».

`fsync(fd)` сбрасывает данные и метаданные и ждёт подтверждения; `fdatasync(fd)` — без метаданных, не нужных для чтения. Корректная запись файла:

```python
import json, os, tempfile

def atomic_write(path: str, payload: dict) -> None:
    d = os.path.dirname(path) or "."
    fd, tmp = tempfile.mkstemp(dir=d, prefix=".tmp-")
    try:
        with os.fdopen(fd, "w") as f:
            json.dump(payload, f)
            f.flush()
            os.fsync(f.fileno())     # 1. содержимое временного файла на диске
        os.replace(tmp, path)        # 2. атомарная подмена имени
        dfd = os.open(d, os.O_DIRECTORY)
        try:
            os.fsync(dfd)            # 3. запись каталога на диске
        finally:
            os.close(dfd)
    except BaseException:
        if os.path.exists(tmp):
            os.unlink(tmp)
        raise
```

Все три шага обязательны. `rename` атомарен: читатель видит либо старый файл, либо новый, но не половину. Но сам `rename` — изменение каталога, и без `fsync` на его дескрипторе после сбоя имя может откатиться, а данные остаться. Это и есть разница между «файл не побьётся» и «файл точно есть».

Цена durability — задержка: `fsync` на SSD — от десятых долей до нескольких миллисекунд, на сетевой ФС — десятки. Поэтому Postgres с `synchronous_commit=on` делает порядка тысячи транзакций в секунду, а не сто тысяч.

## df vs du

`df` спрашивает у файловой системы, сколько блоков занято; `du` обходит дерево и складывает размеры файлов. Расхождение дают три механизма.

**Удалённый, но открытый файл.** Дескриптор жив, inode жив, блоки не освобождены, имени в дереве нет:

```bash
sudo lsof +L1 | awk 'NR==1 || $7 > 0'
```

```
COMMAND  PID     USER   FD   TYPE DEVICE  SIZE/OFF NLINK     NODE NAME
nginx   2210 www-data    4w   REG   8,17 10737418240     0  1843321 /var/log/nginx/access.log (deleted)
```

`NLINK 0` и `(deleted)` — приметы. Лечится перезапуском процесса или `: > /proc/2210/fd/4`.

**Разреженные файлы.** Логический размер 10 ГБ, физически — единицы блоков:

```bash
truncate -s 10G sparse.img
du -h sparse.img; du -h --apparent-size sparse.img
```

```
0	sparse.img
10G	sparse.img
```

**Зарезервированные блоки.** ext4 держит 5% под root, поэтому `Avail` меньше, чем `Size − Used`; меняется `tune2fs -m 1 /dev/sdb1`.

## Типичные ошибки

1. **Смотреть на `free` вместо `available`.** Ядро держит в page cache всё прочитанное и отдаёт при первой нужде. 148 МБ «свободной» памяти на здоровом сервере — норма.
2. **Ставить `vm.swappiness=0`, «чтобы не было swap».** При нуле ядро всё равно вытесняет анонимные страницы под давлением, но перестаёт освобождать память заранее — OOM приходит раньше и резче. Разумный диапазон 1–10.
3. **Считать `write()` гарантией сохранности.** Возврат означает лишь копирование в page cache; без `fsync` сбой питания забирает последние секунды записей.
4. **Писать «в тот же файл» без rename.** Запись не атомарна — читатель увидит обрезанный файл. Схема «временный + fsync + rename» обязательна.
5. **Верить, что `du` показывает занятое место.** Удалённые открытые файлы и разреженность в него не попадают.
6. **Swap-файл на btrfs без `nodatacow`.** CoW ломает требование фиксированных блоков, ядро откажется его использовать.

## Чек-лист

- [ ] `free -m`: смотрим `available`, тревога — стабильно ниже 10% от `total`.
- [ ] Для каждого сервиса известны `oom_score_adj` и лимит cgroup `memory.max`.
- [ ] Важные файлы пишутся через `fsync` + `rename` + `fsync` каталога.
- [ ] Есть алерты на `df -h` и `df -i` выше 85%.
- [ ] Известно, что покажет `lsof +L1` на машине с «исчезнувшим» местом.
- [ ] После каждого OOM разбирается `dmesg`, а не только `kubectl describe`.
- [ ] Для БД проверено отношение к THP и `vm.swappiness`.
