# Глава 1a. Алгоритмика: как оценивать алгоритмы и не изобретать велосипед

Инженер, который обслуживает сервисы, редко пишет сортировки — он их вызывает. Но каждый день он
принимает решения, которые по сути алгоритмические: парсить лог построчно или загрузить в память,
искать в конфиге перебором или по индексу, хранить сессии в списке или в словаре, обходить граф
зависимостей в ширину или в глубину. Ошибка здесь стоит не «некрасиво», а «джоб встал на шесть часов»
или «сервис съел 8 ГБ на ровном месте».

Эта глава — короткий вход в алгоритмическое мышление: без доказательств и без олимпиадных трюков,
но с числами, которые позволяют на глаз отличить решение, которое масштабируется, от решения, которое
работает только на тестовом стенде. Формат намеренно простой: одна идея — один пример — одна оценка
стоимости.

## Бинарный поиск: разница между 128 и 7

Задача: найти имя в отсортированном списке из 128 элементов. Перебор в худшем случае — 128 сравнений.
Бинарный поиск делит список пополам и отбрасывает половину: 128 → 64 → 32 → 16 → 8 → 4 → 2 → 1.
Семь шагов вместо ста двадцати восьми.

```python
def binary_search(items: list[int], target: int) -> int:
    low, high = 0, len(items) - 1
    while low <= high:
        mid = low + (high - low) // 2      # не (low + high) // 2 — см. ниже
        if items[mid] == target:
            return mid
        if items[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return -1
```

Вывод: `binary_search(list(range(128)), 100)` → `100`, семь итераций. Для миллиона элементов —
двадцать итераций против миллиона.

Почему `low + (high - low) // 2`, а не `(low + high) // 2`: в языках с фиксированной разрядностью
сумма двух больших индексов переполняется и становится отрицательной — знаменитый баг, который
прожил в стандартной библиотеке Java двадцать лет. В Python переполнения нет, но привычка полезная:
тот же код переживёт перенос на Go.

Условие применимости одно и жёсткое: **массив отсортирован**. Если данные меняются каждый день,
дешевле пересортировать и искать бинарно, чем перебирать; если меняются каждую секунду — нужен
индекс (B-дерево, хеш-таблица), а не бинарный поиск.

В эксплуатации это встречается буквально: `journalctl --since` работает по отсортированному по времени
журналу, `git bisect` ищет коммит, сломавший сборку, делением истории пополам, а `sorted` + `bisect`
в Python — стандартный способ найти окно в таймсерии без полного прохода.

## O-большое: как разговаривать о скорости, не запуская код

O-большое описывает, как растёт время работы при росте входа, и отбрасывает всё, что не влияет на
рост: константы и младшие слагаемые. `3n + 100` — это O(n): при n = миллион сто сравнений не значат
ничего. `n² + n` — это O(n²): квадрат съест линейное слагаемое.

Практическая таблица для n = 1 000 000 (порядок величины, не бенчмарк):

| Класс | Что это | Операций при n = 10⁶ | Пример |
|---|---|---|---|
| O(1) | не зависит от n | 1 | доступ к `dict[key]` |
| O(log n) | деление пополам | ~20 | бинарный поиск, B-дерево |
| O(n) | один проход | 10⁶ | чтение файла, `in` по списку |
| O(n log n) | проход с сортировкой | ~2·10⁷ | `sorted()`, `sort -k` |
| O(n²) | вложенный цикл | 10¹² | сравнение всех пар |
| O(2ⁿ) | перебор подмножеств | — | точное покрытие, брутфорс |

Два вывода, которые экономят годы. Первый: разница между O(n) и O(log n) на миллионе — пять порядков,
и именно она отделяет «грепнул лог за секунду» от «грепал сутки». Второй: O(n²) на десяти тысячах
элементов — это сто миллионов операций, то есть секунды в Python и мгновения в Go; на миллионе —
уже сутки, и никакой оптимизацией констант это не лечится.

O-большое говорит о худшем случае, если не оговорено иное. Средний случай может быть лучше: quicksort
в среднем O(n log n), но на неудачном входе деградирует до O(n²).

## Массив или связный список

Классическая таблица, которую полезно помнить наизусть:

| Операция | Массив | Связный список |
|---|---|---|
| Чтение по индексу | O(1) | O(n) |
| Вставка в начало | O(n) | O(1) |
| Вставка в конец | O(1)* | O(1) |
| Поиск значения | O(n) | O(n) |
| Память на элемент | компактно | +указатель |

*амортизированно, с редкой переаллокацией.

На бумаге список выигрывает на вставках, на практике — почти никогда. Причина не в асимптотике,
а в железе: элементы массива лежат подряд, и процессор тянет их в кэш пачками по 64 байта; узлы
списка разбросаны по куче, и каждое обращение — промах кэша (глава 3). Замер из главы 3 на этой же
машине: обход массива быстрее обхода связного списка в 91 раз при одинаковой O(n).

Отсюда рабочее правило: по умолчанию массив (в Python — `list`, в Go — слайс). Связный список
оправдан, когда элементы вставляются и удаляются в середину потоком и узел уже найден, — например,
LRU-кэш на двусвязном списке.

## Рекурсия: база, шаг и стек

Рекурсивная функция — это функция, которая вызывает себя с меньшей задачей, плюс условие остановки.
Без остановки — бесконечность и `RecursionError` (в CPython по умолчанию около 1000 кадров).

```python
def factorial(n: int) -> int:
    if n <= 1:          # база: дальше некуда
        return 1
    return n * factorial(n - 1)   # шаг: задача меньше на единицу
```

Каждый вызов кладёт кадр в стек: аргументы, локальные переменные, адрес возврата. Глубина рекурсии —
это глубина стека; десять тысяч вложенных вызовов в Python упадут раньше, чем закончится память.
Поэтому обход дерева каталогов пишут итеративно с явным стеком или через `os.walk`, а не рекурсией
«в лоб».

Рекурсия хорошо ложится на задачи, где структура данных сама рекурсивна: дерево JSON, файловая
иерархия, разбор выражения, обход графа зависимостей.

## Сортировки: почему `sorted()` — почти всегда правильный ответ

Сортировка выбором — учебный минимум: найти минимум, поставить первым, повторить. O(n²), для десяти
тысяч элементов — сто миллионов сравнений.

Быстрая сортировка (quicksort) выбирает опорный элемент, разбивает массив на меньшие и большие, и
рекурсивно сортирует половины. В среднем O(n log n), но при неудачном выборе опорного (например,
первого элемента в уже отсортированном массиве) — O(n²) и глубокая рекурсия.

Сортировка слиянием стабильно даёт O(n log n) и сохраняет порядок равных элементов, но требует
дополнительной памяти под слияние.

Практический вывод: не писать сортировку. В Python `sorted()` и `list.sort()` — Timsort, гибрид
слияния и вставок, O(n log n) в худшем случае, стабильный, с оптимизацией под почти отсортированные
данные. В Go `sort.Slice` и `slices.Sort` — тоже O(n log n). Своя сортировка нужна ровно тогда, когда
меняется критерий, а не алгоритм: например, «сначала по severity, потом по времени» — это ключ
сортировки, а не новая сортировка.

```python
events.sort(key=lambda e: (severity_rank[e["sev"]], e["ts"]))
```

## Хеш-таблицы: O(1), которое иногда становится O(n)

Словарь (`dict` в Python, `map` в Go) хранит пары «ключ — значение» в массиве бакетов: хеш ключа
превращается в индекс, коллизии разрешаются цепочкой или открытой адресацией. В среднем чтение,
запись и удаление — O(1). В худшем (все ключи в один бакет) — O(n), но это требует либо плохой
хеш-функции, либо целенаправленной атаки.

Что важно эксплуатационно:

- **Загрузка (load factor).** Когда таблица заполнена примерно на две трети, она вырастает вдвое и
  пересчитывает все хеши. Отсюда «неожиданные» всплески latency при массовой вставке в кэш.
- **Ключ должен быть неизменяемым.** В Python `list` нельзя положить ключом: его хеш меняется при
  мутации. Кортеж — можно.
- **Порядок обхода.** В Python 3.7+ `dict` сохраняет порядок вставки, в Go порядок обхода мапы
  намеренно случайный — код, который на него полагается, ломается нестабильно.
- **Память.** Словарь на миллион ключей — это десятки мегабайт, а не «пара мегабайт», как кажется.

## Графы: BFS, DFS и порядок деплоя

Граф — это узлы и связи: сервисы и их зависимости, хосты и маршруты, пакеты и их требования.
Два обхода решают почти всё:

- **BFS (в ширину)** — очередь, обходим слой за слоем. В невзвешенном графе даёт кратчайший путь в
  рёбрах: «через сколько сервисов проходит запрос».
- **DFS (в глубину)** — стек (или рекурсия), идём до упора и откатываемся. Нужен для обнаружения
  циклов, топологической сортировки, обхода дерева каталогов.

```python
from collections import deque

def bfs_distance(graph: dict[str, list[str]], start: str, goal: str) -> int | None:
    seen, queue, dist = {start}, deque([(start, 0)]), {}
    while queue:
        node, d = queue.popleft()
        if node == goal:
            return d
        for nxt in graph.get(node, []):
            if nxt not in seen:
                seen.add(nxt)
                queue.append((nxt, d + 1))
    return None
```

Почему очередь даёт кратчайший путь: мы обрабатываем узлы в порядке удаления от старта, поэтому,
когда цель встречена, короче пути не существует. Стек такого свойства не даёт: DFS найдёт *какой-то*
путь, но не обязательно короткий.

Прикладной пример, знакомый каждому, кто катил Kubernetes: граф зависимостей сервисов и топологическая
сортировка — это DFS с запоминанием порядка выхода, и именно она отвечает на вопрос «в каком порядке
поднимать сервисы и где цикл, из-за которого деплой не сходится».

## Жадные алгоритмы и цена жадности

Жадный алгоритм на каждом шаге берёт локально лучшее решение и не оглядывается назад. Иногда это
оптимально (задача о выборе монет в канонической системе, минимальное остовное дерево), часто — нет.
Классический контрпример: покрытие множествами. Есть радиостанции, каждая покрывает набор городов,
нужно покрыть все города минимальным числом станций. Жадность «взять станцию, покрывающую больше
всех непокрытых» даёт решение не хуже ln(n) от оптимума, но не обязательно оптимальное.

Практический смысл: когда планировщик раскладывает задачи по нодам «самой свободной», а кэш вытесняет
«самый давний» элемент, это жадные эвристики. Они быстрые и почти всегда достаточно хорошие — и
именно поэтому LRU-кэш иногда вытесняет элемент, который понадобится через секунду.

## Динамическое программирование: запомнить подзадачу

Динамическое программирование — это рекурсия без повторного счёта: результат подзадачи запоминается
и переиспользуется. Наивное `fib(n)` — O(2ⁿ) и минуты на `fib(35)`; с мемоизацией — O(n) и микросекунды.

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n: int) -> int:
    return n if n < 2 else fib(n - 1) + fib(n - 2)
```

Идея шире, чем числа Фибоначчи: если задача разбивается на пересекающиеся подзадачи, кэш результатов
превращает экспоненту в полином. В эксплуатации это встречается как «посчитать стоимость запроса по
звеньям цепочки вызовов без повторного обхода общего хвоста» и как мемоизация в компиляторах и
планировщиках.

## Что из этого реально нужно в DevOps

- **Топ-K по частоте** (самые частые IP, коды ответа): `heapq.nlargest(k, counter.items(), key=...)` —
  O(n log k) вместо полной сортировки O(n log n). На гигабайтном логе разница заметна.
- **Бинарный поиск по времени** в отсортированном логе: `bisect` вместо линейного прохода.
- **Множества для дедупликации**: `set` даёт O(1) на проверку, список — O(n); дедуп миллиона строк
  списком — квадратичное время и часы ожидания.
- **BFS по зависимостям** — порядок запуска и поиск циклов.
- **LRU-кэш** — словарь плюс двусвязный список (или `OrderedDict.move_to_end`) для O(1) на чтение и
  вытеснение.

## Типичные ошибки

1. **Оптимизация констант вместо алгоритма.** Ускорять Python-цикл на 20%, когда сложность O(n²) и
   нужно O(n log n), — это неделя работы ради процентов вместо часа ради порядка.
2. **`in` по списку внутри цикла.** `if x in list_` — это O(n) на каждую проверку, то есть O(n²) в
   сумме. Замена списка на `set` обычно даёт ускорение в сотни раз на реальных данных.
3. **Сортировка внутри цикла.** `sorted(...)` на каждой итерации вместо одного прохода с накоплением —
   типовая ошибка в отчётах и health-check-скриптах.
4. **Рекурсия без базы или на глубоких данных.** Обход файловой системы рекурсией падает на
   `RecursionError` там, где итеративный стек работает.
5. **Полагаться на порядок обхода `map` в Go.** Он рандомизирован специально; код, который «работает
   локально», начнёт мигать в проде.
6. **Считать O(1) у словаря гарантией.** При плохом хеше или атаке коллизиями деградация до O(n)
   превращает кэш в тормоз.
7. **Путать «работает на 1000 строк» с «работает».** Квадратичный алгоритм на тестовых данных
   незаметен, на проде — стена.

## Чек-лист

- [ ] Для каждой горячей операции известна сложность и размер входа в проде, а не на фикстурах.
- [ ] Поиск по коллекции — в `set`/`dict`/индексе, а не `in` по списку в цикле.
- [ ] Сортировка выполняется один раз, а не внутри цикла.
- [ ] Для топ-K используется куча, а не полная сортировка.
- [ ] Рекурсия имеет базу и ограничение глубины; на глубоких данных есть итеративный вариант.
- [ ] Ключи словаря неизменяемы; порядок обхода не используется как контракт (кроме Python 3.7+).
- [ ] Обход графа зависимостей начинается с проверки на цикл.
