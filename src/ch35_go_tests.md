# Глава 35. Тесты, бенчмарки, pprof, race detector

В Go инструменты тестирования встроены в тулчейн: `go test` знает про покрытие, профилирование и детектор гонок, и всё это не требует сторонних библиотек. Из-за этого тесты в Go пишут чаще, а профилируют реже, чем следовало бы: `pprof` кажется чем-то для избранных. В главе — табличные тесты, бенчмарки и `-benchmem`, чтение вывода `pprof`, поимка гонки и пределы покрытия.

## Табличные тесты

Идиома Go — один тест, много случаев в срезе структур, каждый прогоняется через `t.Run`:

```go
func TestParsePort(t *testing.T) {
	tests := []struct {
		name    string
		in      string
		want    int
		wantErr bool
	}{
		{"valid", "8080", 8080, false},
		{"lower bound", "0", 0, true},
		{"too big", "65536", 0, true},
		{"not a number", "http", 0, true},
		{"empty", "", 0, true},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := ParsePort(tt.in)
			if (err != nil) != tt.wantErr {
				t.Fatalf("err = %v, wantErr %v", err, tt.wantErr)
			}
			if got != tt.want {
				t.Errorf("got %d, want %d", got, tt.want)
			}
		})
	}
}
```

Подтест с именем даёт адресную фильтрацию: `go test -run 'TestParsePort/too_big'`. Новый случай — одна строка вместо функции. Сообщения пишут в стиле «получили — ожидали», а `t.Fatalf` используют, когда продолжать нет смысла (иначе паника на нулевом значении).

## t.Helper и t.Cleanup

Проверки, вынесенные в функции, без `t.Helper()` ломают номера строк: ошибка указывает внутрь хелпера, а не в место вызова.

```go
func assertStatus(t *testing.T, got, want int) {
	t.Helper()
	if got != want {
		t.Fatalf("status = %d, want %d", got, want)
	}
}

func newTestDB(t *testing.T) *sql.DB {
	t.Helper()
	db, err := sql.Open("sqlite", "file:"+t.TempDir()+"/test.db")
	if err != nil {
		t.Fatalf("open db: %v", err)
	}
	t.Cleanup(func() { db.Close() })
	return db
}
```

`t.Cleanup` регистрирует уборку в обратном порядке регистрации и выполняется даже при `t.Fatal` — в отличие от `defer` в хелпере, который сработает при выходе из хелпера, а не из теста. `t.TempDir()` создаёт каталог, который Go удалит сам, и не требует `defer os.RemoveAll`.

## httptest

Для хендлеров есть два уровня. Юнит-уровень — `httptest.NewRecorder()`: запрос проходит через хендлер в память, без сети.

```go
func TestHealth(t *testing.T) {
	req := httptest.NewRequest(http.MethodGet, "/healthz", nil)
	rec := httptest.NewRecorder()
	HealthHandler(rec, req)
	if rec.Code != http.StatusOK {
		t.Fatalf("code = %d, want 200", rec.Code)
	}
	if body := rec.Body.String(); body != "ok\n" {
		t.Errorf("body = %q, want %q", body, "ok\n")
	}
}
```

Интеграционный — `httptest.NewServer(handler)`: поднимается настоящий HTTP-сервер на localhost со случайным портом, и клиент проходит весь путь через сетевой стек, включая заголовки, таймауты и {{L|g59|keep-alive}}. Так проверяют middleware, редиректы и {{L|g46|graceful shutdown}}; `srv.Close()` вызывают через `t.Cleanup`.

## Бенчмарки и -benchmem

```go
func BenchmarkEncode(b *testing.B) {
	payload := make([]byte, 1024)
	b.ReportAllocs()
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		if _, err := Encode(payload); err != nil {
			b.Fatal(err)
		}
	}
}
```

`b.N` подбирает сам `go test`: он увеличивает число итераций, пока измерение не станет статистически устойчивым. Подготовку данных делают до `b.ResetTimer()`, иначе она попадёт в измерение. Запуск:

```bash
go test -run '^$' -bench . -benchmem -count 5 ./...
```

```text
BenchmarkEncode-8   1248390    941.2 ns/op    2048 B/op    3 allocs/op
```

Здесь важны не наносекунды, а `B/op` и `allocs/op`: они не зависят от загрузки машины и показывают, сколько памяти и объектов на итерацию создаёт код. Рост аллокаций — почти всегда рост нагрузки на GC, и это видно даже на шумном ноутбуке. `-count 5` даёт пять прогонов для оценки разброса; сравнение версий удобно через `benchstat`.

## pprof: где на самом деле уходит время

Профиль CPU снимают прямо с теста:

```bash
go test -run '^$' -bench BenchmarkEncode -cpuprofile cpu.out -memprofile mem.out
go tool pprof -top -nodecount=10 cpu.out
```

```text
      flat  flat%   sum%        cum   cum%
     1.42s 28.40%  28.40%      1.42s 28.40%  runtime.memmove
     0.88s 17.60%  46.00%      2.10s 42.00%  encoding/json.Marshal
     0.41s  8.20%  54.20%      0.41s  8.20%  runtime.mallocgc
```

`flat` — время в самой функции, `cum` — включая вызываемые. Если сверху `memmove` и `mallocgc`, проблема не в логике, а в копировании и аллокациях: лечится переиспользованием буферов и `sync.Pool`. Команда `go tool pprof -list Encode cpu.out` показывает время по строкам функции:

```text
ROUTINE ======================== main.Encode in /src/encode.go
     0.88s      2.10s (flat, cum) 42.00% of Total
         .          .     12: func Encode(v any) ([]byte, error) {
     0.20s      0.20s     13:     buf := new(bytes.Buffer)
     0.50s      1.80s     14:     enc := json.NewEncoder(buf)
```

Интерактивный режим `go tool pprof cpu.out` даёт те же `top` и `list`, плюс `web` — граф вызовов, для него нужен graphviz. Для живого сервиса профиль снимают через `net/http/pprof`, подключённый пустым импортом на отдельном порту, — `go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30`. Порт наружу не публикуют.

## Race detector

`go test -race` включает детектор гонок — инструментирование доступа к памяти. Классическая гонка:

```go
var counter int

func TestRace(t *testing.T) {
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() { defer wg.Done(); counter++ }()
	}
	wg.Wait()
}
```

```text
WARNING: DATA RACE
Write at 0x00c00001a0a8 by goroutine 8:
  main.TestRace.func1()
      /src/main_test.go:12 +0x30
Previous write at 0x00c00001a0a8 by goroutine 7:
  main.TestRace.func1()
```

Детектор не «иногда» находит, а сообщает о реальном пересечении доступа, но только о том, который случился в прогоне: гонка в редкой ветке может не проявиться. Поэтому `-race` гоняют в CI на каждом коммите, а не раз в месяц. Цена — замедление в 5–10 раз и рост потребления памяти; в продакшене сборку с `-race` не выпускают. Лечение: `atomic.Int64`, `sync.Mutex` или передача данных через канал.

## Покрытие и его пределы

```bash
go test -coverprofile=cover.out ./...
go tool cover -func=cover.out | tail -1
go tool cover -html=cover.out
```

Покрытие считает, какие строки выполнялись, а не какие проверены. Строка `if err != nil { return err }` покрыта, если ошибка произошла, но никто не проверял её содержимое. Отсюда типичная картина: 85% покрытия при нулевой проверке граничных случаев. Ориентир для сервисного кода — 60–80% на пакетах с логикой; гнаться за 100% в хендлерах и сгенерированном коде бессмысленно. Полезнее смотреть на покрытие диффа: не изменил ли новый PR ветку без теста.

## Тесты с таймаутами

По умолчанию `go test` убивает весь пакет через 10 минут. Отдельный тест ограничивают `-timeout`:

```bash
go test -timeout 60s -run TestSlowIntegration ./...
```

Внутри теста полезен `t.Deadline()`: он возвращает момент, когда пакет будет убит, и позволяет выделить операции бюджет.

```go
func TestWorkerShutdown(t *testing.T) {
	dl, ok := t.Deadline()
	ctx := context.Background()
	if ok {
		var cancel context.CancelFunc
		ctx, cancel = context.WithDeadline(ctx, dl.Add(-5*time.Second))
		defer cancel()
	}
	if err := worker.Shutdown(ctx); err != nil {
		t.Fatalf("shutdown: %v", err)
	}
}
```

Запас в пять секунд оставляет время на `t.Fatalf` и уборку, иначе тест падает по общему таймауту. `t.Parallel()` ускоряет пакет, но требует независимых тестов: общий `temp`-каталог или общая БД превратят параллельный прогон в источник флаки.

## Фаззинг

С версии 1.18 в тулчейне есть нативный фаззинг: `go test -fuzz` подставляет в тест случайные строки и ищет панику или нарушение инварианта.

```go
func FuzzParsePort(f *testing.F) {
	f.Add("8080") // начальный корпус
	f.Fuzz(func(t *testing.T, s string) {
		port, err := ParsePort(s)
		if err == nil && (port < 1 || port > 65535) {
			t.Fatalf("out of range: %d", port)
		}
	})
}
```

```bash
go test -fuzz FuzzParsePort -fuzztime 30s
```

Фаззер держит найденный вход в `testdata/fuzz/`, и он превращается в обычный регрессионный кейс, который гоняется при каждом `go test`. Тридцати секунд обычно хватает, чтобы найти панику в парсере; в CI фаззинг запускают по расписанию, а не на каждый коммит.

## Полезные флаги go test

| Флаг | Что делает |
|---|---|
| `-run` | фильтр тестов по регулярному выражению |
| `-bench` | фильтр бенчмарков |
| `-benchmem` | добавляет `B/op` и `allocs/op` |
| `-count` | число прогонов для оценки разброса |
| `-race` | включает детектор гонок |
| `-shuffle=on` | случайный порядок тестов и пакетов |
| `-timeout` | предел времени на пакет |

`-shuffle=on` стоит включить в CI хотя бы раз в неделю: он вскрывает тесты, которые проходят только благодаря порядку запуска и общему состоянию.

## Типичные ошибки

1. **Тест проверяет реализацию, а не поведение.** Моки на каждый вызов ломаются от любого рефакторинга; тест должен фиксировать контракт — код ответа, тело, побочный эффект.
2. **Хелпер без `t.Helper()`.** Ошибка указывает внутрь хелпера, и в большом пакете непонятно, какой тест упал.
3. **`defer` вместо `t.Cleanup` в хелпере.** `defer` срабатывает при выходе из хелпера, то есть до конца теста: ресурс закрывается раньше, чем тест им пользуется.
4. **Бенчмарк с подготовкой внутри цикла.** `b.N`-цикл меряет генерацию данных вместе с кодом; результат зависит от машины и вводит в заблуждение.
5. **Оценка по `ns/op` без `-benchmem`.** Наносекунды шумят, а аллокации стабильны; оптимизация без счёта аллокаций часто делает хуже.
6. **`-race` только локально.** Гонка в редкой ветке не воспроизводится, а в CI с параллельными тестами всплывает; детектор должен быть в пайплайне.
7. **Погоня за 100% покрытия.** Время уходит на тесты геттеров, а необработанная ошибка в середине остаётся незамеченной.

## Чек-лист

- [ ] Каждый тест-кейс — подтест с осмысленным именем, фильтруемый через `-run`.
- [ ] Все хелперы начинаются с `t.Helper()`, уборка — через `t.Cleanup`.
- [ ] Для хендлеров есть и юнит-тест на `httptest.NewRecorder`, и хотя бы один на `httptest.NewServer`.
- [ ] Бенчмарки запускаются с `-benchmem`, подготовка вынесена до `b.ResetTimer()`.
- [ ] `go test -race ./...` выполняется в CI на каждый коммит.
- [ ] Профили CPU и heap снимаются воспроизводимой командой и читаются через `-top` и `list`.
- [ ] У интеграционных тестов есть `-timeout` и запас на уборку через `t.Deadline()`.

## Упражнения

1. Перепишите набор из пяти отдельных тестов в табличный и добавьте флаг `-run` для одного случая.
2. Найдите в своём коде функцию с аллокациями внутри цикла, снимите `-benchmem` до и после `sync.Pool`, сравните `allocs/op` через `benchstat`.
3. Снимите CPU-профиль теста и найдите в `-top` три самые дорогие функции; проверьте догадку командой `list`.
4. Внесите гонку в счётчик, поймайте её `-race`, затем исправьте тремя способами: мьютекс, атомик, канал. Сравните сложность.
5. Сделайте тест, который без `t.Deadline()` падает по общему таймауту, и почините его, выделив бюджет операции.
