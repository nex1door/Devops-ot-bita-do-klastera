# Глава 7. TCP и UDP: надёжность, порты, сокеты

IP умеет доставить пакет «куда-нибудь и как-нибудь»: он не гарантирует ни порядка, ни доставки, ни целостности потока. TCP поверх этого делает вид, что между двумя процессами проложен надёжный двунаправленный канал, хотя под ним — сеть, теряющая пакеты. Почти все «странные» сетевые симптомы в эксплуатации объясняются деталями этой надстройки: соединение висит 127 секунд при недоступном хосте, приложение копит CLOSE_WAIT, сервер под нагрузкой теряет SYN, а `TIME_WAIT` на клиенте не даёт открыть новый сокет. В этой главе — рукопожатие, окна и congestion control, состояния из `ss`, порты, backlog, UDP и по одному сокету на Python и Go.

## Что именно гарантирует TCP

TCP (RFC 9293) даёт четыре вещи: доставку без потерь (потерянный сегмент будет передан снова), порядок байт, обнаружение дубликатов и управление потоком. Модель данных — поток байт (byte stream), а не сообщения: `send()` дважды по 100 байт может прийти одним `recv()` на 200. Поэтому в прикладных протоколах нужен свой фрейминг — длина в заголовке или разделитель.

Нумерация идёт по байтам: sequence number (seq) — номер первого байта сегмента, acknowledgement (ack) — номер следующего ожидаемого байта. Начальный номер выбирается случайно (ISN) — это защита от подмены и от старых дубликатов, блуждающих по сети. Отсюда «надёжность»: получив сегмент с дыркой, получатель продолжает подтверждать последний непрерывный байт, а отправитель по таймеру (RTO, retransmission timeout) пересылает потерянное.

## Трёхстороннее рукопожатие

Соединение открывается тремя пакетами:

1. клиент → сервер: `SYN`, seq = x, опции (MSS, window scale, SACK, timestamps);
2. сервер → клиент: `SYN-ACK`, seq = y, ack = x+1;
3. клиент → сервер: `ACK`, ack = y+1. С этого момента соединение ESTABLISHED у обеих сторон.

Зачем три, а не два: обе стороны должны подтвердить и свой ISN, и чужой. Два пакета не позволяют одновременно синхронизировать номера в обе стороны.

Если сервер недоступен (пакеты уходят в никуда), клиент повторяет SYN с экспоненциальной задержкой. При `tcp_syn_retries=6` (значение по умолчанию) попытки идут примерно через 1, 2, 4, 8, 16, 32 и 64 секунды — итого около 127 секунд до `ETIMEDOUT`. Именно поэтому «сайт не открывается две минуты» — не баг приложения, а таймер ядра: `connect()` без своего таймаута ждёт столько, сколько скажет TCP.

Рукопожатие видно в захвате: в прошлой главе мы снимали `Flags [S]` и через секунду — повторный `[S]` с тем же seq. Для сервера важен другой счётчик: полуоткрытые соединения (SYN queue) и завершённые, ожидающие `accept()` (accept queue). Если accept queue переполнена, ядро по умолчанию молча выбрасывает SYN — клиент видит ретрансмиссии, а в `nstat` растёт `TcpExtListenOverflows`.

## Окно и скользящее окно

Получатель не может бесконечно принимать данные: у него есть буфер. Размер свободного места объявляется в поле window каждого ACK — это receive window (rwnd). Отправитель держит «окно» неподтверждённых байт и может отправить не больше, чем разрешает минимум из rwnd и своего congestion window (cwnd).

Скользящее окно (sliding window) означает, что окно не фиксировано: по мере подтверждения старых байт оно сдвигается вправо, открывая место новым. Если приложение не читает из сокета, буфер заполняется, окно становится нулевым (zero window), и отправитель останавливается. Это самая частая причина «соединение живо, но данные не идут»: сервер принял запрос и завис в обработке, не вызывая `recv()`.

Изначально окно — 16 бит (максимум 65535), чего мало для быстрых каналов: при RTT 100 мс это 5 Мбит/с. Расширение (RFC 7323) добавляет множитель: в нашем дампе была опция `wscale 7`, то есть окно умножается на 2⁷ = 128, и максимум становится 8 МБ.

## Congestion control: коротко о главном

Потери в сети — не всегда вина получателя; чаще это перегрузка на пути. Поэтому отправитель держит ещё один лимит — cwnd, и растит его осторожно:

- **slow start** — cwnd начинается с 10 сегментов и удваивается каждый RTT, пока не упрётся в порог;
- **congestion avoidance** — дальше растёт на один сегмент за RTT (аддитивно), а при потере уменьшается вдвое (мультипликативно). Это AIMD — та самая «аддитивная скорость, мультипликативное снижение».

Алгоритмы отличаются реакцией на потери: `cubic` (по умолчанию в Linux) считает cwnd функцией от времени с момента последней потери и хорошо ведёт себя на длинных толстых каналах; `bbr` измеряет пропускную способность и RTT и не реагирует на потери как на сигнал перегрузки — на каналах с потерями (Wi-Fi, мобильные сети, дальние маршруты) даёт заметно больше.

Посмотреть всё это вживую:

```bash
ss -tin state established
```

```
0  0  192.168.0.75:35576  149.154.167.220:443
    cubic wscale:10,7 rto:280 rtt:77.215/17.871 mss:1228 pmtu:1500 cwnd:10
    bytes_sent:2652 bytes_acked:2653 bytes_received:6182 segs_out:13 segs_in:11
    send 1272292bps pacing_rate 2544576bps delivery_rate 355488bps app_limited
    busy:160ms rcv_space:14480 snd_wnd:73728 rcv_wnd:79488
```

Читается так: `rto:280` — текущий таймер ретрансмиссии в миллисекундах, `rtt:77.215/17.871` — средний RTT и отклонение, `cwnd:10` — десять сегментов в полёте (соединение только что открылось, slow start ещё не разогнался), `app_limited` — приложение само не даёт больше данных, `snd_wnd:73728` — сколько разрешил получатель. Если `cwnd` большой, а `delivery_rate` низкий, узкое место не в TCP; если `snd_wnd` близок к нулю — тормозит получатель.

## Состояния TCP и ss

Соединение проходит 11 состояний. Практически важны шесть:

| Состояние | Что означает | Когда это проблема |
|---|---|---|
| `LISTEN` | сокет ждёт подключений | не тот адрес (`127.0.0.1` вместо `0.0.0.0`) |
| `SYN-SENT` | клиент отправил SYN | много таких — сервер не отвечает |
| `ESTAB` | соединение работает | много — норма для нагруженного сервиса |
| `CLOSE-WAIT` | получили FIN, но `close()` не вызван | растёт — приложение не закрывает сокеты |
| `TIME-WAIT` | закрыли первыми, ждём 60 с | тысячи на клиенте — кончаются порты |
| `FIN-WAIT-2` | отправили FIN, ждём FIN от второй стороны | висит — вторая сторона не закрывает |

```bash
ss -tan
```

```
State      Recv-Q Send-Q Local Address:Port     Peer Address:Port
LISTEN     0      4096       0.0.0.0:8080          0.0.0.0:*
LISTEN     0      128          0.0.0.0:22            0.0.0.0:*
ESTAB      0      0       192.168.0.75:35576  149.154.167.220:443
ESTAB      0      0       192.168.0.75:51422  170.246.55.162:9230
TIME-WAIT  0      0       192.168.0.75:42512  149.154.167.220:443
```

Для `LISTEN` колонка `Send-Q` — это размер accept queue (текущий backlog), для остальных — байты в буфере отправки. Именно поэтому `ss -lnt` с ненулевым `Send-Q` на слушающем сокете — признак, что приложение не успевает вызывать `accept()`.

Диагностическое правило: **CLOSE-WAIT — всегда баг приложения**, оно получило FIN и не закрыло дескриптор; ядро тут ничего не сделает, пока не кончится лимит файловых дескрипторов. **TIME-WAIT — норма протокола**, и бороться с ним настройками ядра нужно очень осторожно.

```bash
ss -s
```

```
Total: 320
TCP:   151 (estab 49, closed 85, orphaned 0, timewait 77)
```

## TIME_WAIT и почему он болит

Сторона, закрывшая соединение первой, уходит в `TIME_WAIT` на 2×MSL — в Linux это 60 секунд (`tcp_fin_timeout` относится к другому, FIN-WAIT-2). Причина двойная: нужно дождаться запоздавших сегментов старого соединения, чтобы они не попали в новое с теми же номерами портов, и нужно, чтобы последний ACK дошёл, если он потерялся.

Боль возникает не от самого состояния, а от исчерпания портов. Сокет однозначно определяется четвёркой (src IP, src port, dst IP, dst port). Клиент, делающий тысячи коротких соединений к одному серверу, тратит эфемерные порты:

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
```

```
32768	60999
```

Это 28 232 порта. При 500 соединениях в секунду и 60 секундах в {{L|g117|TIME_WAIT}} нужно 30 000 одновременно занятых портов — пределов больше нет, и `connect()` начинает падать с `Cannot assign requested address`. Правильные лечения по порядку: переиспользовать соединения ({{L|g59|keep-alive}} в HTTP-клиенте, пул соединений), увеличить диапазон портов, и только потом `net.ipv4.tcp_tw_reuse=1` (безопасно для исходящих соединений при включённых timestamps). `tcp_tw_recycle` в современных ядрах удалён — он ломал NAT и был опасен.

Серверную сторону TIME_WAIT обычно не трогают: там закрывает клиент, а если закрывает сервер — это признак, что приложение рвёт соединение первым (например, `Connection: close` вместо keep-alive).

## Порты, сокеты и backlog

Порт — 16 бит, 0–65535. Порты ниже 1024 требуют привилегий в Unix (либо `CAP_NET_BIND_SERVICE`). Диапазоны: 0–1023 системные, 1024–49151 регистрируемые, 49152–65535 динамические; Linux использует для исходящих свой диапазон из `ip_local_port_range`.

Сокет в ядре — структура, привязанная к четвёрке адресов. Сервер делает `socket()` → `bind()` → `listen(backlog)`. Аргумент `listen()` задаёт длину очереди завершённых соединений, но реальный лимит — минимум из backlog и `net.core.somaxconn` (в наших системах 4096). Отдельно есть очередь полуоткрытых (`tcp_max_syn_backlog`, 512 по умолчанию).

Что происходит при переполнении accept queue, зависит от `tcp_abort_on_overflow`: по умолчанию (0) сервер молча выбрасывает ACK, клиент считает соединение установленным и отправляет данные, они теряются, и клиент видит загадочный таймаут при полностью «живом» сервере. Счётчики:

```bash
nstat -az | grep -E 'ListenOverflows|ListenDrops'
```

```
TcpExtListenOverflows           0                  0.0
TcpExtListenDrops               0                  0.0
```

Ненулевой `ListenOverflows` — прямое указание: либо приложение медленно принимает, либо backlog мал. В nginx это лечится `listen 80 backlog=4096;` и увеличением числа worker-процессов.

## UDP: где он уместен

UDP (RFC 768) даёт только мультиплексирование по портам и контрольную сумму. Нет рукопожатия, нет подтверждений, нет порядка, нет управления потоком — есть датаграмма, которая либо доедет, либо нет. Заголовок — 8 байт против 20 у TCP.

Уместен он там, где задержка важнее гарантий, либо где надёжность реализуют выше:

- DNS — один вопрос, один ответ, переспросить дешевле, чем держать соединение;
- QUIC (основа {{L|g52|HTTP/3}}) — надёжность и управление перегрузкой сделаны в user space поверх UDP;
- голос и видео — опоздавший пакет бесполезен, повторять его незачем;
- метрики (StatsD), логи, syslog — потеря одной точки не критична;
- DHCP, NTP, SNMP, WireGuard.

Две ловушки UDP. Первая — размер: датаграмма больше MTU фрагментируется, а потеря одного фрагмента убивает всю датаграмму; практический безопасный размер — около 1200 байт. Вторая — отсутствие управления перегрузкой: приложение, шлющее UDP в цикле, само создаёт перегрузку, и сеть отвечает потерями; отсюда и ограничение скорости на стороне приложения.

## Keepalive и таймауты

Молчащее TCP-соединение может быть мёртвым: партнёр ушёл, а FIN не пришёл (обрыв Wi-Fi, рестарт NAT, падение процесса без `close()`). Ядро обнаруживает это keepalive-пробами: первый запрос через `tcp_keepalive_time` (7200 с), затем каждые `tcp_keepalive_intvl` (75 с), до `tcp_keepalive_probes` (9) попыток — итого больше двух часов.

Для сервиса это неприемлемо долго, поэтому:

```python
import socket

s = socket.create_connection(("203.0.113.10", 5432), timeout=3)
s.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, 30)     # первая проба через 30 с
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)    # далее каждые 10 с
s.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, 3)       # 3 промаха — соединение мертво
s.settimeout(5)                                               # таймаут на recv/send
s.sendall(b"PING\n")
print(s.recv(64))
```

Важная деталь: `settimeout()` в Python — не «таймаут соединения», а таймаут каждой операции ввода-вывода. Без него `recv()` висит вечно, даже если TCP-соединение полумёртвое. И `timeout` в `create_connection` ограничивает только установку.

В Go принято управлять дедлайнами явно:

```go
func fetch(addr string) ([]byte, error) {
	conn, err := net.DialTimeout("tcp", addr, 3*time.Second)
	if err != nil {
		return nil, fmt.Errorf("dial: %w", err)
	}
	defer conn.Close()

	conn.SetDeadline(time.Now().Add(5 * time.Second)) // и на чтение, и на запись
	if _, err := conn.Write([]byte("PING\n")); err != nil {
		return nil, fmt.Errorf("write: %w", err)
	}
	buf := make([]byte, 64)
	n, err := conn.Read(buf) // вернётся по дедлайну, даже если данных нет
	if err != nil {
		return nil, fmt.Errorf("read: %w", err)
	}
	return buf[:n], nil
}
```

Дедлайн в Go — абсолютное время, а не длительность, поэтому его нужно пересчитывать перед каждой операцией; иначе второй `Read` упадёт мгновенно с `i/o timeout`.

## Типичные ошибки

1. **Ждать `connect()` без своего таймаута.** Ядро ждёт до ~127 секунд при `tcp_syn_retries=6`, и всё это время пул потоков или {{L|g37|event loop}} занят. Таймаут прикладного уровня обязателен и всегда меньше внешнего.
2. **Считать TCP потоком сообщений.** Два `send()` не равны двум `recv()`: границы размываются, особенно при ретрансмиссиях. Нужен фрейминг.
3. **Лечить CLOSE_WAIT настройками ядра.** Это всегда незакрытый дескриптор в коде; `tcp_fin_timeout` тут ни при чём.
4. **Бороться с TIME_WAIT через `tcp_tw_recycle`.** В современных ядрах опции нет; попытки включить её через sysctl молча ничего не делают, а старые рецепты из интернета опасны для NAT.
5. **Ставить `listen(128)` и забыть про `somaxconn`.** Реальный backlog — минимум из двух; при переполнении SYN выбрасывается, и клиенты видят ретрансмиссии вместо ошибки.
6. **Гнать UDP-датаграммы больше MTU.** Фрагментация умножает вероятность потери: при 1% потерь на пакет датаграмма из трёх фрагментов теряется почти в 3% случаев.
7. **Игнорировать `ss` при отладке «медленного» сервиса.** Растущая accept queue (`Send-Q` в `LISTEN`) объясняет задержки быстрее, чем профайлер.

## Чек-лист

- [ ] У всех клиентов есть явные таймауты: connect, чтение, общий дедлайн запроса.
- [ ] HTTP-клиенты используют keep-alive или пул соединений, а не новое соединение на запрос.
- [ ] `ss -s` и `nstat -az` снимаются при каждом инциденте с задержками.
- [ ] Метрика `TcpExtListenOverflows` под наблюдением и равна нулю.
- [ ] `somaxconn` и backlog приложения согласованы и проверены под нагрузкой.
- [ ] Для UDP-сервисов размер датаграммы ≤ 1200 байт.
- [ ] Keepalive включён на уровне приложения или ОС для долгоживущих соединений.
- [ ] `TIME_WAIT` на клиенте измерен, а не предполагаем: `ss -tan state time-wait | wc -l`.
