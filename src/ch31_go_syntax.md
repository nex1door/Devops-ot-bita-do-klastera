# Глава 31. Синтаксис: срезы, мапы, указатели, интерфейсы, ошибки

Go намеренно маленький язык: в нём 25 ключевых слов, нет наследования, нет исключений, нет перегрузки операторов. Эта минимальность — не бедность, а решение: код на Go читается одинаково у разных команд, потому что способов выразить одну мысль мало. Но несколько механизмов устроены не так, как ожидает человек из Python или Java, и именно на них ломаются новички: срез — это не массив, мапа обходится в случайном порядке, интерфейс может быть не nil при nil-значении внутри, а ошибка — обычное значение, которое надо возвращать, а не бросать. В этой главе мы разберём эти механизмы на уровне модели памяти, чтобы поведение программ перестало быть сюрпризом. Все примеры проверены компилятором Go 1.26: добавив `package main` и импорты, любой можно запустить через `go run`.

## Массивы и срезы

Массив в Go — значение фиксированной длины, известной на этапе компиляции. `[4]int` и `[8]int` — разные типы, и присваивание копирует все элементы целиком.

```go
var a [4]int
b := a          // полная копия, 32 байта
b[0] = 7
fmt.Println(a[0], b[0]) // 0 7
```

Срез (slice) — это дескриптор массива, лежащего в куче или на стеке. Он состоит из трёх машинных слов: указатель на первый элемент, длина (len) и ёмкость (cap). На 64-битной платформе — 24 байта независимо от количества элементов. Копирование среза копирует дескриптор, а не данные: обе переменные смотрят в один и тот же массив.

```go
s := []int{1, 2, 3, 4}
t := s[1:3]      // len=2, cap=3, указывает на s[1]
t[0] = 99
fmt.Println(s)   // [1 99 3 4] — изменился исходный срез
```

`len(t)` равен 2, а `cap(t)` — 3, потому что от индекса 1 до конца исходного массива остаётся три элемента. Отсюда правило: `cap` среза после `s[i:j]` уменьшается на `i`, но не на `j-i`. Понимание этого объясняет большинство «магических» багов с неожиданно изменившимися данными.

### append и переаллокация

`append` добавляет элементы в конец. Если в ёмкости есть место, он пишет в тот же массив и возвращает новый дескриптор с увеличенной длиной. Если места нет — выделяет новый массив, копирует туда старые элементы и возвращает дескриптор на него.

```go
func main() {
	s := make([]int, 0, 2)
	s = append(s, 1, 2)
	fmt.Printf("len=%d cap=%d %p\n", len(s), cap(s), s) // len=2 cap=2 0xc000...
	s = append(s, 3)
	fmt.Printf("len=%d cap=%d %p\n", len(s), cap(s), s) // len=3 cap=4 0xc000... (новый адрес)
}
```

При росте (`runtime.growslice`) ёмкость увеличивается примерно вдвое для небольших срезов и примерно на четверть для больших. Это амортизирует стоимость копирования: серия из N добавлений даёт O(N) работы, а не O(N²). Практический вывод: если заранее известно количество элементов, `make([]T, 0, n)` избавит от нескольких копирований — на миллионе элементов это заметно.

Ловушка, которая следует из общей памяти: `append` в срез, полученный через `s[:2]`, может перезаписать элемент `s[2]`, если ёмкости хватило.

```go
s := []int{1, 2, 3}
t := s[:2]
t = append(t, 10)  // ёмкости хватило — пишем в s[2]
fmt.Println(s, t)  // [1 2 10] [1 2 10]
```

Если такая запись нежелательна, срез копируют явно: `t := slices.Clone(s[:2])` или `append([]int(nil), s[:2]...)`. Пакет `slices` (стандартная библиотека с Go 1.21) содержит `Clone`, `Contains`, `Index`, `Sort`, `Equal`, `Delete`, `Insert` и избавляет от ручных циклов.

## Мапы

Мапа (map) — хеш-таблица. Объявление `map[string]int` создаёт nil-мапу: читать из неё можно (вернётся нулевое значение), писать — паника `assignment to entry in nil map`. Создавать нужно через `make` или литерал.

```go
m := map[string]int{"a": 1}
m["b"] = 2
delete(m, "a")

v, ok := m["missing"]   // v==0, ok==false
_, exists := m["b"]     // проверка наличия без значения
```

Идиома `v, ok := m[k]` — единственный способ отличить отсутствующий ключ от ключа с нулевым значением. Для `map[string]struct{}` (множество) значение не нужно вовсе: `m[k] = struct{}{}` занимает ноль байт.

Порядок обхода мапы не определён и намеренно рандомизирован в рантайме. Две итерации по одной и той же неизменённой мапе дадут разный порядок.

```go
for k, v := range m {
	fmt.Println(k, v)
}
```

Это сделано специально, чтобы код не опирался на порядок, который может измениться при росте мапы и между версиями рантайма. Если нужен детерминированный обход — сортируйте ключи: `slices.Sorted(maps.Keys(m))` возвращает отсортированный срез (итераторы `maps.Keys` появились в Go 1.23). Кстати, `fmt.Println` мапы печатает ключи отсортированными — это особенность форматирования, а не свойство мапы, и полагаться на неё в логике нельзя.

Мапа — ссылочный тип: копия переменной указывает на ту же таблицу. И мапы не безопасны для одновременной записи из разных горутин: параллельная запись даёт фатальную ошибку `concurrent map writes`, которую нельзя перехватить через `recover`. Для конкурентного доступа нужен `sync.Mutex` или `sync.Map` (глава 32).

## Указатели

Указатель хранит адрес значения. `&x` берёт адрес, `*p` разыменовывает. В Go нет арифметики указателей: `p++`, `p+1`, приведение произвольного числа к указателю запрещены на уровне языка. Это убирает целый класс ошибок работы с памятью, который есть в C, и позволяет сборщику мусора точно знать, какие адреса живые.

```go
type Counter struct{ n int }

func (c *Counter) Inc()       { c.n++ }      // меняет оригинал
func (c *Counter) Value() int { return c.n }  // тот же получатель

func main() {
	c := Counter{}
	c.Inc()
	fmt.Println(c.Value()) // 1
}
```

Указатель нужен в трёх случаях: чтобы метод менял получателя; чтобы не копировать большую структуру (условно — больше нескольких десятков байт); чтобы отличать «значение отсутствует» от нулевого значения (`*int` со значением nil). Во всех остальных случаях значение проще и безопаснее.

`new(T)` возвращает `*T`, указывающий на нулевое значение; на практике чаще пишут `&T{}`. Разыменование nil-указателя — паника, и это нормально: программа, которая дошла до nil там, где ожидалось значение, уже сломана, и падение с трассировкой лучше, чем тихая порча данных.

## Структуры и методы

Структура — набор полей. Метод — функция с получателем (receiver), объявленная в том же пакете, что и тип.

Ключевое решение при проектировании — value или pointer receiver. Правила простые: если хотя бы один метод меняет состояние, все методы типа делают pointer receiver; если тип содержит `sync.Mutex` или другой некопируемый примитив, — тоже pointer; если тип маленький и неизменяемый (`time.Time`, `url.URL`), — value. Смешивать нельзя: методы с разными получателями попадают в разные наборы методов, и тип может перестать удовлетворять интерфейсу.

```go
type Buffer struct {
	mu   sync.Mutex
	data []byte
}

func (b *Buffer) Write(p []byte) (int, error) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.data = append(b.data, p...)
	return len(p), nil
}
```

Встраивание (embedding) заменяет наследование: поле без имени продвигает методы встроенного типа наружу.

```go
type Logger struct{ prefix string }

func (l Logger) Log(msg string) { fmt.Println(l.prefix, msg) }

type Service struct {
	Logger       // встроено: s.Log("...") работает
	name   string
}
```

Это композиция, а не подтипизация: `Service` не является `Logger` в смысле присваивания, но получает его методы. Переопределение делается объявлением метода с тем же именем у внешнего типа.

## Интерфейсы

Интерфейс — набор сигнатур методов. Реализация неявная: тип удовлетворяет интерфейсу, если у него есть все эти методы, и объявлять `implements` не нужно. Отсюда принцип «интерфейсы объявляет потребитель»: пакет, которому нужно писать в поток, объявляет у себя `type writer interface{ Write([]byte) (int, error) }` — и любой тип с методом `Write` подходит, включая `os.File`, `bytes.Buffer` и `net.Conn`.

Стандартная библиотека построена на маленьких интерфейсах: `io.Writer` (один метод), `io.Reader`, `fmt.Stringer`, `error`. Маленький интерфейс легко реализовать и легко подменить в тесте — в этом главная практическая ценность.

Значение интерфейса — пара (динамический тип, значение). Пустой интерфейс `any` (алиас `interface{}` с Go 1.18) хранит что угодно. Отсюда знаменитая ловушка:

```go
type MyErr struct{}
func (e *MyErr) Error() string { return "my error" }

func do() error {
	var e *MyErr = nil
	return e            // вернули интерфейс с типом *MyErr и nil-значением
}

func main() {
	err := do()
	fmt.Println(err == nil) // false!
}
```

Интерфейс равен nil только если nil и тип, и значение. Здесь тип — `*MyErr`, поэтому `err != nil`, и проверка `if err != nil` сработает, хотя внутри пусто. Лечится тем, что функция возвращает `nil` явно, а не nil-указатель конкретного типа.

Приведение типа: `v, ok := x.(io.Writer)` — безопасная форма, `v := x.(io.Writer)` паникует при несоответствии. Множественное приведение удобно делать через `switch v := x.(type)`.

## Ошибки как значения

`error` — встроенный интерфейс с единственным методом `Error() string`. Ошибки возвращаются последним значением и проверяются сразу — исключений в языке нет.

```go
var ErrNotFound = errors.New("not found")

func find(id string) (*Item, error) {
	it, ok := db[id]
	if !ok {
		return nil, fmt.Errorf("find %q: %w", id, ErrNotFound)
	}
	return &it, nil
}
```

`fmt.Errorf` с глаголом `%w` оборачивает ошибку, сохраняя цепочку. `errors.Is(err, ErrNotFound)` проходит по цепочке и сравнивает с sentinel-ошибкой, `errors.As(err, &target)` ищет в цепочке ошибку конкретного типа и записывает её в target. С Go 1.20 `errors.Join` объединяет несколько ошибок в одну, а `errors.Is/As` умеют обходить и такое дерево.

Разделение ответственности: низкоуровневый код возвращает ошибку с контекстом и обёрткой, вызывающий решает, что с ней делать — повторить, вернуть 500 или 404. Логировать нужно один раз, на верхнем уровне; логирование и возврат одной и той же ошибки на каждом слое даёт тройные записи об одном сбое.

```go
it, err := find("42")
switch {
case errors.Is(err, ErrNotFound):
	http.Error(w, "not found", http.StatusNotFound)
case err != nil:
	log.Printf("find: %v", err)
	http.Error(w, "internal error", http.StatusInternalServerError)
}
```

Такой `switch` — типичный обработчик на границе сервиса: наружу отдаётся минимальная информация, внутрь лога — полная цепочка.

## defer, panic, recover

`defer` откладывает вызов до выхода из функции. Отложенные вызовы выполняются в обратном порядке (LIFO), как стек. Аргументы вычисляются в момент `defer`, а не в момент выполнения:

```go
func f() {
	i := 1
	defer fmt.Println("deferred:", i) // запомнит 1
	i = 2
	fmt.Println("now:", i)            // 2
}
// now: 2
// deferred: 1
```

Отсюда правило: `defer f.Close()` безопасен, а `defer os.Remove(name)` с переменной, которая потом меняется, — нет. `defer` внутри цикла копит отложенные вызовы до конца функции; для файлов в цикле нужен либо явный `Close()`, либо функция-обёртка на итерацию. После open-coded defers (Go 1.14) накладные расходы `defer` почти нулевые — экономить на нём не нужно.

`panic` разворачивает стек и выполняет отложенные вызовы. `recover` в отложенной функции останавливает панику и возвращает её значение. Применять `recover` стоит в двух местах: на границе процесса (HTTP-обработчик, воркер очереди, gRPC-интерцептор), чтобы одна паника не убила весь сервис, и в тестовых хелперах. Превращать панику в ошибку внутри бизнес-логики не нужно: если функция может не справиться — она возвращает `error`.

```go
func safeHandler(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if v := recover(); v != nil {
				log.Printf("panic: %v\n%s", v, debug.Stack())
				http.Error(w, "internal error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}
```

Важно: `recover` работает только при непосредственном вызове из отложенной функции. `defer func() { helper() }()`, где `helper` вызывает `recover`, панику не остановит.

## Типичные ошибки

**Ожидание, что срез — это копия.** `t := s[1:3]` даёт дескриптор на ту же память; изменение `t[0]` меняет `s[1]`. Механизм — общий массив и разные заголовки. Копия делается `slices.Clone` или `copy(dst, src)`.

**append в под-срез портит исходные данные.** Если у под-среза осталась ёмкость, `append` пишет в общий массив за пределами его длины. Механизм тот же: `cap` считается от начала под-среза до конца буфера. Лечится трёхиндексным срезом `s[i:j:k]`, который ограничивает ёмкость, или клонированием.

**Порядок обхода мапы как контракт.** Код, который печатает элементы мапы и надеется на стабильный вывод, ломается при добавлении ключа или смене версии. Рантайм рандомизирует стартовую позицию итерации намеренно. Нужен порядок — сортируйте ключи.

**Запись в nil-мапу.** `var m map[string]int; m["a"] = 1` — паника, потому что таблица не выделена. Чтение при этом работает и возвращает нулевое значение, из-за чего ошибка обнаруживается позже, чем хотелось бы.

**nil-указатель внутри интерфейса.** Функция возвращает `error`, внутри `var e *MyErr`, и `err != nil` истинно при пустом значении. Механизм — интерфейс хранит пару (тип, значение); nil-интерфейс требует nil в обоих полях.

**Смешанные получатели.** Часть методов объявлена на `T`, часть на `*T`. В набор методов `T` попадают только value-методы, поэтому `T` перестаёт удовлетворять интерфейсу, а `*T` — удовлетворяет. Компилятор скажет об этом только в месте присваивания интерфейсу, что затрудняет диагностику.

**Потеря обёртки при возврате ошибки.** `return err` без `%w` разрывает цепочку, и `errors.Is` наверху не находит sentinel. Обёртка должна быть на каждом слое, где добавляется контекст.

## Чек-лист

- [ ] Перед `append` в срез, полученный нарезанием, вы понимаете, есть ли у него запас ёмкости.
- [ ] Для известного заранее количества элементов используется `make([]T, 0, n)`.
- [ ] Ни одна проверка не зависит от порядка обхода мапы.
- [ ] Все методы типа имеют одинаковый вид получателя.
- [ ] Функции, возвращающие `error`, возвращают литерал `nil`, а не nil-указатель конкретного типа.
- [ ] Ошибки оборачиваются через `%w`, а проверяются через `errors.Is/As`, а не сравнением строк.
- [ ] `defer` внутри циклов либо отсутствует, либо вынесен в отдельную функцию.
- [ ] `recover` есть только на границах (HTTP-обработчик, воркер), не в бизнес-логике.

2. Реализуйте тип `Matrix` с методами `At(row, col int) float64`, `Set(row, col int, v float64)` и `Transposed() *Matrix`. Решите, где нужны pointer-получатели, и объясните выбор для каждого метода.
3. Объявите свой интерфейс `Store` с методами `Get(string) ([]byte, error)` и `Put(string, []byte) error`. Реализуйте его поверх мапы и поверх временного каталога, затем напишите функцию, работающую с любым `Store`.
4. Создайте иерархию ошибок: `ErrNotFound`, `ErrConflict` и тип `ValidationError` с полем `Field`. Напишите функцию, возвращающую разные ошибки, и обработчик, который через `errors.Is/As` отдаёт 404, 409 и 422.
