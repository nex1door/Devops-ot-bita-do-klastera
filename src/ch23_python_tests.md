# Глава 23. Тесты: pytest

Тесты — это единственный способ менять код в production и не бояться. Не потому, что они доказывают отсутствие ошибок, а потому, что позволяют за минуту проверить сотню предположений, которые иначе проверялись бы неделей наблюдения за графиками. В Python де-факто один инструмент — `pytest`. В этой главе разбирается его практическая часть: как устроен набор тестов, как работают фикстуры и их области, как подменять окружение и HTTP, что именно мокать, почему покрытие в 100% ничего не гарантирует и как выглядит цикл TDD на коротком примере.

## Структура тестов

Тесты лежат отдельно от кода, в каталоге `tests/`, и повторяют структуру пакета:

```text
proj/
├── booking/
│   ├── __init__.py
│   ├── api.py
│   └── duration.py
├── pyproject.toml
└── tests/
    ├── conftest.py
    ├── test_api.py
    └── test_duration.py
```

`pytest` сам находит файлы `test_*.py` и функции `test_*`. Запуск:

```bash
python -m pytest -q
```

```text
..............                                                           [100%]
14 passed in 0.05s
```

Точки — по одному символу на тест; `-q` убирает шапку, `-v` печатает имена, `-x` останавливается на первой ошибке, `-k duration` фильтрует по подстроке, `--lf` перезапускает только упавшие в прошлый раз. Последний флаг экономит минуты при отладке.

Имя теста — это документация. `test_parse_ok` бесполезен, `test_parse_rejects_trailing_garbage` сразу объясняет, что проверяется. Схема `test_<что>_<условие>_<ожидание>` покрывает 90% случаев.

`conftest.py` — файл, который `pytest` импортирует до тестов и из которого фикстуры доступны без импорта. Он же место для общих настроек: маркеров, плагинов, хуков.

## assert и почему сообщения понятные

В `pytest` не нужны `self.assertEqual` и подобное — достаточно `assert`. Причина в переписывании утверждений (assertion rewriting): перед выполнением `pytest` заменяет байткод `assert`, чтобы показать значения подвыражений.

```python
def test_ttl_for_hold():
    ttl = parse_duration("1h30m")
    assert ttl == 1800, "TTL заявки должен быть полчаса"
```

```text
    def test_ttl_for_hold():
        ttl = parse_duration("1h30m")
>       assert ttl == 1800, "TTL заявки должен быть полчаса"
E       AssertionError: TTL заявки должен быть полчаса
E       assert 5400 == 1800

tests/test_fail.py:6: AssertionError
```

Видно и сообщение, и фактическое значение. Без переписывания было бы просто `AssertionError`. Отсюда практическое правило: `assert result == expected` лучше, чем `assert result == expected, "не совпало"` — второе сообщение перекрывает информативный вывод `pytest`.

Для исключений есть `pytest.raises` с проверкой текста:

```python
with pytest.raises(DurationError, match="неразобранный хвост"):
    parse_duration("1h30")
```

`match` — регулярное выражение, а не точное совпадение; злоупотреблять не стоит, привязка к тексту сообщения ломается при его переформулировке.

## Фикстуры и их области

Фикстура — функция с декоратором `@pytest.fixture`, которая готовит данные или ресурс. Тест запрашивает её по имени параметра.

```python
import httpx
import pytest

from booking.api import Api, build_client

@pytest.fixture
def seen():
    return []

@pytest.fixture
def api(seen):
    def handler(request):
        seen.append((request.method, request.url.path))
        return httpx.Response(201, json={"hold_id": "h-42"})
    return Api(build_client("https://booking.internal",
                            transport=httpx.MockTransport(handler)))
```

Фикстуры могут зависеть друг от друга — как `api` зависит от `seen`. Область видимости задаётся параметром `scope`:

| Область | Когда создаётся | Типичное применение |
|---|---|---|
| `function` (по умолчанию) | на каждый тест | изменяемое состояние, соединения |
| `class` | на класс тестов | общий контекст группы |
| `module` | на файл | дорогая подготовка данных |
| `session` | на весь запуск | поднятый контейнер, тестовая БД |

Правило: чем шире область, тем выше скорость и тем выше риск протечки состояния между тестами. `scope="session"` для контейнера с БД оправдан, `scope="session"` для списка, который тесты мутируют, — источник «мигающих» падений, воспроизводимых только при полном прогоне.

Ресурс, требующий закрытия, отдают через `yield`:

```python
import sqlite3

@pytest.fixture
def db(tmp_path):
    conn = sqlite3.connect(tmp_path / "test.db")
    yield conn
    conn.close()
```

Код после `yield` выполняется всегда, даже если тест упал. `autouse=True` делает фикстуру обязательной для всех тестов в области — этим пользуются для настройки логов или переменных окружения, но злоупотребление прячет зависимости.

## Параметризация

Один тест — много входов. Вместо копипаста используется `parametrize`:

```python
@pytest.mark.parametrize("text,expected", [
    ("1s", 1),
    ("90s", 90),
    ("15m", 900),
    ("1h30m", 5400),
    ("2d", 172800),
])
def test_parse_ok(text, expected):
    assert parse_duration(text) == expected
```

Пять наборов данных — пять независимых тестов в отчёте, каждый со своим именем вида `test_parse_ok[1h30m-5400]`. Именно независимых: падение на одном наборе не мешает остальным, и в выводе сразу видно, какой именно вход сломался.

Для проверки ошибок удобно параметризовать «плохие» входы отдельно:

```python
@pytest.mark.parametrize("bad", ["", "10x", "1h 30m", "m10", "1h30"])
def test_parse_rejects(bad):
    with pytest.raises(DurationError):
        parse_duration(bad)
```

Если наборов много и они громоздкие, задают `ids=[...]` — короткие имена вместо автоматических.

## Временные файлы и окружение

Жёстко заданных путей в тестах быть не должно: `/tmp/test.db` не существует в чужом CI, а параллельный запуск двух прогонов даёт конфликт. `pytest` даёт фикстуру `tmp_path` — уникальный каталог на каждый тест, который удаляется автоматически.

```python
def test_state_roundtrip(tmp_path):
    path = tmp_path / "seats.json"
    save_state(path, {"12A": "alice"})
    assert load_state(path) == {"12A": "alice"}
    assert path.read_text(encoding="utf-8").startswith("{")
```

`tmp_path` — это `pathlib.Path`; `tmp_path_factory` нужен, когда каталог готовится на уровне модуля или сессии.

Окружение меняется через `monkeypatch` — он автоматически откатывает изменения после теста:

```python
def test_token_from_env(monkeypatch):
    monkeypatch.setenv("BOOKING_TOKEN", "s3cret")
    monkeypatch.delenv("HTTP_PROXY", raising=False)
    assert load_settings().token == "s3cret"
```

`monkeypatch` умеет `setenv`, `delenv`, `setattr`, `setitem`, `chdir` и `syspath_prepend`. Ключевое свойство — откат: без него `os.environ` протекает в следующие тесты, и порядок запуска начинает влиять на результат.

## Что мокать и что нет

Мок — подмена зависимости объектом, поведение которого задаёт тест. Мокать стоит **на границах системы**: HTTP, база, файловая система, часы, генератор случайных чисел, платёжный провайдер. Всё это медленное, недетерминированное или недоступное в CI.

Мокать не стоит собственную логику. Если тест подменяет функцию, которую сам же и проверяет, он проверяет мок. Классический антипример — мок `httpx.Client.get`, который возвращает подготовленный `Response`: тест зелёный, а в проде падает на неверном URL, потому что URL проверялся не в том слое.

Отдельно — не мокать то, чем вы не владеете, на слишком глубоком уровне. Подмена приватных методов библиотеки ломается при обновлении и создаёт ложное чувство защищённости.

Два инструмента: `monkeypatch` (встроен, для атрибутов и окружения) и `mocker` из `pytest-mock` (обёртка над `unittest.mock`, даёт `assert_called_once_with`, `return_value`, `side_effect`). Когда нужен именно мок объекта:

```python
def test_notifier_called(mocker):
    send = mocker.patch("booking.notify.send_email")
    confirm_booking("12A")
    send.assert_called_once_with("12A", template="confirm")
```

Путь в `patch` — тот, **откуда** импортируется имя (`booking.notify.send_email`), а не там, где оно определено. Это самая частая ошибка при моках: патч ставится на оригинал, а модуль под тестом держит свою ссылку.

## HTTP в тестах: MockTransport

`httpx` даёт транспорт, который перехватывает запросы без сети. Это лучше мока метода: настоящий `Client` строит URL, сериализует JSON, применяет таймауты и заголовки, а подменяется только сокет.

```python
import json
import httpx
import pytest
from booking.api import Api, build_client

@pytest.fixture
def seen():
    return []

@pytest.fixture
def api(seen):
    def handler(request: httpx.Request) -> httpx.Response:
        seen.append((request.method, request.url.path,
                     json.loads(request.content)))
        return httpx.Response(201, json={"hold_id": "h-42"})
    return Api(build_client("https://booking.internal",
                            transport=httpx.MockTransport(handler)))

def test_hold_sends_ttl_in_seconds(api, seen):
    assert api.hold("12A", ttl="1h30m") == {"hold_id": "h-42"}
    assert seen == [("POST", "/holds", {"seat": "12A", "ttl_s": 5400})]
```

Тест проверяет не «вызвался ли метод», а контракт: правильный путь, правильный метод и правильное тело. Ошибки тоже воспроизводятся тривиально:

```python
def test_hold_raises_on_conflict():
    transport = httpx.MockTransport(
        lambda request: httpx.Response(409, json={"error": "seat_taken"}))
    api = Api(build_client("https://booking.internal", transport=transport))
    with pytest.raises(httpx.HTTPStatusError) as exc:
        api.hold("12A")
    assert exc.value.response.status_code == 409
```

## Покрытие и его пределы

```bash
python -m pytest --cov=booking --cov-branch --cov-report=term-missing -q
```

```text
Name                  Stmts   Miss Branch BrPart  Cover   Missing
-----------------------------------------------------------------
booking/api.py           12      0      0      0   100%
booking/duration.py      18      0      8      0   100%
-----------------------------------------------------------------
TOTAL                    30      0      8      0   100%
```

Покрытие отвечает на вопрос «какие строки выполнились», а не «какие сценарии проверены». Строка `if resp.status_code == 409: raise Conflict` считается покрытой, если условие было ложным: интерпретатор в неё заходил при вычислении. Ветвевое покрытие (`--cov-branch`) частично лечит это, требуя пройти обе ветки, но не проверяет, что результат проверен `assert`.

Практическая позиция: покрытие — индикатор, а не цель. Падение с 80% до 40% означает, что новый код пришёл без тестов. Гонка за 100% приводит к тестам, которые вызывают функции ради строчки в отчёте. Ориентир — 70–85% по критичным модулям, при этом обязательны тесты на отказные пути: таймаут, 429, битый JSON, пустой список.

## Пирамида тестов

| Уровень | Что проверяет | Скорость | Доля |
|---|---|---|---|
| Модульные | функции и классы в изоляции | миллисекунды | ~70% |
| Интеграционные | связка с БД, HTTP, очередью | сотни мс | ~20% |
| Сквозные | весь сервис снаружи | секунды и минуты | ~10% |

Пирамида отражает экономику: модульные тесты дёшевы в написании и мгновенны в запуске, сквозные дороги и нестабильны. Перевёрнутая пирамида — сотни сквозных тестов через браузер — даёт прогон на сорок минут, который все перестают запускать локально, а падения списывают на «флаки».

## TDD на коротком примере

Цикл: красный — зелёный — рефакторинг. Сначала тест, который падает, потом минимальный код, который его проходит.

Красный: пишем тест на ещё не реализованную функцию.

```python
from rate import parse_duration

def test_minutes():
    assert parse_duration("15m") == 900
```

```text
    def test_minutes():
>       assert parse_duration("15m") == 900
E       AssertionError: assert 0 == 900
E        +  where 0 = parse_duration('15m')

1 failed in 0.01s
```

Заглушка `return 0` уже даёт падение по правильной причине — не `ImportError`, а неверное значение. Теперь зелёный:

```python
_UNITS = {"s": 1, "m": 60, "h": 3600, "d": 86400}

def parse_duration(text: str) -> int:
    return int(text[:-1]) * _UNITS[text[-1]]
```

```text
1 passed in 0.01s
```

Рефакторинг начинается с нового падающего теста: `1h30m` текущая реализация не разберёт. Так появляется регулярное выражение и проверка хвоста. Ценность цикла не в «тестах после кода», а в том, что каждая строка реализации появляется потому, что её потребовал конкретный падающий тест, — и мёртвого кода не остаётся.

## Типичные ошибки

1. **Тест зависит от порядка запуска.** Механизм: фикстура с `scope="session"` возвращает изменяемый объект, тесты его мутируют. По отдельности всё зелёное, в полном прогоне падает — и воспроизвести можно только полным набором.
2. **Мок не той цели.** Механизм: `patch("httpx.Client.get")` подменяет метод класса, но модуль под тестом держит свою ссылку или создаёт клиент иначе. Тест проходит мимо реального вызова и проверяет собственную заглушку.
3. **`sleep` в тестах.** Механизм: тест с `time.sleep(1)` в наборе из тысячи тестов добавляет минуты, а на медленном CI всё равно падает. Время подменяют, а не ждут.
4. **Проверка реализации вместо поведения.** Механизм: `assert mock.call_count == 3` фиксирует внутреннее устройство. После безобидного рефакторинга тест падает, хотя поведение не изменилось, и его отключают.
5. **Один тест на десять утверждений.** Механизм: первое падение скрывает остальные девять, а имя теста не говорит, что сломалось. Диагностика начинается с чтения кода теста.
6. **Тесты без отказных сценариев.** Механизм: проверены только успешные ответы, поэтому обработка 429, таймаута и битого JSON не выполняется ни разу — и первый реальный сбой уходит в прод.
7. **Сеть в модульных тестах.** Механизм: тест ходит в настоящий API, падает при недоступности и медленный; в CI он либо отключён, либо «флакует» и приучает игнорировать красное.

## Чек-лист

- [ ] Тесты лежат в `tests/`, имена файлов и функций начинаются с `test_`.
- [ ] Общие фикстуры вынесены в `conftest.py`, их области обоснованы.
- [ ] Каждый тест проверяет одно поведение и имеет говорящее имя.
- [ ] Временные файлы создаются через `tmp_path`, окружение — через `monkeypatch`.
- [ ] HTTP подменяется `MockTransport`, а не моком метода клиента.
- [ ] Проверены отказные пути: 4xx/5xx, таймаут, битый JSON, пустой ответ.
- [ ] Набор проходит без сети и без `sleep`.
- [ ] Покрытие измеряется с `--cov-branch`, но не является единственной метрикой.
