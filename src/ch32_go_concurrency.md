# Глава 32. Конкурентность: горутины, каналы, context

Конкурентность в Go — не библиотека, а часть языка: горутина создаётся словом `go`, канал — встроенный тип, `select` — конструкция. Это меняет масштаб задачи: сервис, который держит десять тысяч соединений, пишется как обычный последовательный код, где на каждое соединение приходится одна горутина ценой в несколько килобайт стека. Но у простоты есть цена — цена дисциплины: утечки горутин, гонки данных и забытые отмены не видны компилятору. В этой главе мы разберём, как устроен планировщик и почему горутины дешевле потоков, как правильно работать с каналами и `select`, что делает `context` и чего он делать не должен, как выглядит рабочая очередь задач и какими инструментами ловить проблемы — от `runtime.NumGoroutine` до {{L|g87|pprof}} и {{L|g90|race detector}}.

## Горутины и планировщик

Горутина ({{L|g45|goroutine}}) — функция, запущенная словом `go` и исполняемая планировщиком Go. Начальный стек — 2 КБ, он растёт и сжимается динамически, поэтому сотни тысяч горутин в одном процессе реальны. Поток ОС имеет стек фиксированного размера (обычно 8 МБ виртуальной памяти), и переключение между потоками делает ядро; переключение горутин делает рантайм в пространстве пользователя, без системного вызова.

```go
func main() {
	var wg sync.WaitGroup
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func(id int) {          // параметр передаётся явно
			defer wg.Done()
			fmt.Println("worker", id)
		}(i)
	}
	wg.Wait()
}
```

Планировщик устроен по модели GMP. `G` — горутина со своим стеком и состоянием. `M` — поток ОС (machine), который исполняет код. `P` — логический процессор (processor) с локальной очередью горутин; их количество равно `GOMAXPROCS` и по умолчанию — числу доступных CPU. Поток может исполнять код, только удерживая `P`. Это даёт локальные очереди без блокировок и работу кражи задач (work stealing): простаивающий `P` забирает половину очереди у занятого.

Планировщик вытесняющий: с Go 1.14 горутина может быть прервана в любой точке через сигнал, а не только на вызовах функций. До этого цикл без вызовов функций мог занять поток навсегда. Блокирующие операции не занимают поток: сетевой ввод-вывод обслуживается поллером (`epoll` в Linux), и горутина, ждущая сокет, просто снимается с `P`, освобождая поток для других. Системный вызов, который нельзя разбить (например, чтение файла), блокирует `M`, и рантайм создаёт дополнительный поток — поэтому «дешёвая» горутина может стоить потока, если она делает блокирующие {{L|g114|syscall}}.

Практическое следствие для контейнеров: `GOMAXPROCS` влияет на параллелизм. С Go 1.25 значение по умолчанию учитывает лимиты {{L|g13|cgroup}} (`cpu.max` в Kubernetes), а не только `runtime.NumCPU()`, — раньше под с лимитом 2 CPU на 64-ядерной ноде получал `GOMAXPROCS=64` и страдал от троттлинга и лишних переключений. Если вы задаёте `GOMAXPROCS` переменной окружения, помните: она отключает новое поведение по умолчанию.

## Каналы

Канал — типизированная очередь с синхронизацией. Небуферизованный (`make(chan int)`) работает как рандеву: отправитель блокируется, пока получатель не готов, и наоборот. Буферизованный (`make(chan int, 10)`) принимает до `cap` значений без получателя; отправка в полный канал блокируется, чтение из пустого — тоже.

```go
jobs := make(chan int, 3)   // буфер на 3 задачи
jobs <- 1                    // не блокируется, пока есть место
close(jobs)                  // закрывает отправитель, когда задач больше не будет

for j := range jobs {        // цикл завершится, когда канал закрыт и пуст
	fmt.Println(j)
}
```

Семантика, которую нужно помнить целиком:

| Операция | nil-канал | закрытый канал |
|---|---|---|
| Отправка `ch <- v` | блокируется навсегда | паника |
| Получение `<-ch` | блокируется навсегда | сразу нулевое значение, `ok=false` |
| `close(ch)` | паника | паника |

Закрывать канал должен отправитель, и только он: получателей может быть несколько, и никто из них не знает, закончили ли остальные. Закрытие — это сигнал «данных больше не будет», а не «я больше не читаю». Если получатель хочет сообщить, что ему надоело, для этого есть отдельный канал или `context`.

Проверка `v, ok := <-ch` отличает закрытый канал от нулевого значения в потоке данных. Правило: если по каналу передаются значения, которые могут быть нулевыми, проверяйте `ok`; если канал используется только как сигнал завершения — достаточно `range` или `<-done`.

Ещё одно правило, которое экономит отладку: не смешивайте «данные» и «завершение» в одном канале. Отдельный `done chan struct{}` и отдельный канал данных читаются проще и не требуют различать «пришёл ноль» и «канал закрыт».

## select

`select` ждёт готовности любого из нескольких каналов и выполняет соответствующую ветку. Если готовы несколько — выбор случайный, что защищает от starvation.

```go
select {
case v := <-results:
	handle(v)
case <-ctx.Done():
	return ctx.Err()
case <-time.After(2 * time.Second):
	return errors.New("timeout")
}
```

Ветка `default` делает `select` неблокирующим — удобно для «попробуй забрать, не жди». Но `select` с `default` в цикле превращается в busy-loop, который съедает CPU; если нужен опрос, добавьте паузу или используйте тикер.

`time.After` в горячем цикле раньше был известной утечкой: таймер жил до срабатывания, даже если ветка уже не нужна. С Go 1.23 неиспользуемые таймеры освобождаются сборщиком мусора, но привычка `timer := time.NewTimer(d); defer timer.Stop()` всё равно полезна — она делает намерение явным и не зависит от версии.

## sync: WaitGroup, Mutex, Once

`sync.WaitGroup` ждёт завершения группы горутин. `Add` вызывается **до** запуска горутины, иначе `Wait` может проскочить раньше, чем счётчик увеличится. `Done` обычно ставят через `defer`.

`sync.Mutex` защищает критическую секцию. `sync.RWMutex` даёт параллельное чтение, но пишет всё равно по одному; он выигрывает только при заметно преобладающем чтении и коротких секциях, иначе накладные расходы съедают выгоду.

```go
type Metrics struct {
	mu     sync.Mutex
	counts map[string]int
}

func (m *Metrics) Inc(key string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	if m.counts == nil {
		m.counts = make(map[string]int)
	}
	m.counts[key]++
}
```

`sync.Once` выполняет инициализацию ровно один раз, даже при одновременных вызовах; `sync.OnceValue` (с Go 1.21) оборачивает функцию и возвращает её результат, сохраняя его.

Отдельно стоит запомнить: мьютекс нельзя копировать после первого использования. Поэтому структура с мьютексом передаётся по указателю, а `go vet` предупреждает о копировании (`copylocks`).

## context: отмена, дедлайны, значения

`context.Context` — стандартный способ передать сигнал отмены, дедлайн и небольшую порцию метаданных через границы вызовов. Контекст всегда первый параметр функции, всегда называется `ctx`, никогда не хранится в структуре и никогда не равен nil (если сомневаетесь — `context.Background()`).

```go
func fetchAll(ctx context.Context, urls []string) ([]string, error) {
	ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel() // обязательно, иначе утечка таймера и горутины

	results := make([]string, len(urls))
	errCh := make(chan error, len(urls))

	var wg sync.WaitGroup
	for i, u := range urls {
		wg.Add(1)
		go func() {
			defer wg.Done()
			body, err := fetchOne(ctx, u)
			if err != nil {
				errCh <- err
				return
			}
			results[i] = body
		}()
	}
	wg.Wait()
	close(errCh)
	for err := range errCh {
		return nil, err
	}
	return results, nil
}
```

Каждая горутина пишет в свой индекс `results`, поэтому мьютекс не нужен: непересекающаяся запись в разные элементы среза безопасна. Буфер `errCh` равен числу URL — гарантия, что ни одна горутина не заблокируется на отправке ошибки, даже если читатель уже ушёл. Тот же паттерн с автоматической отменой остальных запросов при первой ошибке даёт `errgroup` из `golang.org/x/sync`.

Правила, которые нарушают чаще всего. `defer cancel()` нужен всегда, даже если контекст с дедлайном и вы уверены, что он истечёт: до истечения таймер и дочерний контекст держат память. Отмену надо проверять: функция, которая получила `ctx`, но ни разу не посмотрела `ctx.Done()` или `ctx.Err()`, отмену игнорирует. И `context.WithValue` — не для передачи параметров: это для request-scoped метаданных (идентификатор запроса, идентификатор трассировки, данные аутентификации), которые нужны на всех уровнях, но не являются аргументами бизнес-логики. Ключ должен быть неэкспортируемым типом, а не строкой, иначе два пакета перетрут друг друга.

```go
type ctxKey struct{}

func WithRequestID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, ctxKey{}, id)
}

func RequestID(ctx context.Context) string {
	id, _ := ctx.Value(ctxKey{}).(string)
	return id
}
```

## Утечки горутин

Горутина не собирается сборщиком мусора, пока выполняется: она держит стек и всё, на что ссылается. Утечка — горутина, заблокированная навсегда. Три типовых сценария: отправка в канал, который никто не читает; чтение из канала, в который никто не пишет; цикл, у которого нет условия выхода при отмене.

```go
func leak() {
	ch := make(chan int)
	go func() { ch <- 1 }() // никто не прочитает — горутина висит вечно
	// return без чтения
}
```

Ловится это профилем горутин. В сервисе поднимают `net/http/pprof` и смотрят:

```bash
go tool pprof -http=:8081 http://127.0.0.1:6060/debug/pprof/goroutine
```

Профиль показывает стеки всех горутин, сгруппированные по месту создания; растущее число одинаковых стеков на одном канале — почти всегда утечка. Быстрая проверка без pprof: `runtime.NumGoroutine()` в метрике; стабильный сервис держит примерно постоянное число, линейный рост при постоянной нагрузке — сигнал.

## Worker pool

Канонический паттерн: фиксированное число воркеров читает задачи из канала. Число воркеров ограничивает параллелизм — важно, когда работа упирается во внешний ресурс (БД, API), а не в CPU.

```go
func Run(ctx context.Context, n int, jobs <-chan Job) error {
	var wg sync.WaitGroup
	errCh := make(chan error, n)

	for i := 0; i < n; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done():
					return
				case j, ok := <-jobs:
					if !ok {
						return
					}
					if err := process(ctx, j); err != nil {
						select {
						case errCh <- err:
						default: // не блокируемся, если ошибку уже никто не ждёт
						}
						return
					}
				}
			}
		}()
	}

	wg.Wait()
	close(errCh)
	for err := range errCh {
		return err // наружу — первая из собранных ошибок
	}
	return nil
}
```

Здесь важны три детали. Буфер `errCh` равен числу воркеров, поэтому ни один воркер не блокируется навсегда, даже если никто не читает. `default` в отправке ошибки гарантирует, что поздние ошибки не подвесят горутину. `select` с `ctx.Done()` в каждом цикле — единственный способ остановить воркер, который ждёт задачу. Побочный эффект схемы: воркер, вернувший ошибку, выбывает, и пул продолжает работу меньшим числом горутин — для «первая ошибка отменяет всё» нужен ещё один `cancel`.

## Race detector

Гонка данных — два обращения к одной памяти, хотя бы одно из них запись, без синхронизации. Компилятор её не видит, тесты часто тоже: результат зависит от планирования.

```bash
go test -race ./...
go run -race ./cmd/exporter
```

Детектор инструментирует код и отслеживает доступы к памяти; при гонке печатает два стека — где читали и где писали. Цена: замедление в 5–10 раз и кратный рост памяти, поэтому в продакшне его не включают. И главное ограничение: детектор находит только те гонки, которые реально произошли в этом запуске. Отсутствие отчёта не доказывает отсутствие гонки, поэтому `-race` гоняют в CI на тестах с параллельными сценариями. Бенчмарки и профилирование подробно разбираются в главе 35.

## Типичные ошибки

**Захват переменной цикла без параметра.** До Go 1.22 все итерации делили одну переменную, и горутины видели последнее значение. С Go 1.22 переменная своя на каждой итерации, и старый баг исчез — но код, написанный до этого, всё ещё встречается, а в модулях с `go 1.21` в `go.mod` старое поведение сохраняется. Механизм: версия языка в `go.mod` определяет семантику цикла.

**`wg.Add` внутри горутины.** `Wait` может выполниться до первого `Add` и вернуться сразу, после чего `main` завершит процесс с работающими горутинами. `Add` должен вызываться в порождающем коде, до `go`.

**Чтение из закрытого канала как из живого.** Закрытый канал отдаёт нулевые значения бесконечно, и цикл `for { v := <-ch }` без проверки `ok` крутится вхолостую, потребляя CPU. Механизм: закрытие — не ошибка, а нормальное состояние, и отличить его можно только вторым значением.

**Отправка в канал без получателя.** Воркер, который пишет в небуферизованный канал после того, как читатель ушёл по таймауту, висит навсегда. Лечится `select` с `ctx.Done()` или буфером, достаточным для всех отправителей.

**`defer cancel()` забыт.** Контекст с таймаутом держит таймер и родительскую ссылку до истечения срока; в цикле на каждый запрос это накопление. `go vet` ловит часть таких случаев (`lostcancel`), но не все — например, когда `cancel` присвоен в поле структуры.

**Мьютекс вокруг долгой операции.** Блокировка, удерживаемая на время сетевого вызова, сериализует весь сервис и превращает параллельный обработчик в однопоточный. Критическая секция должна содержать только работу с памятью.

**Проверка `err == context.Canceled` вместо `errors.Is`.** Отменённый контекст почти всегда возвращается обёрнутым (`fmt.Errorf("fetch: %w", err)`), и прямое сравнение не срабатывает. Нужен `errors.Is`.

## Чек-лист

- [ ] `Add` у `WaitGroup` вызывается до запуска горутины.
- [ ] Каждый канал закрывает ровно один отправитель, и это не получатель.
- [ ] Все горутины, запущенные на запрос, завершаются по `ctx.Done()` или по закрытию канала.
- [ ] `cancel` вызывается через `defer` в той же функции, где создан контекст.
- [ ] `context.WithValue` используется только для метаданных, ключи — неэкспортируемые типы.
- [ ] В тестах есть `-race`, и хотя бы один тест работает параллельно.
- [ ] `runtime.NumGoroutine()` не растёт линейно под нагрузкой (проверено нагрузочным прогоном).
- [ ] Мьютекс не удерживается во время сетевых вызовов и не копируется.

## Упражнения

1. Напишите функцию `Merge(chans ...<-chan int) <-chan int`, которая сливает несколько каналов в один и закрывает результат, когда закрыты все источники. Проверьте на трёх каналах с разной скоростью.
2. Реализуйте worker pool из раздела про пул, добавив ограничение «не более N одновременных HTTP-запросов» и сбор всех ошибок через `errors.Join`. Прогоните под `-race`.
3. Сделайте намеренную утечку горутин и найдите её через `pprof` по адресу `/debug/pprof/goroutine`. Опишите, как по стеку понять место блокировки.
4. Напишите HTTP-обработчик, который отменяет работу при разрыве соединения клиентом (`r.Context()`), и проверьте через `curl --max-time`, что горутина завершается, а не продолжает считать.
5. Сравните два варианта счётчика: под `sync.Mutex` и на атомарных операциях `sync/atomic`. Замерьте `go test -bench` на 1, 4 и 8 горутинах и объясните разницу.
