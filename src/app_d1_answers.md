# Приложение D. Ответы и решения — часть 1 (главы 1–8 и Linux)

## Глава 1. Что такое вычисление: автоматы, машина Тьюринга, вычислимость

1. Четыре состояния: `red` (30 с), `green` (25 с), `yellow` (3 с), `ped_green` (15 с). Кнопка состояние не меняет, а поднимает флаг `ped_wait`; переход `green → yellow → ?` смотрит на флаг: если он выставлен, дальше `ped_green`, иначе `red`. Критерий: после `ped_green` автомат возвращается в `red`, флаг сброшен, повторное нажатие фазу не продлевает.

2. Добавляются состояния `IN_STRING`, `ESCAPE`, `COMMENT`: в строке `\` переводит в `ESCAPE`, а `"` возвращает назад; `ESCAPE` съедает ровно один символ. Вне строки `#` включает комментарий до `\n`. Память ограничена текущим состоянием, счётчиков и вложенности нет — язык остаётся регулярным; вложенные комментарии потребовали бы стека.

3. Два состояния — `even` и `odd`: головка идёт вправо, на каждом `1` переключает чётность, на `0` не меняет, на пустой ячейке пишет `Y` для чётного и `N` для нечётного. Шагов ровно `n + 1` — n чтений и одна запись, то есть O(n). Проверка: «1011» даёт `N`, «1010» — `Y`; лимит шагов нужен как внешняя страховка от зацикливания.

4. Состояния `starting`, `ready`, `degraded`, `stopping`, `failed`; события — старт процесса, успех и провал пробы, `SIGTERM`, таймаут. Неявных переходов обычно два: `starting → ready` по факту открытого порта без проверки БД (отсюда «готов, но отдаёт 500») и отсутствие ребра `stopping → failed` по таймауту — оно даёт зависший при деплое контейнер рядом со старым.

## Глава 2. Биты, числа и кодировки

1. `0xDEADBEEF` = `1101 1110 1010 1101 1011 1110 1110 1111`, восьмеричное `0o33653337357`, десятичное `3735928559`. Hex читается «глазами», потому что 16 — степень двойки: каждая цифра это ровно 4 бита и перевод сводится к подстановке. Для десятичной такой таблицы нет, нужна позиционная арифметика — восемь умножений на 16 и сложений.

2. Знаковые значения идут от −128 до 127, байты `0x80`–`0xFF` — это −128…−1. Сравнение расходится только когда операнды лежат по разные стороны границы 128: `0xFF` больше `0x01` как беззнаковое (255 > 1) и меньше как знаковое (−1 < 1). Равенство, сложение и вычитание совпадают всегда: они идут по модулю 256, битовая картина одна.

3. Печатаются знак, смещённая экспонента (8 или 11 бит) и мантисса без неявной единицы (23 или 52). `0.1` во float32 — `0x3DCCCCCD`, `1/3` — `0x3EAAAAAB`. `1e300` во float32 даёт `inf` (переполнение), в float64 — `0x7E37E43C8800759C`; `5e-324` — минимальный субнормал double `0x0000000000000001`, во float32 он равен нулю. Соседние целые float32 перестаёт различать сразу за `2^24 = 16 777 216`.

4. Декодер определяет длину последовательности по ведущему байту (`0xxxxxxx` — 1, `110xxxxx` — 2, `1110xxxx` — 3, `11110xxx` — 4), проверяет префикс `10` у продолжений и собирает код по маскам. Обрезанная последовательность даёт ошибку в позиции ведущего байта. Пара `c0 af` — перекодировка нуля: `0xC0` запрещён как ведущий (двухбайтовые начинаются с `C2`), иначе у символа было бы два представления.

5. Не-ASCII ищутся как `grep -P '[^\x00-\x7F]' app.log | head`, кодировка проверяется `file -bi` и `iconv -f utf-8 -t utf-8` (падение — файл не UTF-8). Прогон в cp1251 на кириллице часто даёт `cannot convert`. Двойное кодирование выглядит как `ÐŸÑ€Ð¸Ð²ÐµÑ‚` и обратимо; неверная кодировка даёт `?????` или потерю символов — данные утрачены.

## Глава 3. Процессор и память: как код превращается в такты

1. На графике «нс на элемент от размера» видны полки: до 32–48 КиБ около 0,3–0,5 нс (L1), до 1–2 МиБ около 1 нс (L2), затем 2–4 нс (L3) и 5–8 нс на последовательном чтении из DRAM. Границы сравниваются с `lscpu | grep -i cache`. Критерий: перегибы совпадают с `lscpu` в пределах 20–30 %; ступени в сто раз нет — префетчер сглаживает DRAM.

2. Вручную: `char`, 3 паддинга, `int`, `char`, 7 паддинга, `double`, `char`, 7 паддинга — 32 байта. Проверка: `printf("%zu\n", sizeof(struct S));`. Минимум даёт порядок `double, int, char, char, char`: 8 + 4 + 3 = 15, округление до 16. Меньше нельзя: выравнивание структуры 8, размер обязан быть кратен 8, а значащих байт 14.

3. Оба потока пишут в поля одной структуры, то есть в одну 64-байтовую линию, и она по очереди переходит между ядрами — каждое `++` становится промахом когерентности. На миллионе инкрементов разница обычно 5–20 раз: десятки миллисекунд против секунды. После `alignas(64)` на каждый счётчик время почти линейно: линии не пересекаются.

4. Указатель занимает 8 байт, узел с ним — 16, узел с 32-битным индексом — 8–12: обход читает вдвое меньше линий, префетчер лучше предсказывает адрес. Выигрыш 1,3–2 раза и растёт с высотой дерева: каждый уровень — отдельный зависимый промах, при 24 уровнях это 24 латентности DRAM подряд, и лишние байты умножаются на их число.

5. Для однопоточного кода разница в пределах 5–10 %: он упирается в латентность, а не в полосу, и удалённых обращений при прогретом кэше мало. Многопоточный насыщает межсокетный канал, и пропускная способность падает почти вдвое. Смотреть `numactl --hardware`, `numastat -p PID` (доля local/remote) и сравнивать прогоны с `--cpunodebind=N --membind=N`.

## Глава 4. Операционная система: процессы, потоки, планировщик

1. `ps -o pid,stat,wchan` даёт `R+` с `wchan` `-`, `S+` с `ep_poll` или `do_wait`, `T` с `do_signal_stop`, `Z` с `-`. В `T` процесс снят с очереди планировщика и тактов не получает, но остаётся в таблице: память, дескрипторы и открытые файлы за ним сохранены. Продолжает его только `SIGCONT`, а `SIGKILL` для остановленного откладывается до продолжения.

2. При `nice 0` и `nice 10` веса равны 1024 и 110, то есть примерно 9:1 — на двух счётчиках выходит 90 % и 10 %. Две группы с `cpu.weight=100` дают 50/50. Расхождение потому, что nice — свойство задачи внутри группы, а вес — свойство группы: процессор сначала делится между группами, потом внутри. В контейнере nice может не влиять вовсе, если задачи уже в разных группах.

3. Побайтное чтение — миллион `read()`, и каждый при отсутствии данных усыпляет поток, давая добровольное переключение. С буфером 64 КиБ вызовов около шестнадцати при том же объёме. Смотреть `grep voluntary_ctxt_switches /proc/PID/status`: разница в тысячи раз, по времени секунды против миллисекунд, потому что переключение стоит порядка микросекунды.

4. `EMFILE` наступает на 1024-м дескрипторе. В контейнере помогает `--ulimit nofile=4096:4096`, в systemd — `LimitNOFILE=65536` в `[Service]` и `daemon-reload`. `ulimit` в оболочке меняет rlimit только у новых процессов: значение копируется при `fork`/`exec`, у работающего сервиса остаётся своё. Зомби: 100 потомков в `Z`; обработчик `SIGCHLD` с `waitpid(-1, &st, WNOHANG)` в цикле собирает их.

## Глава 5. Виртуальная память и файловые системы

1. В `maps` три области: `r-xp` — код, `rw-p` — `[heap]`, `rw-p` — `[stack]`. Код `r-x`, потому что его исполняют, но не меняют: страница, куда можно писать и откуда исполнять, — готовый вектор атаки, поэтому соблюдается W^X. Стек `rw-` без `x`: в него пишут локальные переменные и адреса возврата, исполнять оттуда нечего. Строка `rwxp` — почти всегда JIT.

2. Для разреженного файла 500 МБ: `ls -l` даёт 524288000, `du -h` — 0 или 4,0K, `du -h --apparent-size` — 500M. `du` считает выделенные блоки, `--apparent-size` и `ls` — поле `st_size`. У обычного файла все три совпадут. Практическое следствие: занятое место проверяют `du`/`df`, а не `ls`.

3. Без `fsync` десять тысяч строк уходят в страничный кэш и пишутся одним потоком — около 0,02 с. С `fsync` после каждой строки это 10 000 обращений к устройству по 0,1–5 мс, от секунды до десятков секунд: разница в 100–1000 раз. `fsync` ждёт подтверждения от накопителя со сбросом его кэша, поэтому цена — латентность диска на вызов.

4. Процесс доходит примерно до 512 МиБ и получает `SIGKILL`: код 137 (`128+9`), в `memory.events` растут `max` и `oom_kill`, в `memory.peak` виден потолок. В `dmesg` строка `Memory cgroup out of memory: Killed process 2417 (python) total-vm:612345kB, anon-rss:510000kB, file-rss:0kB, oom_score_adj:0` — по `anon-rss` видно, что съедена анонимная память, а не кэш.

5. Файл удаляют по имени (`rm /var/log/app.log`), а место возвращают, обрезав открытый дескриптор: `: > /proc/2417/fd/3` или `truncate -s 0 /proc/2417/fd/3`. Дескриптор ищется через `ls -l /proc/2417/fd | grep deleted` и `lsof +L1`. Inode и блоки живут, пока открыт хотя бы один дескриптор — поэтому `df` место показывает, а `du` уже нет.

## Глава 5a. Linux: пользователи, права, sudo

1. `chgrp dev /srv/shared && chmod 3775 /srv/shared`. Отвечают три бита: setgid (`2000`) — новые файлы наследуют группу каталога; sticky (`1000`) — удалять и переименовывать чужие файлы может только владелец, владелец каталога и root; групповой `w` — право править содержимое. Проверка: файл другого участника группы правится, а `rm` его же возвращает `Operation not permitted`.

2. Список даёт `find / -xdev -perm -4000 -type f`. `/usr/bin/passwd` пишет в `/etc/shadow`, недоступный на чтение обычному пользователю; без бита смена своего пароля станет невозможна. `/usr/bin/sudo` читает `sudoers` и меняет uid — без setuid перестанут работать все делегированные права. `/usr/bin/mount` монтирует по записи в `fstab`; без бита пользователь не смонтирует разрешённый носитель.

3. `setfacl -m u:deploy:--x /srv/app` даёт только проход по каталогу (без `r` листинга нет), затем `setfacl -m u:deploy:r /srv/app/config.yml`. Строка `mask::r-x` — верхняя граница прав для именованных записей и группы-владельца: эффективные права равны пересечению записи с маской, поэтому при ручной правке выходит «право есть, а доступа нет». `setfacl` пересчитывает маску сам.

4. Первый способ: `setcap cap_net_bind_service=+ep /usr/sbin/nginx`, проверка `getcap`. Второй: `sysctl -w net.ipv4.ip_unprivileged_port_start=80`, для стойкости — файл в `sysctl.d`. Обновление пакета заменяет бинарник и стирает capability — сервис не стартует до повторного `setcap`; при переносе на другой хост право тоже теряется. Sysctl переезжает с хостом, но открывает младшие порты всем процессам.

5. В `/etc/sudoers.d/ci` (режим `0440`, владелец `root:root`): `ci ALL=(root) NOPASSWD: /usr/bin/systemctl restart app.service`. Ни `ALL`, ни масок, ни оболочки, аргумент фиксирован, поэтому `sudo systemctl restart ssh` и `systemctl edit` отклоняются. Root через запись не получить, пока сам юнит и `ExecStart` принадлежат root: иначе `ci` правит `ExecStart=` и запускает свой код от root. Проверка — `sudo -l -U ci`.

## Глава 5b. Linux: пакеты, systemd, журналы

1. `dpkg -S /usr/bin/ss` отвечает `iproute2: /usr/bin/ss`, полный список файлов даёт `dpkg -L iproute2`. В `dpkg -l` две первые буквы — желаемое и текущее состояние: `ii` значит «должен быть установлен» и «установлен»; `rc` — удалён, конфиги остались; `iU` — распакован, но не настроен. Файл, не принадлежащий пакету, даёт `no path found` — он собран вручную.

2. `apt-mark hold nginx`, затем `apt update` и `apt-cache policy nginx`: `Installed` и `Candidate` совпадают, `apt list --upgradable` имени не содержит. Это и есть доказательство — индекс обновился, кандидат прежний. После `unhold` следующий `upgrade` может прыгнуть через несколько версий сразу: конфиги потребуют ответов, зависимости потянут новые библиотеки, и всё в один момент, вместе с накопленными CVE.

3. Юнит: `Type=notify`, `ExecStart=/opt/app/venv/bin/python /opt/app/main.py`, `User=app`, `LimitNOFILE=65536`, `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/app`, `Restart=on-failure`. `systemd-analyze verify app.service` должен дать код 0 и пустой вывод. `Type=notify` требует вызова `sd_notify(READY=1)` из приложения, иначе старт повиснет до `TimeoutStartSec`.

4. `health.service` (`Type=oneshot`, `ExecStart=/usr/local/bin/healthcheck.sh`) и `health.timer` с `OnCalendar=*:0/5`, `Persistent=true`, `Unit=health.service`, `WantedBy=timers.target`. `Persistent=true` хранит отметку в `/var/lib/systemd/timers`, поэтому пропущенный за время простоя запуск выполнится один раз после загрузки. Проверка — `systemctl list-timers health.timer` и журнал юнита.

5. В `/etc/systemd/journald.conf` — `Storage=persistent` и `SystemMaxUse=500M`, затем `mkdir -p /var/log/journal` и `systemctl restart systemd-journald`; размер показывает `journalctl --disk-usage`, чистят `journalctl --vacuum-size=500M`. Ошибки прошлой загрузки одной командой: `journalctl -b -1 -p err`. Без каталога `/var/log/journal` журнал живёт в `/run` и после перезагрузки исчезает.

## Глава 5c. Linux: namespaces, cgroups, диагностика

1. `unshare --fork --pid --mount-proc --uts --net bash`, внутри `hostname c1` и `ps -ef`: две строки — сам `bash` с PID 1 и `ps`. Снаружи `ps -ef` показывает процесс с настоящим PID хоста и весь остальной список. Сеть пуста: только `lo` в состоянии DOWN, адресов нет. Критерий: три проверки — `hostname`, число строк `ps`, `ip addr` — ведут себя одинаково и воспроизводимо.

2. `memory.max` — потолок в байтах (`536870912`) или `max`; `cpu.max` — «квота период», например `50000 100000` = 0,5 CPU; `pids.max` — максимум задач; `memory.events` — счётчики `low`, `high`, `max`, `oom`, `oom_kill`. Текущее потребление — `memory.current`, пик — `memory.peak`. Рост `max` значит упор в потолок, рост `oom_kill` — процессы уже убивают.

3. Процесс с лимитом 64 МиБ, выделяющий 256 МиБ, убивается на подходе к 64 МиБ: код 137, `max` в `memory.events` инкрементируется многократно, `oom_kill` — на единицу, в `memory.events.local` те же счётчики без потомков. В `dmesg` остаётся `Memory cgroup out of memory: Killed process ... anon-rss:...`. От утечки отличается тем, что `memory.current` упирался в потолок.

4. `free -m` читает `/proc/meminfo`, а тот собирается из глобальных счётчиков ядра: в контейнере с лимитом 512 МиБ видно 15,5 ГиБ хоста. `memory.current` берётся из cgroup и включает page cache, поэтому он больше RSS приложения, но отражает реальное потребление. Смотреть надо пару `memory.max`/`memory.current`; `free` внутри контейнера для планирования непригоден.

5. `SIGTERM` перехватывается: приложение закрывает соединения, дописывает буферы и выходит с кодом 143 (`128+15`). `SIGKILL` не перехватывается и не откладывается, код 137. `terminationGracePeriodSeconds` (30 в Kubernetes, 10 в `docker stop`) — срок между ними; если обработчик не успел, процесс убивают и данные теряются. Долгие задачи выносят в `preStop`-хук или увеличивают grace.

## Глава 6. Сети: от кабеля до IP-пакета

1. `arping -I eth0 -c 3 192.168.0.250` (или `tcpdump -ni eth0 arp`) даёт `who-has 192.168.0.250 tell 192.168.0.75` с адресом назначения `ff:ff:ff:ff:ff:ff`. Кадр широковещательный, потому что MAC получателя неизвестен, а ARP работает внутри сегмента: узнать адрес можно только спросив всех. Ответ приходит юникастом, и дальше запрос идёт на конкретный MAC.

2. `/22` — маска `255.255.252.0`, шаг сетей по третьему октету 4: 130 попадает в блок 128, значит сеть `10.8.128.0`, broadcast `10.8.131.255`, хостов `1024 − 2 = 1022`, диапазон `10.8.128.1–10.8.131.254`. `ipaddress.ip_network("10.8.130.200/22", strict=False)` даёт те же значения. Вручную достаточно взять 130 = `10000010` и обнулить два младших бита.

3. `ping -M do -s 1472 host` проходит — MTU пути 1500. При `Frag needed and DF set` размер уменьшают: 1452 — IPsec, 1420 — WireGuard, 1412 — OpenVPN, 1392 — VXLAN, 1492 — PPPoE. Интерфейс сравнивают по `ip link show eth0 | grep mtu`. Расхождение означает инкапсуляцию: локально 1500, а путь меньше, и большие пакеты молча теряются при фильтрации ICMP.

4. Заголовок TCP — 20 байт: sport (2), dport (2), seq (4), ack (4), data offset и флаги (2), window (2), checksum (2), urgent (2). В дампе после IP: `1f 90 01 bb` — порты 8080 и 443, два поля по четыре нуля — seq и ack в SYN, `50 02` — смещение 5 слов и флаг `S`, `ff ff` — окно, далее опции `02 04 05 b4` (MSS 1460), `03 03 07` (wscale 7).

5. Типовая схема: роутер `192.168.0.1/24` (DHCP, DNS, NAT), хост `192.168.0.75`, шлюз по умолчанию — роутер, за ним адрес провайдера. Проверки: `ip -br addr`, `ip route` (строка `default via`), `curl ifconfig.me`, правила DNAT в роутере. Если внешний адрес из `100.64.0.0/10`, проброс портов невозможен из-за CGNAT.

## Глава 7. TCP и UDP: надёжность, порты, сокеты

1. `sudo tcpdump -ni any -c 20 'tcp port 443 and tcp[tcpflags] & tcp-syn != 0'`: в первом сегменте видны `seq` (ISN), `win`, опции `mss 1460` и `wscale 7`. ISN случаен и у каждого соединения свой — Linux считает его по RFC 6528 из адресов, портов и таймера, поэтому разница с предыдущим обычно в сотни миллионов. Это защита от подмены и коллизий, а не счётчик.

2. Сервер принимает соединение и не вызывает `recv()`: приёмный буфер заполняется, и в ACK он объявляет нулевое окно. На сервере `ss -tn` показывает `Recv-Q` равным размеру буфера (обычно 131072), на клиенте `ss -tin` — `Send-Q` с непереданными байтами и таймер `persist`. Клиент блокируется, отправив объём буферов с обеих сторон — единицы мегабайт, а не мегабайт «в трубу».

3. Сервер получает FIN и не вызывает `close()`: соединение уходит в `CLOSE-WAIT`, и ядро его не закрывает — таймаута для этого состояния нет. `ss -tan state close-wait` показывает рост, дескрипторы не освобождаются, и через часы сервис упирается в `EMFILE`. Лечится только `close()` в приложении; `tcp_fin_timeout` относится к `FIN-WAIT-2` и здесь не помогает.

4. Эфемерных портов 28 232 (`32768–60999`), порт занят 60 с в `TIME_WAIT`, значит к одному адресу выходит около 470 новых соединений в секунду. Для 30 000/с нужно 1,8 млн портов — в 16-битном поле их нет. Лечение: пул с keep-alive (одно соединение обслуживает сотни запросов), затем расширение `ip_local_port_range`, и только потом `tcp_tw_reuse=1`.

5. UDP-эхо на 50 строк: `socket(AF_INET, SOCK_DGRAM)`, `recvfrom`, `sendto` обратно. При `tc qdisc add dev eth0 root netem loss 10%` теряется примерно каждый десятый ответ, и клиент видит пропуски — повторов нет по построению. TCP на том же канале не теряет данных, но платит повторами: падает пропускная способность и растёт p99 из-за RTO от 200 мс, тогда как задержка UDP ровная.

## Глава 8. DNS: как имя становится адресом

1. `dig +short app.example.com` спрашивает DNS напрямую, `getent hosts app.example.com` идёт через NSS и сначала читает `/etc/hosts`, `nslookup` использует тот же резолвер, но в своём формате. Расходятся они, когда в `/etc/hosts` есть строка: `dig` покажет адрес из зоны, `getent` — из файла. Отсюда правило: расхождение `dig` и `getent` — вина hosts или `nsswitch.conf`, а не DNS.

2. TTL понижают заранее и ждут старый TTL: правка TTL чужие кэши не чистит, в них лежит прежнее значение. После смены A-записи локальный резолвер увидит её через 0–60 с, публичные (`1.1.1.1`, `8.8.8.8`) — в пределах нового TTL, корпоративный — до 60 с плюс свой минимум. Мерить: `dig +noall +answer` (колонка TTL убывает) и опрос нескольких резолверов раз в 10 с.

3. Split-horizon на dnsmasq: `address=/app.example.com/10.8.0.10` в локальном конфиге и `local=/example.com/`, чтобы зона не уходила в upstream; на BIND — два `view` с выбором по `match-clients`. Внутренний клиент получает `10.8.0.10`, внешний — публичный адрес. Проверка: `dig @127.0.0.53 app.example.com` против `dig @1.1.1.1 app.example.com`.

4. `ndots:5` означает: имя, в котором меньше пяти точек, сначала пробуется с каждым доменом из `search`. При двух доменах поиска и десяти коротких именах выходит 10 × 3 = 30 запросов вместо 10 — по два `NXDOMAIN` на имя. В дампе видно пачки `api.corp.local`, `api.svc.cluster.local`, затем `api.`. Лечение — `ndots:2` или FQDN с точкой на конце.

5. `dig +trace app.example.com` проходит цепочку: корневые серверы → серверы зоны `com` → делегирование на NS провайдера. Неожиданность видна там, где `NS` в ответе родительской зоны не совпадает с ожидаемым: регистратор отдаёт `ns1.parking.example` вместо ваших `ns1.yourhost`. Дальше `dig NS example.com @<сервер родителя>` и `dig +norecurse` к найденному серверу показывают, где теряется актуальная зона.

## Глава 1a. Алгоритмика: как оценивать алгоритмы и не изобретать велосипед

1. Бинарный поиск: 10⁶ запросов × 20 сравнений = 2·10⁷ операций, но каждый поиск — по списку, то есть промахи кэша на каждом шаге. `set`: 10⁶ вставок при построении плюс 10⁶ проверок, каждая O(1) в среднем. По операциям выигрывает `set` примерно в десять раз, по константе — сильнее; цена — память: множество из миллиона int в CPython занимает порядка 40–60 МБ против ~36 МБ у списка (указатели плюс объекты). Если запросов мало, а память в дефиците — бинарный поиск выгоднее.

2. Проход по файлу построчно с `Counter` по IP и `heapq.nlargest(20, counter.items(), key=lambda kv: kv[1])`: один проход O(n) по строкам и O(u log 20) на выборку, где u — число уникальных IP. `sorted(Counter.items())` сортирует по ключу (строке IP), а не по частоте — это не тот ответ; полная сортировка по значению даёт O(u log u) и требует держать все уникальные ключи, а их на 2 ГБ лога могут быть миллионы. Если уникальных слишком много, точный счётчик заменяют на Count-Min Sketch: памяти фиксировано, результат приблизительный с гарантированной ошибкой.

3. Три цвета в DFS: белый — не посещён, серый — в текущем стеке, чёрный — обработан. Ребро в серый узел и есть цикл, а восстановить его позволяет стек пути.

```python
def find_cycle(graph: dict[str, list[str]]) -> list[str] | None:
    color, stack, pos = {}, [], {}
    def dfs(u: str) -> list[str] | None:
        color[u] = "gray"; pos[u] = len(stack); stack.append(u)
        for v in graph.get(u, []):
            if color.get(v) == "gray":
                return stack[pos[v]:] + [v]          # нашли петлю
            if color.get(v) is None:
                got = dfs(v)
                if got:
                    return got
        color[u] = "black"; stack.pop(); pos.pop()
        return None
    for node in graph:
        if color.get(node) is None:
            got = dfs(node)
            if got:
                return got
    return None
```

Сложность O(V + E): каждый узел и каждое ребро посещаются один раз.

4. `OrderedDict` даёт O(1) на чтение и вставку: `move_to_end(key)` при обращении, `popitem(last=False)` при переполнении. Связный список нужен затем, что удаление из середины по известному узлу — O(1); в `OrderedDict` эту роль играет внутренний двусвязный список, поэтому перебор ключей в порядке вставки бесплатен. Ключевое условие O(1): доступ к узлу по хешу, а не поиск по списку.

```python
from collections import OrderedDict

class LRU:
    def __init__(self, cap: int):
        self.cap, self.d = cap, OrderedDict()
    def get(self, k):
        if k not in self.d:
            return None
        self.d.move_to_end(k)
        return self.d[k]
    def put(self, k, v):
        self.d[k] = v
        self.d.move_to_end(k)
        if len(self.d) > self.cap:
            self.d.popitem(last=False)
```

5. Типовой результат: вложенный цикл `for a in A: for b in B: if a in seen_list` — это O(n²) из-за `in` по списку; замена на `set` даёт O(n) и ускорение в десятки-сотни раз на массивах от 10⁴. Если же перебор пар действительно нужен (например, поиск пересечений), сложность остаётся O(n·m), и ускорять надо не константы, а сам алгоритм — сортировкой и двумя указателями или хеш-соединением.
