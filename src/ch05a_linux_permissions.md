# Глава 5a. Linux: пользователи, права, sudo

Права доступа — та часть Linux, которую инженер трогает каждый день и чаще всего понимает наполовину. Симптомы одинаковы годами: «nginx отдаёт 403», «сервис не может писать в лог», «после `chmod -R 777` заработало, а через месяц нас взломали», «sudo просит пароль root, а мы его не знаем». Все они родом из одной модели: у процесса есть uid и gid, у файла — девять бит прав и владелец, и ядро при каждом `open()` сверяет одно с другим. Ниже эта модель собирается целиком: от `/etc/passwd` до capabilities, с разбором `ls -l` по колонкам.

## uid, gid и /etc/passwd

Для ядра субъект — это число: идентификатор пользователя (uid) и группы (gid). Имена существуют для людей и лежат в текстовой базе `/etc/passwd`, которую читают все, а пишут через `vipw` и `useradd` (параллельная правка двумя редакторами портит файл).

```
nextdoor:x:1000:1000:Next Door,,,:/home/nextdoor:/bin/bash
```

Семь полей: имя, место пароля (`x` — «смотри в `/etc/shadow`»), uid, gid основной группы, комментарий, домашний каталог, shell входа. Диапазоны заданы в `/etc/login.defs`: 0 — root, 1–99 — статические системные, 100–999 — системные, создаваемые пакетами, от 1000 — люди. Поэтому `www-data` с uid 33 — системная учётка без shell (`/usr/sbin/nologin`) и без пароля: под ней не логинятся, под ней работает сервис.

Группы — в `/etc/group`, членство в последнем поле: `adm:x:4:syslog,nextdoor`.

У процесса ровно один основной gid и произвольный набор дополнительных; проверка прав идёт по всем, но только по тем, что были на момент запуска. Добавили себя в `docker` через `usermod -aG docker $USER` и не перелогинились — текущая оболочка всё ещё без группы. Смотреть фактический набор — `id`, обновлять — новым входом.

## /etc/shadow и хеши паролей

`/etc/passwd` читаем всем, значит хешу там не место. Пароли уехали в `/etc/shadow` с режимом `640 root:shadow`: группа нужна ровно для того, чтобы `passwd` мог писать, а обычный пользователь — нет.

```
root:$y$j9T$Fv3s...:20345:0:99999:7:::
```

Поля: имя, хеш, дата последней смены (дни с 1 января 1970), минимум и максимум дней жизни пароля, сколько предупреждать, сколько дней после истечения вход ещё разрешён, дата блокировки, резерв. `!` или `*` вместо хеша — вход запрещён (так выглядят системные учётки), `!!` — учётка заблокирована.

Хеш — односторонняя функция с солью, не шифрование. Префикс говорит об алгоритме: `$y$` — yescrypt (по умолчанию в Debian и Ubuntu последних лет), `$6$` — SHA-512 (долгий стандарт, в том числе в семействе RHEL), `$2b$` — bcrypt, `$1$` — MD5, взломанный и недопустимый. Соль у каждого своя, поэтому одинаковые пароли дают разные хеши, а радужные таблицы бесполезны. Стоимость подбирают так, чтобы проверка одного пароля занимала десятки миллисекунд: незаметно при входе и смертельно при переборе. Отсюда правило: `$1$` в системе — инцидент, а не мелочь.

## Права rwx и восьмеричная запись

У файла три набора по три бита: владелец (user), группа (group), остальные (other). Для каталога смысл другой, и это главный источник путаницы:

| Бит | Для файла | Для каталога |
|---|---|---|
| `r` | прочитать содержимое | список имён (`ls`) |
| `w` | изменить содержимое | создавать, удалять, переименовывать |
| `x` | запустить как программу | войти и обращаться к файлам внутри |

Каталог с `r` без `x` — `ls` работает, `cat file` внутри даёт «Permission denied». Поэтому `/var/www` делают `755`.

Восьмеричная запись — упаковка трёх бит в цифру: `r`=4, `w`=2, `x`=1. Отсюда `7`=rwx, `6`=rw-, `5`=r-x, `4`=r--, `0`=---.

```
644  rw- r-- r--   владелец пишет, остальные читают: конфиг
755  rwx r-x r-x   владелец пишет, все читают и входят: каталоги, скрипты
600  rw- --- ---   только владелец: приватный ключ, .env, база SQLite
640  rw- r-----     владелец пишет, группа читает: лог с чувствительными данными
777  rwx rwx rwx   все могут всё: почти всегда ошибка
```

`777` — зло не из-за эстетики. `w` на каталоге означает право удалять и переименовывать чужие файлы, `w` на файле — право подменить содержимое: конфиг, скрипт, шаблон. Любой локальный пользователь и любой процесс под сервисной учёткой (а взламывают первыми именно веб-приложения и парсеры) получает запись в ваш конфиг. Многие демоны ещё и отказываются работать с world-writable файлами: ssh молча игнорирует слишком открытый `authorized_keys`.

## Разбор `ls -l` по колонкам

```
-rwsr-xr-x 1 root root  118168 Apr 19  2025 /usr/bin/passwd
drwxrwxrwt 13 root root     900 Oct 29 19:54 /tmp
-rw-r----- 1 root adm  1048576 Oct 28 03:12 /var/log/syslog
lrwxrwxrwx 1 root root      27 Sep  1  2025 /etc/localtime -> /usr/share/zoneinfo/Europe/Moscow
```

Первая колонка — тип и права. Первый символ: `-` файл, `d` каталог, `l` ссылка, `b`/`c` устройства, `s` сокет, `p` FIFO. Дальше девять бит; `s` на месте `x` — setuid (в групповой тройке setgid), `t` — sticky, `+` после битов — есть ACL, `.` — контекст SELinux.

Вторая колонка — число жёстких ссылок (для каталога — число подкаталогов плюс два). Третья и четвёртая — владелец и группа. Пятая — размер в байтах; для каталога это размер его {{L|g55|inode}}, а не сумма файлов. Шестая — время модификации: если вместо года стоят часы и минуты, файл изменён менее полугода назад (поведение GNU coreutils). Последняя — имя, для ссылки ещё и цель.

## umask: маска, которая вычитает права

Программа при создании файла просит режим (обычно `0666` для файла и `0777` для каталога), ядро вычитает из него маску процесса. Файл никогда не получает `x` из umask — только явным `chmod`.

| umask | Файлы (из 666) | Каталоги (из 777) | Когда уместна |
|---|---|---|---|
| `022` | `644` | `755` | дефолт системных файлов |
| `002` | `664` | `775` | групповая работа |
| `027` | `640` | `750` | серверы: чужие не читают |
| `077` | `600` | `700` | приватные данные |

`umask` печатает текущую маску (`0002` в Debian для людей, `0022` для root), `umask 027` меняет её для текущей оболочки. Системно — `UMASK` в `/etc/login.defs` и `UMask=` в systemd-юните (глава 5b): сервис наследует маску от демона, а не от вашей оболочки, и это объясняет половину «файлы создаются 644, хотя я поставил 600».

## chmod, chown, chgrp

```bash
chmod 640 /etc/app/config.yml          # восьмерично: rw-r-----
chmod u+x deploy.sh                    # символьно: добавить x владельцу
chmod g-w,o-rwx secrets.env            # снять w у группы, у остальных всё
chmod -R g+rX /srv/www                 # X: x только каталогам и уже исполняемому
chmod 2750 /srv/shared                 # setgid на каталог
chown app:app /srv/app                 # владелец и группа
chgrp adm /var/log/app.log
```

`X` (заглавная) ставит `x` каталогам и тем файлам, где `x` уже у кого-то есть, и не делает исполняемыми данные. Поэтому `chmod -R 755` на дерево с картинками вредно, а `chmod -R a+rX` — почти всегда то, что имелось в виду.

Смена владельца требует root или `CAP_CHOWN`: отдать свой файл другому нельзя, иначе можно подсунуть root'у setuid-бинарник. Смена группы разрешена, если вы член целевой группы.

## Специальные биты: setuid, setgid, sticky

**setuid** (`4000`, в `ls` — `s` на месте `x` владельца) даёт процессу euid владельца файла. Классика — `/usr/bin/passwd`: запускается обычным пользователем, но пишет в `/etc/shadow`, потому что владелец — root. Это же делает setuid главным подарком атакующему: setuid-бинарник с ошибкой = root. На скриптах ядро setuid игнорирует, а список в системе стоит знать: `find / -perm -4000 -type f`.

**setgid** (`2000`) на файле даёт egid владельца группы; на каталоге — новые файлы и подкаталоги наследуют группу каталога. Стандартный способ сделать общий каталог: `chgrp dev /srv/shared`, `chmod 2775` — всё внутри автоматически принадлежит `dev`, и бегать с `chgrp` не нужно.

**sticky** (`1000`, `t`) на каталоге с `w` для всех запрещает удалять и переименовывать чужие файлы — это может владелец файла, владелец каталога и root. Ровно поэтому `/tmp` имеет режим `1777`:

```
drwxrwxrwt 13 root root 900 Oct 29 19:54 /tmp
```

Без sticky в мире, где `/tmp` открыт на запись всем, любой процесс мог бы удалить чужой сокет или подменить чужой временный файл. Тот же приём — на общих каталогах загрузок и в спуле печати.

## ACL: права для тех, кто не владелец и не в группе

Девяти бит не хватает, когда нужно дать чтение одному человеку, не добавляя его в группу. Для этого — списки контроля доступа (ACL), в Debian пакет `acl`.

```bash
setfacl -m u:deploy:rx /srv/app            # пользователю deploy — чтение и вход
setfacl -m g:qa:r /srv/app/report.csv      # группе qa — только чтение
setfacl -m d:u:deploy:rx /srv/app          # default ACL: наследуется новыми файлами
getfacl /srv/app
```

```
# file: srv/app
# owner: app
# group: app
user::rwx
user:deploy:r-x
group::r-x
mask::r-x
other::---
```

Строка `mask` — верхняя граница прав для именованных записей и группы-владельца; `setfacl` пересчитывает её сам, но при ручной правке легко получить «права есть, а доступа нет» — применяются именно эффективные права из `effective:`. В `ls -l` ACL отмечается плюсом: `drwxr-x---+`. Default-ACL работает только на каталоги и только для новых объектов.

## sudo и /etc/sudoers.d

`su` переключает пользователя и требует пароль целевой учётки — для `su -` это пароль root. `sudo` проверяет пароль вызывающего и сверяет его с политикой: кто, от кого, какие команды, нужен ли пароль. Root-пароль не нужен вообще — поэтому в Ubuntu учётка root заблокирована, а первый пользователь входит в группу `sudo`.

Политика — `/etc/sudoers` плюс подключаемые файлы; правят только через `visudo`, потому что синтаксическая ошибка означает потерю доступа к root.

```bash
visudo -f /etc/sudoers.d/deploy
```

```
# файл должен иметь режим 0440 и принадлежать root:root
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart app.service
%devops ALL=(ALL) ALL
Defaults:%devops timestamp_timeout=15
```

Формат: `кто где=(от кого) что`; первое поле — пользователь или `%группа`, `ALL` — любые хосты. Голое `ALL` в последнем поле означает и `sudo vi /etc/sudoers`, то есть полный root. Опасны и «безобидные» записи: `NOPASSWD: /usr/bin/systemctl` без юнита даёт root через `systemctl edit`; `journalctl`, `less`, `find`, `awk`, `tar` дают shell или чтение-запись файлов.

`NOPASSWD` снимает вторую аутентификацию: любой процесс под этим пользователем (взломанное приложение, cron-скрипт, чужой код в CI) получает привилегии без секрета. В контейнерах `NOPASSWD: ALL` — обычная практика, и её цена в том, что граница «root» внутри образа стирается.

Помнить: `sudo` по умолчанию сбрасывает окружение (`env_reset`) и подставляет `secure_path`, поэтому `PATH` из вашей оболочки не доезжает до root-команды — это защита, а не баг. Каждый вызов попадает в журнал через PAM/{{L|g57|journald}}, и «кто, когда, какую команду» — главный аргумент против общей учётки root.

## Capabilities: привилегии по частям

Root — не «всё», а набор из нескольких десятков возможностей, которые ядро проверяет по отдельности: `CAP_NET_BIND_SERVICE` (порты ниже 1024), `CAP_NET_ADMIN` (сеть), `CAP_SYS_ADMIN` (монтирование), `CAP_CHOWN`. Можно выдать одну.

Именно поэтому nginx от root слушает 80-й порт, а потом сбрасывает привилегии: мастер держит сокет, рабочие процессы работают под `www-data`. Альтернатива без root:

```bash
sudo setcap cap_net_bind_service=+ep /usr/sbin/nginx
getcap /usr/sbin/nginx
```

```
/usr/sbin/nginx cap_net_bind_service=ep
```

`e` — effective (действует сразу), `p` — permitted (можно включить). Цена: capability привязана к файлу, а не к пользователю; кто может заменить бинарник, наследует право; обновление пакета сбрасывает `setcap`. В {{L|g115|systemd}} то же описывается декларативно: `AmbientCapabilities=`, `CapabilityBoundingSet=`. Третий путь — `sysctl net.ipv4.ip_unprivileged_port_start=0`: Docker именно так разрешает контейнерам любые порты.

## Практика: «сервис не может писать в /var/log»

Приложение работает под `app`, пишет в `/var/log/app/app.log`, и после переустановки в журнале появляется:

```
app[2417]: PermissionError: [Errno 13] Permission denied: '/var/log/app/app.log'
```

Диагностика — три команды, каждая отвечает на свой вопрос.

```bash
id app
ls -ld /var/log/app /var/log/app/app.log
namei -l /var/log/app/app.log
```

```
uid=995(app) gid=995(app) groups=995(app)
drwxr-x--- 2 root root 4096 Oct 28 10:02 /var/log/app
-rw-r----- 1 root root  812 Oct 28 10:02 /var/log/app/app.log
```

Читается так: каталог `root:root 750` — `app` не в группе `root` и даже войти в каталог (`x`) не может; файл тоже чужой. Приложение не «сломало права», оно их никогда не имело: каталог создали руками от root, а пакет и юнит ожидали `app:adm 0750`.

Лечение — не `chmod 777`, а явное владение:

```bash
install -d -o app -g adm -m 0750 /var/log/app
touch /var/log/app/app.log
chown app:adm /var/log/app/app.log && chmod 0640 /var/log/app/app.log
```

`install -d` создаёт каталог с нужными владельцем и режимом за один шаг. В systemd то же делает `LogsDirectory=app` с `LogsDirectoryMode=0750`: демон сам создаст каталог с владельцем из `User=`/`Group=`. Если же включён `ProtectSystem=strict`, запись запрещена вообще, пока каталог не добавлен в `ReadWritePaths=`, и текст ошибки будет `Read-only file system`, а не `Permission denied` — это разные поломки.

Проверять доступ нужно от имени сервиса:

```bash
sudo -u app sh -c 'echo probe >> /var/log/app/app.log' && tail -1 /var/log/app/app.log
```

```
probe
```

`test -w` от вашей учётки ничего не доказывает: uid другой.

## Типичные ошибки

1. **`chmod -R 777` как универсальное средство.** Права «починились», потому что запись получили все, включая скомпрометированный сервис; причина — неверный владелец, неверная группа или отсутствующий `x` у каталога — осталась.
2. **Путаница `r` и `x` на каталоге.** Файл читается, а `cd` не работает. Механизм: путь резолвится по компонентам, и каждому нужен `x`; `r` нужен только для листинга.
3. **Добавили в группу и не перелогинились.** `id` в новой сессии группу показывает, а старый процесс — нет. Механизм: набор дополнительных групп фиксируется при входе.
4. **`umask` из оболочки не действует на сервис.** Механизм: маска наследуется от родителя, у systemd-сервиса это демон; нужен `UMask=` в юните.
5. **`sudo echo ... > /etc/file` не работает.** Механизм: редирект открывает файл ваша оболочка, а не `sudo`. Лечится `sudo tee` или `sudo sh -c '...'`.
6. **Оставили setuid на самописном бинарнике.** Любая ошибка в нём — локальное повышение привилегий, а обновление пакета может вернуть бит: euid root получает весь процесс, включая разбор входных данных.

## Чек-лист

- `ls -l` разбирается по колонкам: тип, девять бит, `s`/`t`/`+`/`.`, ссылки, владелец, группа, размер, время.
- Для любого «Permission denied» проверены `id` процесса, `ls -ld` на каждый компонент пути и `namei -l`.
- Нет world-writable файлов вне `/tmp`-подобных каталогов: `find / -xdev -perm -0002 -type f`.
- Список setuid известен и объяснён: `find / -xdev -perm -4000 -type f`.
- В `/etc/sudoers.d` нет лишних `ALL` и `NOPASSWD` на интерпретаторы; файлы `0440 root:root`.
- Приватные ключи и `.env` — `600`, каталоги `700`.
- Сервисные каталоги создаются декларативно (`install -d`, `LogsDirectory=`), а доступ проверен от имени сервиса.

## Упражнения

1. Создайте `/srv/shared` так, чтобы файлы внутри всегда принадлежали группе `dev`, любой из группы мог их править, а удалять чужие не мог никто, кроме владельца. Объясните, какие три бита за это отвечают.
2. Найдите все setuid-файлы и для трёх объясните, зачем бит нужен и что сломается, если его снять.
3. Настройте ACL: `deploy` читает `/srv/app/config.yml`, но не видит остальных файлов каталога. Объясните строку `mask` в `getfacl`.
4. Разрешите nginx слушать 80 без root двумя способами (capabilities и `ip_unprivileged_port_start`) и сравните, что сломается при обновлении пакета и при переносе на другой хост.
5. Дайте `ci` право без пароля перезапускать ровно один юнит и докажите, что через эту запись нельзя получить root.
