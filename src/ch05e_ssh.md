# Глава 5e. SSH: ключи, конфиг, туннели

SSH — протокол, которым DevOps-инженер пользуется каждый день и чаще всего не понимает до конца: подключение «просто работает», пока не появится `Permission denied (publickey)`, не перестанет открываться база за бастионом или не выяснится, что ключ с продакшена унесли вместе с ноутбуком. В этой главе — что происходит за секунду рукопожатия, почему ed25519 лучше rsa 4096, как устроены `authorized_keys` и `~/.ssh/config`, чем отличаются три вида туннелей, как закрыть `sshd` и как диагностировать отказ, не перебирая наугад. Команды и вывод проверены на OpenSSH 10.0p2 с реального sshd.

## Что происходит при подключении

Полсекунды между Enter и приглашением шелла — это четыре этапа, и каждый отказывает по-своему.

Сначала TCP на порт 22 и обмен версиями: обе стороны присылают строку `SSH-2.0-OpenSSH_10.0p2`.

Затем обмен ключами (key exchange, KEX) по RFC 4253: стороны договариваются об алгоритмах и вырабатывают общий секрет, из которого выводятся ключи шифрования и MAC для каждого направления. Асимметричная криптография нужна для двух вещей — договориться о симметричном ключе и подтвердить, что сервер тот, за кого себя выдаёт (подпись host key, сверяемая с `known_hosts`). OpenSSH по умолчанию берёт гибридную схему `mlkem768x25519-sha256`: постквантовый ML-KEM-768 плюс X25519.

Дальше аутентификация клиента (RFC 4252): при входе по ключу клиент не отправляет ключ «как пароль», а подписывает приватным ключом сессионный хэш, а сервер проверяет подпись по строке из `authorized_keys`. Приватный ключ не покидает машину никогда — в этом смысл схемы. После этого открывается канал (RFC 4254): по одному TCP мультиплексируются сессии, `exec`, `sftp`, проброс портов.

```bash
ssh -vv -p 2222 -i ~/.ssh/id_ed25519 nextdoor@127.0.0.1 'uptime -p'
```

```
debug1: Remote protocol version 2.0, remote software version OpenSSH_10.0p2 Debian-7+deb13u4
debug1: kex: algorithm: mlkem768x25519-sha256
debug1: kex: host key algorithm: ssh-ed25519
debug1: Server host key: ssh-ed25519 SHA256:MVp668g1RL1ExRB+/+H47RhyC+3gO07TbgKQifG408A
debug1: Offering public key: id_ed25519 ED25519 SHA256:mmhapd3hr8pdHItCgsxvivdaofR8DNuddHVEwllea58
debug1: Server accepts key: id_ed25519 ED25519 SHA256:mmhapd...
Authenticated to 127.0.0.1 ([127.0.0.1]:2222) using "publickey".
```

Порядок строк и есть порядок этапов: `kex` — чем шифруется канал, `Server host key` — чем сервер доказал, что он сервер, `Offering`/`Server accepts` — какой ключ он согласился принять, `Authenticated` — итог. При отказе полезная строка всегда между `Offering` и `Authenticated`.

## Ключи: ed25519 против rsa

Ключ ed25519 — 32 байта, подпись — 64 байта. Ключ RSA-4096 — 512 байт модуля и 512 байт подписи, и подпись заметно дороже. Стойкость при этом сопоставима: ed25519 даёт около 128 бит, RSA-4096 — порядка 140, и 12 бит разницы не компенсируют ни десятикратный размер, ни чувствительность RSA к выбору схемы дополнения.

Историческая ловушка: с OpenSSH 8.8 алгоритм `ssh-rsa` (подпись по SHA-1) отключён по умолчанию, и старый сервер, который умеет только его, отвечает `no matching host key type found`. Включать `PubkeyAcceptedAlgorithms +ssh-rsa` ради такого сервера — сознательный шаг назад по безопасности, а не «настройка совместимости».

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -C 'nextdoor@workstation'
ssh-keygen -l -f ~/.ssh/id_ed25519.pub
ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa -C 'nextdoor@workstation'
ssh-keygen -l -f ~/.ssh/id_rsa.pub
```

```
256 SHA256:mmhapd3hr8pdHItCgsxvivdaofR8DNuddHVEwllea58 nextdoor@workstation (ED25519)
4096 SHA256:nniMFPIZtEzEStb/IgvSuNsfhE3LvP8lL4GLwMqa44Q nextdoor@workstation (RSA)
```

Отпечаток (fingerprint) — SHA256 от тела ключа в base64, одинаковый у публичной и приватной части. Права на файлы не косметика: `ssh` отказывается использовать ключ, если файл читаем группой или другими, — сообщение `Permissions 0644 for '...' are too open` означает ровно это.

## Passphrase, ssh-agent и authorized_keys

Парольная фраза защищает файл: без неё украденный `id_ed25519` — готовый доступ, с ней — бесполезный зашифрованный блок. Плата — ввод фразы при каждом подключении, и здесь появляется агент.

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
ssh-add -l
```

```
256 SHA256:mmhapd3hr8pdHItCgsxvivdaofR8DNuddHVEwllea58 nextdoor@workstation (ED25519)
```

Агент держит расшифрованный ключ в памяти и подписывает запросы по UNIX-сокету `SSH_AUTH_SOCK`. Отсюда правило, которое нарушают чаще всего: **проброс агента (`-A`) на чужой сервер равен передаче ключа**. На бастионе сокет доступен процессам вашей учётной записи, а root бастиона может подключиться к нему и подписать что угодно вашим ключом. Нужен «прыжок» — используйте `ProxyJump`: трафик идёт через бастион, ключ остаётся дома.

`authorized_keys` — не список ключей, а список правил: перед типом ключа ставятся опции, ограничивающие то, что этим ключом можно делать.

```
command="echo forced-command-ok; id -un",no-pty,no-port-forwarding ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIFwC7txsUAuXxHM6EpTThcSTgrne5x0qDErkefBG+d7J ci@build
```

```bash
ssh -p 2222 -i ~/.ssh/id_ed25519 nextdoor@127.0.0.1 'ls /'
```

```
forced-command-ok
nextdoor
```

`ls /` не выполнилась: `command=` подменяет любую запрошенную команду на фиксированную, и это стандартный способ дать CI одну узкую операцию вместо шелла. Другие опции: `from="10.20.0.0/16"` (только с этих адресов), `restrict` (выключить всё необязательное — PTY, forwarding, X11), `permitopen="db.internal:5432"` (проброс только к одной цели), `expiry-time="20270101"`. Ограничения проверяет сервер, поэтому они работают, даже если клиент не настроен.

## ~/.ssh/config

Блоки `Host` применяются по порядку, первый совпавший выигрывает по каждому параметру, `Host *` в конце задаёт значения по умолчанию.

```
Host bastion
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/id_ed25519

Host db
    HostName 10.20.0.15
    User postgres
    ProxyJump bastion
    LocalForward 15432 127.0.0.1:5432

Host *
    ServerAliveInterval 30
    ControlMaster auto
    ControlPath ~/.ssh/cm/%r@%h:%p
    ControlPersist 10m
```

Проверить результат подстановок можно без подключения:

```bash
ssh -G db | grep -E '^(hostname|user|port|proxyjump|localforward)'
```

```
user postgres
hostname 10.20.0.15
port 22
localforward 15432 [127.0.0.1]:5432
proxyjump bastion
```

`ssh -G` печатает итоговую конфигурацию со всеми значениями по умолчанию — единственный надёжный способ узнать, какой ключ и порт будут использованы.

`ProxyJump` (короткая форма `-J`) — SSH внутри SSH: клиент подключается к бастиону и просит его открыть TCP-канал до целевого хоста. Целевой хост видит соединение с бастиона, бастион не видит ваших ключей.

`ControlMaster`/`ControlPersist` убирают рукопожатие на каждое подключение: первое соединение становится мастером и держит сокет, последующие идут через него.

```
без мультиплексирования: 91 ms, 92 ms, 98 ms
с ControlMaster:         106 ms, 10 ms, 8 ms
```

На канале с RTT 80 мс экономия — сотни миллисекунд на команду, а `rsync` из тысячи файлов превращается из минуты в секунды. Цена: сокет живёт после выхода, а при смене сети мастер «висит» — `ssh -O exit db` закрывает его.

## Туннели: -L, -R, -D

Три ключа решают три разные задачи.

| Ключ | Что делает | Где слушает | Типичная задача |
|---|---|---|---|
| `-L` | локальный порт → адрес с точки зрения сервера | ваша машина | достучаться до БД за бастионом |
| `-R` | порт на сервере → адрес с вашей машины | удалённая машина | показать локальный сервис наружу |
| `-D` | SOCKS5-прокси через SSH | ваша машина | пустить браузер или `curl` через сервер |

Локальный проброс: соединение к `127.0.0.1:19080` уходит в SSH-канал, а TCP к `127.0.0.1:8080` открывает уже удалённая сторона.

```bash
python3 -m http.server 8080 --bind 127.0.0.1 &
ssh -f -N -p 2222 -i ~/.ssh/id_ed25519 -L 19080:127.0.0.1:8080 nextdoor@127.0.0.1
ss -tlnp | grep 19080
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:19080/
```

```
LISTEN 0 128 127.0.0.1:19080 0.0.0.0:* users:(("ssh",pid=595634,fd=5))
200
```

`-N` — не выполнять команду, только проброс, `-f` — уйти в фон после аутентификации. Слушает именно `ssh`, а не удалённый сервис, и по умолчанию только на loopback.

Шаблон «база за бастионом» — тот же механизм: `ssh -N -L 15432:db.internal:5432 bastion`, затем `psql -h 127.0.0.1 -p 15432`. Важно: `db.internal` резолвится **на бастионе**, поэтому локальный DNS о такой записи может не знать — это нормально.

Динамический проброс превращает SSH в SOCKS5-прокси:

```bash
ssh -f -N -D 11080 nextdoor@127.0.0.1
curl -s --socks5 127.0.0.1:11080 -o /dev/null -w '%{http_code}\n' https://example.com
```

```
200
```

DNS по умолчанию резолвится на стороне прокси (`--socks5-hostname` в curl) — это и нужно, когда внутренние имена видны только изнутри.

Обратный проброс (`-R`) нужен, когда сервис у вас, а смотреть на него будут с сервера: `ssh -R 8080:127.0.0.1:3000 user@remote` открывает порт на удалённой машине и ведёт к вашему `localhost:3000`. По умолчанию он слушает только loopback удалённой машины; снаружи — только при `GatewayPorts yes`.

## scp, sftp, rsync

`scp` с OpenSSH 9.0 работает поверх SFTP, а не собственного legacy-протокола; старый режим остался под флагом `-O`. Разница практическая: современный `scp` умеет то же, что `sftp`, но не умеет докачивать и синхронизировать.

```bash
scp -P 2222 ./dump.sql nextdoor@127.0.0.1:/tmp/
rsync -avz --progress -e 'ssh -p 2222' ./site/ nextdoor@127.0.0.1:/srv/site/
```

`scp` копирует целиком и всегда; `rsync` сравнивает и передаёт разницу, умеет `--partial` (докачка), `--delete` (удалить лишнее на приёмнике) и `--dry-run` (показать план, ничего не делая). Для больших каталогов и повторяющихся выкладок `rsync` быстрее на порядок, но требует установки на обеих сторонах. Косая черта в конце источника (`./site/`) означает «содержимое каталога», без неё — «каталог целиком»; это самая частая ошибка первой выкладки.

## sshd_config: что менять

Настройки сервера — `/etc/ssh/sshd_config` (в Debian и Ubuntu бывает ещё `/etc/ssh/sshd_config.d/*.conf`, подключаемый через `Include`). Минимальный набор для машины в интернете:

```
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
MaxAuthTries 3
LoginGraceTime 20
AllowUsers deploy
```

`PermitRootLogin no` запрещает вход под root полностью (`prohibit-password` — только по ключу, значение по умолчанию с OpenSSH 7.0). `PasswordAuthentication no` убирает подбор пароля как класс атаки и требует, чтобы ключи работали у всех, кому доступ нужен. `AllowUsers` — белый список: всё, что не перечислено, не входит, даже с правильным ключом.

Проверять конфиг нужно до перезапуска, иначе опечатка оставит вас без доступа:

```bash
sudo sshd -t
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|kbdinteractiveauthentication)'
```

```
permitrootlogin no
passwordauthentication no
kbdinteractiveauthentication no
```

`sshd -t` — синтаксическая проверка, `sshd -T` — дамп итоговой конфигурации: он печатает и то, чего в файле нет, подставляя значения по умолчанию, поэтому правду показывает именно `-T`. Изменения применяются через `systemctl reload ssh`, а не `restart`: reload перечитывает конфиг, не разрывая текущие сессии.

`Match`-блоки делают исключения без второго демона:

```
Match Address 10.20.0.0/16
    PasswordAuthentication yes

Match User backup
    ForceCommand /usr/local/bin/backup-only.sh
```

Первый блок оставляет пароли для внутренней сети, второй запирает служебную учётную запись в одну команду. `Match` действует до конца файла или до следующего `Match`, поэтому порядок блоков — часть логики.

`fail2ban` в одном абзаце: демон читает журнал (`/var/log/auth.log` или журнал {{L|g115|systemd}}) по шаблону `[sshd]`, считает неудачные попытки с одного адреса и на время банит его правилом nftables или {{L|g56|iptables}}. С ключами и выключенным паролем он не столько защищает, сколько уменьшает шум и трафик ботов; обязательный параметр — `ignoreip` со своими сетями, иначе ошибка в конфиге клиента блокирует вам доступ.

## Диагностика

Уровни подробности: `-v` — этапы подключения, `-vv` — плюс алгоритмы и попытки ключей, `-vvv` — всё, включая побайтовый обмен. Начинать всегда со второго.

```bash
ssh -T git@github.com
```

```
git@github.com: Permission denied (publickey).
```

`ssh -T` отключает PTY (так требует GitHub, который шелла не даёт). `Permission denied (publickey)` означает, что сервер не принял ни один ключ: ключа нет в `authorized_keys`, не тот файл или не те права. При успехе GitHub печатает приветствие с логином и отдельно сообщает, что шелл не предоставляется, — это нормальный результат.

Отпечаток ключа сервера проверяется без подключения:

```bash
ssh-keyscan -t ed25519 github.com | ssh-keygen -lf -
```

```
256 SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU github.com (ED25519)
```

В `known_hosts` записи по умолчанию хэшированы, и `ssh-keygen -F host` находит строку, не выдавая, к каким ещё серверам вы подключались. При смене ключа хоста правильная реакция — `ssh-keygen -R host` и сверка нового отпечатка, а не отключение `StrictHostKeyChecking`.

## Типичные ошибки

1. **Права 0644 на приватном ключе.** `ssh` отвечает `Permissions 0644 for '...' are too open` и ключ не использует. Механизм: клиент требует, чтобы файл не читался группой и остальными, иначе любой пользователь машины мог бы подписывать вашим ключом.
2. **`PermitRootLogin no` без второго администратора.** После reload доступа нет ни у кого. Механизм: настройка применяется к новым сессиям, а текущая не спасает после выхода; лечится `sshd -t`, отдельной учётной записью и открытой сессией до reload.
3. **Проброс агента на бастион (`-A`).** Ключ фактически доступен root бастиона. Механизм: сокет агента принадлежит вашей учётной записи, а root читает чужие сокеты, и подпись выполняется без вашего участия.
4. **`command=` без `no-pty`.** Получается «полушелл»: команда подменена, но PTY выдан. Механизм: `command=` ограничивает запуск, но не запрещает запрос псевдотерминала — его запрещает отдельная опция.
5. **`-L 5432:localhost:5432` при базе на другом хосте.** Туннель открывается, а соединение не идёт. Механизм: адрес назначения резолвится и открывается на удалённой стороне, поэтому `localhost` — это бастион.
6. **Проверка отпечатка тем же каналом.** Отпечаток берут `ssh-keyscan` с того же сервера, который подозревают. Механизм: подмена хоста даёт согласованный ответ в обоих запросах; сверять нужно с консолью или документацией провайдера.

## Чек-лист

- Приватные ключи ed25519, с парольной фразой, права 600.
- У служебных ключей в `authorized_keys` есть `from=`, `command=` или `restrict`.
- Проброс агента `-A` не используется; для прыжков настроен `ProxyJump`.
- В `~/.ssh/config` есть `ServerAliveInterval`, `IdentitiesOnly yes` и блоки `Host` для каждого окружения.
- `sshd -t` проходит, `sshd -T` показывает ожидаемые `PasswordAuthentication no` и `AllowUsers`.
- Вход по паролю выключен, root закрыт, для изменений есть вторая учётная запись с sudo.
- Отказ диагностирован по `ssh -vv`: видно, какой ключ предложен и принят ли он.

## Упражнения

1. Сгенерируйте ключ ed25519, добавьте его на тестовый sshd и добейтесь входа. Затем закройте вход по паролю и объясните по `ssh -vv`, почему подключение с неверным ключом отклонено.
2. Настройте в `~/.ssh/config` два окружения (`staging`, `prod`) с разными ключами и `IdentitiesOnly yes`. Проверьте через `ssh -G`, что для каждого используется свой ключ.
3. Поднимите HTTP-сервер на `127.0.0.1:8080`, пробросьте его на `19080` через `ssh -L` и объясните, почему `ss -tlnp` показывает процесс `ssh`, а не сервер.
4. Ограничьте ключ в `authorized_keys` так, чтобы он мог только читать файл через `command=`, и проверьте, что произвольная команда не выполняется и PTY не выдаётся.
5. Настройте `ControlMaster` с `ControlPersist 10m`, измерьте время первой и второй команды, затем добавьте `ProxyJump` через второй sshd и посчитайте, сколько соединений в цепочке.
