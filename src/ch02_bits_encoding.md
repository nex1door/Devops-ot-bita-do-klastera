# Глава 2. Биты, числа и кодировки

Любая программа, любой протокол, любой файл в конечном счёте — это последовательность битов, и большинство загадочных багов рантайма растёт из несовпадения представлений: сервер отдал 4 байта в одном порядке, клиент прочитал их в другом; в базе лежала строка в cp1251, а в JSON ушла как {{L|g125|UTF-8}}; сумма в бухгалтерии не сошлась на копейку, потому что деньги считали во `float`. В этой главе разбирается, как из битов получаются числа: позиционные системы счисления, беззнаковые и знаковые целые, дополнительный код, переполнение, формат IEEE-754 с его знаменитым `0.1 + 0.2 != 0.3`, а затем — как из чисел получаются тексты: ASCII, Windows-1251, UTF-8. Читатель научится читать дампы байтов, понимать вывод `hexdump` и не удивляться, увидев `ÐŸÑ€Ð¸Ð²ÐµÑ‚` вместо `Привет`.

## Бит и позиционные системы счисления

Бит хранит одно из двух значений. Байт — это 8 бит, он же октет (octet) в сетевых стандартах; восьмибитный байт стал стандартом де-факто потому, что его хватало на один символ ASCII и на два шестнадцатеричных знака. `n` бит дают `2ⁿ` различных комбинаций: 8 бит — 256 значений, 16 бит — 65 536 (ровно столько портов в TCP и UDP), 32 бита — около 4,29 млрд (адрес IPv4), 128 бит — число с 39 цифрами (адрес IPv6).

В позиционной системе счисления вес разряда — это степень основания. В двоичной основание 2, поэтому `1011₂ = 1·8 + 0·4 + 1·2 + 1·1 = 11`. В шестнадцатеричной основание 16, цифры `0–9` и `a–f`. Шестнадцатеричная запись удобна не традицией, а арифметикой: одна hex-цифра — ровно 4 бита, две — ровно байт. Перевод между двоичной и hex-записью делается глазами, без вычислений, а между двоичной и десятичной — нет. Поэтому дампы памяти, хэши, цвета `#ff8800`, MAC-адреса и UUID печатают в hex.

```python
n = 0xB4                      # hex-литерал, 180 в десятичной
print(n, bin(n), hex(n))      # 180 0b10110100 0xb4
print(int("10110100", 2))     # 180 — разбор строки в заданном основании
print(bin(0xB4 | 0x0F))       # 0b10111111 — побитовое ИЛИ
print(bin(0xB4 & 0x0F))       # 0b100 — маска младших 4 бит
print(0xB4 >> 4, 0xB4 & 0x0F) # 11 4 — старший и младший полубайты
```

Операции `>>`, `&`, `|`, `^` — это не «низкоуровневая экзотика»: на них построены флаги прав доступа (`0o755`), маски подсетей (`/24` — это `255.255.255.0`), битовые наборы признаков в заголовках TCP, сжатие (`gzip`), контрольные суммы и хэш-функции.

## Знаковые числа и дополнительный код

Для беззнаковых целых из `n` бит диапазон — от `0` до `2ⁿ − 1`. Для знаковых нужен способ кодировать минус. Наивный вариант «старший бит — знак, остальные — модуль» (sign-magnitude) неудобен: получается два нуля (`+0` и `−0`), а сложение требует отдельной логики для разных знаков. Вариант «обратный код» (ones' complement) тоже даёт два нуля.

Победил дополнительный код (two's complement): отрицательное число `−x` кодируется как `~x + 1`, то есть побитовая инверсия плюс единица. Старший бит получает вес `−2ⁿ⁻¹`, остальные — обычные положительные веса. Для 8 бит:

| Биты | Беззнаковое | Знаковое |
|---|---|---|
| `0000 0000` | 0 | 0 |
| `0111 1111` | 127 | 127 |
| `1000 0000` | 128 | −128 |
| `1111 1111` | 255 | −1 |

Главное свойство: сложение не зависит от знака. `−1 + 1` в 8 битах — это `1111 1111 + 0000 0001 = 1 0000 0000`, старший бит переноса теряется, остаётся `0000 0000`. Одна и та же схема сумматора работает для всех чисел, поэтому дополнительный код стоит в каждом процессоре.

```python
print(bin(-5 & 0xFF))     # 0b11111011 — -5 в 8 битах
print((~5) & 0xFF)        # 250, инверсия пяти
print((~5 & 0xFF) + 1)    # 251 — то же число по формуле ~x + 1
print((-5 + 1) & 0xFF)    # 252 — сложение идёт по модулю 2^8
```

В Python целые произвольной точности, поэтому переполнения нет: `2**100` — обычное число. В C, Go, Java, Rust типы фиксированной ширины, и там граница реальна.

```python
import ctypes

x = ctypes.c_int32(2**31 - 1)   # максимум для int32
print(x.value)                  # 2147483647
x.value = x.value + 1           # переполнение
print(x.value)                  # -2147483648
```

Переполнение знакового целого в C — неопределённое поведение (undefined behavior), и компилятор вправе выбросить проверку `if (x + 1 < x)`: он исходит из того, что переполнения не бывает. Отсюда классические уязвимости в проверках размера буфера. В Go переполнение определено и просто заворачивается по модулю `2ⁿ`, в Rust в debug-сборке — паника, в release — заворачивание. В Python безопасно, но за счёт другого представления чисел и скорости.

### Порядок байтов

Многобайтовое число в памяти можно разложить двумя способами: старший байт первым (big-endian, «сетевой порядок») или младший первым (little-endian, x86-64 и ARM по умолчанию). `0x12345678` в little-endian лежит в памяти как `78 56 34 12`.

```python
import struct
print(struct.pack("<I", 0x12345678).hex(" "))  # 78 56 34 12
print(struct.pack(">I", 0x12345678).hex(" "))  # 12 34 56 78
```

Символ `<` задаёт little-endian, `>` — big-endian, `!` — сетевой порядок. Все целые в заголовках IP, TCP, UDP передаются big-endian, поэтому код, который читает бинарный протокол, обязан указывать порядок явно. Если данные читаются «правильно» на одной машине и мусором — на другой, причина почти всегда здесь.

## IEEE-754: почему 0.1 + 0.2 != 0.3

Дробные числа хранятся в формате IEEE-754 как `(−1)^s · 1.m · 2^e`. В `float64` (double) 1 бит знака, 11 бит экспоненты со смещением 1023 и 52 бита мантиссы; в `float32` — 1, 8 и 23. Ненулевое нормализованное число имеет неявную ведущую единицу, поэтому точность `float64` — около 15–17 значащих десятичных цифр, а `float32` — около 7.

Двоичная дробь представляет только суммы степеней двойки: `0.5`, `0.25`, `0.75` точны, а `0.1` — это `1/10`, и в двоичной системе она превращается в бесконечную периодическую дробь, как `1/3` в десятичной. Хранится ближайшее приближение. Отсюда знаменитый результат:

```python
import struct

def bits(v: float) -> str:
    return format(struct.unpack("<Q", struct.pack("<d", v))[0], "064b")

b = bits(0.1)
print(b[:1], b[1:12], b[12:])   # знак, экспонента, мантисса
print(struct.pack(">d", 0.1).hex())  # 3fb999999999999a
print(repr(0.1 + 0.2))          # 0.30000000000000004
print(0.1 + 0.2 == 0.3)         # False
print((0.1 + 0.2) - 0.3)        # 5.551115123125783e-17
```

Ошибка `5.55e-17` — это примерно `2⁻⁵⁴`, половина шага сетки в районе 0.3. Она не «баг Python»: тот же результат дадут C, Go, JavaScript и калькулятор с двоичной арифметикой. `float32` ошибается заметнее:

```python
import struct
print(struct.unpack("<f", struct.pack("<f", 0.1))[0])  # 0.10000000149011612
```

Практические правила. Деньги считать в целых минимальных единицах (копейки, центы) или в `decimal.Decimal`; `Decimal("0.1") + Decimal("0.2")` даёт ровно `0.3`, но `Decimal(0.1)` — уже нет, потому что во `Decimal` попадёт двоичное приближение. Вещественные числа сравнивать с допуском: `math.isclose(a, b, rel_tol=1e-9)`. Никогда не проверять `if x == 0.0` после серии вычитаний — вместо нуля получится `1e-17`, а деление на него даст бесконечность. И помнить, что `float` не хранит `NaN`-семантику по правилам сравнения: `nan != nan` — это `True`.

## Кодировки: от ASCII до UTF-8

### ASCII и однобайтовые кодировки

ASCII (1963) закрепляет 128 кодов: управляющие символы `0x00–0x1F`, цифры `0x30–0x39`, заглавные латинские буквы `0x41–0x5A`, строчные `0x61–0x7A`. Семь бит, старший бит свободен — и именно это обстоятельство позже породило хаос: разные страны использовали освободившиеся 128 кодов под свои алфавиты. Так появились Windows-1251 (кириллица), KOI8-R, ISO-8859-1 (latin-1), CP866. Все они однобайтовые: один символ — один байт, `256` возможных символов.

Проблема не в самих кодировках, а в том, что байт не говорит, какой алфавит применять. Файл `cf f0 e8 e2 e5 f2` — это `Привет` в cp1251 и мусор в UTF-8. Пока весь мир писал внутри одной страны, это работало; с появлением веба любой текст мог прийти в любой кодировке, и угадывание превратилось в отдельную индустрию.

```python
s = "Привет"
print(len(s), s.encode("utf-8")[:6].hex(" "))   # 6 d0 9f d1 80 d0 b8
print(len(s.encode("cp1251")), s.encode("cp1251").hex(" "))  # 6 cf f0 e8 e2 e5 f2
```

Обратите внимание: `len(s) == 6` — это шесть символов, а в UTF-8 получается 12 байт. Строка и её байтовое представление — разные вещи, и путаница между ними даёт баги в валидации длины полей и в обрезке сообщений.

### Как устроен UTF-8

UTF-8 кодирует кодовые точки Unicode последовательностями от 1 до 4 байт по строгой схеме: ведущие биты первого байта говорят, сколько байт в последовательности, а каждый следующий байт начинается с `10`.

| Диапазон кода | Байт | Первый байт | Остальные |
|---|---|---|---|
| U+0000–U+007F | 1 | `0xxxxxxx` | — |
| U+0080–U+07FF | 2 | `110xxxxx` | `10xxxxxx` |
| U+0800–U+FFFF | 3 | `1110xxxx` | 2 × `10xxxxxx` |
| U+10000–U+10FFFF | 4 | `11110xxx` | 3 × `10xxxxxx` |

Взгляните на байты `Привет`: `d0 9f` — это `П`. `d0` = `11010000`, значит, два байта, полезных бит пять: `10000`. `9f` = `10011111`, шесть бит: `011111`. Склеиваем: `10000 011111` = `0x041F` = U+041F — заглавная «П». Проверим на настоящем вызове:

```python
raw = "Привет".encode()
print(raw.hex(" "))              # d0 9f d1 80 d0 b8 d0 b2 d0 b5 d1 82
print(raw[:2].hex(" "))          # d0 9f
print(int("10000" + "011111", 2))  # 1055 = 0x41F
print(chr(0x41F))                # П
print("🚀".encode().hex(" "))     # f0 9f 9a 80 — четыре байта
```

Схема даёт три свойства, которых не было ни у одной однобайтовой кодировки. Первое: ASCII — подмножество UTF-8, поэтому старые протоколы, regex и `grep` по латинице работают без изменений. Второе: самосинхронизация — по любому байту можно определить, начало это символа или продолжение (`10xxxxxx` — продолжение), поэтому потерю одного байта в потоке можно обнаружить и восстановиться на следующем символе. Третье: отсутствие `0x00` внутри многобайтовых последовательностей, поэтому UTF-8 безопасен в C-строках с нулевым терминатором. Именно эти свойства, а не чья-то политическая воля, сделали UTF-8 стандартом де-факто: по разным оценкам, более 98% веб-страниц сегодня в UTF-8.

### Ловушки текста

Первая — обрезка по байтам. `"Привет".encode()[:5]` даёт `b'\xd0\x9f\xd1\x80\xd0'` — последний символ разрезан, и `decode()` выбросит `UnicodeDecodeError`. Правильно резать строку по символам, а если нужна длина в байтах — считать `len(s.encode())`, а не `len(s)`.

Вторая — «кракозябры» (mojibake): байты UTF-8, прочитанные как cp1251. `"Привет".encode("utf-8").decode("cp1251")` возвращает `ÐŸÑ€Ð¸Ð²ÐµÑ‚` — узнаваемый признак того, что где-то в цепочке «БД → бэкенд → HTTP → шаблон» потеряли кодировку или дважды её применили.

Третья — нормализация Unicode. Символ `й` существует в двух формах: одна кодовая точка U+0439 и композиция `и` + U+0306 (комбинирующая бревис). Визуально идентичны, при сравнении — разные строки, `len()` даёт 1 и 2. Решение: `unicodedata.normalize("NFC", s)` перед сравнением, сохранением в ключ или поиском.

Четвёртая — BOM. В UTF-8 маркер `EF BB BF` не нужен, но некоторые редакторы его пишут; в начале файла он превращается в невидимый символ U+FEFF и ломает парсинг YAML, JSON и shell-скриптов (`#!/bin/bash` с BOM не исполняется). В UTF-16 BOM обязателен и задаёт порядок байтов.

## Типичные ошибки

1. **Считать деньги во `float`.** Двоичная дробь не представляет 0.1 точно, ошибки накапливаются при каждом сложении, и на тысяче операций сумма расходится с бухгалтерской на копейки. Помогает переход на целые минимальные единицы или `Decimal` с явным контекстом округления.

2. **Сравнивать вещественные числа на равенство.** `0.1 + 0.2 == 0.3` ложно из-за округления, а результат зависит от порядка операций и уровня оптимизации. Нужен допуск (`math.isclose`) или целочисленная арифметика.

3. **Оценивать размер строки через `len(s)`.** В Python это число символов, в Go — байт, в C — байт до нуля. Валидация «не больше 255 символов» по разным метрикам даёт разные ответы для кириллицы и эмодзи, а лимит в БД обычно задан в байтах.

4. **Резать текст по байтам или по индексу байта.** Разрезанная многобайтовая последовательность не декодируется вовсе. Обрезка должна идти по границам символов (или графем, если важны эмодзи с модификаторами).

5. **Полагаться на «угадывание» кодировки.** Автодетект работает статистически и ошибается на коротких строках. Кодировку нужно фиксировать в протоколе (`Content-Type: text/html; charset=utf-8`), в схеме БД (`COLLATE`) и в настройках клиента.

6. **Игнорировать порядок байтов в бинарном протоколе.** `struct.pack("<I")` на x86 и чтение `>I` на другой стороне дают другое число, а не ошибку: молчаливое искажение данных опаснее падения.

7. **Путать переполнение и насыщение.** При переполнении счётчика запросов `int32` значение уходит в минус и алерт «превышен порог» перестаёт срабатывать. Счётчики и таймеры надо держать в 64 битах и уметь насыщать, а не заворачивать.

## Чек-лист

- Деньги и любые точные дробные величины хранятся в целых единицах или `Decimal`; в схеме БД тип `NUMERIC`, а не `FLOAT`?
- Все сравнения вещественных чисел идут через допуск, а не через `==`?
- В бинарных протоколах порядок байтов указан явно и одинаков на обеих сторонах?
- Кодировка задана в каждом звене: HTTP-заголовок, `Content-Type` письма, схема БД, `LANG`/`LC_ALL` в контейнере?
- Валидация длины строки считает байты, а не символы (или наоборот — осознанно)?
- Обрезка текста выполняется по границам символов, а не по индексам байтов?
- Строки перед сравнением нормализуются (`NFC`), если они приходят из разных источников?
- Текстовые файлы сохраняются без BOM, а чтение конфигов устойчиво к BOM на случай чужого редактора?
