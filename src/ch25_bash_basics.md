# Глава 25. Шелл: переменные, кавычки, подстановки

Шелл (shell) — это программа, которая читает строки, разбирает их на слова и запускает другие программы. Всё остальное — переменные, кавычки, подстановки — обслуживает этот единственный цикл. Большинство «загадочных» багов в скриптах автоматизации сводится к тому, что автор представляет себе строку как текст, а шелл видит в ней набор токенов, которые он обрабатывает в строго определённом порядке. В этой главе мы разберём этот порядок: как шелл хранит переменные, чем окружение процесса отличается от переменных оболочки, как работают три вида кавычек и почему отсутствие кавычек ломает скрипт на файле с пробелом. После главы вы сможете читать чужой скрипт и заранее говорить, что он сделает с конкретным именем файла.

## Что такое шелл и чем bash отличается от sh

Шелл — интерпретатор с очень маленьким языком: присваивание, подстановки, условные конструкции, циклы, функции, конвейеры. Никаких типов, классов и сборщика мусора здесь нет, зато есть прямая связь с ядром через системные вызовы `fork`, `execve`, `pipe`, `wait`. Когда вы пишете `ls -l /tmp`, шелл делает `fork`, в дочернем процессе ищет `ls` в `PATH` и вызывает `execve`. Родительский процесс ждёт завершения и получает код возврата — целое число от 0 до 255, о котором подробно пойдёт речь в следующей главе.

`sh` — это не «старый bash», а имя POSIX-совместимой оболочки. В Debian, Ubuntu и производных `/bin/sh` — символическая ссылка на `dash`, в Alpine — на `busybox ash`, в RHEL-семействе исторически на `bash` в режиме совместимости. Отсюда главное практическое правило: если в первой строке скрипта написано `#!/bin/sh`, скрипт обязан быть переносимым и не использовать расширения bash. В `dash` нет `[[ ]]`, нет массивов, нет `${var//a/b}`, нет `<<<`, нет `function`, нет `source` (вместо неё — `.`), нет `set -o pipefail`. Скрипт, который прекрасно работал у вас, на сервере с `dash` упадёт на первой же строке с `[[`.

| Возможность | POSIX sh (dash) | bash 5.x |
|---|---|---|
| `[[ ... ]]`, регулярные выражения | нет | да |
| Массивы, ассоциативные массивы | нет | да |
| `${var//шаблон/замена}` | нет | да |
| `set -o pipefail` | нет | да |
| `local` в функциях | да (не POSIX, но есть) | да |
| `$(...)`, `${var:-default}` | да | да |

Правило: для Linux-сервера берите `#!/usr/bin/env bash`, для initramfs и Alpine-контейнеров держитесь POSIX и проверяйте запуском под `dash`.

## Переменные: оболочка и окружение

Присваивание в bash не содержит пробелов вокруг `=`:

```bash
RELEASE="2026.10"
BUILD=42
```

`RELEASE = "2026.10"` с пробелами — это не присваивание, а попытка запустить команду с именем `RELEASE` и аргументами `=` и `2026.10`. Шелл честно ответит `RELEASE: command not found`. Это первая ошибка, которую делает каждый.

Переменная, созданная присваиванием, существует только в текущей оболочке. Чтобы она попала в окружение (environment) дочерних процессов, её нужно экспортировать:

```bash
export RELEASE
export RELEASE="2026.10"   # экспорт и присваивание одной строкой
```

Разница принципиальная. Окружение — это массив строк вида `KEY=value`, который ядро передаёт в `execve` и который новый процесс получает в `environ`. Переменные, не помеченные на экспорт, в этот массив не попадают, и дочерний процесс о них не знает. Проверить, что видит конкретная команда, можно так:

```bash
$ APP_ENV=staging bash -c 'echo "env=$APP_ENV"'
env=staging
$ APP_ENV=staging
$ bash -c 'echo "env=$APP_ENV"'
env=
```

В первом случае присваивание стоит перед командой и действует только на время её выполнения, при этом переменная автоматически экспортируется. Во втором — переменная осталась в текущей оболочке и в дочернюю не попала.

Посмотреть окружение — `env`, все переменные оболочки включая неэкспортированные — `set`. Удалить переменную — `unset NAME`, запретить изменение — `readonly NAME`.

`PATH` — обычная переменная окружения, список каталогов через двоеточие. Шелл перебирает их слева направо и запускает первый найденный файл, поэтому команда либо не находится (код 127), либо находится не та, что вы ждали. Bash кэширует поиск в хеш-таблице, сбросить кэш — `hash -r`.

Специальные переменные, которые шелл ведёт сам:

| Переменная | Значение |
|---|---|
| `$0` | имя скрипта или оболочки |
| `$#` | число позиционных параметров |
| `$@`, `$*` | все параметры (различаются в кавычках) |
| `$?` | код возврата последней команды |
| `$$` | PID текущей оболочки |
| `$!` | PID последнего фонового процесса |
| `$1`, `$2`, … | позиционные параметры |

## Кавычки: три режима и цена ошибки

Это ядро главы. У шелла есть три режима заключения текста, и они влияют на то, что произойдёт с содержимым до запуска команды.

**Без кавычек.** Результат подстановки проходит разбиение на слова (word splitting) по символам из `IFS`, а затем — подстановку имён файлов (globbing) по `*`, `?`, `[...]`. Пустая строка после разбиения исчезает вовсе: аргумент не передаётся.

**Двойные кавычки `"..."`.** Внутри работают `$`, `` ` ``, `\` и `!` (в интерактивном режиме), но нет разбиения на слова и нет globbing. Это режим по умолчанию для любой переменной, которую вы подставляете в команду.

**Одинарные кавычки `'...'`.** Внутри не работает вообще ничего, кроме закрывающей кавычки. Идеальны для литералов: регулярных выражений, `awk`-программ, JSON.

Есть ещё `$'...'` — ANSI-C quoting, где работают escape-последовательности: `$'строка\nс переводом'`, `$'\t'`, `$'\x41'`. Это расширение bash, в `dash` его нет.

Практическое следствие: **подставляйте переменные в двойных кавычках всегда**, кроме случаев, когда вам осознанно нужно разбиение на слова. Сравните:

```bash
$ touch "report 2026.txt"
$ f="report 2026.txt"
$ ls $f
ls: cannot access 'report': No such file or directory
ls: cannot access '2026.txt': No such file or directory
$ ls "$f"
report 2026.txt
```

Во втором случае шелл получил два аргумента вместо одного. Команда `ls` не виновата — она получила ровно то, что ей передали.

## Подстановки: $(), ${}, арифметика

**Подстановка команд.** `$(команда)` заменяется на stdout команды с удалёнными завершающими переводами строк. Обратные кавычки делают то же, но не вкладываются без экранирования — используйте `$()`.

```bash
$ now=$(date +%F)
$ echo "Сегодня $now, файлов в /etc: $(find /etc -maxdepth 1 -type f | wc -l)"
Сегодня 2026-10-29, файлов в /etc: 81
```

Внутри `$()` можно писать любой конвейер, включая кавычки и вложенные подстановки.

**Подстановка параметров** — способ задать значение по умолчанию, обрезать путь, заменить подстроку, не вызывая внешних программ:

```bash
$ unset PORT
$ echo "${PORT:-8080}"
8080
$ echo "после: '${PORT:-}'"
после: ''
$ : "${PORT:=8080}"
$ echo "$PORT"
8080
$ file="/var/log/nginx/access.log.1"
$ echo "${file%/*}  ${file##*/}  ${file%.*}  ${file%%.*}"
/var/log/nginx  access.log.1  /var/log/nginx/access.log  /var/log/nginx/access
```

Ключевые формы:

| Форма | Смысл |
|---|---|
| `${v:-x}` | значение `v`, а если пусто — `x` (не присваивает) |
| `${v:=x}` | то же, но присваивает `v` |
| `${v:?сообщение}` | ошибка и выход, если `v` пусто |
| `${v:+x}` | `x`, только если `v` непусто |
| `${#v}` | длина строки |
| `${v#шаблон}`, `${v##шаблон}` | срезать кратчайший/длиннейший префикс |
| `${v%шаблон}`, `${v%%шаблон}` | срезать кратчайший/длиннейший суффикс |
| `${v/шаблон/замена}`, `${v//шаблон/замена}` | первое/все вхождения |
| `${v:смещение:длина}` | подстрока |
| `${!имя}` | значение переменной, имя которой лежит в `имя` |

`${v:?}` — самый недооценённый инструмент. Вместо того чтобы через двадцать строк упасть на пустом пути и удалить не тот каталог, вы падаете сразу и с внятным сообщением:

```bash
: "${BACKUP_DIR:?BACKUP_DIR не задан}"
```

**Арифметика.** `$(( выражение ))` считает в целых числах со знаком, 64 бита, с C-подобным синтаксисом. Деление — целочисленное, с усечением к нулю: `$(( 17 / 5 ))` даёт `3`, `$(( -17 / 5 ))` даёт `-3`. Дробных чисел в bash нет; для них нужен `awk`, `bc` или python.

```bash
$ n=17; m=5
$ echo "частное $(( n / m )), остаток $(( n % m ))"
частное 3, остаток 2
$ (( n > m )) && echo "n больше m"
n больше m
```

Конструкция `(( выражение ))` без `$` возвращает код 0, если результат не ноль, и 1, если ноль — именно поэтому она удобна как условие.

## IFS и разбиение на слова

`IFS` (Internal Field Separator) — переменная, по символам которой шелл режет результат подстановки. По умолчанию это пробел, табуляция и перевод строки. Разбиение применяется **только** к неэкранированным подстановкам: `$var`, `$(...)`, `$((...))`. Литеральный текст в командной строке не разбивается — он уже разбит парсером.

Отсюда два следствия.

Первое: `for x in $(cat list.txt)` — плохая конструкция. Она разобьёт строки по пробелам, а не по строкам, и выполнит globbing для каждого слова. Правильно — `while IFS= read -r line; do ...; done < list.txt`. `IFS=` отключает обрезку ведущих и хвостовых пробелов, `-r` запрещает интерпретацию обратных слэшей.

Второе: если вы меняете `IFS` для своих нужд, делайте это локально для команды или сохраняйте старое значение. `IFS=,` на всю оболочку ломает разбор `$@` и всё, что ниже.

Отключить globbing для фрагмента можно через `set -f` (вернуть — `set +f`); это нужно, когда имена приходят из данных и содержат `*` или `?`.

## Массивы

Индексированный массив объявляется скобками, элементы разделяются пробелами:

```bash
$ hosts=(web-01 "web 02" db-01)
$ echo "${#hosts[@]} элемента, первый ${hosts[0]}"
3 элемента, первый web-01
$ hosts+=(cache-01)
$ printf '<%s>\n' "${hosts[@]}"
<web-01>
<web 02>
<db-01>
<cache-01>
```

`"${hosts[@]}"` разворачивается в отдельные слова с сохранением границ, `"${hosts[*]}"` — в одну строку, склеенную первым символом `IFS`. Разница та же, что между `"$@"` и `"$*"`. Обращение к несуществующему индексу при `set -u` — ошибка, поэтому для «может быть пусто» используйте `${hosts[0]:-}`.

Ассоциативные массивы (bash 4+) требуют `declare -A` — без него `arr[key]=value` молча создаст индексированный массив с индексом 0:

```bash
$ declare -A codes=([200]=ok [404]=missing [500]=error)
$ for k in "${!codes[@]}"; do echo "$k=${codes[$k]}"; done | sort
200=ok
404=missing
500=error
```

## shebang и PATH

Первая строка скрипта — `#!` плюс путь к интерпретатору. Это не комментарий: ядро читает эти байты и запускает указанную программу, передавая ей путь к скрипту как аргумент. Отсюда два варианта:

```bash
#!/bin/bash          # фиксированный путь, bash точно есть в системе
#!/usr/bin/env bash  # найти bash в PATH
```

`env`-вариант удобен, когда bash стоит в `/usr/local/bin`, но он же и опаснее: `PATH` может указать на другую версию, и скрипт с `declare -A` упадёт на bash 3.2 из системного каталога macOS. Для юнитов {{L|g115|systemd}} и cron надёжнее явный путь.

Скрипт должен быть исполняемым (`chmod +x`), иначе оболочка попробует выполнить его как текст и получит `Permission denied` (код 126). Запуск `bash script.sh` shebang игнорирует полностью — это частая причина «локально работает, в cron нет», если локально вы запускаете через `bash`, а cron — напрямую.

## Пример: почему пробел в имени файла ломает скрипт

Соберём минимальный полигон. В каталоге два файла с пробелами в именах:

```bash
$ mkdir -p /tmp/demo && cd /tmp/demo
$ printf 'alpha\nbeta\n' > "my report.txt"
$ printf 'gamma\n' > "my notes.txt"
$ ls -1
my notes.txt
my report.txt
```

Плохой вариант — «перебрать все txt через `ls`»:

```bash
for f in $(ls *.txt); do
    echo "== $f"
    wc -l $f
done
```

Реальный вывод:

```
== my
wc: my: No such file or directory
== notes.txt
wc: notes.txt: No such file or directory
== my
wc: my: No such file or directory
== report.txt
wc: report.txt: No such file or directory
```

Что произошло: `$(ls *.txt)` вернул строку `my notes.txt\nmy report.txt`; разбиение по `IFS` разрезало её на четыре слова; цикл получил четыре итерации; `wc` получил по одному неверному аргументу. Скрипт не сообщил об ошибке внятно, а код возврата цикла — 0, потому что последняя команда `echo` успешна.

Правильный вариант:

```bash
for f in *.txt; do
    printf '== %s\n' "$f"
    wc -l < "$f"
done
```

```
== my notes.txt
1
== my report.txt
2
```

Здесь `*.txt` разворачивает сам шелл (globbing), каждое имя остаётся одним словом, а `"$f"` защищает его от повторного разбиения. Редирект `< "$f"` избавляет от вывода имени файла в `wc`.

Для имён из `find` используйте NUL как разделитель: `find ... -print0` и `read -r -d ''` — NUL не может встретиться в имени файла, это единственный полностью надёжный способ передать произвольный список.

## Типичные ошибки

1. **Отсутствие кавычек вокруг переменной.** Механизм: результат подстановки проходит word splitting и globbing. Имя с пробелом превращается в несколько аргументов, имя с `*` — в список файлов. Лечится `"$var"` везде, где разбиение не нужно осознанно.
2. **`var = value` с пробелами.** Механизм: парсер видит команду `var` с аргументами, а не присваивание. Bash печатает `command not found`, а в скрипте с `set -e` просто завершается.
3. **Расчёт на `export` по умолчанию.** Механизм: дочерний процесс получает только то, что попало в `environ`. Переменная, заданная без `export`, невидима для `kubectl`, `envsubst` и любого скрипта, вызванного из вашего.
4. **`for i in $(cat file)`.** Механизм: разбиение идёт по `IFS`, а не по строкам, плюс globbing. Строки с пробелами и `*` обрабатываются неверно. Лечится `while IFS= read -r`.
5. **`sh` вместо `bash` при bash-синтаксисе.** Механизм: `/bin/sh` — это `dash` или `ash`, где `[[ ]]` и массивов нет. Скрипт падает на разборе, иногда после частичного выполнения.
6. **`echo` для данных.** Механизм: `echo` по-разному трактует `-n`, `-e` и обратные слэши в разных реализациях. Для предсказуемого вывода используйте `printf`.
7. **Сравнение чисел как строк.** Механизм: `[ "$a" \> "$b" ]` сравнивает лексикографически, поэтому `10` меньше `9`. Для чисел — `(( a > b ))` или `[ "$a" -gt "$b" ]`.

## Чек-лист

- Все подстановки переменных в командах заключены в двойные кавычки, кроме мест, где разбиение нужно намеренно.
- В первой строке указан интерпретатор, и он соответствует синтаксису: `#!/usr/bin/env bash` для bash-конструкций, `#!/bin/sh` только для POSIX.
- Обязательные переменные проверены через `${VAR:?сообщение}` или явный `if [ -z ... ]`.
- Для обхода файлов используется glob или `find -print0`, а не `$(ls)` и не `$(find)`.
- Для чтения строк из файла — `while IFS= read -r line`, для списков в массиве — `"${arr[@]}"`.
- Для вывода данных используется `printf`, а не `echo` с флагами.
- Арифметика выполняется через `$(( ))` или `(( ))`, а не через `expr` и не строковыми сравнениями.
- Скрипт прогнан `shellcheck` и запущен под тем интерпретатором, который указан в shebang.

## Упражнения

1. Напишите скрипт, который принимает путь к файлу и печатает имя каталога, имя файла без расширения и расширение, используя только подстановки параметров (`${var%...}`, `${var##...}`) без вызова `basename` и `dirname`. Проверьте на путях без слэшей и без расширения.
2. Есть файл со списком хостов, по одному в строке, некоторые строки содержат пробелы и символ `*`. Напишите цикл, который печатает каждый хост в угловых скобках, не интерпретируя содержимое. Объясните, почему вариант с `for h in $(cat hosts)` даёт другой результат.
3. Объявите индексированный массив из пяти элементов, добавьте шестой через `+=`, выведите количество и все элементы по одному на строку. Затем сделайте то же для ассоциативного массива «код HTTP → описание».
4. Напишите функцию `die`, которая печатает сообщение в stderr и завершает скрипт с заданным кодом, используя `${2:-1}` как значение по умолчанию. Примените её для проверки двух обязательных переменных окружения.
5. Возьмите любой свой скрипт, где есть `$(ls ...)` или неквотированные переменные, и перепишите его так, чтобы он корректно работал в каталоге с именами вида `a b.txt`, `*star`, `-n`. Проверьте `shellcheck` до и после.
