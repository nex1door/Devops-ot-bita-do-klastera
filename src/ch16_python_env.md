# Глава 16. Python: окружение

Половина проблем «у меня не работает, а у тебя работает» решается не кодом, а окружением. Разные версии интерпретатора, глобально установленные пакеты, забытый `pip install`, конфликт зависимостей двух проектов на одной машине — всё это исчезает, когда окружение описано файлами и воспроизводится одной командой. В этой главе — что такое CPython и байткод, зачем нужен GIL (и чего он не делает), как устроен `venv`, чем отличаются pip, uv и poetry, как выглядит современный `pyproject.toml`, зачем нужен src-layout, как обращаться с переменными окружения и как добиться воспроизводимых сборок. Актуальная ветка на момент написания — Python 3.14 (3.14.0 вышла 7 октября 2025, последний патч 3.14.8 — 30 сентября 2026).

## Интерпретатор и байткод

CPython — эталонная реализация Python на C. Она не исполняет текст программы напрямую: при импорте модуль компилируется в **байткод** (bytecode) — компактные инструкции для виртуальной машины CPython, и результат складывается в `__pycache__/module.cpython-314.pyc`. Байткод кэшируется и переиспользуется, пока не изменится исходник или версия интерпретатора.

Посмотреть, во что превращается код, можно модулем `dis`:

```bash
python3 -c "import dis; dis.dis('sum(x * 2 for x in range(3))')"
```

```text
  0 RESUME                   0
  2 LOAD_GLOBAL              1 (NULL + sum)
 12 LOAD_CONST               0 (<code object <genexpr> ...>)
 14 MAKE_FUNCTION            0
 16 LOAD_GLOBAL              3 (NULL + range)
 28 LOAD_CONST               1 (3)
 30 CALL                     1
 32 GET_ITER
 34 CALL                     1
 36 RETURN_VALUE
```

Байткод — не машинный код и не «полукомпиляция для скорости»: он нужен для переносимости и быстрого старта. Виртуальная машина читает инструкции, работает со стеком значений и обращается к объектам Python. Отсюда две вещи, важные на практике.

Первая: `.pyc` — кэш, а не артефакт. Его не коммитят, не переносят между версиями и спокойно удаляют; при следующем импорте он создастся заново. Второе: байткод привязан к минорной версии интерпретатора — файл от 3.13 не подхватится на 3.14, что видно по имени `cpython-314`.

Python 3.14 принёс изменения, заметные и в рантайме: t-strings (шаблонные строки, PEP 750), отложенное вычисление аннотаций (PEP 649/749) и субинтерпретаторы в стандартной библиотеке. Первое меняет работу с шаблонами, второе — импорт модулей с аннотациями, третье открывает путь к параллелизму без GIL. Для окружения важно другое: **версия интерпретатора — часть контракта проекта**, и её надо фиксировать так же, как зависимости.

## GIL в двух словах

GIL (Global Interpreter Lock) — мьютекс, который позволяет исполнять байткод только одному потоку одновременно. Даже на 16 ядрах восемь потоков Python не ускорят вычисление в восемь раз: они будут по очереди захватывать GIL.

Зачем он нужен: управление памятью в CPython — подсчёт ссылок. Каждое присваивание меняет счётчик объекта, и без глобальной блокировки два потока могли бы одновременно испортить счётчик и освободить живую память. GIL — грубое, но дешёвое решение этой проблемы.

Что важно понимать:

- GIL не мешает вводу-выводу. Пока поток ждёт сеть или диск, он отпускает GIL, и другие потоки работают. Поэтому `ThreadPoolExecutor` для сотни HTTP-запросов даёт реальное ускорение.
- GIL мешает CPU-bound задачам. Парсинг, сжатие, численные расчёты в потоках не ускоряются; нужны процессы (`multiprocessing`, `ProcessPoolExecutor`) или код на C/Rust, отпускающий GIL.
- Экспериментальная сборка без GIL (PEP 703) появилась в Python 3.13 и на момент написания не является вариантом по умолчанию: у неё своя цена по памяти и скорости однопоточного кода. Планировать архитектуру «GIL скоро исчезнет» пока рано.

## venv: зачем нужно виртуальное окружение

Пакеты, установленные глобально, лежат в одном каталоге `site-packages` и доступны всем проектам сразу. Два проекта, которым нужны разные версии одной библиотеки, в такой схеме несовместимы: обновив зависимость для одного, вы сломали другой. Плюс глобальная установка на системный Python в Linux конфликтует с пакетами дистрибутива.

`venv` решает это копированием структуры: создаётся каталог с собственным интерпретатором (симлинком или копией), собственным `site-packages` и скриптами активации.

```bash
python3.14 -m venv .venv
source .venv/bin/activate
python -V
which python
```

```text
Python 3.14.8
/home/nextdoor/project/.venv/bin/python
```

Активация — это всего лишь правка `PATH`: каталог `.venv/bin` ставится первым, поэтому `python` и `pip` резолвятся в окружение. Никакой магии и никакой изоляции процессов: если запустить `/usr/bin/python3`, он увидит системные пакеты.

Отсюда правило, которое экономит часы отладки: **не полагайтесь на активацию в скриптах и CI**. Вызывайте интерпретатор по пути или через `uv run` / `poetry run`. Активация удобна интерактивно, но в cron, systemd-юните и CI её нет, и `python` там окажется системным.

`--system-site-packages` при создании позволяет видеть глобальные пакеты — иногда нужно для доступа к собранным из дистрибутива библиотекам, но ломает изоляцию. `--upgrade-deps` обновляет `pip` и `setuptools` внутри окружения сразу после создания.

## pip, uv, poetry

| Инструмент | Что делает | Скорость установки | Lock-файл | Мнение |
|---|---|---|---|---|
| pip | ставит пакеты по требованиям | базовая | нет (нужен pip-tools) | минимализм |
| uv | ставит, разрешает, собирает, запускает | очень высокая | `uv.lock` | быстрый, один бинарь |
| poetry | управление проектом и зависимостями | средняя | `poetry.lock` | своя экосистема |
| pip-tools | компилирует requirements | средняя | `requirements.txt` с пинами | привычный формат |

`pip` — стандарт де-факто и всегда доступен, но он не умеет разрешать зависимости в воспроизводимый набор: `pip install requests` поставит то, что актуально сегодня, и через месяц набор будет другим. Для фиксации используют `pip freeze > requirements.txt` или `pip-compile` из pip-tools.

`uv` написан на Rust и на момент написания заметно быстрее pip на холодной установке: он кэширует колеса, параллелит загрузку и разрешает зависимости целиком, а не пошагово. Он же умеет ставить нужную версию Python (`uv python install 3.14`), что снимает половину проблем с «а у меня 3.11».

`poetry` исторически дал первое удобное управление проектом: `pyproject.toml`, {{L|g67|lock-файл}}, виртуальное окружение, публикация. Он остаётся разумным выбором для библиотек, но его разрешение зависимостей медленнее, а собственная схема `pyproject.toml` (`[tool.poetry]`) отличается от стандарта PEP 621.

Практический выбор для нового проекта: `uv` для приложений и сервисов, `poetry` или `uv` для библиотек, `pip` — когда нужен только стандартный инструмент (например, в минимальном Docker-образе).

## requirements.txt и pyproject.toml

`requirements.txt` — плоский список требований, по одному на строку, с необязательными маркерами окружения:

```text
httpx==0.28.1
uvicorn[standard]>=0.34,<0.40
pydantic==2.11.3 ; python_version >= "3.10"
```

`pyproject.toml` — стандартизованный файл конфигурации проекта (PEP 518/621). Он описывает метаданные, зависимости, точки входа и настройки инструментов в одном месте:

```toml
[project]
name = "tasks-api"
version = "0.3.0"
requires-python = ">=3.12"
dependencies = ["httpx>=0.28,<1.0", "pydantic>=2.11,<3.0"]

[project.optional-dependencies]
postgres = ["asyncpg>=0.30"]

[dependency-groups]
dev = ["pytest>=8.3", "ruff>=0.11", "mypy>=1.15"]
```

Разница принципиальная. `requirements.txt` описывает **что установить в это окружение**; `pyproject.toml` — **что представляет собой проект** и от чего он зависит. Из `pyproject.toml` генерируется lock-файл с точными версиями, а `requirements.txt` в старых проектах играет роль и того, и другого одновременно, что и порождает путаницу.

Два разных набора зависимостей стоит держать раздельно: `dependencies` — то, без чего пакет не работает (нужно пользователям), `dev` — тесты, линтеры, отладчики (не нужно). Группы разработки описаны в PEP 735 (`[dependency-groups]`), extras — в `[project.optional-dependencies]`.

## Структура проекта: src-layout

```text
tasks-api/
├── pyproject.toml
├── uv.lock
├── README.md
├── .python-version
├── src/
│   └── tasks_api/
│       ├── __init__.py
│       ├── __main__.py
│       ├── api.py
│       └── storage.py
└── tests/
    ├── conftest.py
    └── test_api.py
```

Пакет лежит в `src/`, а не рядом с `pyproject.toml`. Причина не в эстетике: если пакет в корне, то `import tasks_api` в тестах находит каталог по текущей директории, а не установленный пакет. Тесты начинают проходить на неработающей конфигурации упаковки, а ошибки `package_data`, `include` и точек входа обнаруживаются только после публикации.

С `src`-layout импорт возможен только после установки (`uv sync`, `pip install -e .`), и это сразу проверяет, что метаданные корректны. Установка в редактируемом режиме (`-e`, editable) создаёт ссылку на исходники: правки видны без переустановки, но сама установка нужна.

`__main__.py` даёт `python -m tasks_api`, а `[project.scripts]` — консольную команду:

```toml
[project.scripts]
tasks-api = "tasks_api.__main__:main"
```

После установки в `PATH` окружения появляется `tasks-api`, которая вызывает `main()`.

## Переменные окружения и .env

Конфигурация, которая меняется между средами (адреса баз, ключи, уровни логов), не должна лежать в коде. Принцип из «12-factor»: конфигурация — в переменных окружения.

```python
import os

DATABASE_URL = os.environ["DATABASE_URL"]          # упадёт, если нет — и это хорошо
LOG_LEVEL = os.environ.get("LOG_LEVEL", "info")    # дефолт для необязательного
DEBUG = os.environ.get("DEBUG", "0") == "1"
```

`os.environ[...]` без дефолта — сознательный выбор: отсутствие обязательной настройки должно ломать старт сразу, а не через час в проде. Обязательно приводите типы: всё, что пришло из окружения, — строка, и `DEBUG="false"` в `bool()` даст `True`.

Локально удобно держать `.env` рядом с проектом и загружать его библиотекой `python-dotenv` или встроенной поддержкой фреймворка. Файл **никогда не коммитится**: в репозиторий идёт `.env.example` с именами переменных и без значений. Иначе ключи утекают в историю git, а оттуда — в форки и сканеры.

Ещё одно правило: не подмешивайте `.env` в продакшн. Там переменные приходят от оркестратора или секрет-хранилища, и лишний файл создаёт неопределённость «какое значение победило».

## Воспроизводимость

Воспроизводимость — свойство, при котором установка из репозитория через год даёт тот же набор пакетов. Достигается тремя вещами.

**Пины версий.** `httpx>=0.28` — диапазон, `httpx==0.28.1` — точная версия. В lock-файле пины есть всегда, включая транзитивные зависимости; в `pyproject.toml` — только диапазоны для прямых.

**Фиксация версии Python.** Файл `.python-version` (его читают uv, pyenv, asdf) и `requires-python` в `pyproject.toml`. Первое выбирает интерпретатор, второе запрещает установку на неподходящей версии.

**Хеши и запрет неявных обновлений.** `pip install --require-hashes -r requirements.txt` откажется ставить пакет, хеш которого не совпал, — защита от подмены на зеркале. `uv sync --frozen` не будет обновлять lock при расхождении, а упадёт.

```bash
uv sync --frozen    # поставить всё строго по uv.lock
uv add httpx        # добавить зависимость, обновить pyproject.toml и uv.lock
uv run pytest -q    # выполнить команду в окружении проекта
uv lock             # пересчитать lock
```

Эквивалент на чистом pip:

```bash
python3.14 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install -e ".[dev]"
.venv/bin/pip freeze > requirements.lock.txt
```

Разница в поведении: `pip freeze` фиксирует то, что реально стоит, включая случайные транзитивные версии; `uv lock`/`poetry lock` разрешает зависимости детерминированно и хранит граф, поэтому обновление одной библиотеки не тянет за собой половину стека.

## Типичные ошибки

1. **Глобальная установка вместо venv.** `pip install` без активированного окружения кладёт пакеты в системный `site-packages` (или падает с `externally-managed-environment` на современных дистрибутивах). Механизм: окружение не создано, а pip резолвится в системный.
2. **Активация вместо явного интерпретатора.** В cron или CI `source .venv/bin/activate` не выполняется, и запускается системный Python. Механизм: активация — это только `PATH`, а не свойство каталога.
3. **`pip freeze` как источник зависимостей.** В lock попадают пакеты, стоявшие в окружении случайно, включая dev-инструменты и локальные сборки, а транзитивные версии зафиксированы без графа. Механизм: freeze снимает снимок диска, а не описание проекта.
4. **Пакет в корне репозитория.** `import tasks_api` работает из текущей директории, тесты проходят, а после `pip install` пакет не находится или не содержит данных. Механизм: текущая директория в `sys.path` маскирует ошибки упаковки.
5. **Секреты в `.env`, закоммиченном в git.** Утечка обнаруживается через месяцы, ключи приходится ротировать. Механизм: файл удобно коммитить «для примера», а `.gitignore` добавляют позже.
6. **`DEBUG="false"` вместо `0`.** Строка непустая, `bool("false")` — `True`, и прод работает в режиме отладки с трассировками в ответах. Механизм: переменные окружения всегда строки, приведение типов забыто.
7. **Незафиксированная версия Python.** Локально 3.14, в CI 3.11, синтаксис t-strings падает на этапе импорта. Механизм: версия интерпретатора не описана ни в одном файле проекта.

## Чек-лист

- [ ] Версия Python зафиксирована: `.python-version`, `requires-python`, версия в CI-образе.
- [ ] Окружение создаётся одной командой из чистого клона, без ручных шагов.
- [ ] Lock-файл в репозитории; CI ставит по нему, а не по диапазонам.
- [ ] Зависимости разделены: runtime и dev не смешаны в одном списке.
- [ ] Проект использует src-layout, установка проверяется `pip install -e .` в чистом окружении.
- [ ] Секреты не в git; есть `.env.example` с именами переменных.
- [ ] Обязательные переменные читаются без дефолта и падают на старте.
- [ ] `python -m build` или сборка колеса проходит без предупреждений об отсутствующих файлах.

## Упражнения

1. Создайте venv на Python 3.14, установите `httpx` и покажите через `sys.path` и `sys.prefix`, чем окружение отличается от системного интерпретатора.
2. Переведите проект с `requirements.txt` на `pyproject.toml` + lock: сравните набор транзитивных зависимостей до и после и объясните расхождения.
3. Разберите вывод `dis.dis` для функции с циклом и с генераторным выражением. Найдите, где создаётся объект-генератор.
4. Соберите колесо своего пакета, распакуйте его как zip и проверьте, что все нужные файлы внутри; найдите минимум одну ошибку упаковки, которую скрывал запуск из корня репозитория.
5. Настройте CI, который ставит зависимости по lock-файлу с `--frozen`, запускает тесты на двух версиях Python и падает при расхождении `pyproject.toml` и lock.
