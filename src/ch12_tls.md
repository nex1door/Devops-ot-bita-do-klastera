# Глава 12. TLS и сертификаты

TLS — слой, на котором держится вся современная сеть: без него нет ни HTTPS, ни {{L|g51|HTTP/2}}, ни {{L|g52|HTTP/3}}. При этом именно TLS даёт самую частую аварию в эксплуатации — истёкший сертификат, который никто не заметил. После этой главы вы сможете разобрать рукопожатие TLS 1.3 по шагам, объяснить, зачем нужны и симметричное, и асимметричное шифрование одновременно, прочитать цепочку доверия сертификата, выпустить и обновить сертификат через ACME, и диагностировать проблему через `openssl s_client` без обращения в поддержку.

## Три задачи TLS

TLS решает ровно три задачи и делает это одновременно. Конфиденциальность — трафик нельзя прочитать по дороге; её обеспечивает симметричное шифрование. Целостность — трафик нельзя незаметно изменить; за неё отвечает код аутентификации сообщения (AEAD). Аутентификация — клиент уверен, что говорит с тем сервером, чьё имя набрал; за это отвечает сертификат, подписанный удостоверяющим центром.

Без третьей задачи первые две бесполезны: шифрование с неизвестным собеседником защищает канал, который ведёт прямо к атакующему.

## Симметрика и асимметрика

Симметричное шифрование использует один ключ для шифрования и расшифровки. Оно быстрое — гигабайты в секунду на современном процессоре, особенно с AES-NI. Асимметричное использует пару ключей: открытый шифрует, закрытый расшифровывает (или наоборот, для подписи). Оно медленное — на порядки.

Поэтому TLS гибридный: асимметричная криптография применяется только на этапе рукопожатия, чтобы договориться о сессионном ключе, а дальше весь трафик идёт симметричным шифром. В TLS 1.3 обязательны AEAD-шифры: `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`. Первые два выигрывают на процессорах с AES-NI, третий — на мобильных без аппаратного ускорения AES.

Ключевой обмен в TLS 1.3 — только (EC)DHE, обычно X25519. Это даёт свойство прямой секретности (forward secrecy): компрометация долговременного ключа сервера не позволит расшифровать записанный ранее трафик, потому что сессионные ключи уже уничтожены.

## Рукопожатие TLS 1.3 по шагам

TLS 1.2 (RFC 5246) требовал двух round-trip до первых данных. TLS 1.3 (RFC 8446) уложился в один:

1. **ClientHello.** Клиент отправляет список поддерживаемых шифров, версий, расширение `server_name` (SNI), `alpn` и, главное, свой `key_share` — открытую часть для обмена ключами.
2. **ServerHello.** Сервер выбирает параметры и отправляет свой `key_share`. С этого момента обе стороны могут вычислить общий секрет.
3. Всё дальнейшее уже шифруется: `EncryptedExtensions` (в том числе выбранный ALPN), `Certificate`, `CertificateVerify` (подпись закрытым ключом сервера, доказывающая владение ключом), `Finished`.
4. Клиент проверяет цепочку и подпись, отправляет свой `Finished`. Соединение готово.

Один round-trip — потому что клиент угадывает группу для обмена ключей и присылает `key_share` заранее. Если угадал не ту, сервер пришлёт `HelloRetryRequest` и добавит ещё один round-trip.

Повторное подключение может уложиться в 0-RTT: клиент использует сохранённый тикет (PSK) и отправляет данные в первом же пакете. Ранние данные не защищены от повторного воспроизведения, поэтому в 0-RTT допустимы только идемпотентные запросы.

## Сертификат и цепочка доверия

Сертификат X.509 связывает имя (или имена) с открытым ключом и подписан издателем. Браузер не знает ваш сертификат; он знает корневые сертификаты удостоверяющих центров, вшитые в систему и браузер.

Цепочка выглядит так: корневой сертификат (root, в trust store) → промежуточный (intermediate) → ваш (leaf). Сервер обязан отдавать leaf и все промежуточные; корневой клиент найдёт сам. Самая частая ошибка конфигурации — отдать только leaf: браузеры с кэшем промежуточных иногда спасают, а `curl`, мобильные приложения и Java — нет.

Что проверяется: подпись каждого звена, срок действия (`notBefore`/`notAfter`), соответствие имени из `subjectAltName` запрошенному хосту, назначение ключа, отзыв. Поле `CN` устарело — современные клиенты смотрят только на SAN, и сертификат без SAN не будет принят.

Отзыв реализуется через CRL и OCSP; и то, и другое в последние годы вытесняется короткоживущими сертификатами и Certificate Transparency (CT) — публичными логами, куда CA обязаны записывать каждый выпущенный сертификат.

## SNI и ALPN

SNI (Server Name Indication) — расширение, в котором клиент передаёт имя хоста в открытом виде ещё до установки шифрования. Без него сервер не знает, какой из сотен сертификатов показать, и пришлось бы держать отдельный IP на каждый сайт. Имя в SNI не шифруется: провайдер видит, к какому сайту вы идёте, даже не видя содержимого. Расширение ECH (Encrypted Client Hello) призвано это закрыть, но на момент написания поддержано не везде.

ALPN (Application-Layer Protocol Negotiation) — согласование прикладного протокола внутри TLS: `h2`, `http/1.1`, `h3`. Именно поэтому HTTP/2 требует TLS: без ALPN клиент и сервер не договорятся о версии.

## ACME и Let's Encrypt

ACME (RFC 8555) автоматизирует выпуск: клиент доказывает контроль над доменом, получает сертификат и обновляет его сам. Let's Encrypt выдаёт короткоживущие сертификаты (90 дней на момент написания, с курсом на дальнейшее сокращение срока) — это вынуждает автоматизировать обновление, и это правильно.

Самый распространённый клиент — certbot. Проверка домена идёт по HTTP-01 (файл в `/.well-known/acme-challenge/`) или DNS-01 (TXT-запись, единственный вариант для wildcard-сертификатов).

```bash
sudo certbot --nginx -d example.com -d www.example.com --redirect
```

```
Requesting a certificate for example.com and www.example.com

Successfully received certificate.
Certificate is saved at: /etc/letsencrypt/live/example.com/fullchain.pem
Key is saved at:         /etc/letsencrypt/live/example.com/privkey.pem
This certificate expires on 2027-01-07.
These files will be updated when the certificate renews.
Certbot has set up a scheduled task to automatically renew this certificate.
```

`--redirect` добавляет редирект с HTTP на HTTPS. Обновление проверяется прогоном без реального выпуска:

```bash
sudo certbot renew --dry-run
```

```
Congratulations, all simulated renewals succeeded:
  /etc/letsencrypt/live/example.com/fullchain.pem (success)
```

`--dry-run` не трогает боевые файлы и ходит на staging-сервер ACME — именно поэтому его стоит ставить в CI раз в сутки, а не полагаться на «certbot же настроил таймер».

```bash
openssl s_client -connect example.com:443 -servername example.com </dev/null
```


Читать этот вывод нужно сверху вниз. Блок `depth=0/1/2` — цепочка, которую построил клиент: если depth=0 не совпадает с ожидаемым именем, вы попали на другой сервер (или SNI не передан). `Certificate chain` показывает, что отдал сервер: если там одно звено, промежуточный отсутствует — часть клиентов получит ошибку.

`Verification: OK` и `Verify return code: 0 (ok)` — цепочка и срок в порядке. `TLSv1.3` и имя шифра подтверждают современный стек. `No ALPN negotiated` — признак того, что клиент не просил протокол; с `-alpn h2` здесь появится `ALPN protocol: h2`.

Флаг `-servername` критичен при проверке виртуальных хостов: без него openssl возьмёт сертификат по умолчанию, и вы получите ложную ошибку несоответствия имени.

Быстрая проверка срока годности на сервере:

```bash
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -enddate
```

```
subject=CN = example.com
issuer=C = US, O = DigiCert Inc, CN = DigiCert TLS RSA SHA256 2020 CA1
notAfter=Jan  7 09:12:44 2027 GMT
```

## Что не так с TLS 1.2

TLS 1.2 (RFC 5246) работает до сих пор и всё ещё встречается в старых интеграциях, но его недостатки хорошо изучены. Рукопожатие требует двух round-trip, а не одного. Разрешён обмен ключами по RSA, когда сессионный ключ шифруется открытым ключом сервера: удобно, но нет прямой секретности — украденный закрытый ключ расшифровывает весь записанный ранее трафик.

Список шифров в 1.2 настраивается вручную и включает CBC-режимы, для которых годами находили атаки на паддинг (BEAST, Lucky13; POODLE была про SSL 3.0, но показала цену режимов с дополнением). Сжатие убрали после CRIME, пересогласование ограничили отдельным RFC.

TLS 1.3 убрал всё перечисленное: остались только AEAD-шифры, только (EC)DHE, нет сжатия, нет пересогласования, нет статических RSA-ключей в обмене. Поэтому правильная конфигурация на 2026 год — `TLSv1.3` и `TLSv1.2` с ограниченным набором AEAD-шифров; 1.0 и 1.1 отключены везде, где есть хоть какой-то аудит.

Проверить, что старые версии отключены, а не просто «не предлагаются браузером», можно явным указанием версии:

```bash
openssl s_client -connect example.com:443 -servername example.com -tls1_1 </dev/null
```

```
1407B7F505C77F0000:error:0A00018E:SSL routines::unsupported protocol
```

Ошибка `unsupported protocol` — правильный ответ. Если же в выводе появился `Protocol  : TLSv1.1` и `Cipher`, сервер принимает устаревший протокол, и это находка для аудита.

## HSTS и pinning

`Strict-Transport-Security` говорит браузеру, что к этому домену можно обращаться только по HTTPS, и подменять схему нельзя даже при явном `http://`.

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
```

`max-age` — сколько секунд браузер помнит правило. `includeSubDomains` распространяет его на поддомены, и это ловушка: если какой-то поддомен живёт только на HTTP, он станет недоступен. `preload` добавляет домен в список, вшитый в браузеры, и выйти из него можно месяцами. Включать `preload` стоит только после того, как все поддомены годами работают по HTTPS.

Certificate pinning — привязка к конкретному ключу или сертификату. В браузерах механизм HPKP провалился и удалён: ошибка в пине ломает сайт на месяцы. В мобильных приложениях и в межсервисном общении pinning применяется, но требует плана ротации: пин наleaf-сертификат гарантирует аварию при каждом обновлении, поэтому пинят промежуточный CA или пару ключей.

## Mutual TLS

В обычном TLS сертификат предъявляет только сервер. В mutual TLS (mTLS) сервер требует сертификат и от клиента: в рукопожатии появляется `CertificateRequest`, клиент присылает свой сертификат, сервер проверяет его против своего набора доверенных CA.

Применяется там, где нет пользователя с паролем: между сервисами в {{L|g104|service}} mesh (sidecar-прокси аутентифицируют друг друга), в B2B-интеграциях, для внутренних API. Проверить вручную можно так:

```bash
curl -sS --cert client.pem --key client.key https://internal.example.com/health
```

Без сертификата тот же запрос вернёт ошибку рукопожатия, а не 401: соединение не устанавливается вовсе, потому что клиент не прошёл аутентификацию на уровне TLS.

Главная проблема mTLS — жизненный цикл клиентских сертификатов: выпуск, ротация и отзыв ложатся на эксплуатацию. В Kubernetes это решают через cert-manager и SPIFFE, где сертификат живёт часы, а не годы. Ручной mTLS с годовыми сертификатами — почти гарантированная авария при первом истечении.

## Почему «сертификат истёк» — самая частая авария

Причины прозаичны. Автообновление настроено, но не проверено: certbot не смог пройти HTTP-01, потому что `.well-known` перехватывается редиректом или закрыт в WAF, и падал молча в логах, которые никто не читает. Сертификат выпущен вручную и положен в Docker-образ, а образ не пересобирался год. Или домен переехал за CDN, и обновляется сертификат CDN, а не ваш.

Симптомы различаются: браузер показывает страницу-заглушку с ошибкой `NET::ERR_CERT_DATE_INVALID`, `curl` пишет `SSL certificate has expired`, а Android может не показать ошибку вовсе, если приложение игнорирует проверку.

Лечится тремя вещами: мониторингом даты `notAfter` с алертами за 21, 14 и 7 дней; автоматическим обновлением с явным хуком перезагрузки (`--deploy-hook "systemctl reload nginx"`, потому что nginx держит сертификат в памяти и не перечитает файл сам); и проверкой результата — `curl` к своему же домену из внешней сети, а не только `systemctl status certbot`.

Проверка срока встраивается в CI и в cron одной командой:

```bash
end=$(openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
      | openssl x509 -noout -enddate | cut -d= -f2)
days=$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 ))
echo "days left: $days"
if [ "$days" -lt 21 ]; then exit 1; fi
```

```
days left: 71
```

Код возврата 1 при остатке меньше 21 дня — пайплайн краснеет, и дежурный узнаёт о проблеме за три недели, а не за три минуты.

## Типичные ошибки

1. **Отдавать только leaf-сертификат.** Часть клиентов (curl, Java, мобильные) не имеют кэша промежуточных и падает на проверке цепочки. Механизм: сервер обязан передать все звенья, кроме корневого.
2. **Сертификат без SAN.** Имя в `CN` современные клиенты игнорируют, и проверка хоста не проходит. Механизм: RFC 6125 и все браузеры требуют `subjectAltName`.
3. **`includeSubDomains` в HSTS при живом HTTP-поддомене.** Поддомен мгновенно становится недоступен для всех, кто уже получил заголовок. Механизм: браузер применяет политику до истечения `max-age` и не спрашивает сервер.
4. **Ручной выпуск и ручная установка.** Через 90 дней сертификат истекает, потому что человек помнит о нём ровно до следующего релиза. Механизм: короткий срок жизни требует автоматизации, а не дисциплины.
5. **Перезагрузка не выполнена после обновления.** Файлы на диске новые, nginx в памяти держит старые. Механизм: сертификат читается при старте воркеров; нужен reload по хуку.
6. **Часы сервера уехали.** Клиент видит `certificate is not yet valid` или просрочку на живом сертификате. Механизм: проверка срока идёт по локальным часам клиента, и дрейф в минуты уже критичен для короткоживущих сертификатов.
7. **Проверка «работает» только изнутри.** Внутренний curl идёт напрямую к origin, минуя CDN и WAF, и не видит, что наружу отдаётся другой сертификат.

## Чек-лист

- [ ] Сервер отдаёт полную цепочку, кроме корневого сертификата.
- [ ] В сертификате есть SAN со всеми используемыми именами.
- [ ] TLS 1.3 включён, TLS 1.0/1.1 отключены, слабые шифры запрещены.
- [ ] Автообновление работает, `--dry-run` проходит, `--deploy-hook` перезагружает nginx.
- [ ] Алерт на остаток срока (21/14/7 дней) идёт в дежурного, а не в общий чат.
- [ ] Внешняя проверка (`curl` снаружи) подтверждает сертификат на периметре, включая CDN.
- [ ] HSTS выставлен без `preload`, пока не проверены все поддомены.
- [ ] Время синхронизировано (NTP), дрейф контролируется.

## Упражнения

1. Разберите вывод `openssl s_client` для трёх сайтов и сравните: версия протокола, шифр, число звеньев цепочки, наличие ALPN.
2. Выпустите сертификат через `certbot --nginx` на тестовом домене, затем сломайте HTTP-01 (закройте `/.well-known` в конфиге) и добейтесь, чтобы `--dry-run` упал с понятной ошибкой.
3. Настройте мониторинг срока: скрипт вычисляет дни до `notAfter` и отдаёт метрику, алерт срабатывает на 21 день. Проверьте на сертификате с укороченным сроком.
4. Включите HSTS с `max-age=60` на тестовом домене, убедитесь, что HTTP-переход больше не происходит, и объясните, как откатить политику.
