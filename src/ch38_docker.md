# Глава 38. Docker: слои, Dockerfile, compose

Контейнер — это не «лёгкая виртуальная машина», а обычный процесс на хосте, которому ядро ограничило видимость и потребление ресурсов. Понимание этого факта снимает половину проблем эксплуатации: непонятные {{L|g79|OOMKilled}}, «данные пропали после перезапуска», «образ весит два гигабайта». В главе разбирается, как устроены образ и его слои, как писать {{L|g30|Dockerfile}}, который не тащит в прод компилятор, как хранить данные и как описать весь стек в compose. После главы вы сможете собрать образ меньше 100 МБ с {{L|g76|non-root}} пользователем и объяснить, почему правка одной строки обнулила кэш всей сборки.

## Контейнер и виртуальная машина

Виртуальная машина эмулирует железо: гипервизор даёт гостевой ОС собственное ядро, собственный планировщик, собственные драйверы. Контейнер ядро не получает — он использует ядро хоста и изолирован двумя механизмами Linux, которые появились задолго до Docker.

**Namespaces** ограничивают видимость. Каждому контейнеру выдаётся свой набор пространств имён: `pid` (своё дерево процессов, внутри контейнера приложение видит себя как PID 1), `net` (свой сетевой стек, свои интерфейсы и таблица маршрутов), `mnt` (своя точка монтирования корневой файловой системы), `uts` (своё имя хоста), `ipc` (свои очереди SysV и разделяемая память), `user` (свой диапазон UID, что позволяет root внутри быть nobody снаружи), `cgroup` (своё представление иерархии), `time` (смещение часов).

**cgroups** ограничивают потребление. Контроллеры `cpu`, `memory`, `io`, `pids` считают и режут ресурсы: сколько ядер доступно, сколько памяти можно занять до OOM-kill, какая пропускная способность диска, сколько процессов разрешено. В cgroup v2 всё это — единая иерархия файлов, где лимит памяти лежит в `memory.max`, а текущее потребление — в `memory.current`.

| Свойство | Виртуальная машина | Контейнер |
|---|---|---|
| Ядро | своё, гостевое | общее с хостом |
| Запуск | десятки секунд | доли секунды |
| Размер образа | гигабайты | десятки-сотни мегабайт |
| Изоляция | сильная (аппаратная) | процессная, слабее |
| Плотность на хосте | единицы | десятки-сотни |

Практическое следствие: контейнер не может иметь другое ядро, чем хост. Linux-контейнер на Windows или macOS работает внутри служебной виртуальной машины, которую Docker Desktop поднимает прозрачно, — и именно поэтому на macOS bind mount медленнее, чем на Linux.

## Образ и слои

Образ (image) — неизменяемый стек слоёв только для чтения плюс конфиг: переменные окружения, рабочая директория, команда запуска, порт. Слой — это tar-архив с разницей файловой системы относительно предыдущего слоя. Инструкции `RUN`, `COPY` и `ADD` создают по слою каждая; `FROM`, `ENV`, `WORKDIR`, `CMD`, `ENTRYPOINT`, `EXPOSE`, `USER` меняют только конфиг и места не занимают.

При запуске поверх стека монтируется тонкий записываемый слой через {{L|g81|overlayfs}}. Любая запись в файл из нижнего слоя не меняет его, а копирует файл наверх — механизм {{L|g20|copy-on-write}}. Отсюда два следствия: удаление файла в следующем слое не уменьшает образ (файл остаётся в нижнем слое), а записанные внутрь контейнера данные живут ровно до `docker rm`.

```bash
docker build -t shop-api:1.4.2 .
docker image ls shop-api
docker history --no-trunc shop-api:1.4.2 | head -20
```

`docker history` показывает размер каждого слоя — первое, что стоит смотреть, когда образ распух: строка `RUN apt-get install ...` на 400 МБ сразу объясняет, куда ушло место.

## Dockerfile: инструкции, которые важно понимать

Минимальный рабочий Dockerfile для Python-сервиса выглядит так:

```dockerfile
FROM python:3.14-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

WORKDIR /app

RUN groupadd --system --gid 1001 app \
 && useradd --system --uid 1001 --gid app --no-create-home app

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY --chown=app:app . .

USER app
EXPOSE 8000

CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Разберём по строкам. `FROM` задаёт базовый слой; `-slim` — это Debian без компиляторов и документации, около 130 МБ против 1 ГБ у полного образа. `ENV` пишет переменные в конфиг образа, а не в отдельный слой: `PYTHONUNBUFFERED=1` заставляет Python не буферизовать stdout, иначе логи появляются в `docker logs` с задержкой и теряются при падении контейнера. `WORKDIR` создаёт директорию и делает её текущей для последующих инструкций. `RUN groupadd/useradd` создаёт пользователя с фиксированным UID 1001 — от него зависят права на смонтированные тома.

`COPY requirements.txt ./` и `RUN pip install` стоят отдельно от `COPY . .` намеренно: зависимости меняются редко, код — часто. `USER app` переключает пользователя для следующих инструкций и для самого процесса. `EXPOSE 8000` — документация: наружу порт выводит только `-p`. `CMD` в exec-форме (JSON-массив) запускает процесс напрямую, без промежуточного `/bin/sh -c`.

### CMD и ENTRYPOINT

`ENTRYPOINT` задаёт исполняемый файл, `CMD` — аргументы по умолчанию. Если в образе только `CMD`, то `docker run image bash` полностью заменит команду. Если задан `ENTRYPOINT ["python", "-m", "uvicorn"]`, то `docker run image app.main:app` добавит аргумент к entrypoint.

| | `CMD` | `ENTRYPOINT` |
|---|---|---|
| Роль | команда или аргументы по умолчанию | фиксированный исполняемый файл |
| Переопределение | `docker run image <cmd>` заменяет целиком | аргументы дописываются |
| Типичное использование | самостоятельный образ | образ-обёртка, CLI-утилита |

Главная ловушка — shell-форма. `CMD uvicorn app.main:app` выполняется как `/bin/sh -c "uvicorn ..."`, и PID 1 становится shell. Shell не пробрасывает SIGTERM дочернему процессу, поэтому `docker stop` ждёт 10 секунд и добивает контейнер SIGKILL: соединения рвутся, а не закрываются штатно. Всегда используйте exec-форму и убедитесь, что приложение обрабатывает SIGTERM (см. главу 28).

## Кэш слоёв

Docker собирает образ последовательно и после каждой инструкции ищет в кэше слой с точно таким же родителем и точно такой же инструкцией. Совпало — слой берётся из кэша, не совпало — все последующие слои пересобираются. Кэш инвалидируется не только содержимым файла, но и его метаданными: `COPY . .` учитывает mtime и права.

Отсюда правило порядка: от самого стабильного к самому изменчивому. Сначала базовый образ, потом системные пакеты, потом манифест зависимостей, потом установка зависимостей, и только в конце — исходный код. Если поставить `COPY . .` перед `pip install`, то правка одного пробела в README пересоберёт все зависимости: полторы минуты вместо двух секунд.

Кэш сбрасывается `docker build --no-cache`, а в CI его надо выносить наружу (`--cache-to`/`--cache-from` с `type=registry` в BuildKit), иначе каждый запуск собирает образ с нуля.

## Multi-stage сборка

Компилятор нужен, чтобы собрать бинарник, но не нужен, чтобы его запускать: multi-stage оставляет его в сборочном stage, а в финальный копирует только результат.

```dockerfile
FROM golang:1.26-alpine AS builder

WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build \
    -trimpath -ldflags="-s -w" \
    -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot

COPY --from=builder /out/server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
```

Первый stage весит около 300 МБ и остаётся в кэше сборки, но не попадает в результат. Второй — distroless: только бинарник и сертификаты, без shell и пакетного менеджера, около 15–20 МБ. `CGO_ENABLED=0` даёт статически слинкованный бинарник, которому не нужна glibc; `-ldflags="-s -w"` убирает отладочные символы, экономя 20–30%. Отсутствие shell в образе — защита: если в приложение просочится RCE, выполнить `curl | sh` будет нечем.

Тот же приём работает для Python: stage `builder` собирает wheel-пакеты, финальный stage ставит их `pip install --no-cache-dir --no-index --find-links=/wheels` в чистый `python:3.14-slim`.

## Non-root и .dockerignore

Процесс от root внутри контейнера — это root на хосте при монтировании каталога, при работе с сокетом Docker и при эксплойте ядра. Поэтому `USER` в Dockerfile обязателен. Исключение — образы, которые сами сбрасывают привилегии, но и там предпочтительнее unprivileged-вариант.

`.dockerignore` работает как `.gitignore`, но для контекста сборки. Без него `docker build .` отправляет демону весь каталог, включая `.git`, `node_modules`, `venv` и локальные `.env`. Это замедляет сборку, ломает кэш (изменился `.git/index` — изменился слой) и рискует утащить секреты в образ.

```text
.git
.gitignore
.venv
__pycache__
*.pyc
.pytest_cache
.mypy_cache
.env
.env.*
docker-compose*.yml
tests/
docs/
*.md
```

## Данные: volumes и bind mounts

Файловая система контейнера эфемерна. Для данных есть три варианта.

| Тип | Где живёт | Когда использовать |
|---|---|---|
| named volume | `/var/lib/docker/volumes/<name>` | данные БД, загрузки пользователей |
| bind mount | произвольный путь хоста | конфиги, разработка с live-reload |
| tmpfs | RAM | кэш, временные файлы, секреты |

```bash
docker volume create pgdata
docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:17-alpine
docker run --rm -it -v "$PWD":/src -w /src python:3.14-slim python script.py
```

Named volume управляется Docker и переживает `docker rm`. Bind mount связывает путь хоста: удобно в разработке, опасно в проде, потому что файлы приходят с чужими UID и правами, а SELinux на Fedora или RHEL потребует суффикс `:z`. Опция `:ro` должна быть по умолчанию для конфигов.

## Сети

По умолчанию контейнер попадает в bridge-сеть `docker0` и получает адрес вида `172.17.0.1/16`. В дефолтном bridge нет DNS по именам — контейнеры находят друг друга только по IP, что для compose непригодно. Поэтому создаётся пользовательская bridge-сеть: в ней работает встроенный DNS, и имя контейнера резолвится в его адрес.

```bash
docker network create shop-net
docker run -d --name db --network shop-net postgres:17-alpine
docker run -d --name api --network shop-net -p 127.0.0.1:8000:8000 shop-api:1.4.2
```

Теперь `api` подключается к `db:5432`. `--network host` убирает изоляцию: контейнер видит порты хоста напрямую, `-p` игнорируется. Это быстрее, но занимает порт хоста и ломает модель «много реплик на одной машине». `--network none` — для задач без сети.

Публикуйте порты на `127.0.0.1`, а не на `0.0.0.0`, если перед контейнером стоит {{L|g97|reverse proxy}}: иначе приложение окажется доступным напрямую, минуя TLS и rate limiting.

## Compose: сервис, БД, healthcheck

Compose описывает несколько контейнеров как один проект: общая сеть, порядок запуска, тома, переменные окружения.

```yaml
services:
  api:
    build: .
    image: registry.example.com/shop/api:1.4.2
    restart: unless-stopped
    environment:
      DATABASE_URL: postgresql://shop:${POSTGRES_PASSWORD}@db:5432/shop
      APP_ENV: production
    ports:
      - "127.0.0.1:8000:8000"
    depends_on:
      db:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request,sys; r=urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=2); sys.exit(0 if r.status==200 else 1)"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 15s
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 384M
    volumes:
      - uploads:/app/uploads

  db:
    image: postgres:17-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: shop
      POSTGRES_USER: shop
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U shop -d shop"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
  uploads:
```

Ключевые детали. `${POSTGRES_PASSWORD}` подставляется из `.env` в каталоге проекта; сам `.env` в git не попадает. `depends_on` с `condition: service_healthy` ждёт не запуска контейнера, а успешного healthcheck — иначе приложение стартует раньше, чем Postgres начнёт принимать соединения, и падает. `start_period` даёт время на инициализацию, не считая эти секунды ошибками. `deploy.resources.limits` работает и без Swarm — это те же cgroup-лимиты. `restart: unless-stopped` перезапускает упавший контейнер, но не остановленный руками.

## Ресурсные лимиты

```bash
docker run -d --name api \
  --memory 384m --memory-swap 384m \
  --cpus 1.5 --pids-limit 256 \
  shop-api:1.4.2
```

`--memory` задаёт жёсткий лимит: при превышении ядро убивает процесс с кодом 137 (128 + SIGKILL 9). `--memory-swap`, равный `--memory`, запрещает swap — иначе контейнер «уходит в swap» и деградирует вместо быстрого падения. `--cpus 1.5` — это квота, а не привязка к ядрам; для привязки есть `--cpuset-cpus`.

Лимит памяти бесполезен, если приложение о нём не знает. JVM до недавних версий считала heap от памяти хоста; `-XX:MaxRAMPercentage=75` решает проблему, но только при корректном cgroup-лимите. Go-рантайм читает `memory.max` сам. Python с NumPy или большим кэшем нужно ограничивать на уровне приложения, иначе OOM-kill придёт внезапно.

## Типичные ошибки

1. **Гигантский последний слой.** `COPY . .` после установки зависимостей кладёт в образ `.git`, тесты и venv. Причина — отсутствие `.dockerignore` и неверный порядок инструкций; лечится и тем, и другим.
2. **Секреты в образе.** `ENV DATABASE_PASSWORD=...` или `COPY .env .` оставляет секрет в слое навсегда: он виден в `docker history` и в registry, даже если следующей инструкцией файл удалён. Секреты передаются в рантайме через переменные окружения, файлы-монтирования или секрет-хранилище.
3. **Тег `latest`.** `FROM python:latest` и `image: shop-api:latest` означают, что завтрашняя сборка даст другой результат, а откат невозможен — откатывать некуда. Фиксируйте минорную версию базы и immutable-тег приложения (хэш коммита или semver).
4. **`CMD` в shell-форме.** Процесс не получает SIGTERM, `docker stop` всегда ждёт таймаут и убивает SIGKILL. Причина — промежуточный `/bin/sh`, который не форвардит сигналы.
5. **Данные внутри контейнера.** Запись в `/app/uploads` без volume: после `docker compose up --force-recreate` файлов нет. Контейнер — не диск.
6. **`RUN apt-get update` отдельной строкой.** Кэш списка пакетов устаревает, и `apt-get install` падает на 404. `update` и `install` должны быть в одном `RUN` через `&&`, а в конце — `rm -rf /var/lib/apt/lists/*`.

## Чек-лист

- [ ] В Dockerfile есть `USER` с не-root пользователем, и процесс запускается от него.
- [ ] `CMD`/`ENTRYPOINT` в exec-форме, приложение обрабатывает SIGTERM.
- [ ] `.dockerignore` исключает `.git`, `.env`, тесты, кэши.
- [ ] Зависимости копируются и ставятся до копирования исходного кода (кэш работает).
- [ ] Образ собран multi-stage, в финальном слое нет компилятора и пакетного менеджера.
- [ ] Тег образа — версия или хэш, не `latest`; базовый образ зафиксирован по минорной версии.
- [ ] Данные, которые должны пережить перезапуск, лежат в named volume.
- [ ] `docker compose config` проходит без ошибок, у зависимых сервисов есть healthcheck и `depends_on: condition: service_healthy`.

## Упражнения

1. Соберите образ по Dockerfile из раздела про инструкции. Посмотрите `docker history` и найдите три самых больших слоя. Уменьшите итоговый размер хотя бы вдвое, не меняя функциональность.
2. Добавьте в Dockerfile слой, который ставит `curl` и удаляет его в следующей инструкции. Убедитесь, что размер образа не уменьшился, и объясните почему.
3. Переведите Python-сервис на multi-stage сборку с wheel-пакетами. Сравните размер и время холодной сборки до и после.
4. Напишите compose-файл для сервиса, Postgres и Redis с healthcheck у всех трёх. Добейтесь, чтобы `docker compose up` поднимал стек без единого рестарта приложения.
5. Ограничьте контейнер 256 МБ памяти и добейтесь, чтобы приложение при переполнении завершалось с понятной ошибкой в логах, а не молча.
