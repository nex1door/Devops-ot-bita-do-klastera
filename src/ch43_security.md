# Глава 43. Безопасность и supply chain

Безопасность сервиса — это не отдельный этап перед релизом, а набор решений, принятых в {{L|g30|Dockerfile}}, в манифесте, в пайплайне и в коде обработчика. Большинство реальных взломов не экзотичны: утёкший ключ из переменной окружения, контейнер под root с лишними capabilities, зависимость с известной CVE, образ, подменённый по тегу. В главе разбирается модель угроз типового сервиса, хранение и ротация секретов, минимальные привилегии в контейнере, проверка цепочки поставки (lock-файлы, Trivy, SBOM, cosign), OIDC вместо долгоживущих ключей в CI, TLS внутри кластера и обязательный минимум по OWASP для API. Заканчивается главой чек-лист «сервис перед публикацией в интернет».

## Модель угроз: от чего защищаемся

Прежде чем что-то настраивать, полезно выписать, кто и как может навредить. Для типового веб-сервиса угрозы укладываются в пять групп.

Утечка секретов — ключи, пароли, токены попадают в git, в образ, в лог или в вывод ошибки. Компрометация зависимости или образа — атакующий публикует пакет с похожим именем либо подменяет тег в registry. Избыточные права — процесс внутри контейнера может больше, чем нужно, поэтому ошибка в коде превращается в компромисс узла. Атака через входные данные — инъекции, SSRF, доступ к чужим объектам по идентификатору. И, наконец, слабая наблюдаемость: атаку просто не замечают, потому что нет логов доступа и алертов на аномалии.

Модель угроз отвечает на вопрос «что мы защищаем и от кого», а не «какие инструменты модны». Внутренний сервис в закрытом контуре и публичный API с платежами имеют разные приоритеты: первому важнее сегментация и аудит, второму — аутентификация, {{L|g91|rate limit}} и защита от инъекций.

## Секреты: почему не в git и не в образе

Секрет в git — это секрет навсегда: история клонируется, форкается, попадает в бэкапы и в CI-кэш. Удаление коммита не помогает, `git filter-repo` переписывает историю только у тех, кто её перетянул, а старый объект может жить в чужом клоне. Поэтому единственная реакция на секрет в git — ротация, а не «удалили и забыли». То же с образом: слой с `ENV API_KEY=...` остаётся в манифесте даже если следующий слой его «удаляет».

Переменные окружения — компромисс. Их видно в `docker inspect`, в `/proc/<pid>/environ` (для того же пользователя или root), в дампах, в логах исключений при старте, и они наследуются всеми дочерними процессами, включая сторонние утилиты. Файл с правами `0400` внутри тома лучше: он не наследуется и не попадает в `ps e`. Vault (HashiCorp Vault, AWS Secrets Manager, Yandex Lockbox) лучше всего: секрет выдаётся по короткоживущему токену, имеет TTL, а его выдача логируется.

Практичная схема для Kubernetes: секреты живут в хранилище, в кластер попадают через External Secrets Operator или CSI-драйвер, монтируются файлом в `emptyDir`/`tmpfs`, а не в env. Приложение читает файл при старте и умеет перечитывать при изменении.

```yaml
volumes:
  - name: db-creds
    csi:
      driver: secrets-store.csi.k8s.io
      readOnly: true
      volumeAttributes:
        secretProviderClass: shop-db
containers:
  - name: api
    volumeMounts:
      - name: db-creds
        mountPath: /run/secrets/db
        readOnly: true
```

Ротация должна быть процессом, а не событием: два активных ключа одновременно, приложение умеет читать новый, старый отзывается через сутки. Если ротация требует ручного изменения конфига и перезапуска — её не будут делать, и ключ проживёт три года.

## Минимальные привилегии в контейнере

Контейнер — это процесс с namespaces и cgroups (глава 38), а не виртуальная машина. Всё, что процесс может внутри, он может и в ядре: смонтировать, отправить сырой пакет, загрузить модуль. Ограничения ставятся явно.

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
```

`runAsNonRoot` не даст запуститься от uid 0 — типичная ошибка «в Dockerfile нет USER, значит root». `allowPrivilegeEscalation: false` закрывает `setuid`-бинари. `drop: ALL` убирает 14 capabilities, которые Docker даёт по умолчанию, включая `NET_RAW` (сырые сокеты, спуфинг) и `CHOWN`; нужные возвращаются точечно, например `NET_BIND_SERVICE` для порта 80. `readOnlyRootFilesystem` превращает попытку записать webshell в ошибку ввода-вывода; каталоги под запись монтируются отдельно.

seccomp — фильтр системных вызовов. Профиль `RuntimeDefault` блокирует около 40 опасных вызовов (`mount`, `ptrace`, `kexec_load`, `bpf`) и не требует написания политики. В Kubernetes его задают явно, потому что неявные умолчания зависят от версии и от настройки {{L|g62|kubelet}}.

Проверить, что получилось, можно до выката: `kubectl auth can-i --list` и `kubectl exec ... -- id` покажут реальные права, а `kubectl get pod -o yaml | grep -A5 securityContext` — то, что применилось, а не то, что задумано. Pod Security Admission в режиме `restricted` отклонит манифест без этих полей — полезный предохранитель на уровне namespace.

## Supply chain: зависимости, образы, SBOM, подпись

Цепочка поставки — всё, что попадает в артефакт помимо вашего кода. Начните с воспроизводимости: {{L|g67|lock-файл}} (`poetry.lock`, `uv.lock`, `go.sum`, `package-lock.json`) фиксирует точные версии и хэши, а `pip install --require-hashes -r requirements.txt` не даст поставить пакет, чей хэш не совпал. Без lock-файла сборка вчера и сегодня — разные сборки, и «у нас ничего не менялось» перестаёт быть аргументом.

CVE-сканирование образа — второй слой. Trivy сверяет пакеты из слоёв с базами уязвимостей и умеет валить сборку:

```bash
trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 \
  ghcr.io/example/shop-api@sha256:9f2c1e7b4a5d6c8e0f1a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f70
```

```
ghcr.io/example/shop-api (debian 13.1)
Total: 14 (HIGH: 9, CRITICAL: 5)
┌──────────────┬────────────────┬──────────┬───────────────────┐
│   Library    │ Vulnerability  │ Severity │ Fixed Version     │
├──────────────┼────────────────┼──────────┼───────────────────┤
│ libssl3      │ CVE-2026-1234  │ CRITICAL │ 3.5.2-1           │
│ libcurl4     │ CVE-2026-5678  │ HIGH     │ 8.14.1-2          │
└──────────────┴────────────────┴──────────┴───────────────────┘
```

`--ignore-unfixed` отсекает уязвимости без исправления: чинить их всё равно нечем, а шум в пайплайне обесценивает проверку. Сканировать надо не только финальный образ, но и базовый: `debian:13-slim` и `distroless` имеют разный размер поверхности атаки, и distroless-образ без shell и пакетного менеджера выигрывает просто потому, что атакующему нечем воспользоваться.

SBOM (software bill of materials) — машинный список компонентов: имя, версия, лицензия, хэш. Генерируется на сборке (`syft`, `trivy --format cyclonedx`) в форматах SPDX или CycloneDX и хранится рядом с образом. Через полгода, когда объявят CVE в библиотеке, SBOM отвечает на вопрос «какие из наших 40 сервисов её содержат» за минуты, а не за неделю grep'а по репозиториям.

Тег — не идентификатор. `latest` и даже `v1.4.2` перезаписываемы: registry не запрещает запушить другой образ под тем же тегом, а кэш узла оставит старый. Digest — хэш манифеста, он неизменен. Поэтому в продакшн-манифесте пишут `image: ghcr.io/example/shop-api@sha256:...`, а тег оставляют для читаемости.

Подпись замыкает цепочку: cosign подписывает digest ключом или ключом из OIDC-идентичности CI, а кластер проверяет подпись при допуске (Kyverno, Sigstore policy-controller, Gatekeeper).

```bash
cosign verify ghcr.io/example/shop-api@sha256:9f2c1e7b... \
  --certificate-identity-regexp '^https://github.com/example/shop/\.github/workflows/build\.yml@refs/heads/main$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Проверка `--certificate-identity` важна не меньше самой подписи: без неё валидна любая подпись любого аккаунта GitHub, включая ваш личный форк с тем же именем workflow.

## CI: OIDC вместо долгоживущих ключей

Ключ, лежащий в секретах CI, живёт годами и работает откуда угодно — утечка означает доступ, который никто не заметит. OIDC меняет модель: пайплайн получает подписанный токен от провайдера (GitHub, GitLab), облако проверяет его и выдаёт временные креды на 15–60 минут.

```yaml
permissions:
  id-token: write
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-24.04
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gh-deploy-shop
          aws-region: eu-central-1
```

Роль в облаке доверяет конкретному репозиторию, ветке и workflow — в условии trust policy, а не «любому токену GitHub». Тогда компрометация форка не даёт доступа к продакшн-аккаунту. Тот же принцип применим к registry и к Kubernetes: короткоживущий токен вместо kubeconfig с сертификатом на три года.

## TLS внутри кластера

Сеть внутри Kubernetes плоская: любой под по умолчанию может обратиться к любому другому по IP или имени сервиса. Если база принимает соединения без TLS, то компромисс любого пода в namespace — это доступ к трафику и к данным.

Минимум: TLS на всех соединениях сервис-сервис и сервис-БД, сертификаты через cert-manager с автоматическим продлением, проверка цепочки и имени хоста на стороне клиента, а не `verify=False`. Дальше — mTLS: обе стороны предъявляют сертификат, и под без валидного клиентского сертификата не подключится. Это даёт service mesh (Istio, Linkerd) почти без изменений в коде, но добавляет sidecar и сложность; для небольшого контура достаточно cert-manager плюс NetworkPolicy.

NetworkPolicy важна не меньше TLS: политика «разрешено только с подов с меткой `app=api` на порт 5432» сужает доступ даже при украденном пароле. По умолчанию в namespace стоит `default-deny` на {{L|g54|ingress}} и egress, а разрешения выдаются явно.

## Аудит и логирование доступа

Логи доступа отвечают на вопрос «кто что сделал»: аутентификация (успешная и неуспешная), авторизация (отказ по правам), изменения объектов (кто удалил секрет, кто создал RoleBinding). В Kubernetes для этого включают audit policy с уровнями `Metadata` для обычных запросов и `Request` для критичных ресурсов, в облаке — audit trail провайдера.

Что логировать обязательно: неуспешные логины, смену прав и ролей, доступ к секретам, административные операции, выдачу токенов. Чего нельзя: пароли, токены, полные номера карт, содержимое cookie. Маскирование — на уровне логгера, а не «мы аккуратно передаём».

Логи аудита должны быть отдельно от прикладных: другое хранилище, другой retention (обычно год), запрет на удаление приложением. Иначе атакующий с доступом к поду просто сотрёт следы.

## OWASP-минимум для API

**Инъекции.** SQL собирается только параметризованными запросами; конкатенация строк с вводом — запрещена код-ревью. То же для shell: `subprocess.run(["git", "log", ref])` вместо `shell=True`. Валидация входа — вторая линия, а не первая.

**SSRF.** Если сервис ходит по URL, переданному клиентом (вебхук, импорт по ссылке, превью изображения), атакующий попросит `http://169.254.169.254/latest/meta-data/` и заберёт креды инстанса. Защита: allowlist схем и хостов, запрет link-local и приватных диапазонов после резолва, отдельный egress-прокси, IMDSv2 с ограничением hop limit.

**IDOR.** Проверка прав должна быть на уровне объекта, а не только на уровне эндпоинта. `GET /orders/12345` обязан проверить, что заказ принадлежит текущему пользователю, — иначе аутентификация есть, а авторизации нет. Это самая частая уязвимость в API, потому что фильтр «по текущему пользователю» легко забыть в одном из десяти обработчиков.

**Rate limit.** Лимит по ключу (пользователь, токен, IP) с ответом `429` и заголовком `Retry-After`. Без него перебор паролей, перебор OTP и скрейпинг каталога идут со скоростью вашей инфраструктуры. Отдельно лимитируют дорогие операции: поиск, экспорт, отправку писем.

**Аутентификация и токены.** Короткоживущий access token (15 минут), refresh с ротацией и отзывом, пароли — bcrypt cost 12 или argon2id. JWT проверяется по алгоритму из конфигурации, а не из заголовка `alg` — иначе `alg: none` проходит проверку.

## Типичные ошибки

1. **Секрет в `.env`, закоммиченный «на время».** Файл попадает в историю, в CI-кэш и в образ; ротация не делается, потому что «никто не видел». Причина — соблазн запустить локально за 10 секунд.
2. **`USER root` по умолчанию.** В Dockerfile нет `USER`, и процесс получает uid 0 внутри контейнера; при монтировании docker.sock или privileged-режиме это root на узле. Причина — базовые образы не всегда задают пользователя.
3. **`drop: ALL` без проверки.** После ужесточения сервис падает на `bind: permission denied` для порта 80, и правку откатывают целиком, возвращая все capabilities. Причина — ужесточение без теста в staging.
4. **Сканирование только финального слоя.** `trivy` без `--ignore-unfixed` даёт сотни «неисправимых» находок, пайплайн краснеет, проверку отключают. Причина — порог выставлен без учёта реальной исправимости.
5. **Тег вместо digest.** Откат «на предыдущий тег» поднимает не тот образ, а supply-chain-атака через перезапись тега не детектируется. Причина — тег читаемее, и об этом не думают до инцидента.
6. **`curl | bash` в CI.** Установка инструмента из интернета без проверки подписи и версии — исполнение произвольного кода в пайплайне с доступом к секретам. Причина — «так быстрее, чем пиновать версию».
7. **`verify=False` в клиенте к внутреннему сервису.** Отключает проверку цепочки и имени, и mTLS превращается в декорацию. Причина — самоподписанный сертификат в тестовом контуре.

## Чек-лист: сервис перед публикацией в интернет

- [ ] Все секреты приходят из хранилища, не из git и не из образа; ротация описана и проверена.
- [ ] Контейнер: {{L|g76|non-root}}, `drop: ALL`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem`, seccomp `RuntimeDefault`.
- [ ] В манифесте digest, а не тег; образ подписан, подпись проверяется при допуске.
- [ ] Trivy на HIGH/CRITICAL с `--ignore-unfixed` валит сборку; SBOM сохранён рядом с образом.
- [ ] Зависимости зафиксированы lock-файлом, установка с проверкой хэшей.
- [ ] В CI нет долгоживущих ключей: только OIDC и временные креды.
- [ ] TLS на всех внутренних соединениях, `default-deny` NetworkPolicy, mTLS там, где нужен.
- [ ] Аутентификация, авторизация на уровне объекта, rate limit; аудит-логи отдельно и с retention не меньше года.

## Упражнения

1. Соберите образ без `USER` и проверьте `id` внутри контейнера. Затем добавьте non-root пользователя, `drop: ALL` и `readOnlyRootFilesystem` — и найдите, какие каталоги приложению всё-таки нужны на запись.
2. Прогоните один и тот же образ через `trivy image` с `--ignore-unfixed` и без него. Сравните число находок и объясните, почему порог «ноль уязвимостей» на практике неработоспособен.
3. Сгенерируйте SBOM в формате CycloneDX для образа, найдите в нём конкретную библиотеку и её версию. Оцените, за сколько вы ответите на вопрос «где ещё используется эта версия».
4. Подпишите образ через cosign и проверьте его с неверным `--certificate-identity`. Объясните, почему подпись без проверки идентичности не защищает от подмены.
5. Напишите обработчик, который принимает URL и скачивает его. Реализуйте защиту от SSRF и проверьте её на `http://169.254.169.254/` и на домене, резолвящемся в приватный адрес.
