# Глава 30. Go: начало

Go появился в 2009 году как ответ на боль внутренних сервисов Google: медленная сборка C++, сложность управления памятью и потоками, отсутствие единого способа ставить зависимости. Для DevOps-инженера Go ценен тремя свойствами: он компилируется в один статический бинарник, который запускается на любом Linux без интерпретатора и зависимостей; он даёт конкурентность на уровне языка, а не библиотек; и его инструментальная цепочка едина — форматирование, тесты, сборка и проверка кода встроены в один бинарник `go`. В этой главе мы установим Go, разберёмся с модулями и типичной структурой проекта, соберём минимальный HTTP-сервер и научимся собирать бинарник под другую архитектуру. Синтаксис подробно разбирается в следующей главе, поэтому здесь мы смотрим на рабочий процесс, а не на язык.

## Зачем Go в инфраструктуре

Типичная задача DevOps-инженера, для которой Go подходит лучше Python: небольшой контроллер, экспортёр метрик, вебхук для приёма алертов, sidecar-прокси, CLI для внутреннего API. У Python в такой роли два слабых места. Первое — поставка: нужен интерпретатор нужной версии, виртуальное окружение, зависимости, и всё это надо доставить в контейнер или на хост. Второе — старт и потребление памяти: интерпретатор поднимается десятки миллисекунд и занимает десятки мегабайт до первой строки полезной работы.

Go решает обе проблемы одним движением. `go build` создаёт один файл, внутри которого лежат и ваш код, и рантайм Go (сборщик мусора, планировщик горутин, сетевой поллинг). Файл не требует ни libc (если отключить cgo), ни переменных окружения, ни установленных пакетов. Его можно положить в `scratch`-образ Docker (пустой, без оболочки) или в `FROM gcr.io/distroless/static`, и он заработает.

| Свойство | Python | Go |
|---|---|---|
| Артефакт поставки | исходники + интерпретатор + venv | один бинарник |
| Старт процесса | десятки мс | единицы мс |
| Базовая память | десятки МБ | единицы–десятки МБ |
| Конкурентность | потоки ОС / asyncio | горутины, тысячи на процесс |
| Сборка | нет этапа сборки | `go build`, секунды |

Цифры в таблице — порядки величин, а не бенчмарк. Важна разница в модели: у Go нет отдельного этапа «подготовить окружение» — окружение упаковано в бинарник.

## Установка и проверка

Дистрибутивные пакеты отстают от релизов. В Debian и Ubuntu репозиторный `golang-go` обычно на несколько минорных версий позже текущей, а вместе с языком отстают и исправления безопасности в стандартной библиотеке. Для рабочих машин и CI правильнее ставить официальный архив с go.dev.

```bash
curl -LO https://go.dev/dl/go1.26.0.linux-amd64.tar.gz
sudo rm -rf /usr/local/go
sudo tar -C /usr/local -xzf go1.26.0.linux-amd64.tar.gz
export PATH=$PATH:/usr/local/go/bin
go version
```

Вывод последней команды на момент написания — `go version go1.26.0 linux/amd64`. Актуальная ветка Go — 1.26 (1.26.0 вышла 10 февраля 2026 года, последний патч 1.26.10 — 19 октября 2026); предыдущая — 1.25. Поддерживаются две последние минорные ветки, поэтому обновляться стоит каждый релиз, а не раз в несколько лет: как только ветка выпадает из поддержки, патчи безопасности для неё не выходят.

Строку `export PATH=...` нужно добавить в `~/.profile` или `~/.bashrc`, иначе после перезапуска оболочки `go` исчезнет. В CI то же самое делают в шаге установки или берут готовый образ `golang:1.26`.

### go env: где Go хранит своё

`go env` печатает конфигурацию тулчейна. Полный вывод длинный, полезно смотреть выборочно:

```bash
go env GOROOT GOPATH GOMODCACHE GOCACHE GOPROXY CGO_ENABLED
```

```
/usr/local/go
/home/user/go
/home/user/go/pkg/mod
/home/user/.cache/go-build
https://proxy.golang.org,direct
1
```

`GOROOT` — каталог с самим тулчейном и стандартной библиотекой; его не надо трогать. `GOPATH` — рабочая область пользователя, по умолчанию `~/go`; внутри `bin` (куда `go install` кладёт бинарники), `pkg/mod` (кэш скачанных модулей) и `src` (историческое место, в модульном режиме не используется). `GOCACHE` — кэш сборки: объектные файлы и результаты тестов. Именно он делает повторную сборку почти мгновенной, и именно его теряют, когда в CI не настраивают кэш между запусками. `GOPROXY` — откуда брать модули; `direct` в конце означает «если прокси не ответил, иди в git напрямую».

`CGO_ENABLED=1` разрешает вызовы C-кода. Для статических бинарников его выключают.

## Модули

До версии 1.11 зависимости искались по путям внутри `GOPATH`, и проект нельзя было собрать вне этой структуры. Модуль (module) заменил её: теперь у проекта есть явный список зависимостей и версий, а расположение на диске не важно. Модуль — это набор пакетов с общим префиксом импорта и файлом `go.mod` в корне.

```bash
mkdir -p ~/src/metrics-exporter && cd ~/src/metrics-exporter
go mod init example.com/platform/metrics-exporter
go get github.com/prometheus/client_golang@v1.20.5
go mod tidy
```

После этого в каталоге два файла. `go.mod` описывает модуль (сокращённо):

```
module example.com/platform/metrics-exporter

go 1.26.0

require github.com/prometheus/client_golang v1.20.5
```

Первая строка — путь модуля. Для внутреннего проекта он может быть любым, лишь бы уникальным: `example.com/platform/metrics-exporter` или `git.company.internal/team/exporter`. Для публикуемого в открытый доступ модуля путь обязан совпадать с URL репозитория, иначе `go get` у пользователей не найдёт код. Строка `go 1.26.0` фиксирует минимальную версию языка, которую требует код; тулчейн новее её соберёт, старее — откажется с внятной ошибкой. Начиная с Go 1.21 в этой строке допустима полная версия с патчем, а не только `1.26`.

Файл `go.sum` — контрольные суммы скачанных модулей. Он защищает от подмены кода в кэше или на прокси: если хеш не совпал, сборка остановится. `go.sum` коммитят в репозиторий вместе с `go.mod`, иначе воспроизводимость теряется.

Ключевая команда повседневной работы — `go mod tidy`. Она проходит по импортам, добавляет отсутствующие зависимости, удаляет неиспользуемые и обновляет `go.sum`. Запускать её нужно после каждого изменения импортов, а в CI — проверять, что она не даёт диффа: это ловит ситуацию «на машине разработчика работает, потому что в кэше лежит пакет, которого нет в `go.mod`».

Версии Go выбирает по принципу минимальной достаточной версии (minimal version selection, MVS): если ваши зависимости требуют `v1.4.0` и `v1.2.0`, будет выбрана `v1.4.0` — наибольшая из минимально необходимых, а не последняя выпущенная. Это делает сборки предсказуемыми: обновление происходит только тогда, когда вы явно попросили. `go get package@latest` — явная просьба, и она меняет `go.mod`; `go get` без версии в современном Go ведёт себя как `@latest` для указанного пакета, поэтому в скриптах версию лучше писать всегда.

## Структура проекта

Формально Go не навязывает структуру каталогов: пакеты — это каталоги, и всё. Но несколько соглашений сложились де-факто и поддерживаются инструментами.

```
metrics-exporter/
├── go.mod
├── go.sum
├── cmd/
│   └── exporter/
│       └── main.go
├── internal/
│   ├── collect/
│   │   └── collect.go
│   └── httpserver/
│       └── server.go
└── pkg/
    └── client/
        └── client.go
```

`cmd/<имя>/main.go` — точка входа. Если бинарников несколько (`cmd/exporter`, `cmd/migrate`), у каждого свой каталог и свой `package main`. Это позволяет одному репозиторию собирать несколько программ: `go build ./cmd/exporter`.

`internal/` — пакеты, которые нельзя импортировать снаружи модуля. Это не соглашение, а правило компилятора: если пакет лежит в `internal`, импорт из другого модуля не соберётся с ошибкой `use of internal package not allowed`. Всё, что не является публичным API, стоит держать здесь — тогда рефакторинг внутренностей не ломает чужие сборки.

`pkg/` — необязательный каталог для кода, который предполагается переиспользовать внешними модулями. Многие команды его не заводят вовсе: пока нет внешних потребителей, `internal` честнее. Пустой `pkg/` только вводит в заблуждение.

Тесты лежат рядом с кодом: `collect.go` и `collect_test.go` в одном каталоге и одном пакете (`package collect`, не `collect_test`, если нужен доступ к неэкспортируемым функциям). Отдельного каталога `tests/` в идиоматичном Go нет.

## Рабочий цикл: run, build, test, vet, fmt

`go run` компилирует во временный каталог и сразу запускает — удобно для проверки, но каждый запуск это сборка.

```bash
go run ./cmd/exporter -listen=:9101
```

`go build` создаёт бинарник в текущем каталоге (или в `$GOBIN` при `go install`). Флаг `-o` задаёт имя, `-trimpath` убирает локальные пути из бинарника — полезно для воспроизводимых сборок и чтобы не светить структуру домашних каталогов.

```bash
go build -trimpath -ldflags="-s -w" -o bin/exporter ./cmd/exporter
```

`-ldflags="-s -w"` убирает таблицу символов и отладочную информацию: на простом сервисе бинарник уменьшается примерно с 8,4 до 5,4 МБ (треть), но перестаёт работать `delve`.

`go test ./...` запускает тесты во всех пакетах модуля, `go vet ./...` — статический анализ на подозрительный код: забытый `Printf` с неверным числом аргументов, потерянный `cancel` у контекста, некорректное копирование мьютекса, недостижимый код. `go vet` входит в стандартную поставку и не требует установки; в CI его гоняют до тестов, потому что он быстрее.

`gofmt` — форматтер: `gofmt -l .` печатает файлы, отличающиеся от канонического формата, `gofmt -w .` переписывает их. Отступы — табы, выравнивание — пробелы. В CI `gofmt -l` ставят отдельным шагом: непустой список валит пайплайн.

## Минимальный HTTP-сервер

Пятнадцать строк, которые уже работают, но по таймаутам некорректны — об этом в главе 33; здесь важен каркас.

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/plain; charset=utf-8")
		fmt.Fprintln(w, "ok")
	})

	log.Println("listening on :8080")
	log.Fatal(http.ListenAndServe(":8080", nil))
}
```

Разбор по строкам. `package main` и функция `main` — обязательная пара для исполняемой программы; пакет с другим именем компилируется в библиотеку. `http.HandleFunc` регистрирует обработчик в глобальном мультиплексоре (`http.DefaultServeMux`) по пути `/healthz`. Обработчик — функция с сигнатурой `func(http.ResponseWriter, *http.Request)`: первый аргумент пишет ответ, второй содержит разобранный запрос. `w.Header().Set` добавляет заголовок до первого `Write` — после записи тела заголовки уже отправлены, и попытка их поменять молча игнорируется. `fmt.Fprintln(w, "ok")` пишет тело и неявно ставит статус 200, если он не был задан раньше. `http.ListenAndServe(":8080", nil)` слушает все интерфейсы на порту 8080; `nil` означает «взять `DefaultServeMux`».

Важная деталь: `log.Fatal` завершает процесс с кодом 1, если сервер не смог запуститься (порт занят, нет прав). Без него программа молча завершится, и в {{L|g115|systemd}} вы увидите только `status=0/SUCCESS` — классическая ловушка при отладке юнита.

Проверить:

```bash
go run . &
curl -sS -i http://127.0.0.1:8080/healthz
```

```
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Date: Thu, 29 Oct 2026 14:12:03 GMT
Content-Length: 3

ok
```

Обратите внимание на `Content-Length: 3`: Go буферизует небольшие ответы и вычисляет длину сам, если вы не вызвали `Flush`.

## Кросс-компиляция

Компилятор Go умеет собирать под другую платформу без дополнительных тулчейнов: достаточно переменных `GOOS` и `GOARCH`. Сборка под Linux ARM64 с машины на amd64 — одна команда.

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
  go build -trimpath -ldflags="-s -w" -o bin/exporter-linux-arm64 ./cmd/exporter
file bin/exporter-linux-arm64
```

```
bin/exporter-linux-arm64: ELF 64-bit LSB executable, ARM aarch64, statically linked, Go BuildID=..., stripped
```

Слова `statically linked` — результат `CGO_ENABLED=0`. Если cgo включён и код использует, например, системный DNS через glibc, бинарник окажется динамически слинкованным и потребует совместимую версию libc в контейнере. Поэтому в Docker-сборках для Go почти всегда ставят `CGO_ENABLED=0`; следствие — DNS резолвится встроенным резолвером Go, который читает `/etc/resolv.conf` сам, и это поведение отличается от системного в редких случаях (например, при `nsswitch.conf` с нестандартными источниками).

Список поддерживаемых пар — `go tool dist list`. Полноценная сборка и поставка разбираются в главе 36.

## Типичные ошибки

**Зависимость от локального пути вместо модуля.** Импорт вида `import "metrics-exporter/internal/collect"` не работает: Go ищет пакет по пути модуля из `go.mod`, а не по каталогу на диске. Правильно — `example.com/platform/metrics-exporter/internal/collect`, префикс модуля обязателен. Ошибка возникает у тех, кто пришёл из Python, где пакет ищется относительно текущего файла.

**`internal` за пределами модуля.** Пакет в `internal/` импортируется только кодом внутри родительского каталога модуля. Попытка импортировать его из соседнего репозитория даёт ошибку компиляции, а не предупреждение. Это защита, а не баг: не переносите `internal` в `pkg`, если не готовы поддерживать API.

**`go.sum` в `.gitignore`.** Без него сборка на чистой машине либо падает на проверке контрольных сумм, либо тянет то, что оказалось в кэше. `go.sum` — часть исходников, как `package-lock.json` или `poetry.lock`.

**`go get` без версии в скрипте.** `go get github.com/x/y` обновляет зависимость до последней версии, и сборка, которая вчера работала, завтра может не собраться из-за несовместимого минорного релиза. Версию фиксируют в `go.mod` и меняют осознанно, отдельным коммитом.

**Сборка без `-trimpath` в CI.** В бинарник попадают абсолютные пути сборочной машины (`/home/runner/work/...`), из-за чего два бинарника из одного коммита имеют разные хеши. Это ломает проверку воспроизводимости и подпись артефактов.

**`go build` без указания пакета.** Команда собирает пакет текущего каталога: в корне с несколькими `cmd/` и без собственных `.go`-файлов она падает с `no Go files in ...`. Явно указывайте `./cmd/<имя>`.

**Игнорирование `go vet`.** `fmt.Printf("%d", name)` с `name string` компилируется, но печатает `%!d(string=...)`. `go vet` ловит это до запуска; без него ошибка доживает до продакшна и проявляется в логах.

## Чек-лист

- [ ] `go version` показывает поддерживаемую ветку (1.26 или 1.25), а не репозиторную сборку двухлетней давности.
- [ ] В корне проекта есть `go.mod`, в нём осмысленный путь модуля, а `go.sum` закоммичен.
- [ ] `go mod tidy` не даёт диффа на чистом клоне.
- [ ] Точки входа лежат в `cmd/<имя>`, приватный код — в `internal/`.
- [ ] `gofmt -l .` возвращает пустой список.
- [ ] `go vet ./...` и `go test ./...` проходят локально и в CI.
- [ ] Релизная сборка идёт с `-trimpath` и `CGO_ENABLED=0`, бинарник проверен через `file` на `statically linked`.
- [ ] `go build` запускается из чистого клона без сети (при заполненном кэше модулей) — проверка воспроизводимости.

## Упражнения

1. Создайте модуль `example.com/lab/hello`, добавьте `cmd/hello/main.go`, который печатает версию Go из `runtime.Version()` и количество CPU из `runtime.NumCPU()`. Соберите его с `-trimpath -ldflags="-s -w"` и сравните размер с обычной сборкой.
2. Добавьте в проект пакет `internal/greet` с функцией `Hello(name string) string` и покройте его тестом в том же каталоге. Убедитесь, что `go test ./...` находит тест, а импорт пакета из другого модуля невозможен.
3. Расширьте HTTP-сервер: пусть `/healthz` отвечает `ok`, а `/version` возвращает JSON с версией Go и временем сборки, переданным через `-ldflags "-X main.buildTime=..."`. Проверьте оба эндпоинта через `curl`.
4. Соберите тот же сервер под `linux/arm64` и `windows/amd64`, проверьте результаты командой `file`. Объясните, почему для `windows` расширение `.exe` добавляется автоматически.
5. Настройте в проекте шаг CI, который падает, если `gofmt -l .` непуст или `go mod tidy` изменяет файлы. Опишите, какие ещё проверки стоит добавить в этот же шаг и почему именно в таком порядке.
