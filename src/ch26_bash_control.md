# Глава 26. Управляющие конструкции и коды возврата

В шелле нет логического типа. Есть целое число от 0 до 255, которое возвращает каждая команда, и есть конструкции, которые это число читают. Вся ветвящаяся логика скрипта — `if`, `while`, `&&`, `||`, `case` — это проверка кода возврата, а не проверка истины. Кто это понимает, тот перестаёт писать `if [ $? -eq 0 ]` после каждой команды и начинает пользоваться языком так, как он задуман. В главе разобраны `test` и `[[ ]]`, числовые и строковые сравнения, `case`, циклы, функции с локальными переменными, `set -euo pipefail` вместе с его реальными ловушками, `trap` для очистки и полный пример скрипта с разбором аргументов и валидацией.

## Код возврата — единственный способ общения

Каждый процесс завершается с кодом выхода (exit status). Соглашение в Unix описано в `sysexits.h` и в документации bash:

| Код | Значение |
|---|---|
| 0 | успех |
| 1–125 | ошибка приложения, смысл задаёт сама программа |
| 126 | команда найдена, но не исполняема |
| 127 | команда не найдена |
| 128+N | процесс убит сигналом N (например, 143 = 128+15, SIGTERM) |

Шелл хранит код последней команды в `$?`. Прочитать его можно один раз: следующая команда, включая `echo`, его перезапишет. Отсюда классическая ошибка:

```bash
$ grep -q pattern file
$ echo "нашлось: $?"
нашлось: 0
$ if [ $? -eq 0 ]; then echo yes; fi
```

Во второй строке `$?` уже относится к `echo`, а не к `grep`. Правильно — проверять команду напрямую: `if grep -q pattern file; then ...`.

Конструкции `&&` и `||` — это тоже проверки кода возврата, сокращённые до одной строки. `a && b` выполнит `b`, только если `a` вернула 0. `a || b` выполнит `b`, только если `a` вернула не 0. Комбинировать их как `a && b || c` опасно: `c` выполнится и тогда, когда `a` успешна, а `b` упала. Для «сделай или умри» есть идиома `cmd || { echo "ошибка" >&2; exit 1; }` — фигурные скобки группируют команды в текущей оболочке, в отличие от `( )`, которая создаёт подоболочку.

## test, [ и [[

`test` — встроенная команда, `[` — её синоним с обязательной закрывающей `]`. Обе возвращают 0 при истине, 1 при лжи и 2 при ошибке разбора. Поскольку `[` — обычная команда, пробелы обязательны: `[ -f "$f" ]`, а `[-f "$f"]` даст `command not found`.

`[[ ]]` — не команда, а ключевое слово bash. Отличия существенны:

| Поведение | `[ ]` | `[[ ]]` |
|---|---|---|
| Разбиение на слова внутри | да | нет |
| Globbing внутри | да (опасно) | нет |
| `&&`, `\|\|`, `!` | нет, нужен `-a`/`-o` | да |
| Регулярные выражения `=~` | нет | да |
| Сравнение `<`, `>` | нужно экранировать | работает как есть |
| Пустая переменная | `[ $x = a ]` — синтаксическая ошибка | безопасно |

Практический вывод: в bash используйте `[[ ]]`, в POSIX-скриптах — `[ ]` с обязательными кавычками. Смешивать нельзя: `[[` в `dash` — синтаксическая ошибка.

Основные проверки файлов: `-e` существует, `-f` обычный файл, `-d` каталог, `-L` символическая ссылка, `-r`/`-w`/`-x` доступен на чтение/запись/исполнение, `-s` непустой, `-nt`/`-ot` новее/старее.

```bash
$ f=/etc/hostname
$ [[ -f $f && -r $f ]] && echo "читаемый файл, $(wc -c < "$f") байт"
читаемый файл, 7 байт
$ [[ $f == /etc/* ]] && echo "лежит в /etc"
лежит в /etc
$ s="release-2026.10.tar.gz"
$ [[ $s =~ ^release-([0-9.]+)\.tar\.gz$ ]] && echo "версия: ${BASH_REMATCH[1]}"
версия: 2026.10
```

`=~` срабатывает на регулярном выражении POSIX ERE, а захваченные группы попадают в массив `BASH_REMATCH`. Регулярное выражение не нужно брать в кавычки — в кавычках оно станет литералом.

## Числа и строки

Внутри `[ ]` и `[[ ]]` действуют разные операторы, и путать их — источник тихих ошибок.

| Числа | Строки |
|---|---|
| `-eq`, `-ne`, `-lt`, `-le`, `-gt`, `-ge` | `=`, `==`, `!=`, `<`, `>` |

`[ "$a" -gt "$b" ]` сравнивает числа. `[[ $a > $b ]]` сравнивает строки лексикографически: `10` окажется меньше `9`, потому что `1` < `9`. Если хотя бы одна сторона не число, `-gt` печатает `integer expression expected` и возвращает 2, что в `if` трактуется как «ложь» — скрипт молча пойдёт по ветке `else`.

Надёжнее арифметический контекст: `(( a > b ))`. Он не требует `$`, понимает `+`, `*`, `**`, битовые операции, поддерживает присваивание `(( count += 1 ))`. Ограничение — 64-битные целые со знаком и никаких дробей.

```bash
$ used=87; total=100
$ (( used * 100 / total >= 85 )) && echo "пора чистить диск: ${used}%"
пора чистить диск: 87%
```

Проверка «строка непустая» пишется как `[[ -n $var ]]`, «пустая» — `[[ -z $var ]]`. Сокращение `[[ $var ]]` эквивалентно `-n` и удобно, но менее явно.

## case

`case` сопоставляет строку с glob-шаблонами и читается лучше длинной цепочки `if/elif`. Ветка `*)` — это `default`, она должна идти последней.

```bash
case "$1" in
    start|up)    systemctl start app ;;
    stop|down)   systemctl stop app ;;
    restart)     systemctl restart app ;;
    status)      systemctl status --no-pager app ;;
    *)           echo "использование: $0 {start|stop|restart|status}" >&2; exit 2 ;;
esac
```

В bash 4+ есть `;&` (провалиться в следующую ветку без проверки) и `;;&` (продолжить проверку следующих шаблонов). В POSIX их нет, поэтому в переносимых скриптах — только `;;`.

## Циклы

`for` перебирает список слов; без списка — позиционные параметры (`for a` то же, что `for a in "$@"`).

```bash
for f in /var/log/*.log; do
    printf '%s\t%s\n' "$(stat -c %s "$f")" "$f"
done
```

Если файлов нет, glob останется литералом `/var/log/*.log`, и цикл выполнится один раз с несуществующим путём. Защита — `shopt -s nullglob` (пустой результат вместо литерала) или проверка `[[ -e $f ]]` внутри.

C-подобный цикл нужен, когда важны индексы: `for ((i = 0; i < n; i++)); do ...; done`.

`while` выполняется, пока команда-условие возвращает 0. Главный случай — чтение файла построчно:

```bash
while IFS= read -r line; do
    [[ -z $line || $line == \#* ]] && continue
    printf '%s\n' "$line"
done < /etc/hosts
```

`until` — то же самое с инвертированной проверкой: тело выполняется, пока условие ложно. `break` и `continue` принимают уровень: `break 2` выходит из двух вложенных циклов.

## Функции и локальные переменные

Функция объявляется двумя способами: `name() { ...; }` (POSIX) и `function name { ...; }` (bash). Тело — составная команда в текущей оболочке, поэтому функция может менять переменные вызывающего.

Возвращает функция не значение, а код: `return N`, где N — 0–255. Вернуть строку можно только через stdout и подстановку команд, и это надо делать осознанно:

```bash
count_logs() {
    local dir=${1:?каталог не задан}
    find "$dir" -maxdepth 1 -name '*.log' -type f | wc -l
}
n=$(count_logs /var/log)
echo "логов: $n"
```

`local` объявляет переменную в области функции и восстанавливает прежнее значение при выходе. Без `local` функция затрёт глобальную переменную с тем же именем — классический баг в скриптах, где функции писались позже основного кода. В bash `local` можно комбинировать: `local -r name=value`, `local -a arr`, `local -n ref=$1` (nameref, ссылка на переменную по имени).

## set -euo pipefail и его подводные камни

Стандартная шапка продакшен-скрипта:

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'
```

* `-e` (`errexit`) — завершить скрипт при первой команде с ненулевым кодом.
* `-u` (`nounset`) — ошибка при обращении к необъявленной переменной.
* `-o pipefail` — код конвейера равен коду самой правой упавшей команды, а не последней.

Каждый из этих флагов имеет исключения, и именно на них ломаются скрипты, которые «работали без set -e».

**`-e` не срабатывает там, где код проверяется.** В условиях `if`, `while`, `until`, в левой части `&&` и `||`, а также с унарным `!` errexit отключается. Это задумано: вы же сами проверяете код. Но следствие опаснее, чем кажется: функция, вызванная в условии, выполняется целиком без errexit, и упавшая в середине команда не остановит её.

```bash
$ cat p3.sh
#!/usr/bin/env bash
set -euo pipefail
f() { echo "шаг1"; false; echo "шаг2"; }
if f; then echo "f ok"; else echo "f failed"; fi
$ bash p3.sh
шаг1
шаг2
f ok
```

`false` внутри `f` проигнорирована, `шаг2` выполнился, функция вернула 0 (последняя команда успешна), и скрипт считает, что всё хорошо. Если такая функция делает деплой, вы получите «успешный» деплой без половины шагов.

**`-e` не наследуется в подстановку команд.** `$(...)` выполняется в подоболочке, где errexit выключен, поэтому `x=$(false; echo продолжаем)` напечатает `продолжаем` и вернёт 0. Включается это через `shopt -s inherit_errexit` (bash 4.4+), но тогда ломаются идиомы вида `x=$(grep ... || true)`.

**`local` съедает код возврата.** `local out=$(false)` всегда возвращает 0, потому что код даёт сама `local`, а не подстановка. Проверено:

```bash
$ cat p7.sh
#!/usr/bin/env bash
set -euo pipefail
f() { local out=$(false); echo "внутри f, out='$out'"; }
f
echo "после f"
$ bash p7.sh
внутри f, out=''
после f
```

Правильно — разделять объявление и присваивание: `local out; out=$(false)` — тогда errexit сработает и скрипт остановится.

**Арифметика возвращает код по значению.** `((i++))` при `i=0` возвращает 1, потому что результат выражения — ноль:

```bash
$ cat pitfalls.sh
#!/usr/bin/env bash
set -euo pipefail
i=0
echo "до ((i++))"
((i++))
echo "после: i=$i"
$ bash pitfalls.sh
до ((i++))
$ echo $?
1
```

Скрипт молча умер на первой итерации счётчика. Лечится `((i++)) || true`, `i=$((i+1))` или `(( ++i ))`, где результат не ноль.

**`-u` и пустые массивы.** В bash 4.4+ `"$@"` при отсутствии аргументов безопасен, в более старых версиях `set -u` на нём падал. Для массивов используйте `${arr[@]:-}`, для необязательных параметров — `${1:-}`.

**`pipefail` и штатный ненулевой код.** `grep` возвращает 1, когда ничего не нашёл, — это не ошибка. Конвейер `... | grep -q pattern` под `pipefail` уронит скрипт. Осознанно: `if ! grep -q pattern file; then ...`.

Вывод: `set -euo pipefail` полезен, но не заменяет явные проверки. Ошибки в условиях, в подстановках и в арифметике он не поймает; зато поймает опечатку в имени переменной (`-u`) и падение середины конвейера (`pipefail`).

## trap и очистка

`trap` регистрирует команду, которая выполнится при получении сигнала или при выходе. Синтаксис: `trap 'команды' СПИСОК_СИГНАЛОВ`, где `EXIT` — псевдосигнал завершения.

```bash
#!/usr/bin/env bash
set -euo pipefail
WORK=$(mktemp -d)
cleanup() {
    local rc=$?
    rm -rf "$WORK"
    echo "cleanup: удалил каталог, код=$rc" >&2
}
trap cleanup EXIT
echo "работаю в $WORK"
exit 0
```

```
работаю в /tmp/tmp.Zepla6JscR
cleanup: удалил каталог, код=0
```

Внутри обработчика `$?` ещё содержит код завершения — поэтому `local rc=$?` нужно первой строкой, иначе его перезапишет `rm`. `trap` на `EXIT` выполняется и при `exit 1`, и при падении из-за `set -e`, и при SIGINT, если для него нет отдельного обработчика.

`SIGKILL` перехватить нельзя, `SIGTERM` — можно и нужно: это штатный способ попросить процесс завершиться. Подробно сигналы разобраны в главе 28. Снять обработчик — `trap - EXIT`.

## Пример: скрипт с аргументами и валидацией

Скрипт разбирает флаги через `getopts`, проверяет обязательные параметры и возвращает разные коды для разных классов ошибок.

```bash
#!/usr/bin/env bash
set -euo pipefail

usage() {
    cat <<'USAGE'
Использование: args.sh -e ОКРУЖЕНИЕ [-d КАТАЛОГ] [-n]
  -e  окружение: dev, stage, prod (обязательно)
  -d  каталог релиза (по умолчанию /srv/app)
  -n  dry-run: только показать план
USAGE
}

ENV_NAME=""
TARGET="/srv/app"
DRY_RUN=0

while getopts ":e:d:nh" opt; do
    case "$opt" in
        e) ENV_NAME="$OPTARG" ;;
        d) TARGET="$OPTARG" ;;
        n) DRY_RUN=1 ;;
        h) usage; exit 0 ;;
        :) echo "ошибка: -$OPTARG требует значения" >&2; usage >&2; exit 2 ;;
        *) echo "ошибка: неизвестный флаг -$OPTARG" >&2; usage >&2; exit 2 ;;
    esac
done
shift $((OPTIND - 1))

case "$ENV_NAME" in
    dev|stage|prod) ;;
    "") echo "ошибка: не задан -e" >&2; usage >&2; exit 2 ;;
    *)  echo "ошибка: неизвестное окружение '$ENV_NAME'" >&2; exit 2 ;;
esac

[[ -d "$TARGET" ]] || { echo "ошибка: каталога $TARGET нет" >&2; exit 3; }

echo "окружение=$ENV_NAME каталог=$TARGET dry_run=$DRY_RUN"
if (( DRY_RUN )); then
    echo "план: выложить релиз в $TARGET/$ENV_NAME"
else
    echo "выкладываю релиз в $TARGET/$ENV_NAME"
fi
```

Разбор: `":e:d:nh"` — ведущее двоеточие переводит `getopts` в «тихий» режим: неизвестный флаг приходит как `?`, отсутствующее значение — как `:`. Это позволяет печатать свои сообщения и отделять код 2 (ошибка использования) от кода 3 (неверное состояние среды). `OPTIND` после цикла указывает на первый неопознанный аргумент.

```
$ ./args.sh
ошибка: не задан -e
Использование: args.sh -e ОКРУЖЕНИЕ [-d КАТАЛОГ] [-n]
...
$ echo $?
2
$ ./args.sh -e prod -d /tmp -n
окружение=prod каталог=/tmp dry_run=1
план: выложить релиз в /tmp/prod
$ ./args.sh -e qa
ошибка: неизвестное окружение 'qa'
$ echo $?
2
```

## Типичные ошибки

1. **`if [ $? -eq 0 ]` после команды.** Механизм: `$?` перезаписывается каждой командой, и между проверкой и интересующей командой почти всегда что-то стоит. Проверяйте команду напрямую в `if`.
2. **`[ $var = x ]` при пустой переменной.** Механизм: подстановка исчезает, остаётся `[ = x ]` — `unary operator expected`, код 2, ветка `else`. Лечится кавычками или `[[ ]]`.
3. **`-gt` для строк или `>` для чисел.** Механизм: `-gt` требует целых и печатает ошибку, `>` сравнивает лексикографически. Для чисел — `(( ))`.
4. **`set -e` и функция в условии.** Механизм: errexit отключается на всё время выполнения команды, чей код проверяется. Внутренние сбои игнорируются, функция возвращает код последней команды.
5. **`local x=$(cmd)`.** Механизм: код возврата даёт `local`, а не подстановка, поэтому ошибка теряется. Объявляйте и присваивайте раздельно.
6. **`((i++))` под `set -e`.** Механизм: результат 0 даёт код 1, скрипт завершается. Используйте `((++i))` или `((i++)) || true`.
7. **`grep` в конвейере под `pipefail`.** Механизм: «не найдено» — это код 1, а не ошибка. Оборачивайте в `if` или добавляйте `|| true` осознанно.

## Чек-лист

- Каждая команда, код которой важен, проверяется напрямую (`if cmd; then`), а не через `$?`.
- В сравнениях используются правильные операторы: `-eq`/`-lt` для чисел, `=`/`==` для строк, `(( ))` для арифметики.
- Все раскрытия переменных закавычены, в bash используется `[[ ]]`.
- Скрипт начинается с `set -euo pipefail`, и в нём нет мест, где эти флаги молча не работают (условия, `local x=$(...)`, `((i++))`).
- Каждый `exit` имеет осмысленный код, а `usage` печатается в stderr при ошибке использования.
- Временные файлы создаются через `mktemp`, а удаляются в `trap ... EXIT`.
- Функции используют `local` для всех своих переменных.
- Скрипт проверен `shellcheck` и запущен с пустыми, неверными и граничными аргументами.
