# Глава 19. ООП, dataclasses, протоколы, MRO

Python-код в инфраструктуре редко начинается с классов, но почти всегда ими заканчивается: конфиг превращается в объект с валидацией, HTTP-клиент — в класс с пулом соединений, набор политик ретраев — в иерархию. Проблема в том, что ООП в Python устроено иначе, чем в Java или C++: наследование множественное, интерфейсы не объявляются, а проверяются структурно, а `dataclass` убирает большую часть шаблонного кода.

Глава разбирает модель классов (атрибуты класса против атрибутов экземпляра), порядок разрешения методов и кооперативный `super()`, свойства, `dataclass` с `frozen` и `slots`, структурную типизацию через `Protocol`, абстрактные базовые классы и границу, за которой класс становится лишним. Отдельная тема — композиция против наследования: в DevOps-коде она решает больше проблем, чем любая иерархия. Примеры проверены на CPython 3.14.9.

## Классы и атрибуты: класс против экземпляра

Класс — это пространство имён и фабрика экземпляров. Атрибут, объявленный в теле класса, живёт в словаре класса и виден всем экземплярам; присваивание `self.x = ...` создаёт запись в словаре экземпляра. Разница принципиальна, когда значение изменяемо:

```python
class Queue:
    items = []

q1, q2 = Queue(), Queue()
q1.items.append(1)
print(q1.items, q2.items)
```

```text
[1] [1]
```

`q1.items.append(1)` не создаёт атрибут экземпляра — атрибут читается из класса, а список изменяется на месте, поэтому «вторая очередь» видит те же данные. Это та же ловушка, что и изменяемое значение по умолчанию, только на уровне класса. Лечение — инициализация в `__init__`: `self.items = []`.

Два подводных камня рядом. Первый: `__init__` — не конструктор, а инициализатор; объект уже создан `__new__`, и возвращать из `__init__` ничего нельзя. Второй: имена с двумя подчёркиваниями (`self.__secret`) проходят через name mangling и превращаются в `_ClassName__secret` — это защита от случайного перекрытия в подклассах, а не приватность. Одно подчёркивание (`self._secret`) — соглашение «внутреннее, не трогать снаружи», которое соблюдают инструменты и люди, но не интерпретатор.

## Наследование, MRO и `super()`

При множественном наследовании Python строит линейный порядок разрешения методов (MRO, Method Resolution Order) алгоритмом C3: класс, затем его базовые классы слева направо, с сохранением порядка появления базовых классов. Порядок виден в атрибуте `__mro__`.

```python
class Base:
    def handle(self) -> list[str]:
        return ["Base"]

class WithRetry(Base):
    def handle(self) -> list[str]:
        return ["retry"] + super().handle()

class WithCache(Base):
    def handle(self) -> list[str]:
        return ["cache"] + super().handle()

class Gateway(WithRetry, WithCache):
    def handle(self) -> list[str]:
        return ["gw"] + super().handle()

print([c.__name__ for c in Gateway.__mro__])
print(Gateway().handle())
```

```text
['Gateway', 'WithRetry', 'WithCache', 'Base', 'object']
['gw', 'retry', 'cache', 'Base']
```

Ромб разрешён: `Base` встречается в цепочке один раз, хотя наследуется дважды. `super()` в `WithRetry` — это не «родитель», а «следующий класс в MRO экземпляра»: для `Gateway()` он ведёт в `WithCache`, а не в `Base`. Именно поэтому такой код называют кооперативным: каждый слой делает свою работу и передаёт управление дальше, и все слои выполняются ровно по одному разу. Если бы `WithRetry` вызывал `Base.handle(self)` напрямую, `WithCache` был бы пропущен, и порядок выполнения зависел бы от того, какой класс вызвал метод.

Практическое следствие: любой переопределённый метод в иерархии должен либо вызывать `super()`, либо явно документировать, что он терминальный. Иначе появляются «дыры», в которых не выполняется инициализация или не снимается блокировка.

## `@property`: вычисляемый атрибут с валидацией

Свойство (property) позволяет обращаться к методу как к атрибуту — без скобок. Типичное применение — валидация при присваивании и вычисляемые значения.

```python
class RetryPolicy:
    def __init__(self, attempts: int) -> None:
        self.attempts = attempts

    @property
    def attempts(self) -> int:
        return self._attempts

    @attempts.setter
    def attempts(self, value: int) -> None:
        if not 1 <= value <= 10:
            raise ValueError(f"attempts must be 1..10, got {value}")
        self._attempts = value

p = RetryPolicy(3)
print(p.attempts)
try:
    RetryPolicy(0)
except ValueError as exc:
    print("ValueError:", exc)
print(p.__dict__)
```

```text
3
ValueError: attempts must be 1..10, got 0
{'_attempts': 3}
```

Валидация срабатывает и в `__init__`, потому что там тоже идёт присваивание `self.attempts`. Это важный приём: правило проверки живёт в одном месте и не дублируется. Обратите внимание на `_attempts` в `__dict__` — декоратор `@property` создал в классе объект-дескриптор, а данные лежат в отдельном поле. Если назвать поле так же (`self.attempts = ...` внутри сеттера), получится бесконечная рекурсия.

Свойство без сеттера — способ сделать атрибут только для чтения. Минус `property` в том, что `dataclass` не умеет с ним дружить напрямую: поле, объявленное как `property`, не попадает в `__init__`. Поэтому в новых проектах валидацию чаще выносят в `__post_init__` или в отдельный конструктор вроде `pydantic`.

## `dataclass`: данные без шаблонного кода

`@dataclass` генерирует `__init__`, `__repr__` и `__eq__` по аннотациям полей. Это лучший выбор для значений конфигурации, результатов и DTO.

```python
from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Endpoint:
    host: str
    port: int = 8080
    tags: tuple[str, ...] = ()

e = Endpoint("api.internal")
print(e)
print(e == Endpoint("api.internal"), hash(e) == hash(Endpoint("api.internal")))
```

```text
Endpoint(host='api.internal', port=8080, tags=())
True True
```

`frozen=True` запрещает присваивание полей (бросает `FrozenInstanceError`), делает объект неизменяемым и заодно генерирует `__hash__` — такой объект можно класть в `set` и использовать ключом словаря. `slots=True` создаёт `__slots__` и убирает `__dict__`: на сотнях тысяч экземпляров экономия памяти заметна, а опечатка `e.hots = "x"` сразу даёт `AttributeError` вместо тихого создания нового атрибута.

Изменяемые значения по умолчанию `dataclass` запрещает осознанно: `headers: dict = {}` — ошибка при импорте. Правильно — `field(default_factory=dict)`, тогда каждая копия получает свой словарь:

```python
@dataclass
class Route:
    path: str
    headers: dict[str, str] = field(default_factory=dict)

r1, r2 = Route("/a"), Route("/b")
r1.headers["x"] = "1"
print(r1.headers, r2.headers)
```

```text
{'x': '1'} {}
```

Полезные переключатели: `order=True` добавляет сравнения (`<`, `>`), `kw_only=True` делает все поля именованными (удобно, когда полей много и легко перепутать порядок), `eq=False` отключает генерацию `__eq__`, если нужна идентичность. `__post_init__` вызывается после `__init__` — там валидируют и вычисляют производные поля.

## `Protocol`: структурная типизация

`Protocol` описывает не «от кого наследоваться», а «какие методы должны быть». Класс, у которого есть нужные методы, удовлетворяет протоколу без единого упоминания о нём — это структурная типизация, «утиная типизация» с проверкой статическим анализатором.

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Store(Protocol):
    def get(self, key: str) -> str | None: ...
    def put(self, key: str, value: str) -> None: ...

class MemoryStore:
    def __init__(self) -> None:
        self._d: dict[str, str] = {}
    def get(self, key: str) -> str | None:
        return self._d.get(key)
    def put(self, key: str, value: str) -> None:
        self._d[key] = value

print(isinstance(MemoryStore(), Store), issubclass(MemoryStore, Store))
```

```text
True True
```

Это главное преимущество перед ABC: `MemoryStore` не обязан импортировать `Store`, поэтому протокол можно объявить в вашем модуле для чужого класса — например, для `httpx.Client` или `redis.Redis`. Тесты подставляют фейк, реализующий те же два метода, и никакой иерархии не требуется.

`@runtime_checkable` нужен только для `isinstance`/`issubclass`, и проверяет он лишь наличие имён методов, а не их сигнатуры: класс с `get(self)` без аргументов пройдёт проверку, но упадёт при вызове. Поэтому `isinstance` по протоколу — грубый фильтр, а настоящая проверка типов происходит в `mypy`. Без `runtime_checkable` `isinstance` бросает `TypeError`.

## `ABC`: явный контракт с реализацией по умолчанию

Абстрактный базовый класс задаёт каркас: часть методов обязательна, часть реализована. Экземпляр ABC с нереализованными абстрактными методами создать нельзя.

```python
from abc import ABC, abstractmethod

class Backend(ABC):
    @abstractmethod
    def send(self, payload: bytes) -> None: ...

    def send_many(self, items: list[bytes]) -> int:
        for item in items:
            self.send(item)
        return len(items)

class NullBackend(Backend):
    def send(self, payload: bytes) -> None:
        print("drop", payload)

print(NullBackend().send_many([b"a", b"b"]))
```

```text
drop b'a'
drop b'b'
2
```

`Backend()` бросит `TypeError: Can't instantiate abstract class Backend without an implementation for abstract method 'send'`. Выбор между ABC и Protocol простой: если нужен общий код (как `send_many`) или жёсткая регистрация через `register()`, берите ABC; если нужен лишь контракт для типизации и подстановки в тестах — Protocol, он не создаёт иерархии и не тянет импорты.

## Композиция против наследования

Наследование говорит «является»; композиция — «содержит» и «умеет через». В инфраструктурном коде второе почти всегда точнее: клиент содержит политику ретраев, а не является ею.

```python
@dataclass(frozen=True)
class Policy:
    attempts: int = 3
    timeout: float = 2.0

class Client:
    def __init__(self, policy: Policy) -> None:
        self.policy = policy

    def call(self) -> str:
        return f"call with {self.policy.attempts} attempts"

print(Client(Policy(attempts=5)).call())
```

```text
call with 5 attempts
```

Политика — значение, её можно сравнить, сериализовать, подменить в тесте, не заводя подклассов `ClientWithFiveAttempts`. Наследование здесь дало бы комбинаторный взрыв: политика × транспорт × кэш.

Когда класс вообще лишний? Если нужен один метод — это функция. Если нужна структура данных без поведения — `dataclass` или `NamedTuple`. Если нужно пространство имён — модуль. Класс оправдан, когда есть состояние, инварианты и несколько методов, работающих с этим состоянием, — например, пул соединений с `acquire`/`release` и счётчиком занятых слотов. «Класс на всё» в скрипте деплоя — самый частый источник лишних 300 строк.

## Типичные ошибки

1. **Изменяемый атрибут класса.** `items = []` в теле класса делится всеми экземплярами. Механизм — чтение идёт из словаря класса, а список меняется на месте. Лечение — `__init__` или `field(default_factory=...)`.
2. **Прямой вызов базового метода вместо `super()`.** `Base.handle(self)` ломает кооперативную цепочку MRO, и часть слоёв не выполняется. Механизм — `super()` ищет следующий класс в MRO конкретного экземпляра, а не в иерархии класса.
3. **`self.attempts = ...` внутри сеттера `attempts`.** Бесконечная рекурсия, потому что присваивание снова попадает в сеттер. Механизм — property перехватывает доступ по имени; хранить нужно в `_attempts`.
4. **`isinstance` по `Protocol` как проверка контракта.** `runtime_checkable` смотрит только на имена методов, не на сигнатуры; ошибка всплывает при вызове. Механизм — проверка структурная и поверхностная.
5. **`frozen=True` и мутабельное поле.** Заморозка не глубокая: список внутри замороженного `dataclass` меняется спокойно, и хеш «плывёт». Механизм — `frozen` запрещает присваивание атрибутов, а не изменение объектов.
6. **Наследование ради переиспользования кода.** Подкласс `Client(BaseClient)` ради одного метода тянет за собой все атрибуты и ломается при изменении родителя. Механизм — наследование связывает классы сильнее, чем композиция.
7. **Инициализация в `__init__` тяжёлых ресурсов.** Создание пула или соединения в конструкторе делает класс непроверяемым и опасным при импорте. Механизм — конструктор вызывается там, где об этом не думают (например, в тестах).

## Чек-лист

- [ ] Ни один изменяемый объект не объявлен атрибутом класса; всё в `__init__` или `default_factory`.
- [ ] Все переопределённые методы вызывают `super()` либо явно задокументированы как терминальные.
- [ ] Конфигурационные и «значимые» типы — `@dataclass(frozen=True)`; для больших серий добавлен `slots=True`.
- [ ] Валидация входа живёт в `__post_init__` или сеттере, а не размазана по вызывающему коду.
- [ ] Для подменяемых зависимостей объявлен `Protocol`, а не ABC, если нужен только контракт.
- [ ] ABC используется там, где есть общий код или обязательная регистрация реализаций.
- [ ] Проверено `pytest`-ом, что фейк для протокола действительно реализует все методы (mypy, не `isinstance`).
- [ ] Каждый класс отвечает на вопрос «зачем он», а не «куда его положили»; одноразовые методы вынесены в функции.

## Упражнения

1. **Разминка.** Напишите `dataclass(frozen=True, slots=True)` `Resource(kind, name, namespace="default")` с методом `fqn`, возвращающим `namespace/kind/name`. Проверьте, что объект хешируется и попадает в `set`.
2. **MRO.** Постройте иерархию из четырёх классов-«слоёв» (таймаут, ретрай, метрики, логи) так, чтобы `__mro__` давал порядок «логи → метрики → ретрай → таймаут». Объясните, почему обратный порядок базовых классов ломает ожидания.
3. **Property.** Реализуйте класс `Backoff(base, factor, max_delay)` со свойством `delays`, возвращающим кортеж задержек, и валидацией всех трёх полей. Добейтесь, чтобы некорректное значение падало при создании, а не при использовании.
4. **Protocol.** Опишите протокол `Notifier` с методом `send(text: str) -> bool` и две реализации — в лог и в HTTP. Напишите функцию, принимающую `Notifier`, и проверьте её `mypy`-ом с обеими реализациями.
5. **Рефакторинг.** Возьмите класс на 150 строк с пятью методами, три из которых не используют `self`, и разделите его на `dataclass` + функции. Оцените, насколько уменьшилось число тестовых фикстур.
