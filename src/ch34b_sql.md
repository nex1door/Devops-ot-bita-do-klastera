# Глава 34b. SQL: индексы, планы, блокировки

Запрос на 3 мс и он же на 40 секунд отличаются одной строкой SQL. Причина почти всегда одна: база исполняет не то, что написано, а то, что выбрал планировщик по своей статистике и стоимости. В главе разбирается путь запроса от парсера до executor'а, как устроен B-tree и почему индекс иногда вредит, как читать `EXPLAIN ANALYZE` и ловить расхождение оценки с фактом, что происходит с данными при параллельных транзакциях и как разбирать {{L|g25|deadlock}} по логу. Примеры проверены на PostgreSQL 16 с таблицей в миллион строк.

## Как база исполняет запрос

Запрос проходит четыре стадии. Парсер строит синтаксическое дерево и проверяет имена таблиц и колонок. Переписывание (rewrite) разворачивает представления (views), применяет правила и row-level security. Планировщик (planner) перебирает варианты доступа и соединения и выбирает самый дешёвый по своей модели стоимости. Executor исполняет выбранный план узлами: каждый узел берёт строки у дочерних и отдаёт результат наверх.

Стоимость — условные единицы, а не время. По умолчанию `seq_page_cost = 1.0` (чтение страницы последовательно), `random_page_cost = 4.0` (случайное чтение), `cpu_tuple_cost = 0.01` за строку. Отсюда следует главное: планировщик сравнивает «прочитать 8000 страниц подряд» с «прочитать 20 страниц индекса и 20 страниц таблицы вразброс». На SSD разница между случайным и последовательным чтением меньше, чем заложено в дефолтах, и `random_page_cost = 1.1` часто ближе к реальности.

Решения планировщик принимает по статистике: гистограммы, число различных значений, корреляция физического порядка с логическим. Собирает её `ANALYZE` — вручную, автоанализом или `VACUUM ANALYZE`, по выборке `300 × default_statistics_target` строк (30 000 при дефолтном значении 100). Нет статистики — план строится по константам.

## B-tree: почему поиск логарифмический

B-tree — сбалансированное дерево, где все листья на одной глубине и связаны в список. Внутренние страницы содержат разделительные ключи, листья — пары «ключ → ссылка на строку» (TID: номер блока и смещение). Поиск спускается от корня к листу за высоту дерева: для миллиона строк это обычно три уровня, то есть три страницы вместо восьми тысяч. Диапазон (`BETWEEN`, `>`, `ORDER BY ... LIMIT`) читается как последовательный проход по списку листьев, без повторного спуска.

Индекс хранит ключи отсортированными, поэтому ускоряет и `ORDER BY`: чтение по индексу уже упорядочено. Плата — размер и запись: каждая вставка обновляет все индексы, а случайные ключи (UUID v4) дают случайные страницы и расщепление листьев.

## Селективность: когда индекс вредит

Селективность — доля строк, которую отбирает условие. Индекс выгоден, когда строк мало: прочитать 20 страниц таблицы дешевле, чем 8000. Когда строк много, дешевле прочитать таблицу подряд и отфильтровать на месте.

Живой пример: в таблице миллион заказов, у `status` четыре значения, `paid` — четверть строк.

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT id, total_cents FROM orders WHERE status = 'paid';
```

```
Seq Scan on orders  (cost=0.00..20631.00 rows=249333 width=12)
                    (actual time=0.010..86.978 rows=250000 loops=1)
  Filter: (status = 'paid'::text)
  Rows Removed by Filter: 750000
  Buffers: shared hit=8131
Execution Time: 94.429 ms
```

Индекс по `status` существует, но запрос, отбирающий 75% строк (`status <> 'paid'`), всё равно идёт seq scan'ом: вернуть придётся 750 000 строк, и индекс только добавит случайных чтений.

```
->  Parallel Seq Scan on orders  (cost=0.00..13339.33 rows=312764 width=0)
                                 (actual time=0.021..34.223 rows=250000 loops=3)
      Filter: (status <> 'paid'::text)
      Rows Removed by Filter: 83333
Execution Time: 50.926 ms
```

Практическое правило: индекс оправдан при выборке до нескольких процентов таблицы и почти бесполезен на 20–30%. Вредные индексы не бесплатны: каждый добавляет запись при `INSERT` и `UPDATE` и мешает autovacuum, поэтому индекс на низкоселективной колонке в одиночку — почти всегда ошибка.

## Составные индексы и левый префикс

Индекс по `(user_id, created_at DESC)` отсортирован сначала по `user_id`, внутри — по `created_at`. Поэтому он работает для условий на `user_id`, для `user_id` + диапазон по `created_at`, но бесполезен для одного `created_at`: нужные строки размазаны по всему дереву.

```sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
EXPLAIN (ANALYZE, BUFFERS) SELECT id FROM orders WHERE user_id = 42;
```

```
Bitmap Heap Scan on orders  (cost=4.58..81.85 rows=20 width=12)
                            (actual time=0.075..0.095 rows=20 loops=1)
  Recheck Cond: (user_id = 42)
  Heap Blocks: exact=20
  Buffers: shared hit=23 read=3
  ->  Bitmap Index Scan on idx_orders_user_created  (cost=0.00..4.58 rows=20 width=0)
        Index Cond: (user_id = 42)
Execution Time: 0.131 ms
```

Тот же запрос без индекса шёл 25 мс параллельным seq scan'ом по миллиону строк — выигрыш в двести раз на двадцати строках. А запрос `WHERE created_at > now() - interval '1 hour'` этот индекс не использует: планировщик берёт отдельный `idx_orders_created` и делает `Index Scan ... Index Cond: (created_at > ...)` за 2,5 мс. Правило левого префикса: индекс `(a, b)` обслуживает `a`, `a AND b`, но не `b`.

Порядок колонок: сначала сравнение на равенство, потом одна диапазонная, потом сортировка. `(user_id, created_at)` и `(user_id, status, created_at)` — разные индексы; второй покрывает `user_id AND status AND диапазон`. Колонки с равенством можно менять местами почти без потерь, диапазонную двигать влево нельзя.

## Покрывающий индекс

Если все нужные запросу колонки есть в индексе, executor не идёт в таблицу вовсе — это `Index Only Scan`. Синтаксис Postgres — `INCLUDE` для «полезной нагрузки»:

```sql
CREATE INDEX idx_orders_user_covering ON orders (user_id) INCLUDE (total_cents);
VACUUM ANALYZE orders;
```

```
Index Only Scan using idx_orders_user_covering on orders  (cost=0.42..4.78 rows=20 width=12)
                                                          (actual time=0.037..0.039 rows=20 loops=1)
  Index Cond: (user_id = 42)
  Heap Fetches: 0
  Buffers: shared hit=1 read=3
Execution Time: 0.056 ms
```

`Heap Fetches: 0` — таблица не читалась. Условие: страницы помечены в карте видимости (visibility map), а это делает `VACUUM`; без него в плане появится `Heap Fetches: 20` и выигрыш исчезнет. Колонки в `INCLUDE` не участвуют в сортировке индекса, но занимают место в листьях.

## EXPLAIN и EXPLAIN ANALYZE

`EXPLAIN` показывает план и оценку, не выполняя запрос. `EXPLAIN ANALYZE` выполняет и добавляет фактические строки и время — на продакшене это запрос, который реально пойдёт в базу, поэтому для `UPDATE` и `DELETE` его оборачивают в `BEGIN ... ROLLBACK`.

Читать план нужно как дерево: строки с большим отступом выполняются первыми и отдают результат родителю. В строке узла: `cost=старт..итог` в условных единицах, `rows` — оценка числа строк на выходе, `width` — средняя ширина строки в байтах, `actual time=первая_строка..все_строки`, `rows` после `actual` — фактические, `loops` — сколько раз узел запускался.

Ключевой навык — сравнивать оценку с фактом. Вот запрос с приведением типа, где статистики для выражения нет:

```
Gather  (cost=1000.00..16922.67 rows=5000 width=8) (actual time=11.734..48.227 rows=11 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  ->  Parallel Seq Scan on orders  (cost=0.00..15422.67 rows=2083 width=8)
                                   (actual time=13.702..42.582 rows=4 loops=3)
        Filter: ((total_cents)::text = '4999'::text)
        Rows Removed by Filter: 333330
Execution Time: 48.239 ms
```

Планировщик ждал 5000 строк, получил 11 — ошибка в 450 раз. Причина: гистограммы колонки `total_cents` для выражения `total_cents::text` не применимы, и он взял селективность по умолчанию (0,5%). Тот же запрос без приведения — `WHERE total_cents = 4999` — идёт через `Bitmap Index Scan` за 0,1 мс. В параллельных узлах `rows` — среднее на один воркер, поэтому фактические строки умножают на `loops`: 4 × 3 ≈ 12 при реальных 11, средние округляются.

Оценки врут по трём причинам: планировщик считает условия независимыми (умножает селективности, хотя значения коррелированы), статистики нет для выражений и для `LIKE` с ведущим `%`, и данные успели измениться после `ANALYZE`. Лечится `CREATE STATISTICS`, индексами по выражению, `ALTER COLUMN ... SET STATISTICS` и честным автоанализом.

## N+1 и как его увидеть

Код с циклом по заказам делает один запрос за списком и по запросу на каждый элемент — это 1 + N round-trip. На тысяче заказов при 1–2 мс на запрос получается 2 секунды вместо 10 мс. В плане это не видно: каждый запрос по отдельности идеален и попадает в индекс. Видно по счётчику запросов в middleware, по логу с тысячей одинаковых `SELECT` или по `pg_stat_statements`, где `calls` простого запроса растёт синхронно с RPS. Лечение — `JOIN` или `WHERE order_id = ANY($1)` (глава 34).

## Транзакции: ACID и уровни изоляции

ACID на пальцах: атомарность — либо всё, либо ничего; согласованность — ограничения схемы соблюдаются; изолированность — параллельные транзакции не видят полурезультатов; долговечность — закоммиченное выживает падение. Первые два свойства обеспечивает приложение и схема, два последних — журнал (WAL) и MVCC.

MVCC означает: пишущий не блокирует читающего, потому что читатель видит снимок данных на момент начала запроса, а старые версии строк живут в таблице, пока их не уберёт `VACUUM`. Отсюда главная аномалия PostgreSQL — распухание таблиц при долгих транзакциях: они держат горизонт, и мёртвые версии не удаляются.

| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы |
|---|---|---|---|
| Read Uncommitted | нет (работает как RC) | да | да |
| Read Committed | нет | да | да |
| Repeatable Read | нет | нет | нет |
| Serializable | нет | нет | нет |

`Read Committed` — дефолт: каждый оператор видит свой снимок, поэтому два одинаковых `SELECT` в одной транзакции могут вернуть разное. `Repeatable Read` даёт один снимок на транзакцию и в PostgreSQL дополнительно отлавливает потерянные обновления ошибкой `40001`. `Serializable` строит граф зависимостей (SSI) и откатывает транзакции, которые дали бы неверный результат при последовательном исполнении, — тоже `40001`, и его нужно повторять.

Практика: держать `Read Committed` и защищать конкретные инварианты явно — `SELECT ... FOR UPDATE` на строку, `UPDATE ... WHERE balance >= $1` с проверкой `RowsAffected`, уникальные индексы. `Serializable` берут, когда инвариант распределён по нескольким строкам и его неудобно защищать руками; тогда обязателен ретрай с jitter, иначе часть запросов будет падать под нагрузкой.

## Блокировки: row-level и deadlock

Запись строки берёт эксклюзивную блокировку до конца транзакции; читатель в MVCC не блокируется. `SELECT ... FOR UPDATE` берёт блокировку явно, `NOWAIT` падает сразу вместо ожидания, `SKIP LOCKED` пропускает занятые строки — так строят очередь задач на таблице. Блокировки строк не эскалируются в табличные, но каждая ждущая транзакция занимает соединение.

Deadlock (взаимная блокировка) возникает, когда две транзакции берут блокировки в разном порядке. PostgreSQL находит цикл через `deadlock_timeout` (по умолчанию 1 с) и убивает одну транзакцию:

```
ERROR:  deadlock detected
DETAIL:  Process 158 waits for ShareLock on transaction 845; blocked by process 151.
Process 151 waits for ShareLock on transaction 846; blocked by process 158.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,10) in relation "orders"
```

Читается так: процесс 158 ждёт транзакцию 845 (её держит 151), а 151 ждёт 846 (её держит 158) — цикл. `CONTEXT` показывает, на какой строке всё встало. Дальше в логе ищут два запроса этих сессий и видят разный порядок `UPDATE`: один блокировал заказ 10, потом 11; второй — наоборот. Лечится не ретраем, а порядком: обновлять строки в одном порядке (например, `ORDER BY id` перед циклом), укорачивать транзакции и не держать в них сетевые вызовы. Для разбора на живой базе — `SELECT pid, pg_blocking_pids(pid), query FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0`.

## Типовые убийцы производительности

**Функция от колонки в `WHERE`.** `WHERE date(created_at) = current_date - 3` не может использовать индекс по `created_at`: индекса по `date(created_at)` нет, и планировщик читает всю таблицу — 54 мс и `Rows Removed by Filter: 304533`. Диапазон по голой колонке даёт `Index Only Scan` за 16 мс.

```sql
-- плохо: индекс по created_at не используется
SELECT count(*) FROM orders WHERE date(created_at) = current_date - 3;
-- хорошо: тот же смысл, но sargable-условие
SELECT count(*) FROM orders
 WHERE created_at >= current_date - 3 AND created_at < current_date - 2;
```

**`LIKE '%x%'`.** Ведущий `%` не даёт сузить диапазон в B-tree: индекс упорядочен по началу строки. Даже `LIKE 'user1%'` в общем случае не использует обычный индекс — нужен `text_pattern_ops` или collation `C`; для поиска по подстроке ставят `pg_trgm` с GIN-индексом.

**Неявное приведение типов.** `WHERE total_cents::text = '4999'` — тот же случай, что выше: 48 мс против 0,1 мс. В MySQL хуже: сравнение строковой колонки с числом приводит колонку к числу молча, и индекс перестаёт работать без всякой ошибки в коде.

**`OFFSET` на больших таблицах.** `LIMIT 20 OFFSET 800000` заставляет прочитать и отсортировать 800 020 строк: `Sort Method: external merge Disk: 25488kB`, 412 мс и 25 МБ временных файлов. Keyset-пагинация — `WHERE created_at < $1 ORDER BY created_at DESC LIMIT 20` — те же 20 строк за 54 мс без сортировки.

## Типичные ошибки

1. **Индекс «на всякий случай».** Каждый индекс замедляет запись и занимает место; индекс на низкоселективной колонке не используется и вредит.
2. **`EXPLAIN` без `ANALYZE`.** Оценка не равна факту: план выглядит дешёвым, а запрос идёт секунды.
3. **Вера в `rows` без сравнения с `actual rows`.** Расхождение в десятки раз — сигнал о плохой статистике, а не о медленном диске.
4. **Функция или приведение типа на колонке в `WHERE`.** Условие перестаёт быть sargable, и индекс не применяется.
5. **Долгие транзакции.** Держат горизонт MVCC, мешают `VACUUM`, копят мёртвые строки и блокировки.
6. **Разный порядок блокировок.** Причина большинства deadlock'ов; ретрай лечит симптом, а не цикл.
7. **`OFFSET` для глубокой пагинации.** Стоимость растёт линейно с номером страницы, хотя нужны те же 20 строк.

## Чек-лист

- [ ] У каждого частого запроса есть план из `EXPLAIN (ANALYZE, BUFFERS)` на объёме, близком к продакшену.
- [ ] Оценка `rows` сопоставлена с `actual rows`; расхождение больше 10 раз объяснено.
- [ ] Условия в `WHERE` sargable: нет функций и приведений над колонкой.
- [ ] Составные индексы начинаются с колонок равенства, диапазонная — последняя.
- [ ] Для горячих точечных запросов рассмотрен покрывающий индекс и `Heap Fetches: 0`.
- [ ] Транзакции короткие, порядок блокировок единый, на `40001` есть ретрай.
- [ ] Глубокая пагинация сделана по ключу, а не через `OFFSET`.
- [ ] `autovacuum` и `ANALYZE` работают; статистика не устарела после массовой загрузки.

## Упражнения

1. Создайте таблицу на миллион строк и снимите `EXPLAIN (ANALYZE, BUFFERS)` для запроса без индекса, с индексом и с индексом на низкоселективной колонке; объясните выбор планировщика.
2. Постройте составной индекс `(user_id, status, created_at)` и найдите три запроса, для которых он работает, и три, для которых бесполезен.
3. Добейтесь расхождения оценки и факта в сто раз через приведение типа или коррелированные колонки; почините план через `CREATE STATISTICS` или индекс по выражению.
4. Воспроизведите deadlock двумя сессиями `psql` с обратным порядком `UPDATE`; найдите виновника по `pg_blocking_pids` и исправьте порядок блокировок.
5. Перепишите пагинацию с `OFFSET 800000` на keyset и сравните `Buffers`, `temp` и время на двух планах.
