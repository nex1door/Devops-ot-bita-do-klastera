# Приложение A. Чек-лист продакшн-сервиса

Чек-лист читают выборочно: перед первым деплоем, на ревью архитектуры, при разборе инцидента. Поэтому каждый пункт — проверяемое утверждение с обоснованием: не «используйте таймауты», а «таймаут задан на каждом внешнем вызове, иначе зависшая зависимость исчерпает пул воркеров». Пункт, который нельзя защитить на ревью, в список не попадает.

Блоки идут в порядке пути изменения: код → образ → конфигурация → сеть → данные → наблюдаемость → эксплуатация → безопасность.

## Код и зависимости

- [ ] **Версии зафиксированы lock-файлом** (`uv.lock`, `go.sum`, `package-lock.json`) — сборка без него через месяц возьмёт другие версии, и в прод поедет код, которого не было в тестах.
- [ ] **Lock-файл лежит в репозитории и обновляется отдельным PR** — обновление зависимости должно быть видно в истории и откатываться одним revert.
- [ ] **В репозитории нет секретов**: ни `.env` с паролями, ни ключей в коде, ни токенов в истории — попавший в git секрет считается скомпрометированным, помогает только ротация.
- [ ] **Secret scanning работает в CI** (`gitleaks detect --redact`, secret scanning хостинга) — человек забудет про ключ, автоматика проверит на каждом push.
- [ ] **Линтер и форматтер закреплены версией и запускаются в CI** — иначе ревью обсуждает отступы, а разные версии линтера дают разные приговоры одному коду.
- [ ] **Статический анализ проходит**: `mypy --strict` для Python, `go vet` и `golangci-lint` для Go — часть дефектов дешевле ловить до запуска, чем в инциденте.
- [ ] **Сборка воспроизводится из чистого клона** (`git clone … && make build`) — если нужны локальные доустановки, у команды нет сборки, а есть устная традиция.
- [ ] **Мёртвый код и фича-флаги с постоянным значением удалены** — флаг, который всегда включён, это ветка, которую никто не тестирует.
- [ ] **Правка закрыта тестом, который падает без неё** — тест, написанный после кода и не проверенный на «красном», фиксирует текущее поведение, а не требуемое.
- [ ] **Зависимости берутся из доверенного registry** с проверкой хэшей — подмена пакета в публичном индексе это атака на цепочку поставок, а не теория.

## Сборка и образ

- [ ] **Multi-stage сборка**: компилятор и dev-зависимости остаются в стадии `builder`, в финальный образ копируется только артефакт — иначе компилятор, `.git` и кэш пакетов уезжают в прод.
- [ ] **Базовый образ закреплён по digest** (`python:3.14-slim@sha256:…`), а не `latest` — тег перезаписывается, digest нет.
- [ ] **Процесс работает не от root**: `USER app` в Dockerfile, `runAsNonRoot` в поде — компромисс приложения не должен сразу давать root в контейнере.
- [ ] **Корневая ФС только для чтения**, запись — в явно смонтированные каталоги (`--read-only --tmpfs /tmp`) — так ловится и код, который пишет в случайные места.
- [ ] **Образ собирается в CI, а не на ноутбуке**, и тот же digest едет в стейджинг и прод — «собрал локально» ломает и воспроизводимость, и подпись.
- [ ] **SBOM генерируется на сборке** (`syft`, `trivy image --format cyclonedx`) и хранится рядом с образом — при новой CVE нужно за минуты узнать, затронуты ли вы.
- [ ] **`.dockerignore` исключает `.git`, `node_modules`, `.venv`, тесты** — контекст сборки определяет и скорость, и размер слоёв.
- [ ] **Образ подписан** (`cosign sign`), в кластере проверяется подпись — тег можно перезаписать, подпись привязана к digest.
- [ ] **В слоях нет секретов и мусора**: `docker history --no-trunc` не содержит команд с ключами, а `.git` и тестовые данные не попали в контекст — иначе секрет уезжает туда же, куда и образ.

## Конфигурация

- [ ] **Конфиг приходит из окружения или файла-секрета, а не из кода** — один образ должен работать в стейджинге и проде без пересборки.
- [ ] **Обязательные параметры валидируются на старте** (pydantic-settings, `go-playground/validator`) — упасть при запуске дешевле, чем на первом запросе.
- [ ] **Fail-closed**: нет пароля к БД, ключа подписи или сертификата — сервис не стартует, а не работает в «режиме без проверки».
- [ ] **Различие сред — только в значениях, не в наборе ключей** — иначе прод исполняет ветку кода, которой не было в тестах.
- [ ] **Секреты не видны в `docker inspect` и в env образа** — переменные читает любой с доступом к API; для секретов нужен файл или vault.
- [ ] **У дефолтов один источник правды** — дефолт, продублированный в трёх местах, разъезжается молча.
- [ ] **Изменение конфига не требует пересборки**, но требует рестарта или релоада, и это записано в runbook.
- [ ] **Файлы секретов монтируются с правами 0400 и владельцем процесса** — секрет, читаемый всем в контейнере, бесполезен как секрет.

## Сеть и доступ

- [ ] **TLS терминируется на границе, внутри — mTLS или приватная сеть** — «внутри доверенная сеть» перестаёт быть правдой в первый день компромисса.
- [ ] **TLS не ниже 1.2, лучше 1.3**, слабые шифры отключены — сканеры и комплаенс спрашивают об этом первыми.
- [ ] **Таймаут задан на каждом внешнем вызове** (connect, read, total) и меньше таймаута вызывающего — иначе зависшая зависимость съест пул воркеров.
- [ ] **Есть общий бюджет времени запроса**: дедлайн на входе, context/таймаут вниз по стеку — иначе каскад ретраев превращает деградацию в отказ.
- [ ] **Rate limit на входе** (token bucket по IP или токену) — без него один клиент с циклом `while true` кладёт сервис.
- [ ] **Ограничены размер тела и число одновременных соединений** — иначе память кончается от нескольких медленных клиентов.
- [ ] **Healthcheck разделён**: liveness не зависит от БД, readiness проверяет готовность принимать трафик — иначе падение БД вызывает лавину перезапусков.
- [ ] **Порт слушается на нужном интерфейсе** (`127.0.0.1` для админки и метрик) — «0.0.0.0 по привычке» публикует отладку наружу.
- [ ] **Исходящие соединения ограничены политиками** — сервису нужны БД и два API, а не весь интернет.
- [ ] **Клиент проверяет сертификат сервера**, отключение проверки не зашито в код и не приходит из конфига — `verify=False` в проде обнуляет TLS.

## Данные

- [ ] **Бэкап есть, и восстановление проверено** на чистом окружении за последние 30 дней — непроверенный бэкап — это гипотеза, а не бэкап.
- [ ] **RPO и RTO записаны числами** — «бэкап раз в сутки» отвечает, сколько потеряем, но не за сколько поднимемся.
- [ ] **Копия хранится вне основного отказа**: другой регион или аккаунт, отдельные креды — иначе одна авария уносит и данные, и бэкапы.
- [ ] **Миграции совместимы в обе стороны** (expand/contract): сначала новая колонка, потом код, потом удаление старой — иначе откат приложения ломает схему.
- [ ] **Миграции версионированы и идемпотентны** (Alembic, goose, golang-migrate) — повторный запуск не должен падать.
- [ ] **Долгие миграции не блокируют таблицу** (`CREATE INDEX CONCURRENTLY`, батчи) — `ALTER TABLE` на миллионе строк останавливает сервис целиком.
- [ ] **Данные, которые нельзя потерять, реплицируются синхронно** — асинхронная реплика теряет последние транзакции при падении мастера.
- [ ] **Удаление данных предусмотрено** (retention, запрос на удаление персональных данных) — «храним всё вечно» тоже решение, только со штрафом.
- [ ] **Пул соединений к БД ограничен и имеет таймаут ожидания** — без лимита всплеск трафика открывает тысячи соединений и роняет БД раньше, чем приложение.

## Наблюдаемость

- [ ] **Метрики RED на каждом сервисе** (rate, errors, duration) и USE для ресурсов — без них инцидент обсуждают по ощущениям.
- [ ] **Латентность считается по перцентилям, а не средним** — среднее скрывает хвост, который и чувствуют пользователи.
- [ ] **Логи структурные (JSON) и с correlation id** — grep по тексту работает до первого масштабирования, дальше нужны поля.
- [ ] **Уровень логирования меняется без пересборки**, `debug` не включён в проде — это и объём, и утечка данных.
- [ ] **Алерты по симптомам, а не по причинам**: «5xx выше 2% пять минут», а не «CPU выше 80%» — высокий CPU может быть нормой.
- [ ] **У каждого алерта есть действие**: ссылка на runbook, владелец и порог, при котором он правда требует вмешательства.
- [ ] **Дашборд открывается за один клик** и показывает золотые сигналы, а не сорок графиков.
- [ ] **Трейсинг включён на границах** (HTTP, БД, очередь) с сэмплированием — логи говорят «что», трейс говорит «где».
- [ ] **Логи и метрики живут дольше инцидента**: 14–30 дней минимум — разбор обычно начинается на следующий день.
- [ ] **Лейблы метрик не кардинальны**: `user_id`, `request_id` и сырой URL в лейблах взрывают хранилище — их место в логах и трейсах.

## Эксплуатация

- [ ] **Runbook на каждый сервис**: как проверить, как перезапустить, как откатить, кого звать — в три часа ночи читают runbook, а не архитектурный документ.
- [ ] **On-call расписан** с эскалацией и вменяемым горизонтом — «отвечают все» значит «не отвечает никто».
- [ ] **Requests и limits заданы**: requests для планировщика, limits для защиты соседей — без них один под съедает ноду.
- [ ] **Graceful shutdown реализован**: SIGTERM → перестать принимать → доработать → выйти, и укладывается в `terminationGracePeriodSeconds`.
- [ ] **Есть preStop-пауза или задержка вывода из балансировки** — иначе трафик приходит в уже умирающий процесс.
- [ ] **Несколько реплик и PodDisruptionBudget** — обновление и обслуживание ноды не должны быть заметны.
- [ ] **Откат проверен на практике**, а не описан: предыдущий образ запускается и совместим с текущей схемой БД.
- [ ] **Дежурный набор команд лежит в одном месте** (`rollout undo`, `drain`, `scale`) — импровизация под давлением даёт вторую аварию.
- [ ] **Версия и commit видны снаружи** (`/healthz` или метрика `build_info`) — иначе первый вопрос инцидента «что сейчас развёрнуто» остаётся без ответа.

## Безопасность

- [ ] **CVE-скан блокирует сборку** при critical/high с доступным фиксом (trivy, grype) — скан, который только пишет отчёт, ни на что не влияет.
- [ ] **Секреты ротируются по расписанию и после ухода человека** — неограниченный срок жизни превращает утечку в вечный доступ.
- [ ] **Минимальные привилегии**: сервисный аккаунт с нужными verbs, пользователь БД с правами на свою схему, `privileged: false`, capabilities срезаны.
- [ ] **Доступ к проду именной и аудируемый** (SSO, `kubectl` через прокси с логами) — общий root-пароль делает ответ на вопрос «кто это сделал» невозможным.
- [ ] **Зависимости проверяются не только на CVE, но и на поддержку** — заброшенный пакет — это будущая CVE без патча.
- [ ] **Секреты не попадают в логи и трейсы**: маскирование на уровне логгера, а не «мы аккуратно».
- [ ] **Артефакты проверены на утечку**: `.env`, ключи и дампы не попадают ни в образ, ни в бэкап.
- [ ] **Образ пересканируется и после публикации**, а не только на сборке — CVE появляются у неизменного образа, потому что меняется база уязвимостей.

## Минимум перед первым деплоем в прод

1. Образ собран в CI, закреплён по digest, работает не от root.
2. Lock-файл в репозитории, секретов в git нет.
3. Обязательные параметры валидируются, без секрета сервис не стартует.
4. Таймауты заданы на всех внешних вызовах.
5. Liveness и readiness разделены и настроены.
6. Миграции совместимы с предыдущей версией приложения.
7. Бэкап снят и хотя бы раз восстановлен вручную.
8. Метрики, структурные логи и один алерт на всплеск 5xx.
9. Лимиты ресурсов и graceful shutdown.
10. Runbook с процедурой отката и фамилия дежурного.

## Что проверить при инциденте

Сначала сузить область, потом менять. Любое изменение до диагностики уничтожает улики, а «на всякий случай перезапустил» стирает причину.

1. **Масштаб и начало**: с какого времени, все пользователи или часть, какая доля запросов падает — это отсекает «наш сервис» от «сеть и провайдер».
2. **Что менялось за последние два часа**: деплой, миграция, конфиг, фича-флаг, сертификат.
3. **Ресурсы**: CPU throttling, память и OOMKilled, диск и inodes, число соединений.
4. **Зависимости**: БД (пул, медленные запросы, блокировки), DNS, внешние API, очередь.
5. **Сеть**: код ответа на балансировщике, срок сертификата, потери пакетов до пода.
6. **Логи и трейсы** по correlation id конкретного упавшего запроса.
7. **Решение**: причина коррелирует с изменением — откат; не коррелирует — стабилизация (масштаб, лимиты, отключение фичи).
8. **Коммуникация**: статус, оценка, следующий апдейт через 30 минут.

| Симптом | Первое, что смотреть |
|---|---|
| 5xx на балансировщике, поды живы | логи приложения, `kubectl logs --previous`, ошибки зависимостей |
| 502/504 | readiness, таймаут upstream, порт в Service и targetPort |
| поды в CrashLoopBackOff | `kubectl describe pod` → Last State, exit code, лимит памяти |
| латентность выросла, ошибок нет | CPU throttling, пул соединений к БД, GC-паузы, медленный запрос |
| трафик не доходит | пустые Endpoints, селектор, NetworkPolicy, DNS-имя |
| внезапные 401/403 | ротация секретов, истёкший токен или сертификат, RBAC |
| диск заполнен | логи, `/tmp`, WAL, старые образы, inodes |

Первые команды при разборе:

```bash
kubectl get pods -o wide --sort-by=.status.startTime | tail -5
kubectl describe pod api-7d9f-x2 | sed -n '/Events/,$p'
kubectl logs api-7d9f-x2 --previous --tail=100
kubectl rollout history deploy/api | tail -3
ss -s; df -h /; df -i /
```
