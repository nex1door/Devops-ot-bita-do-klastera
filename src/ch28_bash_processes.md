# Глава 28. Процессы, сигналы, перенаправления

Скрипт — это процесс, у которого есть родитель, идентификатор, файловые дескрипторы и обработчики сигналов. Пока вы пишете линейные команды, эта механика невидима; как только появляется фоновая задача, демон, таймаут или «почему скрипт завис на конвейере», без неё не обойтись. В главе разобрано, как ядро создаёт процессы и кто их хоронит, как работает job control, что означают сигналы `SIGTERM`, `SIGKILL`, `SIGHUP` и `SIGINT`, как устроены перенаправления и дескрипторы, чем опасен конвейер без `pipefail`, зачем нужна подстановка процессов и почему `nohup` — не супервизор. В конце — рабочий пример graceful-останова с таймаутом и эскалацией до `SIGKILL`.

## Процесс, PID, PPID

Каждый запущенный процесс получает идентификатор (PID) — целое число, уникальное в момент жизни процесса и переиспользуемое после выхода. У процесса есть родитель (PPID): тот, кто вызвал `fork`. Корень дерева — процесс с PID 1, в современных дистрибутивах это `systemd`, в контейнере — команда, указанная в `ENTRYPOINT`.

```bash
$ echo "мой pid=$$, родитель=$(ps -o ppid= -p $$ | tr -d ' ')"
мой pid=541909, родитель=541907
$ ps -o pid,ppid,stat,etime,cmd --ppid $$
    PID    PPID STAT     ELAPSED CMD
 541911  541909 S          00:00 sleep 0.2
```

`ps` показывает состояние (`STAT`): `R` — выполняется, `S` — спит в ожидании, `D` — непрерываемый сон (обычно ждёт диск), `Z` — зомби, `T` — остановлен. Зомби — это завершившийся процесс, чей код возврата ещё не забрал родитель: запись в таблице процессов осталась, ресурсов нет. Лечится не убийством зомби (его уже нет), а тем, чтобы родитель вызвал `wait`. Если родитель — ваш скрипт, следите, чтобы он дожидался фоновых задач.

Полезные команды: `ps aux` — всё, `pgrep -af nginx` — найти по имени с полной командной строкой, `pstree -p` — дерево, `kill -0 PID` — проверить существование и право послать сигнал (сигнал не отправляется). Каталог `/proc/PID` даёт всё остальное: `cmdline`, `environ`, `fd`, `status`.

## Job control

Job control — механизм интерактивной оболочки. `cmd &` запускает команду в фоне и печатает номер задачи и PID, `jobs` показывает список, `fg %1` возвращает задачу на передний план, `bg %1` продолжает остановленную в фоне. `Ctrl-Z` посылает `SIGTSTP` — приостановить, `Ctrl-C` — `SIGINT`, `Ctrl-\` — `SIGQUIT` с дампом памяти.

В скриптах job control обычно выключен (`set +m`), и `&` означает просто «не ждать». Управлять такими задачами нужно через `$!` и `wait`:

```bash
./worker-a.sh & a=$!
./worker-b.sh & b=$!
wait "$a"; rc_a=$?
wait "$b"; rc_b=$?
```

`wait` без аргументов ждёт все дочерние процессы и возвращает 0. `wait "$pid"` возвращает код именно этого процесса — это единственный надёжный способ узнать, чем закончилась фоновая задача. `disown` убирает задачу из таблицы оболочки: при выходе из терминала ей не пошлют `SIGHUP`, но и `wait` на неё уже не подействует.

Важно: `kill %1` работает только в интерактивной оболочке с job control. В скрипте адресуйте процессы по PID.

## Сигналы

Сигнал — асинхронное уведомление процессу от ядра или другого процесса. У каждого сигнала есть действие по умолчанию, и его можно изменить: перехватить (обработчик в коде) или игнорировать.

| Сигнал | Номер | Смысл | Ловится |
|---|---|---|---|
| `SIGHUP` | 1 | терминал закрыт; у демонов — «перечитай конфиг» | да |
| `SIGINT` | 2 | `Ctrl-C`, прервать | да |
| `SIGQUIT` | 3 | `Ctrl-\`, завершить с дампом | да |
| `SIGKILL` | 9 | безусловное убийство | **нет** |
| `SIGPIPE` | 13 | запись в закрытый конец конвейера | да |
| `SIGTERM` | 15 | штатное завершение | да |
| `SIGCHLD` | 17 | потомок завершился | да |
| `SIGSTOP` | 19 | приостановить | **нет** |
| `SIGTSTP` | 20 | `Ctrl-Z`, приостановить | да |

Номера зависят от архитектуры; в Linux на x86-64 они такие, как в таблице. В скриптах используйте имена (`kill -TERM`), а не числа: имена переносимы.

`SIGKILL` и `SIGSTOP` нельзя перехватить или проигнорировать — это гарантия ядра. Всё остальное можно. Поэтому «убейте меня аккуратно» — это всегда `SIGTERM`, а `SIGKILL` — крайняя мера, после которой не выполнятся ни `trap`, ни `flush` буферов, ни удаление временных файлов.

`SIGHUP` исторически означал обрыв линии с терминалом. Сейчас его используют демоны как «перечитай конфигурацию» (так делают `nginx`, `haproxy`, `sshd`), а оболочка посылает его фоновым задачам при выходе. `nohup` ровно это и делает — ставит `SIGHUP` в игнор.

`SIGPIPE` — причина кода 141. Он приходит, когда процесс пишет в трубу, читатель которой уже закрылся: `yes | head -1` заставляет `yes` получить `SIGPIPE` после первой строки.

```bash
$ bash -c 'set -o pipefail; yes | head -1; echo "код=$? PIPESTATUS=${PIPESTATUS[*]}"'
y
код=141 PIPESTATUS=141 0
```

Для многих утилит (grep, head, awk) такой исход штатный, и в скрипте с `pipefail` его нужно либо ожидать, либо не использовать `pipefail` на этом конвейере.

## Перенаправления

У процесса три стандартных дескриптора: 0 — stdin, 1 — stdout, 2 — stderr. Перенаправление меняет, куда они указывают, и делает это шелл до запуска программы.

```bash
cmd > file          # stdout в файл, перезапись
cmd >> file         # stdout в файл, дозапись
cmd 2> err.log      # только stderr
cmd &> all.log      # stdout и stderr (bash; в POSIX — > all.log 2>&1)
cmd < input.txt     # stdin из файла
cmd 2>&1 | less     # stderr в тот же поток, что stdout, и в конвейер
```

**Порядок имеет значение.** `команда > file 2>&1` и `команда 2>&1 > file` дают разный результат, потому что перенаправления применяются слева направо. В первом случае stdout уходит в файл, затем stderr дублируется в текущий stdout — то есть тоже в файл. Во втором stderr дублируется в текущий stdout (терминал), и только потом stdout меняется на файл:

```bash
$ ls /nope > a.txt 2>&1; cat a.txt
ls: cannot access '/nope': No such file or directory
$ ls /nope 2>&1 > b.txt
ls: cannot access '/nope': No such file or directory
$ wc -c < b.txt
0
```

Во втором случае сообщение ушло на терминал, а файл пуст. Это самая частая ошибка при написании cron-задач: лог пустой, а письма от cron приходят.

`/dev/null` — устройство, которое принимает всё и возвращает пустоту. `cmd > /dev/null 2>&1` — полностью тихий запуск. `cmd 2>/dev/null` — скрыть только ошибки (опасно: вы теряете диагностику).

Дескрипторы можно открывать вручную, и это полезно в циклах, где нельзя переоткрывать файл на каждой итерации:

```bash
exec 3> report.txt
for h in web-01 web-02 web-03; do
    printf '%s %s\n' "$h" "$(date +%T)" >&3
done
exec 3>&-
```

`exec 3> file` открывает дескриптор 3 в текущей оболочке, `>&3` пишет в него, `3>&-` закрывает. Без закрытия дескриптор живёт до конца скрипта; при передаче его дочерним процессам это иногда нужно намеренно.

## Пайпы и pipefail

Конвейер `a | b` соединяет stdout `a` со stdin `b` через буфер в ядре (по умолчанию 64 КиБ). Обе команды запускаются одновременно, поэтому `tail -f app.log | grep ERROR` работает в реальном времени, а не после завершения `tail`.

Код возврата конвейера по умолчанию — код последней команды. `true | false | true` вернёт 0, хотя середина упала:

```bash
$ bash -c 'true | false | true; echo "без pipefail: $?"'
без pipefail: 0
$ bash -c 'set -o pipefail; true | false | true; echo "с pipefail: $? PIPESTATUS=${PIPESTATUS[*]}"'
с pipefail: 1 PIPESTATUS=0 1 0
```

`PIPESTATUS` — массив кодов всех команд конвейера, доступный сразу после него. Он перезаписывается следующей командой, поэтому читать его нужно немедленно.

`pipefail` — почти всегда правильный выбор для скриптов: иначе `curl ... | jq .` вернёт 0, даже если `curl` не смог соединиться и `jq` разобрал пустоту. Исключения — конвейеры, где ненулевой код штатен: `grep`, `diff`, `head` с `SIGPIPE`.

## Подстановка процессов

`<(команда)` создаёт временный файловый дескриптор (в Linux — `/dev/fd/63`) и подставляет его как имя файла. Это позволяет передать вывод команды туда, где ожидается путь:

```bash
$ diff <(printf 'a\nb\nc\n') <(printf 'a\nc\nd\n')
2d1
< b
3a3
> d
$ while read -r user; do echo "пользователь: $user"; done < <(awk -F: '$3 >= 1000 {print $1}' /etc/passwd)
```

Второй пример важен: `while read` в конвейере выполняется в подоболочке, и переменные, изменённые внутри, не видны снаружи. Подстановка процессов сохраняет цикл в текущей оболочке. `>(команда)` работает в обратную сторону — пишет в stdin команды: `cmd > >(logger -t app)`.

## nohup и почему systemd лучше

`nohup cmd &` игнорирует `SIGHUP`, перенаправляет вывод в `nohup.out` и оставляет процесс жить после закрытия терминала. Этого достаточно, чтобы процесс пережил сессию SSH, но не достаточно, чтобы им управлять: никто не перезапустит его после падения, не ограничит память, не соберёт логи в journal, не остановит при выключении машины и не покажет статус.

`systemd` даёт всё это через unit-файл: перезапуск по `Restart=on-failure`, лимиты через `MemoryMax`, логи в journal автоматически (stdout и stderr процесса), остановка через `systemctl stop` с корректной последовательностью сигналов: `SIGTERM` всей контрольной группе, ожидание `TimeoutStopSec` (по умолчанию 90 секунд), затем `SIGKILL`. Юниты и таймеры разобраны в главе 29; здесь важен принцип: `nohup` — способ отвязаться от терминала, `systemd` — способ управлять жизненным циклом.

## Пример: graceful-остановка процесса по SIGTERM

Задача: остановить воркер так, чтобы он успел дописать текущую задачу, а если не успел за отведённое время — добить. Сначала сам воркер с обработчиком:

```bash
#!/usr/bin/env bash
set -euo pipefail
PIDFILE=${1:?pidfile}
echo $$ > "$PIDFILE"
stopping=0
on_term() {
    echo "[worker $$] получил SIGTERM, завершаю текущую задачу" >&2
    stopping=1
}
trap on_term TERM INT
while (( ! stopping )); do
    sleep 0.2
done
echo "[worker $$] очистка и выход" >&2
rm -f "$PIDFILE"
exit 0
```

Обработчик не завершает процесс сразу: он выставляет флаг, и цикл выходит сам, когда текущая итерация закончена. Прерывать работу посреди записи файла нельзя — это и есть смысл graceful-останова. `sleep` при этом прерывается сигналом, поэтому реакция быстрая.

Теперь останавливающий скрипт с таймаутом и эскалацией:

```bash
#!/usr/bin/env bash
set -euo pipefail
PIDFILE=${1:?укажите pid-файл}
TIMEOUT=${2:-10}
pid=$(cat "$PIDFILE")
kill -TERM "$pid"
for ((i = 0; i < TIMEOUT * 10; i++)); do
    if ! kill -0 "$pid" 2>/dev/null; then
        echo "процесс $pid завершился штатно за ~$((i / 10)) с"
        exit 0
    fi
    sleep 0.1
done
echo "процесс $pid не ответил за ${TIMEOUT} с, отправляю SIGKILL" >&2
kill -KILL "$pid" 2>/dev/null || true
exit 1
```

Запуск в фоне, ожидание и остановка дают такой результат:

```
worker pid=541909, ppid=541907
процесс 541909 завершился штатно за ~0 с
stop rc=0
[worker 541909] получил SIGTERM, завершаю текущую задачу
[worker 541909] очистка и выход
```

Разбор деталей. `kill -0` не посылает сигнал, а проверяет, существует ли процесс и есть ли право ему сигналить; это стандартный способ polling-ожидания. `2>/dev/null` скрывает `No such process` после выхода. `|| true` после `kill -KILL` нужен потому, что процесс мог умереть между проверкой и сигналом, а `set -e` на этом бы остановил скрипт с невнятной ошибкой. `exit 1` сигнализирует вызывающему, что штатного останова не было, — это важно для `systemctl`, который в таком случае зафиксирует проблему.

## Типичные ошибки

1. **`cmd > file 2>&1` в неправильном порядке.** Механизм: перенаправления применяются слева направо; `2>&1 > file` отправляет stderr на старый stdout (терминал), а stdout — в файл. Диагностика теряется, лог пуст.
2. **`SIGKILL` как первый выбор.** Механизм: сигнал нельзя перехватить, `trap` не выполнится, временные файлы останутся, буферы не сброшены, соединения не закрыты. Сначала `SIGTERM` и ожидание.
3. **`kill %1` в скрипте.** Механизм: job control в неинтерактивной оболочке выключен, `%1` не разрешается. Адресуйте по PID из `$!` или pid-файла.
4. **Переменные из `while read` в конвейере.** Механизм: конвейер создаёт подоболочку, изменения переменных не видны снаружи. Лечится подстановкой процессов `< <(...)` или `mapfile`.
5. **Нет `pipefail`.** Механизм: код конвейера — код последней команды, падение середины маскируется. `curl | jq` вернёт 0 при неудачном соединении.
6. **`nohup` вместо супервизора.** Механизм: `nohup` только игнорирует `SIGHUP`; перезапуска, лимитов и ротации логов нет. Для сервисов — {{L|g115|systemd}} unit.
7. **Ожидание `kill` без проверки.** Механизм: сигнал асинхронен, после `kill` процесс ещё жив. Нужен polling через `kill -0` с таймаутом.

## Чек-лист

- Для остановки используется `SIGTERM`, `SIGKILL` — только после таймаута.
- В скрипте-супервизоре есть ожидание с `kill -0` и ограничением по времени.
- Порядок перенаправлений проверен: `> file 2>&1`, а не наоборот.
- В шапке скрипта есть `set -o pipefail`, а случаи штатного ненулевого кода обработаны явно.
- Фоновые задачи адресуются по `$!`/pid-файлу, результат забирается через `wait`.
- PID-файл создаётся после успешного старта и удаляется в `trap ... EXIT`.
- Для сервисов, которые должны жить после выхода из SSH, используется systemd, а не `nohup`.
- Проверено поведение при `Ctrl-C`: временные файлы удаляются, блокировки снимаются.

## Упражнения

1. Напишите скрипт, который запускает три команды параллельно, ждёт все и печатает коды возврата каждой. Убедитесь, что общий код скрипта ненулевой, если упала хотя бы одна.
2. Объясните и проверьте на практике разницу между `cmd > log 2>&1` и `cmd 2>&1 > log`, перенаправив вывод в файл и в терминал. Сделайте таблицу «куда попал stdout / stderr» для четырёх вариантов.
3. Реализуйте цикл, который читает список хостов из команды и накапливает результат в массив, не теряя его после завершения цикла.
4. Модифицируйте пример graceful-останова: добавьте обработку `SIGHUP` как «перечитать конфиг без остановки», обработку повторного `SIGTERM` как немедленный выход и логирование в файл через дополнительный дескриптор.
5. Сравните `nohup ./worker.sh &` и systemd-юнит с `Restart=on-failure`: убейте процесс `SIGKILL` в обоих случаях и опишите, что произойдёт через 5 секунд, какие логи останутся и как узнать причину падения.
