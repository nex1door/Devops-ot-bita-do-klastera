# Глава 5d. eBPF: наблюдение за ядром без пересборки

Диагностика долго делилась на два лагеря: «снаружи» — `strace`, `perf`, логи — и «внутри» — правка кода, пересборка, новый модуль ядра. eBPF убирает выбор: небольшая программа загружается в работающее ядро, проверяется верификатором, компилируется в машинный код и срабатывает на нужных событиях, не меняя ни ядро, ни приложение. В этой главе — что такое eBPF и почему это не модуль ядра, какие бывают точки прикрепления, как читать однострочники `bpftrace`, чем это отличается от `perf` и `strace`, где пределы метода и почему код в ядре опаснее обычной программы. К концу вы сможете ответить, кто открывает файл, сколько длится {{L|g114|syscall}} и почему процесс ждёт, хотя CPU свободен.

## Что такое eBPF

eBPF (extended Berkeley Packet Filter) — виртуальная машина внутри ядра с собственным набором инструкций: 11 регистров по 64 бита (R10 — указатель на кадр стека), стек 512 байт на программу, запрет произвольных переходов. Программа пишется на подмножестве C, компилируется в байт-код (clang с целью `bpf`), загружается системным вызовом `bpf()` и прикрепляется к событию. Исполняется она интерпретатором или JIT-компилятором в машинный код хоста — по умолчанию вторым, и тогда срабатывание стоит десятки-сотни наносекунд.

Отличие от модуля ядра не в мощности, а в способе попадания внутрь. Модуль собран против заголовков конкретного ядра, исполняется с полным доверием, и ошибка в нём означает панику. Программа eBPF не содержит машинного кода платформы: до запуска её разбирает верификатор (verifier), который статически проходит все ветки и либо доказывает безопасность, либо отказывает. Загрузка занимает миллисекунды, выгрузка мгновенна (закрыли дескриптор — программа снята), заголовки ядра не нужны, а худший исход ошибки — сообщение верификатора, а не kernel panic.

Верификатор требует, чтобы программа завершалась (циклы с доказуемым пределом, с ядра 5.3), обращалась к памяти только через проверенную арифметику указателей или хелперы вроде `bpf_probe_read_kernel` и не читала неинициализированный стек. Лимит сложности — около миллиона инструкций; всё, что не доказуемо, отклоняется.

## Точки прикрепления

Тип программы определяет, что ей доступно и какой контекст придёт в аргументах.

| Тип | Что перехватывает | Стабильность | Когда брать |
|---|---|---|---|
| `kprobe` / `kretprobe` | вход и возврат функции ядра по имени | символ могут переименовать или заинлайнить | нет подходящего tracepoint |
| `uprobe` / `uretprobe` | функция в бинарнике или библиотеке user space | ломается при обновлении пакета | нет исходников, а поведение нужно |
| `tracepoint` | статические точки трассировки ядра | стабильный ABI, поля описаны | есть подходящая точка |
| `fentry` / `fexit` | вход и выход функции через BTF | привязано к типу функции | ядро 5.5+, нужна типизация |
| `XDP` | пакет на входе драйвера, до `sk_buff` | стабильно | фильтрация и DDoS на линии |

`kprobe` работает так: ядро заменяет первые байты функции инструкцией останова, по срабатыванию выполняет вашу программу и восстанавливает оригинал. Поэтому перехватывать можно только реально существующие символы (статическая функция, вкомпилированная в вызывающего, символа не имеет), и на горячем пути замена стоит недешево. `tracepoint` дешевле и надёжнее: точка уже вкомпилирована, формат аргументов зафиксирован, обновление ядра программу не ломает.

```bash
sudo bpftrace -l 'kprobe:vfs_*' | head -3
```

```
kprobe:vfs_cancel_lock
kprobe:vfs_clean_context
kprobe:vfs_cleanup_quota_inode
```

Всего на рабочем ядре 6.12 доступно больше ста тысяч точек — без карты список бесполезен.

## bpftrace: анатомия однострочника

`bpftrace` компилирует высокоуровневый язык в eBPF. Синтаксис один: `проба /фильтр/ { действие }`. Доступны `comm` (имя процесса), `pid`, `tid`, `nsecs` (монотонное время), `args->` (аргументы пробы), `retval`, `str(ptr)` и агрегаты `count()`, `sum()`, `hist()`. Карты (maps) объявляются знаком `@`: `@start[tid] = nsecs` — хеш-таблица в ядре, живущая между срабатываниями. В `bpftrace` 0.23 аргументы берутся через стрелку (`args->filename`); синтаксис `args.filename` из старых статей даёт ошибку компиляции.

### Кто запускает процессы

Точка входа `execve` отвечает на вопрос «что вообще происходит на машине»:

```bash
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve { printf("%-16s %-6d %s\n", comm, pid, str(args->filename)); }'
```

```
bash             589529 /usr/bin/docker
bash             589555 /usr/bin/ls
containerd       589561 /usr/bin/containerd-shim-runc-v2
containerd-shim  589580 /usr/bin/runc
```

`comm` — имя процесса, усечённое до 15 символов, `str()` копирует строку из памяти ядра. Видно, что на машине живёт containerd и что `runc` создаёт процессы: кто-то запускает контейнер, а не «непонятно что тормозит».

### Кто открывает конкретный файл

Фильтр в косых чертах отсекает лишнее до того, как событие попадёт в карту, — главный приём экономии.

```bash
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat /str(args->filename) == "/etc/shadow"/ { printf("%-16s pid=%-6d\n", comm, pid); }'
```

```
unix_chkpwd      pid=590146
cat              pid=590147
```

`cat` — это мы, проверяли себя. `unix_chkpwd` — вспомогательный процесс PAM: сам `passwd`/`su`/`sudo` не может прочитать `/etc/shadow` и просит об этом setuid-помощника. Ограничение видно сразу: при относительном пути в `args->filename` будет только имя, а `openat2` приходит в отдельную точку `sys_enter_openat2`.

### Сколько длится syscall

Латентность меряется парой «вход — выход», разница кладётся в гистограмму. Ключ `tid` обязателен: syscall может быть вытеснен, и одно глобальное значение времени перепутает потоки.

```bash
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @start[tid] = nsecs; }
tracepoint:syscalls:sys_exit_openat /@start[tid]/ { @us = hist((nsecs - @start[tid]) / 1000); delete(@start[tid]); }
interval:s:6 { exit(); }'
```

```
@us:
[1]                 2785 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2, 4)               413 |@@@@@@@                                             |
[4, 8)               305 |@@@@@                                               |
[8, 16)               63 |@                                                   |
...
[128, 256)             1 |                                                    |
```

Почти три тысячи открытий уложились в микросекунду (метаданные в {{L|g82|page cache}}), четыреста — от одной до четырёх, единицы вышли за сто микросекунд. Гистограмма показывает распределение, а не среднее: среднее здесь около двух микросекунд и о хвосте не говорит ничего. `interval:s:6 { exit(); }` — штатный способ ограничить сбор по времени, иначе карта печатается по Ctrl-C.

### Латентность TCP-соединений: ловушка, которую проходят все

Первое желание — измерить `connect()` между входом и выходом syscall. Так получаются нули, и это не дефект измерения, а свойство API: неблокирующий сокет (так делает `curl` и почти любой сетевой код) возвращает из `connect()` код `EINPROGRESS` сразу после отправки SYN, а рукопожатие идёт позже, в softirq, где никакого syscall нет.

Правильная точка — переход состояния сокета:

```bash
sudo bpftrace -e 'tracepoint:sock:inet_sock_set_state /args->newstate == 2/ { @start[args->skaddr] = nsecs; @who[args->skaddr] = comm; }
tracepoint:sock:inet_sock_set_state /args->oldstate == 2 && args->newstate == 1/ { @ms[@who[args->skaddr]] = hist((nsecs - @start[args->skaddr]) / 1000000); delete(@start[args->skaddr]); }'
```

```
@ms[curl]:
[32, 64)               1 |@@@@@@@@@@@@@@@@@@@@@@@@@@                          |
[64, 128)              1 |@@@@@@@@@@@@@@@@@@@@@@@@@@                          |
[128, 256)             2 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
```

Состояние 2 — `TCP_SYN_SENT`, 1 — `TCP_ESTABLISHED`; разница и есть время рукопожатия. Обратите внимание на `@who[args->skaddr] = comm`: имя процесса запоминается в момент отправки SYN, потому что смена состояния происходит в контексте softirq, где `comm` — это `swapper/0`, а не ваш процесс. Без этой карты гистограмма разложится по ядру, а не по `curl`.

### Off-CPU: почему процесс ждёт

`top` показывает, что процесс не ест CPU, и на этом останавливается. Вопрос «чего он ждёт» решается временем вне процессора: от переключения задачи наружу до переключения обратно.

```bash
sudo bpftrace -e 'tracepoint:sched:sched_switch /args->prev_comm == "curl"/ { @s = nsecs; }
tracepoint:sched:sched_switch /args->next_comm == "curl" && @s/ { @ms = hist((nsecs - @s) / 1000000); delete(@s); }
interval:s:5 { exit(); }'
```

```
@ms:
[0]                   15 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[1]                    4 |@@@@@@@@@@@@@                                       |
...
[32, 64)              13 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@       |
[128, 256)            11 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@                      |
```

Пик в 32–64 мс и хвост до четверти секунды — это не CPU, а ожидание сети: пока `curl` ждёт ответа, задача снята с процессора, и в `top` её просто нет. Следующий шаг, когда нужно не «сколько», а «почему»: заменить `hist` на `@[kstack] = count()` и получить стеки ядра в точках засыпания — там будет видно `tcp_recvmsg`, `poll` или `io_schedule`.

## perf, strace, bpftrace: что когда

| Инструмент | Механизм | Накладные расходы | Что показывает |
|---|---|---|---|
| `strace` | `ptrace`, остановка на каждом syscall | в 10–100 раз медленнее | аргументы одного процесса |
| `perf` | сэмплирование по таймеру или PMU | единицы процентов | где горит CPU, стеки, off-CPU |
| `bpftrace` | событие и агрегация в ядре | зависит от частоты, обычно < 5 % | распределения по всему хосту |

Один процесс, несколько секунд, нужны точные аргументы — `strace`. Непонятно, кто ест CPU, и нужен профиль на минуту — `perf record`. Нужно распределение по всей машине, и вопрос сформулирован как «кто/сколько/как часто» — `bpftrace`. На нагруженном сервере `strace` не «немного замедляет»: каждый syscall превращается в два переключения контекста, и сервис с сотней тысяч вызовов в секунду просто встаёт. BCC (`execsnoop`, `opensnoop`, `biolatency`, `tcplife`) — те же программы, но уже написанные: начинать разумно с них.

## Ограничения метода

Загружать программы может только root: с ядра 5.8 полномочия разделены на `CAP_BPF` (карты и программы) и `CAP_PERFMON` (прикрепление к событиям), плюс `CAP_SYS_ADMIN` для части типов. Что разрешено остальным:

```bash
cat /proc/sys/kernel/unprivileged_bpf_disabled
```

```
2
```

`2` (норма для Debian, Ubuntu, RHEL) — «запрещено и не переключается без перезагрузки», `1` — «запрещено, но можно вернуть», `0` — «разрешено». В контейнерах `bpf()` дополнительно режется seccomp, поэтому `bpftrace` в поде без `CAP_BPF` не запустится вовсе.

Накладные расходы складываются из срабатываний: программа на `kprobe` функции, вызываемой миллион раз в секунду, добавляет работу на каждый вызов, а `printf` умножает это на копирование в буфер. Лечится фильтром в ядре, агрегатом вместо печати и ограничением сбора по `interval`, а проверяется сравнением throughput до и после.

Версии: `bpftrace` требует ядра 4.9+ (комфортно с 5.x), BTF — 5.2+, `fentry` — 5.5+, `CAP_BPF` и `ringbuf` — 5.8+. И перехватывается не всё: нет символа — нет `kprobe` (статические функции инлайнятся, модули без BTF не типизированы), не видно чистой арифметики в user space и содержимого TLS до расшифровки. А `kprobe` на внутреннюю функцию — обещание, которое ломается при обновлении ядра.

## Безопасность: почему eBPF-программа опаснее обычной

Обычная программа ограничена адресным пространством и правами пользователя: чтобы навредить, ей нужен syscall, а syscall проверяет ядро. Программа eBPF исполняется в режиме ядра, и единственная граница между ней и всей памятью машины — верификатор, то есть статический анализ, выполненный один раз. Дальше изоляции нет: хелпер `bpf_probe_read_kernel` читает произвольную память ядра, а программа на `kprobe` перед `sys_getdents64` может отфильтровать записи и спрятать процесс или файл от `ps` и `ls` — готовый rootkit, невидимый в списке модулей.

Отсюда три правила. Считать `CAP_BPF` эквивалентом root: контейнер с этим правом — контейнер с доступом к ядру хоста. Не запускать чужие однострочники «из статьи», не прочитав их. Смотреть, что загружено (`sudo bpftool prog list`), и держать `unprivileged_bpf_disabled=2`: история CVE в самом верификаторе показывает, что «песочница» здесь не абсолютна.

## Мост: к namespaces и к наблюдаемости

С главой 5c связь прямая и часто неожиданная. `bpf_get_current_pid_tgid()` возвращает PID в корневом namespace, а не тот, который видит процесс внутри контейнера: namespaces подменяют таблицы для процессов, но не для программ ядра. Поэтому `bpftrace` с хоста показывает процессы контейнеров с хостовыми PID — это то, что нужно для отладки, и то, что ломает фильтры «по PID из `docker top`». Ограничить сбор одним контейнером можно по `cgroup_id`, что и делают Cilium и Tetragon.

С главой 42 связь ещё прямее: eBPF — способ получить телеметрию без инструментирования кода. Время в syscall, off-CPU, ретрансмиты, латентность диска и HTTP собираются на уровне ядра одинаково для Go, Python и байтового кода JVM. Дальше — обычная работа с SLO: распределение вместо среднего, хвосты вместо «в целом нормально».

## Типичные ошибки

1. **Синтаксис `args.filename` из старых статей.** В `bpftrace` 0.23 аргументы — указатель, нужен `args->filename`, иначе ошибка компиляции. Механизм: контекст пробы типизирован через BTF, обращение к полям идёт как к структуре по указателю.
2. **Латентность `connect()` через вход и выход syscall.** Получаются нули. Механизм: неблокирующий `connect()` возвращает `EINPROGRESS` сразу, рукопожатие идёт в softirq; нужен `sock:inet_sock_set_state`.
3. **Запуск без root.** Ответ — `ERROR: bpftrace currently only supports running as the root user`. Механизм: нет `CAP_BPF`/`CAP_PERFMON`, а в контейнере ещё и seccomp режет `bpf()`.
4. **Проба на горячей функции без фильтра.** Сервис теряет десятки процентов throughput. Механизм: `kprobe` подменяет первые байты функции точкой останова, каждое срабатывание — исключение плюс JIT-код.
5. **`@start[tid]` без `delete()`.** Карта растёт, память ядра кончается, события теряются. Механизм: карта — хеш-таблица с лимитом элементов, а запись без удаления на выходе накапливается.
6. **`kprobe` на функцию, которой нет.** `Error: failed to attach probe`. Механизм: символ заинлайнен, переименован или это макрос; проверять `bpftrace -l 'kprobe:имя*'` до написания программы.

## Чек-лист

- Известно, что eBPF — байт-код с верификатором и JIT, а не модуль: загрузка без пересборки и перезагрузки.
- Перед программой выполнен `bpftrace -l` по нужному шаблону и точка существует, а не «должна быть».
- В измерительных пробах ключ включает `tid` или `skaddr`, а карта очищается `delete()`.
- Фильтр стоит в косых чертах: лишние события не доходят до карты.
- Для латентности сети используется `sock:inet_sock_set_state`, а не вход/выход `connect`.
- Сбор ограничен `interval:s:N { exit(); }`, а накладные расходы сняты `perf stat` до и после.
- Проверены `unprivileged_bpf_disabled` и состав программ (`bpftool prog list`).
