# Глава 24a. Makefile: контракт репозитория

Репозиторий, в котором нет единой точки входа, обрастает знанием, живущим в головах: «собери через `go build ./cmd/...`, тесты гоняй с `-race`, линтер поставь такой-то, деплой — скриптом из `scripts/`». Через полгода этот набор знает один человек, а CI повторяет его третьей версией. {{L|g146|Makefile}} решает именно это: он описывает, **как** собрать, проверить и выкатить проект, в файле, который лежит рядом с кодом и одинаково работает у разработчика, в CI и на сервере. Глава — про make как про контракт репозитория: правила, переменные, `.PHONY`, параллелизм и полный рабочий Makefile для Go-сервиса. Заодно разберём, где make перестаёт быть удобным и честнее взять `just` или `task`.

## Зачем make, если есть bash

Bash-скрипт исполняет команды сверху вниз. Он не знает, что `build` зависит от `generate`, что пересобирать нужно только изменившиеся файлы и что `test` и `lint` можно запустить одновременно. Make знает: он строит граф зависимостей и выполняет только то, что устарело.

Три свойства, которых нет у скрипта:

- **Декларативность.** Вы описываете результат и его зависимости, а не последовательность шагов. «`bin/tasksvc` зависит от `main.go` и `util.go`» — дальше make сам решает, что делать.
- **Инкрементальность.** Рецепт выполняется, если цель отсутствует или хотя бы одна зависимость новее цели по mtime. Второй `make` подряд не делает ничего — и это не оптимизация, а корректность: пересборка всего на каждый чих съедает минуты на каждом шаге CI.
- **Параллелизм.** Граф зависимостей — это готовый план распараллеливания: `make -j8` выполнит независимые цели одновременно, не нарушая порядок там, где он важен.

Плюс бесплатно: `make` есть в любом образе, где есть компилятор, и не требует установки интерпретатора вроде Python или Node.

## Цели, зависимости, команды

Правило (rule) состоит из трёх частей: цель (target), зависимости (prerequisites) и рецепт (recipe) — команды, которые создают цель.

```make
app: main.o util.o
	cc -o app main.o util.o

main.o: main.c util.h
	cc -c main.c

util.o: util.c util.h
	cc -c util.c
```

Здесь `app` зависит от двух объектных файлов, а те — от исходников и заголовка. Соберём и посмотрим, что происходит при повторном запуске и после правки заголовка:

```bash
make            # cc -c main.c; cc -c util.c; cc -o app ...
make            # make: 'app' is up to date.
touch util.h
make            # пересоберутся оба .o и app
```

Первое правило в файле — цель по умолчанию, если не задан `.DEFAULT_GOAL`. Порядок правил в файле не задаёт порядок выполнения: make идёт по графу от запрошенной цели.

## Табы, а не пробелы

Рецепты должны начинаться с символа табуляции, и это не суеверие. В синтаксисе Makefile пробелы значимы иначе: они разделяют цель и зависимости, продолжают строку, отделяют директивы. Таб был выбран в 1976 году как однозначный маркер «здесь начинается команда», и с тех пор менять его не стали, чтобы не сломать существующие файлы.

Симптом — `Makefile:2: *** missing separator.  Stop.` Четыре пробела вместо таба выглядят неотличимо от таба в большинстве шрифтов, поэтому ошибка считается классикой.

```make
build:
    go build ./...     # четыре пробела — missing separator
```

Что помогает: `.editorconfig` в корне с `indent_style = tab` для `Makefile`, режим `makefile` в редакторе (vim и neovim включают его автоматически), проверка в pre-commit хуке. С версии GNU make 3.82 маркер можно сменить директивой `.RECIPEPREFIX = >`, но это редкий приём: он ломает совместимость с чужими ожиданиями и подсветкой.

## .PHONY и когда он обязателен

Make определяет «устарело ли» по файлам. Цель `test` файла не создаёт, поэтому make считает её всегда устаревшей и выполняет — пока в каталоге не появится файл или каталог с именем `test`.

```bash
mkdir test
make test        # make: 'test' is up to date.
```

Вот это и есть тихая катастрофа: тесты не запускаются, CI зелёный, релиз с багом. `.PHONY` объявляет цель фиктивной — всегда выполнять, никогда не искать файл:

```make
.PHONY: build test lint docker deploy clean
```

Правило простое: **любая цель, которая не создаёт файл со своим именем, должна быть в `.PHONY`**. Это `test`, `lint`, `fmt`, `deploy`, `clean`, `help` — почти весь набор точек входа. Обратная сторона тоже верна: файловые цели (`bin/app`, `docs/index.html`) в `.PHONY` добавлять нельзя, иначе инкрементальность исчезнет и сборка будет полной каждый раз.

## Переменные: `=`, `:=`, `?=`

Make знает несколько операторов присваивания, и разница между ними — источник половины загадочных багов.

| Оператор | Когда вычисляется | Типичное применение |
|---|---|---|
| `=` | при каждом использовании (лениво) | значения, зависящие от поздних переменных |
| `:=` | сразу, в момент присваивания | всё, где важен момент вычисления |
| `?=` | сразу, только если переменная не задана | значения по умолчанию |
| `+=` | дописывает к текущему значению | накопление флагов |

Классическая ловушка — ленивое `=` с побочным эффектом:

```make
NOW  = $(shell date +%Y-%m-%d)   # вычисляется при каждом обращении
STAMP := $(shell date +%Y-%m-%d) # вычисляется один раз
```

`$(NOW)` в двух рецептах может дать разные даты (если сборка перешла через полночь), `$(STAMP)` — всегда одну. Второй эффект ленивого присваивания хуже: `$(shell ...)` внутри `=` выполняется столько раз, сколько раз переменную раскрыли, — и медленная команда незаметно тормозит весь make.

Автопеременные доступны внутри рецепта и избавляют от повторов:

| Переменная | Значение |
|---|---|
| `$@` | имя цели |
| `$<` | первая зависимость |
| `$^` | все зависимости через пробел |
| `$?` | зависимости новее цели |
| `$*` | стебель шаблонного правила |

Они и делают правила переносимыми: `cc -o $@ $^` работает для любой цели, а не для конкретной.

## Шаблонные правила

Шаблон (pattern rule) описывает семейство целей: `%.o: %.c` читается как «любой `.o` собирается из одноимённого `.c`». `%` — стебель, он же `$*`.

```make
PROTOS := $(wildcard proto/*.proto)
GEN    := $(PROTOS:.proto=.pb.go)

%.pb.go: %.proto
	protoc -I proto --go_out=. --go-grpc_out=. $<

gen: $(GEN)
```

Что здесь происходит: `wildcard` собирает список исходников, подстановка `.proto` → `.pb.go` даёт список целей, шаблонное правило описывает, как получить любую из них, а `gen` — это phony-точка входа, которая требует все сгенерированные файлы. Добавили новый `.proto` — он попал в `PROTOS`, и `make gen` его сгенерирует; ничего в правилах менять не нужно.

## Параллелизм и независимость целей

`make -j8` запускает до восьми рецептов одновременно. Это ускоряет сборку в разы, но обнажает ошибки проектирования: цели, которые пишут в один файл, гоняются за него, а порядок их выполнения непредсказуем.

Требование: **цели должны быть независимы по данным**. Если два рецепта пишут в `coverage.out` или в один каталог `bin/`, при `-j` получите то `permission denied`, то битый файл, то зелёный прогон — в зависимости от планировщика. Лечится разнесением артефактов по целям или явной зависимостью.

```bash
make -j"$(nproc)" test build    # параллельно, если цели независимы
make -j1 deploy                 # последовательно там, где важен порядок
```

Для редких случаев есть `.NOTPARALLEL:`, который отключает параллелизм для указанных целей. Соблазн поставить его на всё — признак того, что граф зависимостей описан неправильно.

## Makefile как точка входа

Ниже — полный Makefile для Go-сервиса: сборка, тесты, линт, образ, деплой с `DRY_RUN`. Он рабочий целиком, не фрагмент.

```make
SHELL   := /bin/bash
.DEFAULT_GOAL := help
.DELETE_ON_ERROR:

BINARY  := tasksvc
PKG     := ./...
IMAGE   ?= registry.example.com/tasksvc
TAG     := $(shell git rev-parse --short HEAD)
ENV     ?= staging

.PHONY: help build test lint docker deploy clean

help:            ## список целей
	@grep -hE '^[a-z]+:.*## ' $(MAKEFILE_LIST) | awk -F':.*## ' '{printf "  %-8s %s\n", $$1, $$2}'

build:           ## бинарник в bin/ с версией из git
	CGO_ENABLED=0 go build -trimpath -ldflags "-X main.version=$(TAG)" -o bin/$(BINARY) ./cmd/$(BINARY)

test:            ## тесты с детектором гонок
	go test -race -count=1 -coverprofile=coverage.out $(PKG)

lint:            ## gofmt и go vet
	@test -z "$$(gofmt -l .)" || { gofmt -l .; echo "gofmt: файлы не отформатированы"; exit 1; }
	go vet $(PKG)

docker: build    ## образ с тегом коммита
	docker build --build-arg VERSION=$(TAG) -t $(IMAGE):$(TAG) -t $(IMAGE):latest .

deploy: docker   ## выкатка в ENV, DRY_RUN=1 — только план
ifdef DRY_RUN
	@echo "[dry-run] kubectl -n $(ENV) set image deploy/$(BINARY) $(BINARY)=$(IMAGE):$(TAG)"
else
	kubectl -n $(ENV) set image deploy/$(BINARY) $(BINARY)=$(IMAGE):$(TAG)
	kubectl -n $(ENV) rollout status deploy/$(BINARY) --timeout=120s
endif

clean:           ## удалить артефакты
	rm -rf bin coverage.out
```

Разбор решений, которые здесь не случайны:

- `SHELL := /bin/bash` — make по умолчанию вызывает `/bin/sh`, а в нём нет `[[ ]]`, `pipefail` и процессов подстановки. Явный bash убирает разницу между вашей машиной и Alpine-образом.
- `TAG := $(shell git rev-parse --short HEAD)` — версия попадает в бинарник через `-ldflags`, и `tasksvc --version` показывает коммит, а не «dev».
- `IMAGE ?=` и `ENV ?=` — значения по умолчанию, переопределяемые из окружения: `make deploy ENV=prod`.
- `docker: build` — образ собирается только после успешной сборки; `deploy: docker` — только после образа. Цепочка зависимостей вместо `&&` в скрипте.
- `ifdef DRY_RUN` — деплой без переменной выполняет {{L|g61|kubectl}}, с переменной печатает команду. Проверка «что я собираюсь сделать» становится одним флагом, а не отдельным скриптом.

## .DELETE_ON_ERROR и .DEFAULT_GOAL

`.DELETE_ON_ERROR:` решает проблему, которую легко не заметить: если рецепт упал на середине, недописанный файл остаётся на диске и выглядит новее исходников. Следующий `make` считает цель готовой и молча использует обрезанный бинарник или наполовину сгенерированный файл.

```make
.DELETE_ON_ERROR:
```

Эта директива удаляет цель, если рецепт завершился с ошибкой, — следующая сборка начнётся с чистого места. Ставить её стоит в каждом Makefile, где цели — файлы.

`.DEFAULT_GOAL := help` задаёт цель по умолчанию. Без неё `make` выполнит первое правило в файле — обычно это оказывается `build` или, хуже, `deploy`. Соглашение «`make` без аргументов печатает справку» безопасно и самодокументируемо: строки `## описание` рядом с целями собираются в список, как в примере выше.

## Где make плох

Make — не язык программирования, хотя им пытаются пользоваться как языком. Его функции (`$(foreach)`, `$(if)`, `$(call)`, `$(eval)`) существуют, но строковые: массивов нет, области видимости нет, отладчика нет, а сообщения об ошибках указывают на строку, где раскрылось выражение, — то есть почти всегда не туда.

Признаки, что логика переросла make:

- рецепты длиннее трёх строк с `if`/`for` на bash;
- появляются функции `$(call ...)` с пятью аргументами;
- знание о том, «какой сервис куда деплоить», зашито в Makefile, а не в конфиге;
- чтобы добавить одну операцию, нужно править три места.

| Инструмент | Сильные стороны | Цена |
|---|---|---|
| make | есть везде, граф зависимостей, инкрементальность | синтаксис с табами, слабые строки |
| just | рецепты без зависимостей-файлов, нормальный синтаксис | нужен бинарник, нет инкрементальности |
| task | YAML, переменные, зависимости между задачами | нужен бинарник, многословнее |

Практическое разделение: make — когда важна инкрементальная сборка по файлам (компиляция, генерация кода, сборка документации). `just`/`task` — когда нужен просто список команд («подними окружение», «прогони миграции»), а зависимостей по mtime нет. Держать оба в одном репозитории нормально: Makefile для сборки, `just` для разработнических действий.

## Интеграция с CI и pre-commit

Главная ценность Makefile — одинаковые команды везде. В CI не должно быть `go test -race ./...`, написанного заново: там должен быть `make test`.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.26"
      - run: make lint test
```

Проверка перед коммитом — тот же вызов, только локально:

```bash
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
exec make lint
EOF
chmod +x .git/hooks/pre-commit
```

Важно понимать ограничение: хуки в `.git/hooks` не клонируются вместе с репозиторием, поэтому такой файл — удобство для автора, а не гарантия для команды. Гарантию даёт фреймворк `pre-commit` (файл `.pre-commit-config.yaml` в репозитории, `pre-commit install` ставит хук у каждого) или серверный гейт в CI. Makefile в этой схеме остаётся единственным источником команд: и хук, и CI вызывают `make lint`.

Второе правило CI: версия инструментов должна быть зафиксирована. `go-version: "1.26"` в пайплайне и `go 1.26` в `go.mod` — две записи одного факта, и расхождение между ними даёт «локально работает».

## Типичные ошибки

1. **Пробелы вместо таба.** `missing separator` возникает потому, что строка с рецептом не распознана как рецепт, и make пытается прочитать её как правило. Лечится `.editorconfig` и режимом `makefile`, а не поиском пробелов глазами.
2. **Цель без `.PHONY`, совпавшая с файлом.** Каталог `test` или файл `build` в корне отключает цель: make видит «файл есть, зависимости старше». Тесты не идут, CI зелёный.
3. **`=` там, где нужно `:=`.** `NOW = $(shell date)` вычисляется на каждое обращение: два рецепта получают разные значения, а медленная команда выполняется многократно. Ошибка видна не сразу — только когда сборка переходит через полночь или начинает тормозить.
4. **Скрытая зависимость от порядка при `-j`.** Два рецепта пишут в один каталог; при последовательном запуске работает, при `make -j8` — то ошибка, то битый артефакт. Гонка воспроизводится через раз, поэтому её списывают на «флаки».
5. **Нет `.DELETE_ON_ERROR`.** Упавшая на середине сборка оставляет недописанный файл новее исходников, и следующий запуск молча использует мусор.
6. **Логика в рецептах.** Ветвление на bash внутри make, деплой «по имени сервиса» через `$(call ...)` — через месяц это нечитаемо. Логика должна уходить в скрипт, make — только вызывать.
7. **Деплой по умолчанию.** Первое правило в файле — `deploy`, и `make` без аргументов в чужой руке выкатывает в прод. `.DEFAULT_GOAL := help` стоит одну строку.

## Чек-лист

- [ ] `make` без аргументов печатает справку, `.DEFAULT_GOAL := help` задан.
- [ ] Все нефайловые цели перечислены в `.PHONY`.
- [ ] В Makefile нет строк с рецептами, начинающихся с пробелов; `.editorconfig` это гарантирует.
- [ ] `.DELETE_ON_ERROR` включён, файловые цели не попадают в `.PHONY`.
- [ ] `make -j"$(nproc)"` проходит с первого раза; общих выходных файлов у целей нет.
- [ ] CI вызывает `make lint test`, а не дублирует команды; версия Go совпадает с `go.mod`.
- [ ] Деплой требует явного `ENV` и поддерживает `DRY_RUN=1`.
- [ ] Секреты приходят из окружения, а не записаны в Makefile.

## Упражнения

1. Напишите Makefile с целями `build`, `test`, `clean` для проекта на Go 1.26. Добейтесь, чтобы повторный `make build` ничего не делал, а `touch` любого исходника пересобирал бинарник.
2. Сломайте свой Makefile тремя способами: пробелы вместо таба, отсутствие `.PHONY` при существующем каталоге `test`, `=` вместо `:=` с `$(shell date)`. Зафиксируйте текст каждой ошибки.
3. Добавьте в Makefile цель `gen`, которая собирает все `proto/*.proto` шаблонным правилом. Проверьте, что новый файл подхватывается без правки Makefile.
4. Запустите `make -j8` на наборе из четырёх целей, две из которых пишут в один файл. Воспроизведите гонку, затем устраните её через разнесение артефактов или явную зависимость.
5. Перепишите деплой так, чтобы `make deploy` без переменных печатал план и завершался с кодом 0, а `make deploy ENV=prod CONFIRM=yes` выполнял выкатку. Обоснуйте, почему защита должна быть в Makefile, а не в скрипте.
