# Глава 8. DNS: как имя становится адресом

DNS — самая недооценённая часть инфраструктуры: пока он работает, его никто не замечает, а когда ломается, «падает всё». При этом сбои почти всегда выглядят одинаково — «сайт не открывается», — хотя причин ровно четыре: не тот сервер, не та зона, не тот кэш или не тот поисковый домен. Эта глава объясняет иерархию и рекурсию, типы записей и TTL, а затем разбирает реальные аварии: split-horizon, приоритет `/etc/hosts`, `search`-домены и `ndots`. В конце — пошаговая диагностика, которую можно выполнять сверху вниз, не гадая.

## Иерархия: корень, TLD, авторитативные серверы

DNS — распределённая база данных, организованная как дерево (RFC 1034, RFC 1035). Точка в конце имени — корень; `.com`, `.org`, `.ru` — домены верхнего уровня (TLD); дальше — домены второго уровня и поддомены. Каждый узел дерева обслуживается своими авторитативными серверами (authoritative nameservers): они не кэшируют, а хранят факты о зоне.

Корневых серверов 13 логических имён (`a.root-servers.net` … `m.root-servers.net`), и каждое развёрнуто как сеть anycast-инстансов по миру — поэтому «13 серверов» не значит 13 машин. Корень знает только одно: кто обслуживает каждый TLD. Сервер `.com` знает, кто обслуживает `example.com`. Авторитативный сервер `example.com` знает адреса своих хостов.

Такое разделение означает: ни один сервер не содержит всю базу, и любое имя находится за конечное число шагов — обычно три-четыре.

## Рекурсия и итерация

Клиент почти никогда не общается с корнем. Он спрашивает свой резолвер (recursive resolver) — и просит «дай готовый ответ» (рекурсивный запрос, флаг `RD` — recursion desired). Дальше резолвер сам обходит дерево итеративно: спросил корень → получил адрес сервера `.com` → спросил `.com` → получил адрес авторитативного сервера → спросил его → получил `A`-запись. Каждый ответ по пути кэшируется на время TTL.

Разница принципиальна для эксплуатации:

- рекурсивный запрос делает клиент, и за него платит резолвер (нагрузка, кэш, приватность);
- итеративный запрос резолвер делает к каждому серверу по очереди, и именно эти пакеты видит `dig +trace`.

Публичные рекурсивные резолверы (например, 1.1.1.1 или 8.8.8.8) — это сервисы, которые делают итеративную работу за вас. Внутренний резолвер компании делает то же самое плюс знает про внутренние зоны.

## Типы записей

| Тип | Что содержит | Пример использования |
|---|---|---|
| `A` | IPv4-адрес | `api.example.com → 203.0.113.10` |
| `AAAA` | IPv6-адрес | тот же хост по IPv6 |
| `CNAME` | псевдоним (другое имя) | `www → lb.example.net` |
| `MX` | почтовый сервер + приоритет | `10 mail.example.com` |
| `TXT` | произвольный текст | SPF, DKIM, верификация домена |
| `SRV` | хост + порт + приоритет + вес | `_https._tcp.example.com` |
| `NS` | авторитативные серверы зоны | делегирование |
| `SOA` | первичный сервер, serial, таймеры | служебная запись зоны |

Правила, которые чаще всего нарушают: `CNAME` нельзя ставить в apex-узел зоны (`example.com`), если там есть `MX`, `NS` или `SOA`; `CNAME` не может указывать на другой `CNAME` в ответе (клиент получит цепочку, которую должен развернуть сам резолвер); `MX` без приоритета не существует — число обязательно.

`TXT` сейчас — рабочая лошадка проверок владения доменом и почтовой аутентификации: SPF ограничен 10 DNS-lookup'ами, и «слишком много SPF-записей» — реальная причина, по которой письма попадают в спам.

## TTL и кэширование

TTL (time to live) — сколько секунд ответ можно держать в кэше. Значение выбирается между свежестью и нагрузкой: 300 секунд — типично для сервисов, где адрес может смениться при деплое; 3600–86400 — для стабильной инфраструктуры; 60 — для аварийного переключения.

Практическое следствие: **вы не можете мгновенно изменить DNS**. Если TTL был 86400, старый адрес будет жить в кэшах сутки, и никакие правки в зоне этого не отменят. Поэтому перед миграцией TTL понижают заранее — за время, равное старому TTL.

Кэшируются и отрицательные ответы (NXDOMAIN, NODATA) — на время из поля `minimum` записи `SOA` зоны, но не более суток по рекомендациям. Это объясняет странность «записи нет, а резолвер упорно говорит, что её нет, хотя я её только что создал»: он закэшировал отказ.

## Резолвер: путь от `getaddrinfo` до ответа

Приложение редко вызывает DNS напрямую: `curl`, `ping`, `requests` идут через `getaddrinfo()`, а тот — через NSS (name {{L|g104|service}} switch). Порядок источников задан в `/etc/nsswitch.conf`:

```
hosts:          files dns
```

`files` — это `/etc/hosts`, и он проверяется **раньше** DNS. Одна строка в hosts перекрывает любую зону, и это самая частая причина «у меня работает, у коллег нет» (или наоборот).

Дальше `dns` читает `/etc/resolv.conf`: список `nameserver`, `search`-домены и `options ndots`. В системах с systemd-resolved там обычно `nameserver 127.0.0.53` — это локальный stub-резолвер, который занят портом 53 на loopback и проксирует запросы в реальный upstream (и умеет кэш, DNSSEC, split-DNS по линкам). Проверить, кто именно слушает:

```bash
ss -lunp | grep ':53'
```

Если в ответе `127.0.0.53%lo:53`, DNS обслуживает systemd-resolved, и правки в `/etc/resolv.conf` бессмысленны — файл перезапишется. Настраивать нужно через `resolvectl` или drop-in для `systemd-resolved.service`.

## dig: читаем ответ

`dig` — единственный инструмент, который показывает DNS целиком: вопрос, ответ, флаги, время. Реальный вывод на машине, где stub-резолвер слушает только IPv4:

```bash
dig example.com A
```

```
;; communications error to ::1#53: connection refused
;; communications error to ::1#53: connection refused
;; communications error to ::1#53: connection refused
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 21055
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 512
;; QUESTION SECTION:
;example.com.			IN	A

;; ANSWER SECTION:
example.com.		300	IN	A	104.20.23.154
example.com.		300	IN	A	172.66.147.243

;; Query time: 623 msec
;; SERVER: 127.0.0.1#53(127.0.0.1) (UDP)
;; MSG SIZE  rcvd: 72
```

Разбор. Три строки `communications error to ::1#53` — не ошибка DNS, а следствие того, что резолвер в `/etc/resolv.conf` числится и как `::1`, и как `127.0.0.1`, а слушает только IPv4: `dig` честно пытается по IPv6, получает отказ и переходит к следующему адресу. Итог — 623 мс вместо 5 мс, и это ровно тот случай, когда «DNS тормозит» означает «резолвер настроен на два адреса, один из которых мёртв».

`status: NOERROR` — имя существует; `NXDOMAIN` означал бы, что не существует; `SERVFAIL` — что зона сломана или сервер не отвечает. Флаги: `qr` — это ответ, `rd` — рекурсия запрошена, `ra` — сервер её поддерживает, `ad` — данные аутентифицированы DNSSEC. `ANSWER: 2` — две A-записи, TTL 300 у обеих. `SERVER: 127.0.0.1#53` — кто ответил (важно: это резолвер, а не авторитативный сервер).

Короткие формы для скриптов:

```bash
dig +short example.com A
dig +noall +answer example.com AAAA
dig @1.1.1.1 example.com A +norecurse     # спросить конкретный сервер без рекурсии
dig -x 8.8.8.8 +short                     # обратная зона
getent hosts example.com                  # то, что увидит приложение (через NSS)
```

`getent hosts` — единственная команда, которая показывает результат ровно так, как его получит приложение: с учётом `/etc/hosts` и `nsswitch.conf`. Если `dig` и `getent` расходятся — виноват hosts или NSS, а не DNS.

## DoH и DoT

Классический DNS идёт по UDP/53 открытым текстом: провайдер и любой посредник видит, какие имена вы спрашиваете. Два протокола закрывают это:

- **DoT** (DNS over TLS, RFC 7858) — TLS на порту 853, отдельный порт, легко блокируется и легко детектируется;
- **DoH** (DNS over HTTPS, RFC 8484) — запросы внутри HTTPS на порту 443, неотличимы от обычного веб-трафика, поэтому переживает блокировки, но и фильтровать его сложнее.

Цена — потеря видимости для корпоративной сети: внутренние зоны, split-horizon и блокировки рекламы перестают работать, если браузер ушёл на публичный DoH мимо корпоративного резолвера. Поэтому в компаниях DoH часто отключают политикой, а DoT оставляют для своих резолверов с пином сертификата.

## Типичные аварии

**Split-horizon.** Одна и та же зона отдаётся по-разному изнутри и снаружи: внутри `api.example.com → 10.0.5.20`, снаружи — публичный адрес. Ломается, когда внутренний клиент спрашивает публичный резолвер: он получает внешний адрес, и трафик уходит через NAT наружу и обратно. Симптом — соединение устанавливается, но медленно и через «не тот» путь; проверяется `dig @внутренний_резолвер` против `dig @1.1.1.1`.

**`/etc/hosts` важнее DNS.** Классика при переезде: админ когда-то добавил запись для теста, и теперь один сервер из десяти ходит на старый IP. `getent hosts` показывает правду, `dig` — нет.

**`search`-домены и `ndots`.** В `resolv.conf` есть `search corp.example.com` и по умолчанию `ndots:1` (в Kubernetes — `ndots:5`). Имя `api` без точки сначала пробуется как `api.corp.example.com`, потом как `api.` — то есть несколько запросов подряд. Отсюда «первый запрос всегда медленный» и лишние NXDOMAIN в логах резолвера. Лечится завершающей точкой (`api.example.com.`) или настройкой `ndots`.

**Кэш живёт дольше, чем правда.** TTL 86400 и переключение на новый сервер — это сутки переходного периода, в течение которых часть клиентов ходит на старый адрес. Планировать заранее.

**CNAME в apex.** Попытка поставить `example.com CNAME lb.provider.com` рядом с `MX` даёт либо ошибку загрузки зоны, либо тихо отброшенную запись — в зависимости от провайдера.

## Диагностика по шагам

Порядок важен: каждый следующий шаг исключает предыдущий класс причин.

```bash
getent hosts api.example.com                          # 1. что видит приложение (hosts + nsswitch)
dig api.example.com A +noall +answer +stats           # 2. что отвечает локальный резолвер
cat /etc/resolv.conf; ss -lunp | grep ':53'           # 3. кто настроен и не сломан ли stub
dig @ns1.example.net api.example.com A +norecurse     # 4. отвечает ли авторитативный сервер
dig @1.1.1.1 api.example.com A +short                 # 5. не кэш ли виноват
dig NS example.com +short; dig SOA example.com +short # 6. делегация у родителя
```

Логика чтения: если шаг 1 даёт один адрес, а шаг 2 — другой, виноват `/etc/hosts`. Если шаг 2 отвечает, а шаг 4 — нет, сломан авторитативный сервер или его сеть. Если шаг 4 отвечает правильно, а шаг 2 — нет, вы упёрлись в кэш или в split-horizon. Если не отвечает ничего, начиная с шага 2, — проблема в резолвере или в фильтрации UDP/53.

Ещё один приём: `dig +trace` выполняет итеративный обход с вашей машины и показывает, на каком уровне делегирование расходится с ожиданием. Если родитель отдаёт `NS` на сервер, которого нет, — это видно сразу, без ожидания TTL.

## Типичные ошибки

1. **Диагностировать через `ping` по имени.** `ping` смешивает ICMP, DNS и маршрутизацию: три гипотезы вместо одной. Сначала `dig`, потом `ping` по IP, потом `curl`.
2. **Забыть про `/etc/hosts`.** Он проверяется раньше DNS, и `dig` его не видит. Расхождение `dig` и `getent` — почти всегда hosts.
3. **Снижать TTL после инцидента, а не до.** Кэши с TTL 86400 не обновятся от вашей правки; понижать TTL нужно минимум за старый TTL до переключения.
4. **Ставить `ndots:5` без нужды.** Каждое короткое имя превращается в пять запросов; на Kubernetes это заметная доля трафика и задержек.
5. **Использовать `CNAME` для apex.** Ломает `MX`, `NS` и `SOA`; для apex нужны `A`/`AAAA` или ALIAS/ANAME у провайдера.
6. **Считать `SERVFAIL` проблемой клиента.** Это ответ сервера: зона не загрузилась, DNSSEC не сошёлся или авторитативный сервер недоступен. Клиент тут ничего не исправит.
7. **Пускать DoH в обход корпоративного резолвера.** Внутренние имена перестают резолвиться, а split-horizon — работать; браузер при этом выглядит «сломанным» только в офисе.

## Чек-лист

- [ ] TTL для критичных записей ≤ 300, и это проверено перед каждым переключением.
- [ ] Внутренние зоны резолвятся только через внутренние резолверы; split-horizon проверен с обеих сторон.
- [ ] `/etc/hosts` на всех серверах проверен на «временные» записи.
- [ ] `ndots` и `search` осознанно заданы; в Kubernetes проверено их влияние на latency.
- [ ] Есть мониторинг: время ответа резолвера, доля `SERVFAIL`, доступность авторитативных NS.
- [ ] Настроен и проверен DNSSEC, а `ad`-флаг в `dig` действительно появляется.
- [ ] DoH/DoT политика определена: либо запрещены, либо идут через контролируемый резолвер.
- [ ] Для каждого домена известно, кто держит зону и как её править в 3 часа ночи.

## Упражнения

1. Сравните `dig +short`, `getent hosts` и `nslookup` для одного имени. Найдите случай, где они расходятся, и объясните почему.
2. Понизьте TTL до 60, подождите старый TTL, смените A-запись и замерьте, через сколько её увидят разные резолверы.
3. Организуйте split-horizon на своём резолвере: один и тот же домен отдаёт разные адреса изнутри и снаружи.
4. Включите `ndots:5` и замерьте число DNS-запросов при обращении к десяти коротким именам.
5. Разберите `dig +trace` для домена и найдите точку, где делегирование уходит на неожиданный сервер.
