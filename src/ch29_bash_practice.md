# Глава 29. Практика: скрипты бэкапа, healthcheck, деплоя, systemd timers

Знание синтаксиса не превращается в надёжную автоматизацию само. Разница между учебным скриптом и тем, который можно поставить в cron на боевом сервере, — в проверках, блокировках, таймаутах, кодах возврата и возможности безопасно повторить запуск. В этой главе четыре законченных примера: бэкап с проверкой места и ротацией, healthcheck с алертом и режимом `DRY_RUN`, деплой с идемпотентностью и откатом, запуск по расписанию через {{L|g115|systemd}} timer. Все скрипты рабочие, вывод показан реальный. В конце — чек-лист, по которому можно проверить любой свой скрипт перед тем, как отдать его дежурному.

## Скрипт бэкапа: место, атомарность, ротация

Требования к ночному бэкапу формулируются быстро: упаковать каталог, проверить, что места хватает, не оставить битый архив при обрыве, хранить N последних копий, уметь посчитать контрольную сумму. Плохой бэкап опаснее отсутствующего: он создаёт иллюзию защиты.

```bash
#!/usr/bin/env bash
set -euo pipefail

SRC=${1:?укажите каталог-источник}
DEST=${2:?укажите каталог для архивов}
KEEP=${KEEP:-3}
MIN_FREE_MB=${MIN_FREE_MB:-256}
DRY_RUN=${DRY_RUN:-0}

log() { printf '%s %s\n' "$(date -u +%FT%TZ)" "$*" >&2; }
die() { log "ОШИБКА: $*"; exit 1; }

[[ -d $SRC ]] || die "нет каталога $SRC"
mkdir -p "$DEST"

avail=$(df -Pm "$DEST" | awk 'NR==2 {print $4}')
(( avail >= MIN_FREE_MB )) || die "мало места: ${avail} МБ < ${MIN_FREE_MB} МБ"

ts=$(date -u +%Y%m%dT%H%M%SZ)
archive="$DEST/backup-$ts.tar.gz"

if (( DRY_RUN )); then
    log "DRY_RUN: создал бы $archive и оставил $KEEP последних"
    exit 0
fi

tmp=$(mktemp "$DEST/.part.XXXXXX")
trap 'rm -f "$tmp"' EXIT
tar -C "$(dirname "$SRC")" -czf "$tmp" "$(basename "$SRC")"
mv "$tmp" "$archive"
trap - EXIT
sha256sum "$archive" > "$archive.sha256"
log "создан $archive, $(du -h "$archive" | cut -f1)"

mapfile -t old < <(ls -1t "$DEST"/backup-*.tar.gz 2>/dev/null | tail -n +$((KEEP + 1)))
if ((${#old[@]})); then
    for f in "${old[@]}"; do
        rm -f "$f" "$f.sha256"
        log "удалён старый архив $f"
    done
fi
```

Прогон с `KEEP=2` и четырьмя запусками подряд:

```
2026-10-29T14:52:08Z создан bk/dest/backup-20261029T145208Z.tar.gz, 4.0K
2026-10-29T14:52:09Z создан bk/dest/backup-20261029T145209Z.tar.gz, 4.0K
2026-10-29T14:52:10Z создан bk/dest/backup-20261029T145210Z.tar.gz, 4.0K
2026-10-29T14:52:10Z удалён старый архив bk/dest/backup-20261029T145208Z.tar.gz
2026-10-29T14:52:11Z создан bk/dest/backup-20261029T145211Z.tar.gz, 4.0K
2026-10-29T14:52:11Z удалён старый архив bk/dest/backup-20261029T145209Z.tar.gz
```

Проверка целостности и отказы:

```
$ sha256sum -c backup-20261029T145211Z.tar.gz.sha256
backup-20261029T145211Z.tar.gz: OK
$ ./backup.sh /nope dest; echo $?
2026-10-29T14:52:12Z ОШИБКА: нет каталога /nope
1
```

Что здесь принципиально. `df -Pm` даёт машиночитаемый вывод в мегабайтах: `-P` отключает перенос строк, из-за которого в длинных именах устройств поле `$4` уезжает на другую строку. Архив пишется во временный файл `.part.XXXXXX` в том же каталоге и переименовывается только после успешного `tar` — `mv` в пределах одной ФС атомарен, поэтому читатель никогда не увидит недописанный `.tar.gz`. `trap ... EXIT` удаляет огрызок при любом сбое, а после успешного `mv` снимается через `trap - EXIT`, чтобы не удалить уже готовый файл. Контрольная сумма лежит рядом: восстановление без проверки — лотерея.

Ротация сделана по количеству, а не по возрасту: `ls -1t` сортирует по времени изменения, `tail -n +N` отбрасывает первые N. Альтернатива — `find "$DEST" -name 'backup-*.tar.gz' -mtime +7 -delete`, она лучше, когда политика «неделя копий», а не «семь копий». Ограничение текущего варианта: имена с пробелами и переводами строк в `DEST` сломают разбор, поэтому каталог бэкапов должен быть под вашим контролем.

## Healthcheck: повторы, коды, DRY_RUN

Healthcheck отвечает на один вопрос: приложение действительно обслуживает запросы. Проверка TCP-порта этого не показывает — процесс может слушать порт и возвращать 500. Поэтому проверяется HTTP-код и содержимое ответа.

```bash
#!/usr/bin/env bash
set -euo pipefail

URL=${1:?укажите URL проверки}
TIMEOUT=${TIMEOUT:-5}
RETRIES=${RETRIES:-3}
DELAY=${DELAY:-2}
WEBHOOK=${WEBHOOK:-}
DRY_RUN=${DRY_RUN:-0}
EXPECT=${EXPECT:-ok}

alert() {
    local msg=$1
    if (( DRY_RUN )); then
        printf 'DRY_RUN: алерт "%s" не отправлен\n' "$msg" >&2
        return 0
    fi
    if [[ -z $WEBHOOK ]]; then
        printf 'АЛЕРТ: %s\n' "$msg" >&2
        return 0
    fi
    curl -fsS --max-time 5 -H 'Content-Type: application/json' \
        -d "$(printf '{"text":"%s"}' "$msg")" "$WEBHOOK" >/dev/null \
        || printf 'не удалось отправить алерт\n' >&2
}

check() {
    local body
    body=$(curl -fsS --max-time "$TIMEOUT" "$URL") || return 1
    printf '%s' "$body" | jq -e --arg e "$EXPECT" '.status == $e' >/dev/null || return 2
    return 0
}

for ((i = 1; i <= RETRIES; i++)); do
    rc=0
    check || rc=$?
    if ((rc == 0)); then
        echo "OK: $URL отвечает status=$EXPECT (попытка $i)"
        exit 0
    fi
    echo "попытка $i/$RETRIES неудачна (код $rc)" >&2
    if ((i < RETRIES)); then sleep "$DELAY"; fi
done

alert "healthcheck $URL провален после $RETRIES попыток"
exit 1
```

Реальные прогоны против локального сервера:

```
== успех
OK: http://127.0.0.1:18080/health.json отвечает status=ok (попытка 1)
== неверное поле
попытка 1/2 неудачна (код 2)
попытка 2/2 неудачна (код 2)
DRY_RUN: алерт "healthcheck http://127.0.0.1:18080/health.json провален после 2 попыток" не отправлен
== сервер выключен
curl: (7) Failed to connect to 127.0.0.1 port 18080 after 0 ms: Could not connect to server
попытка 1/2 неудачна (код 1)
```

Два кода различимы не случайно: 1 — сеть или HTTP-ошибка (`curl -f` возвращает 22 на 4xx/5xx), 2 — ответ получен, но контент не тот. Это позволяет в алерте разделить «сервис лежит» и «сервис отвечает неправильно». `rc=0; check || rc=$?` — обязательный приём: запись `if check; then` съедает код, а `check` без обработки убьёт скрипт из-за `set -e` на первой же неудаче, и повторов не будет.

`DRY_RUN` реализован так, что и в «сухом» режиме видно точный текст алерта, но наружу ничего не уходит. Это стандарт для скриптов, которые запускаются по расписанию: сначала прогон вручную с `DRY_RUN=1`, потом включение таймера.

## Деплой: идемпотентность и откат

Схема «релизы + симлинк» проста и переживает сбои: каждый деплой создаёт новый каталог, `current` — симлинк на активный, откат — переключение симлинка, отдача статики и запуск приложения идут через `current`. Идемпотентность обеспечивается сравнением хеша содержимого: если развёрнуто ровно то же, что собрано, деплой ничего не делает.

```bash
#!/usr/bin/env bash
set -euo pipefail

APP_DIR=$(realpath -m "${APP_DIR:-/srv/app}")
KEEP=${KEEP:-3}
SRC=${SRC:-}
RELEASES="$APP_DIR/releases"
CURRENT="$APP_DIR/current"

log() { printf '[deploy] %s\n' "$*" >&2; }
die() { log "ОШИБКА: $*"; exit 1; }
src_hash() { (cd "$1" && find . -type f -print0 | sort -z | xargs -0 sha256sum | sha256sum | cut -d' ' -f1); }

mkdir -p "$RELEASES"
exec 9>"$APP_DIR/.deploy.lock"
flock -n 9 || die "деплой уже выполняется (lock занят)"

rollback() {
    mapfile -t rels < <(find "$RELEASES" -mindepth 1 -maxdepth 1 -type d -printf '%f\n' | sort)
    ((${#rels[@]} >= 2)) || die "нечего откатывать: релизов ${#rels[@]}"
    local cur idx=-1 target
    cur=$(basename "$(readlink -f "$CURRENT")")
    for i in "${!rels[@]}"; do
        [[ ${rels[i]} == "$cur" ]] && idx=$i
    done
    ((idx > 0)) || die "нет предыдущего релиза для отката"
    target=${rels[idx - 1]}
    ln -sfn "$RELEASES/$target" "$CURRENT"
    log "откат: $cur -> $target"
}

if [[ ${1:-} == --rollback ]]; then
    rollback
    exit 0
fi

[[ -n $SRC ]] || die "не задан SRC"
[[ -d $SRC ]] || die "нет каталога $SRC"

hash=$(src_hash "$SRC")
if [[ -L $CURRENT ]] && [[ $(cat "$(readlink -f "$CURRENT")/.release-hash" 2>/dev/null) == "$hash" ]]; then
    log "эта версия уже развёрнута, изменений нет"
    exit 0
fi

rel="$RELEASES/$(date -u +%Y%m%dT%H%M%S.%N)"
mkdir "$rel"
cp -a "$SRC/." "$rel/"
printf '%s\n' "$hash" > "$rel/.release-hash"
log "создан релиз $(basename "$rel")"

ln -sfn "$rel" "$CURRENT"
log "current -> $rel"

if [[ -x $CURRENT/app.sh ]]; then
    "$CURRENT/app.sh" || { rollback; die "проверка после переключения провалена"; }
fi

mapfile -t old < <(find "$RELEASES" -mindepth 1 -maxdepth 1 -type d -printf '%f\n' | sort | head -n -"$KEEP")
if ((${#old[@]})); then
    for r in "${old[@]}"; do
        [[ $CURRENT -ef "$RELEASES/$r" ]] && continue
        rm -rf "${RELEASES:?}/$r"
        log "удалён старый релиз $r"
    done
fi
```

Транскрипт: деплой 1.0.0, повторный запуск без изменений, деплой 1.0.1, откат.

```
[deploy] создан релиз 20261029T145333.760190615
[deploy] current -> /srv/app/releases/20261029T145333.760190615
app 1.0.0 запущен
[deploy] эта версия уже развёрнута, изменений нет
[deploy] создан релиз 20261029T145333.791244330
[deploy] current -> /srv/app/releases/20261029T145333.791244330
app 1.0.1 запущен
[deploy] откат: 20261029T145333.791244330 -> 20261029T145333.760190615
```

Детали, без которых это не работает. `realpath -m` превращает относительный `APP_DIR` в абсолютный до создания симлинков — иначе `ln -sfn` запишет относительный путь, который будет разрешаться от каталога ссылки, и `current` окажется битым. `flock -n 9` на дескрипторе 9 берёт неблокирующую блокировку: два одновременных деплоя из CI и с ноутбука не будут мешать друг другу, второй просто выйдет с ошибкой. Имя релиза содержит наносекунды: секундного разрешения не хватает, два деплоя в одну секунду создают каталоги с одинаковым именем или ломают сортировку, если добавлять случайный суффикс. Проверка после переключения (`$CURRENT/app.sh`) — минимальный smoke-тест: если приложение не стартует, откат автоматический, до того как об этом узнают пользователи. Удаление старых релизов проверяет `[[ $CURRENT -ef ... ]]`: активный релиз не удаляется, даже если вышел за `KEEP`.

## systemd unit и timer

Cron умеет запускать по расписанию и ничего больше. systemd timer даёт журнал, зависимости, таймауты, `Persistent=true` (догнать пропущенный запуск после выключения машины) и случайный разброс, чтобы сотня серверов не била по хранилищу одновременно.

Файл `/etc/systemd/system/backup.service`:

```ini
[Unit]
Description=Nightly backup of /srv/data
After=local-fs.target

[Service]
Type=oneshot
User=backup
Group=backup
Environment=KEEP=7 MIN_FREE_MB=2048
ExecStart=/usr/local/bin/backup.sh /srv/data /var/backups/app
TimeoutStartSec=30min
Nice=10
IOSchedulingClass=idle
StandardOutput=journal
StandardError=journal
```

Файл `/etc/systemd/system/backup.timer`:

```ini
[Unit]
Description=Run backup daily at 02:30

[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
RandomizedDelaySec=10m
Unit=backup.service

[Install]
WantedBy=timers.target
```

Проверка расписания и включение:

```
$ systemd-analyze calendar '*-*-* 02:30:00'
Normalized form: *-*-* 02:30:00
    Next elapse: Fri 2026-10-30 02:30:00 +05
       (in UTC): Thu 2026-10-29 21:30:00 UTC
       From now: 6h left
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now backup.timer
$ systemctl list-timers backup.timer
NEXT                        LEFT    LAST                        PASSED  UNIT          ACTIVATES
Fri 2026-10-30 02:30:00 +05 6h left n/a                         n/a     backup.timer  backup.service
```

`Type=oneshot` — для задач, которые завершаются: systemd ждёт выхода и записывает код возврата. `TimeoutStartSec=30min` убивает зависший бэкап: без него `tar` на огромном каталоге может висеть сутками и блокировать следующий запуск. `Nice=10` и `IOSchedulingClass=idle` снижают нагрузку на диск в час пик. Логи идут в journal автоматически: `journalctl -u backup.service --since yesterday` покажет и вывод скрипта, и код возврата, а `systemctl status backup.service` — последний результат.

Типичная ошибка при переходе с cron: оставить в скрипте относительные пути. В cron рабочий каталог — домашний каталог пользователя, в systemd — `/` (если не задан `WorkingDirectory`). Абсолютные пути в `ExecStart` и внутри скрипта обязательны.

## Чек-лист

Проверка перед тем, как отдать скрипт дежурному:

- Шапка `set -euo pipefail`, интерпретатор в shebang соответствует синтаксису, все пути абсолютные или вычислены от расположения скрипта.
- Обязательные параметры проверены через `${VAR:?}`, неверные значения дают код 2 и сообщение в stderr.
- Есть `DRY_RUN` для всего, что меняет состояние, и он реально прогонялся.
- Запись атомарна: временный файл в том же каталоге плюс `mv`; при сбое `trap` убирает мусор.
- Повторный запуск безопасен: блокировка (`flock`), проверка уже выполненного действия, отсутствие дублей; путь отката проверен хотя бы один раз вручную.
- Внешние вызовы (`curl`, `kubectl`, `psql`) имеют таймаут и проверку кода возврата.
- Ошибки логируются с временной меткой в stderr, успех — одной строкой; секреты не попадают в лог и в `ps`.
- Скрипт прогнан `shellcheck`, запущен с пустыми и неверными аргументами, проверен под тем пользователем, который будет его выполнять.

## Типичные ошибки

1. **Бэкап сразу в целевой файл.** Механизм: при обрыве (OOM, диск, сигнал) остаётся валидный по имени, но битый архив, а ротация считает его успешным. Лечится записью в `.part` и `mv`.
2. **Healthcheck без таймаута.** Механизм: `curl` без `--max-time` висит до TCP-таймаута (минуты), проверка не успевает отработать за интервал запуска и накладывается на следующую. Таймаут обязателен.
3. **`if check; then` и потерянный код.** Механизм: `if` возвращает 0, если выполнилась ветка, а `check` под `set -e` в условии не завершает скрипт — повторов не будет, диагностика теряется. Нужен `check || rc=$?`.
4. **Относительный путь в `ln -sfn`.** Механизм: цель симлинка разрешается относительно каталога ссылки, а не текущего каталога. `realpath` до создания ссылки.
5. **Имя релиза с секундным разрешением.** Механизм: два деплоя в одну секунду создают одинаковое имя (`mkdir: File exists`) или ломают порядок сортировки при откате. Нужны наносекунды или монотонный счётчик.
6. **Деплой без блокировки.** Механизм: два параллельных запуска создают релизы одновременно, `current` переключается дважды, старые релизы удаляются под работающим процессом. `flock` на файле блокировки.
7. **`Persistent=true` без идемпотентности.** Механизм: после простоя systemd догоняет пропущенный запуск, а следом идёт штатный; скрипт выполняется дважды подряд. Второй запуск должен быть безвредным.

## Упражнения

1. Добавьте в скрипт бэкапа шифрование (`age` или `gpg`) и проверку, что ключ доступен до начала архивации. Ошибка должна приводить к коду 3 и не создавать файлов.
2. Переделайте healthcheck так, чтобы он проверял несколько эндпоинтов из файла конфигурации, суммировал результаты и отправлял один алерт со списком упавших.
3. Реализуйте в деплое «канареечную» проверку: после переключения `current` отправьте 10 запросов на новый релиз напрямую по порту, и откатитесь, если доля ошибок выше 10%.
4. Напишите пару unit + timer для healthcheck: запуск каждые 5 минут, `AccuracySec=30s`, алерт в journal при провале. Проверьте `systemd-analyze verify` и `systemctl list-timers`.
5. Возьмите любой свой скрипт и прогоните его по чек-листу из этой главы. Для каждого непройденного пункта опишите конкретный сценарий отказа, который он допускает, и исправьте.
