# Глава 39. CI/CD: пайплайны, кэш, артефакты

Пайплайн — исполняемая документация о том, как код превращается в сервис. Когда он есть, вопрос «какая версия сейчас в проде» имеет ответ в виде хэша коммита, а не воспоминаний дежурного. Когда его нет, каждый релиз — ручная операция, и цена ошибки растёт вместе с командой. В главе разбирается анатомия пайплайна: стадии, кэш, артефакты, матрицы, секреты, окружения и стратегии выката. После неё вы сможете написать workflow для Python и Go, который укладывается в десять минут и не теряет кэш между запусками.

## Что такое пайплайн и из чего он состоит

Пайплайн (pipeline) — последовательность стадий, каждая из которых превращает вход в выход и может упасть. Минимальный набор: проверка стиля и типов, тесты, сборка артефакта, публикация образа, выкат, проверка после выката. Стадии состоят из jobs — единиц работы на отдельном исполнителе (runner). Jobs внутри стадии идут параллельно, стадии — последовательно, и переход возможен только при успехе предыдущей.

Пайплайн должен быть воспроизводимым: один коммит, прогнанный дважды, даёт один результат. Всё, что нарушает это свойство — незафиксированные версии зависимостей, «последняя» версия тула, состояние раннера от прошлого запуска, — превращает его в генератор случайных чисел.

## Быстрый фидбек: порядок стадий

Разработчик узнаёт о поломке через минуты, а не через полчаса, только если дешёвые проверки стоят первыми. Линтер на 8 секунд должен падать раньше, чем тесты на 6 минут: нет смысла гонять интеграционные тесты, если код не компилируется.

Порядок — по возрастанию стоимости:

1. Синтаксис и форматирование (`ruff format --check`, `gofmt -l`) — секунды.
2. Статический анализ и типы (`ruff check`, `mypy`, `go vet`) — десятки секунд.
3. Юнит-тесты без внешних зависимостей — секунды-минуты.
4. Интеграционные тесты с базой и сетью — минуты.
5. Сборка, публикация, выкат, smoke-тесты — минуты.

Бюджет на pull request — до 10 минут: дольше — и люди начинают мержить «на глаз». Дорогие проверки (полный e2e, нагрузочные) выносятся на ночь или на релизную ветку.

## Кэш зависимостей

Установка зависимостей — самая предсказуемая статья расходов: `pip install -r requirements.txt` на чистом раннере занимает 40–90 секунд, `go mod download` — 10–30, и это время умножается на число jobs и матричных комбинаций.

Кэш строится по ключу — обычно это хэш файла с точными версиями (`requirements.txt`, `poetry.lock`, `go.sum`). Пока хэш не меняется, раннер распаковывает архив с пакетами вместо скачивания. Изменилась одна зависимость — ключ другой, кэш промахнулся, пакеты качаются заново, зато старые версии не подмешаются.

В GitHub Actions кэш включается одной строкой у `setup-python` или `setup-go`, и это почти всегда правильнее, чем писать `actions/cache` руками:

```yaml
- uses: actions/setup-python@v5
  with:
    python-version: "3.14"
    cache: pip
    cache-dependency-path: requirements-dev.txt
```

Три правила, без которых кэш вредит. Не кэшируйте venv целиком: пути внутри архива абсолютные, и на другом раннере окружение окажется нерабочим — кэшируйте `~/.cache/pip` и `~/go/pkg/mod`. Не давайте кэшу из pull request перезаписать кэш основной ветки, иначе форк подложит в него свой пакет. И задавайте срок жизни: кэш месячной давности чаще замедляет, чем ускоряет.

## Артефакты между стадиями

Кэш — оптимизация, артефакт (artifact) — контракт. Артефакт — файл или набор файлов, который одна стадия передаёт другой: бинарник, wheel-пакет, Docker-образ, отчёт о тестах.

Принцип «собирай один раз» снимает целый класс расхождений. Если тесты гоняются на одном бинарнике, а в прод уезжает другой, собранный позже с другими флагами, проверяли вы не то, что выкатываете. Поэтому сборка идёт в отдельном job, а выкат берёт загруженный артефакт.

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: server-linux-amd64
    path: bin/server
    retention-days: 14
```

```yaml
- uses: actions/download-artifact@v4
  with:
    name: server-linux-amd64
    path: bin/
- run: sha256sum bin/server
```

Отчёты о тестах загружаются с `if: always()`, иначе при падении тестов отчёта не будет — а нужен он как раз тогда. Для образов артефакт — сам реестр: следующие стадии ссылаются на неизменяемый тег, а не пересобирают.

## Матрица тестов

Матрица (matrix) — способ прогнать один job с разными параметрами, не дублируя YAML: версия языка, версия базы, операционная система.

```yaml
strategy:
  fail-fast: false
  matrix:
    python: ["3.13", "3.14"]
    database: ["postgres:16-alpine", "postgres:17-alpine"]
```

Комбинации идут параллельно, и падение одной не отменяет остальные (`fail-fast: false`) — иначе вы увидите первую ошибку и не узнаете про остальные три. Матрица не должна разрастаться: 2 версии языка на 2 версии базы — это 4 job, а 5 на 5 — уже 25, и очередь съест всю экономию.

## Секреты в CI

Секрет в CI — ключ доступа к инфраструктуре или учётные данные реестра. Хранится он в секрет-хранилище платформы (`secrets.*` в GitHub Actions), подставляется в переменные окружения шага и маскируется в логах. Маскирование не абсолютно: закодированное значение в лог попадёт.

Что закрывает большинство утечек:

- **Минимальные права токена.** `permissions: contents: read` в начале workflow. `GITHUB_TOKEN` с правами `write-all` — готовый вектор атаки через скомпрометированную зависимость.
- **OIDC вместо статических ключей.** Вместо долгоживущего `AWS_SECRET_ACCESS_KEY` workflow получает короткоживущий токен (`permissions: id-token: write`), и облако доверяет конкретному репозиторию и ветке. Утёкший токен живёт минуты, а не годы.
- **Никаких секретов в `pull_request` из форков.** Такой workflow доступа к секретам не получает, и это правильно. `pull_request_target` доступ даёт, но выполняет код форка в контексте базовой ветки — известный путь к краже секретов.
- **Секреты не передаются в аргументах командной строки.** `docker login -p $PASSWORD` виден в `ps` и в логах; используйте `--password-stdin`.

## Окружения и продвижение

Окружение (environment) — среда, куда выкатывается артефакт: dev, stage, prod. Продвижение (promotion) означает, что в следующее окружение едет тот же артефакт, а не пересобранный заново.

```text
коммит → lint → test → build(образ :sha) → dev → stage → prod
                                            ↑       ↑       ↑
                                       авто    авто   ручное подтверждение
```

В GitHub Actions окружение задаётся блоком `environment`, к нему привязываются правила защиты: обязательные ревьюеры, запрет выката из чужих веток, свой набор секретов. Секреты прода не должны быть доступны job, собирающему образ из pull request.

Артефакт помечается неизменяемым тегом (хэш коммита, например `:a1b2c3d`), а `:1.4.2` — метка поверх него. Откатиться с `:latest` невозможно: непонятно, на что откатываться.

## Стратегии деплоя

| Стратегия | Простой | Ресурсы | Скорость отката | Когда применять |
|---|---|---|---|---|
| Recreate | есть, секунды-минуты | 1x | быстрый | dev, внутренние сервисы |
| Rolling | нет | 1x + запас | средний | большинство stateless-сервисов |
| Blue-green | нет | 2x | мгновенный | критичный прод, есть бюджет |
| Canary | нет | 1x + доля | быстрый | рискованные изменения, много трафика |

**Recreate** останавливает старую версию и запускает новую: дёшево, но между остановкой и стартом сервис недоступен, а незавершённые запросы обрываются.

**Rolling** заменяет экземпляры по одному: подняли новый, дождались готовности, погасили старый. Требует совместимости версий: реплики работают параллельно и видят одну базу.

**{{L|g7|Blue-green}}** держит два одинаковых окружения и переключает трафик целиком: не подошло — вернули за секунды. Цена — двойные ресурсы и общее состояние (база, миграции).

**{{L|g10|Canary}}** отправляет на новую версию 1–5% трафика и смотрит на ошибки и задержки. Ловит деградацию, которую не поймали тесты, но требует метрик по версиям и автоматики отката.

## Откат

Откат ({{L|g98|rollback}}) — не скрипт, а свойство процесса. Он работает при трёх условиях: артефакт предыдущей версии существует, конфигурация версионирована, изменения схемы совместимы в обе стороны.

Первое обеспечивают неизменяемые теги и политика хранения в реестре: удалять старые образы можно, но не все и не сразу.

Второе — конфиги лежат в git и применяются тем же пайплайном (глава 40), а не правятся руками на сервере.

Третье — самое болезненное. Миграция «удалить колонку» делает откат кода невозможным: старый код её ждёт. Поэтому миграции делаются в два шага с релизом между ними: добавить новую колонку и писать в обе, через релиз перестать читать старую, затем удалить. Схема называется {{L|g39|expand/contract}}.

```bash
kubectl rollout undo deployment/api -n shop
kubectl rollout status deployment/api -n shop --timeout=120s
```

## Пример: Python в GitHub Actions

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

env:
  PYTHON_VERSION: "3.14"

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ env.PYTHON_VERSION }}
          cache: pip
          cache-dependency-path: requirements-dev.txt
      - run: pip install -r requirements-dev.txt
      - run: ruff format --check . && ruff check .
      - run: mypy app

  test:
    runs-on: ubuntu-24.04
    strategy:
      fail-fast: false
      matrix:
        python: ["3.13", "3.14"]
    services:
      postgres:
        image: postgres:17-alpine
        env:
          POSTGRES_USER: shop
          POSTGRES_PASSWORD: shop
          POSTGRES_DB: test
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U shop -d test"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
          cache: pip
          cache-dependency-path: requirements-dev.txt
      - run: pip install -r requirements-dev.txt
      - run: pytest -q --junitxml=report.xml --cov=app --cov-fail-under=80
        env:
          DATABASE_URL: postgresql://shop:shop@localhost:5432/test
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: reports-py${{ matrix.python }}
          path: report.xml
          retention-days: 7

  build:
    needs: [lint, test]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy-stage:
    needs: build
    runs-on: ubuntu-24.04
    environment:
      name: stage
      url: https://stage.example.com
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/deploy.sh ghcr.io/${{ github.repository }}:${{ github.sha }}
        env:
          KUBE_CONFIG: ${{ secrets.KUBE_CONFIG_STAGE }}
```

Что здесь важно. `concurrency` отменяет предыдущий запуск на той же ветке: пока вы пушите третий коммит, первые два неинтересны. `if: github.ref == 'refs/heads/main'` не даёт собирать образ из pull request. `permissions` сужены до чтения кода и записи пакетов. Тег — `github.sha`, поэтому деплой ссылается на конкретный коммит. `cache-from/to: type=gha` кэширует слои Docker, `deploy-stage` опирается на окружение с секретом `KUBE_CONFIG_STAGE`; в прод-окружении тот же job потребует подтверждения.

## Пример: Go в GitHub Actions

Go собирается быстрее и не требует виртуального окружения, но требует явной матрицы по платформам и `-race` в тестах.

```yaml
name: go-ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.26"
          cache-dependency-path: go.sum
      - run: go vet ./...
      - run: go test -race -covermode=atomic -coverprofile=cover.out ./...
      - run: go tool cover -func=cover.out | tail -1

  build:
    needs: test
    runs-on: ubuntu-24.04
    strategy:
      matrix:
        include:
          - goos: linux
            goarch: amd64
          - goos: linux
            goarch: arm64
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.26"
          cache-dependency-path: go.sum
      - run: |
          CGO_ENABLED=0 GOOS=${{ matrix.goos }} GOARCH=${{ matrix.goarch }} \
          go build -trimpath -ldflags="-s -w" -o bin/server-${{ matrix.goarch }} ./cmd/server
      - uses: actions/upload-artifact@v4
        with:
          name: server-${{ matrix.goos }}-${{ matrix.goarch }}
          path: bin/server-${{ matrix.goarch }}
```

`-race` включает детектор гонок и замедляет тесты в 2–10 раз — приемлемая цена: гонка, пойманная в CI, на порядки дешевле, чем в проде. Кросс-компиляция в матрице даёт два артефакта из одного коммита.

## Типичные ошибки

1. **Деплой без тестов.** Пайплайн из одного шага `docker build && kubectl apply` экономит десять минут и стоит одного инцидента в месяц. Причина — спешка при первом релизе, которая фиксируется в YAML навсегда.
2. **«Зелёный» пайплайн при падающих тестах.** `pytest || true`, `continue-on-error: true` на тестах или `allow_failure` в GitLab делают шаг незаметным. Через месяц никто не помнит, почему там стоит флаг, а тесты не проверяют ничего.
3. **`latest` в деплое.** Деплой по плавающему тегу означает, что откат невозможен, а «та же версия» на stage и prod — разные образы. Причина — удобство ручного `docker push` вне пайплайна.
4. **Пересборка на каждой стадии.** Каждый job собирает свой бинарник — и в прод уезжает не то, что тестировали. Лечится артефактом и `needs`.
5. **Секреты в логах.** `echo $TOKEN`, `set -x` вокруг команд с паролями, передача ключа аргументом. Маскирование в CI не спасает от base64 и посимвольного вывода.
6. **Ручные правки на проде.** `kubectl edit` в обход git создаёт дрейф: пайплайн при следующем выкате затрёт правку, а причина инцидента останется невидимой. Любое изменение проходит через репозиторий.

## Чек-лист

- [ ] Пайплайн запускается на pull request и на push в основную ветку.
- [ ] Дешёвые проверки (формат, линт) идут раньше тестов; общий бюджет PR — до 10 минут.
- [ ] Кэш зависимостей настроен по хэшу lock-файла, а не по имени ветки.
- [ ] Артефакт собирается один раз и передаётся между стадиями; в прод едет он же.
- [ ] Секреты берутся из хранилища платформы, токену выданы минимальные `permissions`.
- [ ] У окружений есть правила защиты; прод требует ручного подтверждения.
- [ ] Образы тегируются хэшем коммита, старые версии хранятся достаточно долго для отката.
- [ ] Откат проверен на практике, а не описан в вики.

## Упражнения

1. Возьмите репозиторий без CI и добавьте workflow из трёх job: линт, тесты с Postgres-сервисом, сборка образа. Добейтесь, чтобы повторный запуск на неизменённом коде занимал вдвое меньше времени за счёт кэша.
2. Добавьте матрицу по двум версиям Python и намеренно сломайте тест только на одной. Убедитесь, что пайплайн показывает обе ветки, а не останавливается на первой.
3. Переведите деплой на схему dev → stage → prod с ручным подтверждением прода. Проверьте, что на всех трёх окружениях работает один и тот же тег образа.
4. Реализуйте canary-выкат: 10% трафика на новую версию, автоматический откат при росте доли 5xx выше 1% за пять минут.
