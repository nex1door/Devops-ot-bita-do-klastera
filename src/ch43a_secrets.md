# Глава 43a. Секреты: Vault, SOPS, age

«Не храните секреты в git» — верное правило, из которого не следует, что делать вместо. Секрет нужен приложению в момент старта, CI — в момент деплоя, инженеру — в момент отладки, и все три пути надо не только закрыть, но и сделать короче, чем небезопасный. В главе разбирается классификация секретов и модель угроз, способы хранения от переменных окружения до {{L|g152|Vault}}, шифрование значений внутри git через SOPS и age, ротация без простоя и порядок действий при утечке. В конце — рабочие примеры: политика Vault для приложения, динамические креды БД и расшифровка values.yaml в CI.

## Почему «не в git» — половина ответа

Секрет, попавший в git, считается скомпрометированным навсегда: история клонируется, форкается, кэшируется в CI, попадает в бэкапы и в чужие рабочие копии. `git rm` и даже `git filter-repo` не отменяют того, что объект уже был скачан. Отсюда единственная разумная реакция — ротация, а не удаление коммита.

Но запрет без альтернативы рождает обходные пути: секрет пересылают в мессенджере, пишут в вики, кладут в переменную окружения CI и называют это «хранилищем». Вопрос надо ставить иначе: где секрет живёт, кто и по какому праву его читает, как он меняется и как узнать, кто его читал. Ответ на эти четыре вопроса и есть система управления секретами.

## Классификация и модель угроз

Разные секреты требуют разной цены защиты. Пароль к тестовой базе и ключ подписи релизов не должны лежать в одном месте с одинаковыми правами.

| Тип | Живёт | Кто читает | Цена утечки |
|---|---|---|---|
| Пароль БД | долго | приложение | доступ к данным, часто ко всем тенантам |
| API-ключ внешнего сервиса | месяцы | приложение | деньги, репутация, данные клиентов |
| TLS-ключ | 90 дней | балансировщик | подмена трафика, обход проверок |
| Токен CI/CD | часы-дни | пайплайн | деплой произвольного кода в прод |
| Ключ шифрования данных | годы | сервис | расшифровка бэкапов и архива |

Модель угроз начинается с перечня, от кого защищаемся: разработчик с доступом к репозиторию, но без доступа к проду; скомпрометированный под, читающий своё окружение; инсайдер с правами администратора кластера; резервная копия в незащищённом хранилище; лог с заголовком авторизации.

Граница: хранилище не защищает от root на хосте и от того, у кого есть право читать память процесса. Оно сокращает поверхность и делает доступ видимым, но не отменяет компромисс узла.

## Три способа хранения и их цена

Переменные окружения (environment variables) — самый распространённый способ и самый утечкоопасный. Значение видно в `/proc/<pid>/environ` любому процессу того же пользователя, в `docker inspect`, в `ps e`, в дампах и логах падений; оно наследуется всеми дочерними процессами, включая чужие утилиты. Плюс один — простота: ничего не надо монтировать.

```bash
tr '\0' '\n' < /proc/1/environ | grep -i pass
```

Файл с правами `0400`, смонтированный в контейнер, лучше: он не наследуется, не попадает в `ps e` и читается только владельцем. Минусы — жизненный цикл: кто обновит файл при ротации, увидит ли приложение изменение, не останется ли копия в образе.

Secret-хранилище (Vault, облачные менеджеры секретов) даёт то, чего нет у первых двух: короткоживущую выдачу, права на конкретный путь, аудит каждого чтения и ротацию в одном месте. Цена — ещё один компонент, который может упасть, и необходимость аутентифицировать приложение, а не человека.

## Vault: движки, политики, токены

Vault — сервер, который выдаёт секреты по токену. Всё остальное — следствия: у токена есть TTL и политика, у секрета — путь и версия, у каждого чтения — запись в аудите.

Движок KV версии 2 хранит версии значений. Путь в API отличается от логического: `secret/shop/api` в CLI — это `secret/data/shop/api` в API и в политиках, потому что `data` — часть движка, а не имени секрета.

```bash
vault secrets enable -path=secret kv-v2
vault kv put secret/shop/api db_password='S3cure-...' stripe_key='sk_live_...'
vault kv get -field=db_password secret/shop/api
vault kv metadata put -max-versions=5 secret/shop/api
```

Политика — единственный способ ограничить доступ; токен без политики не умеет ничего. Минимальные права означают `read` на конкретный путь, без `list` на весь движок и без доступа к `metadata`, если версии не нужны.

```hcl
path "secret/data/shop/api" {
  capabilities = ["read"]
}

path "secret/metadata/shop/api" {
  capabilities = ["read"]
}
```

Приложение аутентифицируется не паролем, а методом, привязанным к платформе: Kubernetes-auth (под предъявляет {{L|g104|service}} account token), AppRole (role_id и secret_id), облачный IAM. Дальше — токен с коротким TTL, который продлевается, пока жив процесс:

```bash
vault policy write shop-api shop-api.hcl
vault token create -policy=shop-api -ttl=1h -renewable=true
curl -s -H "X-Vault-Token: $VAULT_TOKEN" \
  "$VAULT_ADDR/v1/secret/data/shop/api" | jq -r '.data.data.db_password'
```

`renewable=true` важен: без продления приложение умрёт через час после старта. TTL в час означает, что утёкший токен живёт час, а не три года.

### Динамические креды вместо статичного пароля

Статичный пароль БД живёт в Vault, но остаётся одним и тем же для всех реплик: утечка требует ручной ротации, а в логах БД все запросы выглядят как один пользователь. Движок database создаёт пользователя на время: Vault подключается к БД административной учёткой, выполняет `CREATE ROLE`, отдаёт логин и пароль с TTL и удаляет роль по истечении.

```bash
vault secrets enable database
vault write database/config/shop \
  plugin_name=postgresql-database-plugin \
  allowed_roles="shop-api" \
  connection_url="postgresql://{{username}}:{{password}}@db:5432/shop?sslmode=require" \
  username="vault_admin" password="$VAULT_DB_ADMIN_PASS"

vault write database/roles/shop-api db_name=shop default_ttl=1h max_ttl=24h \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}'
    VALID UNTIL '{{expiration}}';
    GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO \"{{name}}\";"
```

Теперь у каждой реплики свой пользователь, в `pg_stat_activity` видно, кто держит соединение, а срок жизни креды ограничен часом. Обратная сторона: приложение обязано переподключаться при истечении, а пул — обновлять пароль, иначе динамические креды дают отказы раз в час.

### Agent, injector и запечатывание

Заставлять каждое приложение ходить в API Vault — лишний код. Vault Agent сайдкаром аутентифицируется сам, держит и обновляет токен, рендерит секреты в файл по шаблону; приложение просто читает файл. Injector делает то же через admission webhook, подменяя поды с аннотациями.

Отдельно — режим запечатывания (seal). После старта Vault запечатан: данные на диске зашифрованы, а ключ шифрования защищён мастер-ключом, который собирается из кворума (например, 3 из 5). Пока три хранителя не введут свои части через `vault operator unseal`, секреты не выдаются.

В продакшене ручное распечатывание — точка отказа: после перезагрузки узла сервис не поднимется, пока не соберутся три человека. Поэтому используют авто-распечатывание (auto-unseal) через KMS или transit-движок другого кластера: кворум людей меняется на доверие к облачному KMS.

## SOPS и age: шифрование значений в git

Если секреты должны лежать в git (например, в GitOps-репозитории), их шифруют так, чтобы расшифровать мог только нужный круг. SOPS шифрует не файл целиком, а значения, оставляя ключи и структуру читаемыми: диффы остаются осмысленными.

Ключи для SOPS бывают разные (age, PGP, KMS); age — самый простой: одна строка приватного ключа, один публичный адрес.

```bash
age-keygen -o age.key
```

```
Public key: age1qyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqs2m6s9
```

```bash
age-keygen -y age.key
```

Правила шифрования задаются в `.sops.yaml` в корне репозитория, чтобы не перечислять получателей в каждой команде:

```yaml
creation_rules:
  - path_regex: environments/prod/.*\.yaml$
    encrypted_regex: ^(data|stringData|password|token|key)$
    age: age1qyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqszqgpqyqs2m6s9
```

`encrypted_regex` шифрует только значения с этими именами: остальное остаётся открытым, и в ревью видно, что изменился, например, только тег образа.

```bash
sops --encrypt --in-place environments/prod/values.yaml
sops --decrypt environments/prod/values.yaml | head -20
```

В зашифрованном файле значения выглядят как `ENC[AES256_GCM,data:...,type:str]`, а в конце появляется блок `sops` с получателями, версией формата и MAC. Правка идёт через `sops environments/prod/values.yaml`: редактор получает расшифрованный текст, а на диск возвращается шифрованный.

Расшифровать может тот, чей приватный ключ указан получателем. Значит, круг доступа к прод-секретам — это список age-адресов в `.sops.yaml`, и его изменение видно в диффе. Отзыв доступа — перевыпуск файла с новым списком, но старые версии в истории остаются читаемыми для того, у кого был ключ.

## Расшифровка в CI и GitOps

В CI приватный ключ лежит в секрете пайплайна (в GitHub — Actions secret, в GitLab — masked variable) и передаётся SOPS через переменную окружения, а не файлом на диске:

```bash
export SOPS_AGE_KEY="$AGE_PRIVATE_KEY"
sops --decrypt environments/prod/values.yaml > /tmp/values.yaml
helm upgrade --install shop ./chart -f /tmp/values.yaml --namespace shop
```

`/tmp/values.yaml` после деплоя надо удалять, а лучше не создавать: `sops exec-file` и `sops exec-env` расшифровывают во временный файл или переменные на время команды и убирают за собой. Печатать расшифрованное в лог нельзя: маскирование в CI не спасает от `set -x` и `helm --debug`.

В GitOps-схеме (глава 41a) кластер сам тянет манифесты из git. Flux расшифровывает SOPS при применении: ключ лежит в Secret в namespace контроллера, в манифесте указан `spec.decryption.provider: sops`; ArgoCD требует для этого плагин или sidecar. Альтернатива — Sealed Secrets: приватный ключ хранит контроллер в кластере, а в git попадает `SealedSecret`, который может расшифровать только этот кластер. Разница принципиальная: SOPS-файл прочитает любой, у кого есть age-ключ, SealedSecret в другом кластере бесполезен — удобно для мультикластера, неудобно для восстановления из бэкапа.

## Ротация без простоя

Ротация — процесс, а не событие. Минимальная схема — два активных ключа и перекрытие (overlap): новый создаётся, распространяется, приложения переключаются, старый живёт ещё сутки и только потом отзывается. Иначе реплики с кэшированной конфигурацией начнут получать отказы.

Порядок для API-ключа: создать второй ключ в панели провайдера, положить оба в Vault (`stripe_key` и `stripe_key_next`), выкатить код, читающий новый, дождаться обновления всех подов, отозвать старый. Окно перекрытия должно быть больше времени жизни пода и TTL кэша конфигурации.

С паролем БД сложнее: PostgreSQL и MySQL допускают один пароль на роль. Варианты — отдельная роль на релиз (старую удаляют после переключения), PgBouncer с двумя пользователями или динамические креды, где перекрытие получается само.

Автоматическая ротация снимает ручную работу, но добавляет следствия: приложение должно перечитывать секрет без рестарта, пул соединений — переподключаться, мониторинг — отличать плановую ротацию от аварии. Худший результат — ротация, которая ломает сервис каждые 30 дней и которую поэтому отключают.

## Что делать при утечке

Порядок важен, и он не совпадает с интуицией «сначала разобраться».

1. Отозвать. Немедленно отключить ключ, сменить пароль, отозвать токен. Разбирательство — после; пока ключ жив, утечка продолжается.
2. Заменить. Выпустить новый секрет и выкатить его; проверить, что все потребители перешли.
3. Найти источник. `gitleaks detect --source . --redact` по репозиторию и истории, поиск по логам CI, по бакетам, по образам, по локальным копиям.
4. Проверить использование. По логам провайдера и БД — были ли обращения из незнакомых мест, какие данные читались, что создано.
5. Записать. Краткая хронология, кто и когда узнал, что сделано; для инцидент-ревью и для регуляторов, если данные персональные.

Поиск по истории не должен светить сам секрет: `git log -S 'sk_live_' --oneline` покажет коммиты, где строка появлялась, не печатая её. Удаления недостаточно: переписывание истории ломает клоны и не гарантирует, что объект исчез у всех, поэтому ротация обязательна независимо от чистки.

## Аудит: кто читал и когда

Аудит отличает управление секретами от их хранения. В Vault включают audit device — файл или syslog, куда пишется каждое обращение: путь, метод, идентичность, адрес, результат.

```bash
vault audit enable file file_path=/var/log/vault/audit.log
jq -r 'select(.request.path=="secret/data/shop/api")
  | [.time, .auth.display_name, .request.remote_address] | @tsv' \
  /var/log/vault/audit.log | tail -20
```

Значения секретов в аудит не попадают, только метаданные; лог надо защищать от удаления приложением и хранить отдельно от прикладных. В Kubernetes к этому добавляется audit policy с уровнем `Metadata` на `secrets`, в облаке — audit trail провайдера.

Аудит отвечает на вопросы: кто читал прод-секрет за 30 дней, были ли чтения из незнакомого namespace, сколько раз выдавались динамические креды. Если ответить нельзя, хранилище используют как дорогой файл.

## Типичные ошибки

1. **Секрет в `.env`, закоммиченный «на время».** Файл попадает в историю, кэш CI и образ; ротации нет, потому что «никто не видел». Причина — соблазн запустить локально быстро.
2. **`ENV API_KEY=...` в {{L|g30|Dockerfile}}.** Слой остаётся в манифесте даже если следующий слой «удаляет» переменную. Причина — путаница между изменением файловой системы и историей слоёв.
3. **Токен Vault без TTL и с политикой `root`.** Утечка даёт доступ ко всем секретам навсегда, а аудит показывает только `root`. Причина — так быстрее отладить.
4. **Ручное распечатывание без плана.** После перезагрузки кластер не поднимается, пока не соберутся три человека с ключами. Причина — seal воспринимают как формальность.
5. **Отзыв ключа до переключения.** Реплики с кэшированной конфигурацией начинают отдавать 500, и инцидент выглядит как последствие ротации. Причина — экономия на окне перекрытия.
6. **Расшифровка в CI с печатью в лог.** `set -x` или `helm --debug` выводят секрет в лог, доступный всем, у кого есть доступ к сборке. Причина — отладка на живых секретах.

## Чек-лист

- [ ] Секреты не в git и не в образе; в репозитории только шифротекст.
- [ ] Приложение получает секрет по короткоживущему токену с минимальной политикой.
- [ ] У каждого секрета есть владелец, срок жизни и описанная процедура ротации.
- [ ] Ротация проверена на стенде с окном перекрытия, а не только описана.
- [ ] Аудит-логи включены, хранятся отдельно и не удаляются приложением; запечатывание покрыто планом: кто и за какое время распечатает.
- [ ] В CI секрет не печатается, временные файлы удаляются, ключ — в masked-переменной.
- [ ] Есть порядок действий при утечке: отзыв, замена, аудит, запись.

## Упражнения

1. Сравните на одном контейнере три способа доставки секрета: env, файл `0400` и том `emptyDir` с `medium: Memory`. Покажите, где значение видно снаружи контейнера и кому.
2. Поднимите Vault в dev-режиме, включите KV v2, создайте политику только на чтение одного пути и токен с TTL 10 минут. Убедитесь, что после истечения токена чтение возвращает 403.
3. Зашифруйте `values.yaml` через SOPS с `encrypted_regex`, измените одно значение и объясните, почему дифф остаётся читаемым. Затем расшифруйте файл ключом, которого нет в списке получателей.
4. Настройте динамические креды PostgreSQL в Vault с TTL 5 минут. Посмотрите, что происходит с открытым соединением после истечения, и предложите, как приложение должно себя вести.
5. Проведите учебную утечку: положите ключ в репозиторий, найдите `gitleaks`, отзовите, замените и соберите хронологию по аудит-логу Vault.
