# Глава 3. Процессор и память: как код превращается в такты

Программа на любом языке в конечном счёте превращается в поток инструкций, которые процессор исполняет по тактам, и в обращения к памяти, которые уходят в кэш или в DRAM. Понимание этой пары — инструкции и данные — объясняет вещи, которые иначе выглядят магией: почему обход массива в девяносто раз быстрее обхода связного списка с теми же данными; почему добавление одного поля в структуру увеличивает её с 16 до 24 байт; почему сервис на 8 ядрах работает медленнее, чем на 4, если память «неправильная». В главе разбираются конвейер, предсказание переходов, иерархия кэшей с латентностями в тактах, выравнивание структур и NUMA. Все замеры в главе сделаны на реальной машине: Xeon E3-1230 v3, 3.3 ГГц, L1 32 КиБ на ядро, L2 256 КиБ, L3 8 МиБ — цифры на вашем железе будут отличаться, порядок величин — нет.

## Такт и конвейер

Такт — минимальный интервал, за который процессор продвигает работу на один шаг. На 3.3 ГГц такт длится около 0.3 нс; за это время свет проходит 10 см. Тактовая частота давно перестала быть главной характеристикой: с середины 2000-х она упёрлась в тепловыделение, и рост производительности пошёл за счёт параллелизма внутри ядра и кэшей.

Современное ядро — конвейер (pipeline) из десятка стадий: выборка инструкции, декодирование, переименование регистров, планирование, исполнение, доступ к памяти, запись результата. Пока инструкция №1 исполняется, №2 декодируется, №3 выбирается из памяти. В идеале за такт завершается одна инструкция, на практике мешают три вида конфликтов (hazards): структурные (один и тот же блок занят), по данным (нужен результат предыдущей инструкции) и по управлению (неизвестно, куда прыгать).

Конфликты по данным процессор обходит пересылкой результатов (forwarding) и внеочередным исполнением (out-of-order): пока ждём данные из памяти, исполняются независимые инструкции, а окно переупорядочивания на современных ядрах — сотни инструкций. Конфликт по управлению решается предсказанием переходов ({{L|g8|branch}} prediction). Ядро угадывает, пойдёт ли ветвление `if` или цикл на следующую итерацию, и спекулятивно исполняет угаданную ветку. Угадало — ветка уже готова; не угадало — конвейер сбрасывается, теряется 15–25 тактов.

Точность современных предсказателей — 95–99% на обычном коде, поэтому средний штраф невелик. Но у предсказания есть цена и цена эта видна в двух местах. Первое: на данных, которые ведут себя непредсказуемо, штраф платится постоянно. Классический пример — фильтрация массива, где условие зависит от случайных данных: тот же код на отсортированных данных работает в разы быстрее не потому, что меньше работы, а потому что предсказатель перестаёт ошибаться. Второе: спекулятивное исполнение — вектор атаки (Spectre и родственники), из-за чего компиляторы и ядра получили барьеры и оговорки, а часть оптимизаций стала недоступной.

Практический вывод для прикладного кода скромен: писать ветвления так, чтобы они были предсказуемы (сначала частый случай), не бояться «лишних» вычислений ради устранения ветки в горячем цикле и не пытаться перехитрить компилятор без замеров.

## Иерархия памяти

Процессор за такт может выполнить несколько инструкций, но данные из DRAM идут сотни тактов. Разрыв компенсируется кэшами: маленькие и быстрые ближе к ядру, большие и медленные — дальше.

| Уровень | Типичный объём | Латентность | Что это в тактах |
|---|---|---|---|
| Регистры | ~1 КБ | < 1 такта | 0 |
| L1d | 32–48 КиБ | ~1 нс | 4–5 |
| L2 | 256 КиБ – 2 МиБ | ~4 нс | 12–20 |
| L3 | 8–64 МиБ | ~15 нс | 40–75 |
| DRAM | десятки–сотни ГиБ | ~70–100 нс | 200–350 |
| NVMe SSD | терабайты | 20–100 мкс | десятки тысяч |
| Сеть (RTT в ДЦ) | — | 0.1–0.5 мс | сотни тысяч |

Числа — порядок величин для настольных и серверных x86; на ARM и на новых поколениях они сдвигаются, но соотношения сохраняются. Разрыв между L1 и DRAM — примерно два порядка, между L1 и SSD — четыре-пять.

Кэш работает не с байтами, а с линиями (cache line) по 64 байта: читая один `int`, процессор тащит всю линию. Отсюда два следствия. Первое: последовательный доступ почти бесплатен — восемь подряд идущих `long` приходят одной линией. Второе: случайный доступ по одному байту из разных линий тратит 64 байта трафика на 8 полезных. Именно поэтому структуры данных, разложенные в памяти подряд, выигрывают у указателей даже при одинаковой алгоритмической сложности.

Ещё один механизм — аппаратный префетчер (hardware prefetcher). Он замечает последовательный или ступенчатый шаблон адресов и заранее подтягивает следующие линии. Префетчер спасает линейный обход: даже когда массив не влезает в кэш, загрузка идёт «пакетом» и латентность прячется. Но он бессилен против зависимых обращений: если адрес следующего элемента неизвестен, пока не прочитан текущий (связный список, обход дерева), предсказать нечего, и каждое обращение ждёт полную латентность DRAM.

## Замер: массив против связного списка

Проверим это на практике. Программа ниже суммирует 4 194 304 числа двумя способами: по массиву подряд и по связному списку, узлы которого лежат в той же выделенной области, но связаны в случайном порядке. Объём данных одинаковый — 32 МиБ, работы одинаково — 4 миллиона сложений. Ниже приведён ключевой фрагмент файла `bench.c`; полная программа (~80 строк) компилируется как `gcc -O2 -o bench bench.c`.

```c
typedef struct Node {
    struct Node *next;   // 8 байт
    long value;          // 8 байт
} Node;

// ... перемешивание индексов Фишера—Йетса ...
for (size_t i = 0; i < N; i++) nodes[i].value = (long)i;
for (size_t i = 0; i < N; i++)
    nodes[perm[i]].next = &nodes[perm[(i + 1) % N]];   // один цикл по всем узлам

// последовательный проход
for (size_t i = 0; i < N; i++) s1 += arr[i];

// обход списка: каждое обращение зависит от предыдущего
for (size_t i = 0; i < N; i++) { s2 += p->value; p = p->next; }
```

Сборка и запуск:

```bash
gcc -O2 -o bench bench.c && ./bench
```

Вывод на тестовой машине:

```text
массив:     3.9 ms    8.60 ГБ/с  0.930 нс/элемент
список:   356.2 ms    0.09 ГБ/с  84.919 нс/элемент
разница: 91x (суммы 8796090925056 и 8796090925056)
```

Девяносто один раз — при одинаковом количестве сложений и одинаковом объёме данных. Контрольные суммы совпадают, значит, оба цикла прочитали ровно одно и то же. Причина — не в указателях как таковых, а в том, что разыменование `p->next` создаёт цепочку зависимостей: адрес следующего узла неизвестен, пока не завершено текущее чтение. 84.9 нс на элемент при 3.5 ГГц — это около 300 тактов, ровно латентность DRAM. Массив же читается по 0.93 нс на элемент, потому что префетчер идёт впереди цикла.

Вторая часть вывода того же прогона показывает, где кончается кэш. Обход массива разного размера, лучшее из 20 прогонов:

```text
размер   мс       нс/элемент
   64 КБ    0.003   0.3499
 1024 КБ    0.046   0.3500
 4096 КБ    0.184   0.3500
16384 КБ    1.334   0.6360
65536 КБ    6.346   0.7564
```

До 4 МиБ производительность не меняется — данные помещаются в L2/L3, дальше начинается DRAM, и время на элемент удваивается. Обратите внимание: рост всего вдвое, а не в сто раз. Это работа префетчера: последовательный доступ к DRAM конвейеризуется. Именно поэтому главный враг производительности — не «медленная память», а непредсказуемый доступ к ней.

## Выравнивание и размер структуры

Компилятор размещает поля структур с выравниванием (alignment): поле типа `long` должно начинаться с адреса, кратного 8. Чтобы это выполнялось, между полями вставляются невидимые байты — паддинг, а размер структуры округляется до кратности её выравнивания.

```c
struct A { char a; long b; char c; };   // sizeof = 24
struct B { long b; char a; char c; };   // sizeof = 16
```

На тестовой машине `sizeof(A)` равен 24, `sizeof(B)` — 16, хотя полей в них поровну и данные те же. В `A` после `char a` вставлено 7 байт паддинга, чтобы `long b` лёг на границу 8, и ещё 7 байт в конце — чтобы размер был кратен 8. Перестановка полей по убыванию размера экономит треть памяти на структуре. На массиве из миллиона записей это 8 МиБ трафика и заметно меньше промахов кэша.

На x86 невыровненный доступ обычно работает, но стоит дороже: обращение, пересекающее границу линии, требует двух обращений к кэшу. На ARM часть невыровненных обращений приводит к исключению. Упаковка структур через `#pragma pack(1)` или атрибут `packed` убирает паддинг, но создаёт ровно эту проблему — и часто вдобавок запрещает векторизацию. Упаковывать имеет смысл только форматы на диске и в сети, а не структуры в памяти.

Отдельный случай — ложное разделение (false sharing). Если два потока пишут в разные поля, попавшие в одну 64-байтовую линию, линия «прыгает» между ядрами, и оба потока тормозят, хотя данные не пересекаются. Лечится выравниванием разделяемых структур по границе линии (в C — `alignas(64)`, в Go — паддинг до 64 байт, в Java — `@Contended`), и это одна из немногих оптимизаций, которая даёт эффект без изменения алгоритма.

## NUMA кратко

На многосокетных серверах память физически привязана к сокетам: часть планок подключена к первому процессору, часть — ко второму. Доступ к «своей» памяти занимает условные 80 нс, к чужой — 130–150 нс плюс ограничение пропускной способности межсокетной шины. Linux распределяет страницы по принципу первого касания (first touch): страница физически выделяется на том узле, чей поток первым в неё записал. Отсюда два практических правила: инициализировать большие массивы в том же потоке, который будет их обрабатывать, и привязывать процессы к узлам (`numactl --cpunodebind=0 --membind=0`). В контейнерах на многосокетном хосте без привязки планировщик легко разложит потоки по разным сокетам, и приложение будет вдвое медленнее «на пустом месте».

## Что из этого следует для кода

Первое: структура данных важнее микрооптимизаций. Массив структур (AoS) хорош, когда нужны все поля записи; массив отдельных полей (SoA) — когда нужен один признак по всем записям: он читает 1/8 трафика и векторизуется. Колоночные СУБД (ClickHouse, Parquet) построены на этом же принципе.

Второе: избегать цепочек указателей в горячем пути. `[]*Item` в Go, `list.List`, словарь объектов в Python — все они превращают линейный обход в набор зависимых обращений. Замена на `[]Item` или на индексы вместо указателей часто даёт больше, чем любой профайлер.

Третье: батчить. Один запрос к БД на 1000 строк дешевле тысячи запросов по одной строке не из-за сети, а из-за локальности: драйвер собирает строки в один буфер.

Четвёртое: не оптимизировать без замеров. Кэш-эффекты нелинейны: программа может ускоряться при добавлении работы (лучше шаблон доступа) и замедляться при её сокращении. Мерить надо на реальном объёме данных, а не на тестовом массиве из десяти элементов.

## Типичные ошибки

1. **Оптимизировать на языке с интерпретатором, глядя на алгоритм.** В Python накладные расходы интерпретатора (десятки-сотни нс на операцию) перекрывают латентность кэша, поэтому «локальность» в чистом Python почти не видна; она проявляется в numpy/pandas, где цикл уходит в C. Замер на CPython-цикле покажет одно, а на реальной нагрузке — другое.

2. **Считать, что связный список медленный из-за аллокаций.** В замере выше все узлы лежали в одном `malloc`, аллокаций во время обхода не было — и всё равно 91-кратная разница. Причина в зависимых обращениях, а не в `malloc`.

3. **Игнорировать паддинг при проектировании структур.** Порядок полей и лишний `bool` в середине структуры увеличивают её на 30–50%, а на массивах это прямо превращается в промахи кэша. Проверять `sizeof` (или `unsafe.Sizeof` в Go) дешевле, чем потом разбираться с памятью.

4. **Упаковывать всё через `packed`.** Экономия байтов оборачивается невыровненными обращениями, падением скорости и потенциальными исключениями на ARM. Упаковка уместна для внешних форматов, а не для рабочих структур.

5. **Держать «горячие» счётчики потоков рядом.** Два атомарных счётчика в одной линии превращают масштабирование в ping-pong; на 8 потоках суммарная пропускная способность падает в разы. Разносить по линиям, а не по структурам.

6. **Забывать про NUMA в контейнерах.** Лимит CPU и memory limit ничего не говорят о топологии; приложение может половину обращений делать в удалённый узел. Проверять `numactl --hardware` и профиль деградации при росте потоков.

7. **Верить одному замеру.** Первый прогон включает прогрев кэшей, page faults и JIT; результат скачет в разы. Нужны прогресс, несколько итераций, минимум или медиана, и фиксация частоты CPU.

## Чек-лист

- Горячие структуры данных лежат в памяти подряд, без цепочек указателей на каждый элемент?
- Порядок полей в часто используемых структурах проверен через `sizeof`/`unsafe.Sizeof`, лишнего паддинга нет?
- Для разделяемых между потоками счётчиков исключено ложное разделение (выравнивание по 64 байтам)?
- Обход больших наборов данных идёт последовательно (по индексу, по колонке), а не в случайном порядке?
- Замеры сделаны на объёме данных, близком к продакшену, с прогревом и несколькими итерациями?
- На многосокетном хосте проверена топология и, если нужно, сделана привязка процессов к NUMA-узлу?
- В коде на интерпретируемом языке тяжёлые циклы вынесены в векторизованные библиотеки, а не написаны на самом языке?
- Известно, какие ветвления в горячем пути зависят от случайных данных (и нельзя ли их устранить)?

## Упражнения

1. **Кэш-лестница.** Повторите замер из главы на своей машине для размеров от 4 КиБ до 256 МиБ. Определите по графику «время на элемент от размера» объёмы L1, L2 и L3 и сравните с выводом `lscpu`.

2. **Структуры.** Для структуры `{char, int, char, double, char}` посчитайте `sizeof` вручную, затем проверьте компилятором. Найдите перестановку полей с минимальным размером и объясните, почему меньше определённого значения размер быть не может.

3. **Ложное разделение.** Напишите программу с двумя потоками, каждый из которых инкрементирует свой счётчик миллион раз: сначала счётчики в одной структуре, затем разнесённые на разные линии. Сравните время и объясните разницу.

4. **Указатели против индексов.** Возьмите обход бинарного дерева на 10 миллионов узлов, реализованный через указатели и через индексы в массиве. Сравните время поиска и объясните, почему разница зависит от высоты дерева.

5. **NUMA.** На машине с двумя сокетами запустите один и тот же процесс с `numactl --cpunodebind` и без него, замерив пропускную способность чтения памяти. Объясните, почему для однопоточного кода разница может быть незаметна, а для многопоточного — двукратной.
