# Глава 1. Что такое вычисление: автоматы, машина Тьюринга, вычислимость

Инженер, который пишет скрипты развёртывания и правит манифесты Kubernetes, редко задумывается о том, что такое вычисление по своей сути. Между тем теория вычислений отвечает на вопросы, с которыми он сталкивается еженедельно: почему линтер не может доказать, что программа корректна; почему «умная» валидация конфигурации всегда остаётся набором эвристик; почему нельзя написать проверялку, которая заранее скажет, зависнет ли чужой процесс. В этой главе мы пройдём путь от простейшей модели вычислений — конечного автомата — до машины Тьюринга, сформулируем тезис Чёрча—Тьюринга и разберём доказательство неразрешимости проблемы остановки. Читатель научится отличать «мы не знаем, как это сделать» от «это невозможно в принципе» и оценивать, где автоматизация заканчивается.

## Конечный автомат: светофор

Конечный автомат (finite state machine, FSM) — это пятёрка: множество состояний `Q`, входной алфавит `Σ`, функция переходов `δ: Q × Σ → Q`, начальное состояние `q₀` и множество принимающих состояний `F`. Всё «знание» автомата о прошлом упаковано в одно число — номер текущего состояния. Собственной памяти у него нет: он не считает, сколько событий пришло, не хранит историю, не накапливает счётчик.

Светофор — канонический пример. У него четыре состояния: красный, красный с жёлтым, зелёный, жёлтый. Единственное внешнее событие — тик таймера. Функция переходов задаётся таблицей, и таблица эта полная: для каждой пары «состояние + вход» определён ровно один следующий шаг.

| Состояние | Вход | Следующее состояние |
|---|---|---|
| красный | тик | красный + жёлтый |
| красный + жёлтый | тик | зелёный |
| зелёный | тик | жёлтый |
| жёлтый | тик | красный |

На Python это отображается почти дословно: словарь, ключом которого служит пара (состояние, вход). Такой код ценен не краткостью, а тем, что он исключает «непредусмотренные» ветки: всё поведение видно в одной структуре данных, и добавление нового состояния — это правка таблицы, а не поиск `if` по всему файлу.

```python
from enum import Enum

class Light(Enum):
    RED = "красный"
    RED_YELLOW = "красный+жёлтый"
    GREEN = "зелёный"
    YELLOW = "жёлтый"

DELTA = {
    (Light.RED, "timer"):        Light.RED_YELLOW,
    (Light.RED_YELLOW, "timer"): Light.GREEN,
    (Light.GREEN, "timer"):      Light.YELLOW,
    (Light.YELLOW, "timer"):     Light.RED,
}

def run(start: Light, events: list[str]) -> list[Light]:
    state, trace = start, [start]
    for e in events:
        state = DELTA.get((state, e), state)  # неизвестный вход игнорируется
        trace.append(state)
    return trace

print([s.value for s in run(Light.RED, ["timer"] * 6)])
```

Вывод:

```text
['красный', 'красный+жёлтый', 'зелёный', 'жёлтый', 'красный', 'красный+жёлтый', 'зелёный']
```

Обратите внимание на строку `DELTA.get((state, e), state)`: она моделирует важное инженерное решение — реакцию на событие, которого нет в таблице. Автомат, у которого переход не определён, «застревает»; практическая реализация обычно игнорирует неизвестный вход или переходит в состояние ошибки. Выбор между этими вариантами — не теоретический: именно он определяет, упадёт ли ваш сервис от лишнего поля в вебхуке.

### Лексер: автомат, который работает в каждом компиляторе

Второй пример ближе к ежедневной работе: лексический анализатор (lexer, tokenizer). Он читает поток символов и выдаёт поток токенов — чисел, идентификаторов, операторов. Формально это тоже конечный автомат: состояния «начало токена», «внутри числа», «внутри идентификатора», «оператор», «ошибка»; памяти хватает лишь на накопление текущего токена.

```python
DIGITS = set("0123456789")
LETTERS = set("abcdefghijklmnopqrstuvwxyz_")
OPS = set("+-*/=()")

def lex(src: str) -> list[tuple[str, str]]:
    tokens, i, n = [], 0, len(src)
    while i < n:
        c = src[i]
        if c in " \t\n":
            i += 1                      # пробелы не порождают токенов
            continue
        if c in DIGITS:                 # состояние NUM
            j = i
            while j < n and (src[j] in DIGITS or src[j] == "."):
                j += 1
            tokens.append(("NUM", src[i:j])); i = j
        elif c in LETTERS:              # состояние IDENT
            j = i
            while j < n and (src[j] in LETTERS or src[j] in DIGITS):
                j += 1
            tokens.append(("IDENT", src[i:j])); i = j
        elif c in OPS:                  # состояние OP
            tokens.append(("OP", c)); i += 1
        else:                           # состояние ERR
            raise SyntaxError(f"недопустимый символ {c!r} в позиции {i}")
    return tokens

print(lex("total = price * 1.2 + shipping_fee"))
```

Разбор строки `total = price * 1.2 + shipping_fee` даёт `IDENT total`, `OP =`, `IDENT price`, `OP *`, `NUM 1.2`, `OP +`, `IDENT shipping_fee`. Никакого «понимания» смысла здесь нет: различить `x*2` и `x**2` лексер не в состоянии, для этого нужен следующий уровень — синтаксический анализатор с магазинной памятью. Это первая важная граница: регулярные языки не умеют считать вложенность произвольной глубины. Скобки, блоки, YAML-отступы — всё, что требует счётчика глубины, выходит за пределы FSM. Поэтому regex не подходит для разбора конфигов, а нужен настоящий парсер.

## Машина Тьюринга

Машина Тьюринга (Turing machine, 1936) добавляет к автомату ровно две вещи: бесконечную ленту с ячейками и головку, которая может читать символ, записывать новый и сдвигаться на ячейку влево или вправо. Формально это набор `(Q, Γ, b, δ, q₀, F)`: состояния, ленточный алфавит, пустой символ, функция переходов вида `Q × Γ → Q × Γ × {L, R}`, начальное и принимающие состояния.

Разница с конечным автоматом принципиальна. FSM с `n` состояниями — это устройство с `n` «ячейками памяти», и всё, что оно способно распознать, описывается регулярным выражением. Машина Тьюринга имеет потенциально бесконечную память и поэтому может считать, сравнивать, умножать, интерпретировать другие машины. При этом её конструкция до смешного проста — и именно простота делает её удобной мерой: если задача решается на машине Тьюринга, она вычислима вообще.

Покажем машину, которая прибавляет единицу к двоичному числу. Идея: головка идёт вправо до пустой ячейки, затем влево, выполняя перенос: `1` заменяется на `0` с переносом дальше, `0` — на `1` с остановкой.

```python
def tm_increment(bits: str, max_steps: int = 10_000) -> tuple[str, int]:
    """Прибавляет 1 к двоичному числу. '_' — пустая ячейка."""
    tape = list(bits) + ["_"]
    head, state, steps = 0, "seek_end", 0
    blank = "_"

    while steps < max_steps:
        steps += 1
        sym = tape[head]

        if state == "seek_end":
            if sym in "01":
                head += 1
            else:                 # дошли до пустой ячейки — шаг назад
                head -= 1
                state = "carry"

        elif state == "carry":
            if sym == "1":        # 1 + 1 = 10: пишем 0, перенос влево
                tape[head] = "0"
                head -= 1
            else:                 # '0' или пустая ячейка: пишем 1, готово
                tape[head] = "1"
                return "".join(tape).rstrip(blank), steps

        if head < 0:              # лента влево не бесконечна — расширяем
            tape.insert(0, blank)
            head = 0

    raise RuntimeError("не остановилась за отведённое число шагов")

for n in ("0", "1011", "111", "11111111"):
    result, steps = tm_increment(n)
    print(f"{n:>10} + 1 = {result:<12} шагов: {steps}")
```

Вывод на этой машине:

```text
         0 + 1 = 1            шагов: 3
      1011 + 1 = 1100         шагов: 8
       111 + 1 = 1000         шагов: 8
  11111111 + 1 = 100000000    шагов: 18
```

Параметр `max_steps` появился не из осторожности программиста, а из теории: у машины Тьюринга нет встроенного представления о том, «долго» она работает или «вечно». Любая реальная реализация обязана ввести внешний лимит — определить факт зацикливания изнутри невозможно.

### Почему одной машины достаточно

Ключевой результат Тьюринга: существует универсальная машина (universal Turing machine), которая, получив на ленту описание любой другой машины и её вход, воспроизводит её поведение. Описание машины — это строка символов, то есть данные. Отсюда следует идея программы, хранящейся в памяти вместе с данными, — архитектура фон Неймана, на которой работают все современные серверы. Интерпретатор Python и есть универсальная машина, а файл скрипта — описание конкретной машины на ленте.

## Тезис Чёрча—Тьюринга

В 1936 году почти одновременно появились две формализации вычислимости: машины Тьюринга и лямбда-исчисление Алонзо Чёрча. Позже выяснилось, что все разумные модели — рекурсивные функции, нормальные алгорифмы Маркова, стековые автоматы с неограниченным стеком, современные языки программирования — определяют один и тот же класс функций. Тезис Чёрча—Тьюринга утверждает: функция вычислима интуитивно (то есть существует механическая процедура её вычисления) тогда и только тогда, когда она вычислима на машине Тьюринга.

Это именно тезис, а не теорема: «интуитивно вычислимая» не имеет формального определения, поэтому доказать эквивалентность нельзя. Зато её можно опровергнуть — достаточно предъявить механическую процедуру, не выразимую на машине Тьюринга. За девяносто лет таких процедур не нашлось, включая квантовые вычисления: квантовый компьютер расширяет класс эффективно решаемых задач, но не класс вычислимых функций. Практический смысл тезиса для инженера простой: любой язык, любая программа, любой скрипт — это ровно машина Тьюринга по своим возможностям. Никакой «более мощный» инструмент не появится, и, что важнее, ограничения, доказанные для машин Тьюринга, действуют и для вашего Bash-скрипта.

## Неразрешимость проблемы остановки

Проблема остановки (halting problem): по описанию программы `P` и её входа `x` определить, завершится ли `P(x)` за конечное время. Тьюринг доказал, что такая программа-анализатор не существует.

Доказательство ведётся от противного. Пусть есть функция `halts(p, x)`, которая всегда завершается и возвращает `True`, если `p(x)` останавливается, и `False` иначе. Построим на её основе программу `troll`:

```python
def troll(p: str) -> bool:
    if halts(p, p):          # если p(p) останавливается...
        while True:          # ...то troll(p) не останавливается никогда
            pass
    return True              # иначе — немедленно возвращает True
```

Теперь спросим: останавливается ли `troll(troll)`? Если `halts(troll, troll)` вернула `True`, то `troll` уходит в бесконечный цикл — противоречие. Если `False` — `troll` немедленно возвращает `True`, то есть останавливается, — снова противоречие. Значит, `halts` не может существовать: любая её реализация либо даёт неверный ответ на некоторой программе, либо сама зависает.

Обратите внимание, чего доказательство не утверждает. Оно не говорит, что нельзя определить остановку для конкретной программы — для `print("hi")` это очевидно. Оно говорит, что нет универсального метода, работающего для всех программ сразу. И это не «пока не придумали», а доказанный предел: любое расширение анализатора можно обойти тем же диагональным трюком.

### Где это встречается в работе

Следствия видны в трёх местах.

Первое — статические анализаторы. Линтеры, `mypy`, `golangci-lint` работают на консервативных приближениях: они либо пропускают часть ошибок (false negative), либо ругаются на корректный код (false positive). Обещать «полную проверку» невозможно не из-за слабости инструмента, а по теореме. Отсюда и культура `# type: ignore` — это не костыль, а плата за неразрешимость.

Второе — таймауты. Любой внешний вызов и любой CI-job должны иметь лимит времени: «дождёмся завершения» — не стратегия. `timeout 30 curl ...`, `context.WithTimeout` в Go, `timeoutSeconds` в Kubernetes — следствия отсутствия оракула остановки.

Третье — эквивалентность программ. Доказать автоматически, что две реализации одной функции идентичны, нельзя, поэтому рефакторинг проверяется тестами, а не анализатором.

## Границы автоматизации

Из сказанного вытекает рабочая классификация задач, полезная при планировании автоматизации.

| Класс задачи | Пример | Что ожидать |
|---|---|---|
| Разрешимая, эффективная | парсинг JSON, проверка схемы | автоматизируется полностью, детерминированно |
| Разрешимая, но дорогая | точное покрытие всех путей, SAT | автоматизируется с оговорками по времени |
| Полуразрешимая | «найдётся ли баг» перебором | ответ «да» рано или поздно придёт, «нет» — никогда |
| Неразрешимая | halt(P, x), эквивалентность программ | только эвристики и приближения |

Инженерный вывод прост: если инструмент обещает «гарантированно найти все проблемы», проверьте, не подменил ли он неразрешимую задачу разрешимой, сузив область (например, анализируя только типы, а не значения). Приём нормальный и полезный — но обещание надо формулировать честно.

Отдельно проговорим разницу между неразрешимостью и сложностью. Задача может быть разрешимой, но требовать экспоненциального времени; тогда практический предел наступает задолго до теоретического. Поэтому, прежде чем строить «умную» систему, оценивают не только «можно ли», но и «за сколько».

## Типичные ошибки

1. **Считать, что регулярное выражение разбирает вложенные структуры.** FSM не имеет счётчика глубины, поэтому regex «работает» на двух уровнях и ломается на трёх. Для произвольной вложенности нужен парсер со стеком.

2. **Доверять «полной» статической проверке.** Анализатор решает неразрешимую задачу, значит, он где-то приближает: либо пропускает случаи, либо ошибается на корректном коде. Настройка строгости — это выбор, в какую сторону ошибаться, а не путь к идеалу.

3. **Путать «программа не зависла» и «программа работает».** Отсутствие ошибки в логе не означает прогресса: процесс может быть в бесконечном цикле без вывода. Нужны внешние признаки живости (health-check, метрика прогресса, watchdog), а не наблюдение за тишиной.

4. **Вводить таймаут только на клиенте.** Таймаут клиента не останавливает работу на сервере; без `context`/дедлайна, проброшенного вглубь, отменённый запрос продолжает жечь CPU и соединения к базе.

5. **Пытаться доказать эквивалентность двух реализаций автоматически.** Проверка эквивалентности — неразрешимая задача в общем виде; тесты и дифференциальное тестирование дают уверенность, но не доказательство.
