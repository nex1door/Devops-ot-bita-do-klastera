# Глава 12a. API: что это такое и как им пользоваться

Большая часть работы DevOps — не писать сервисы, а соединять чужие: снять список инстансов у облака, положить образ в registry, завести тикет, забрать счёт из биллинга. Всё это HTTP API, и почти каждый инцидент «интеграция сломалась» сводится к пяти причинам: не тот заголовок аутентификации, игнорирование `429`, пагинация через `offset`, повтор неидемпотентного `POST` и ключ, закоммиченный в репозиторий. Глава — про потребление чужого API: из чего состоит вызов, как доказать, кто ты, как не упереться в лимиты, как прочитать документацию за десять минут. Проектирование своего API — в главе 13, клиент с ретраями — в главе 21.

## API — контракт, а не страница

Страница и API могут отдавать одни и те же данные из одной базы, но это разные продукты. Страница — представление для человека: вёрстка и тексты меняются свободно, потребитель смотрит глазами. API — интерфейс для программы: формат зафиксирован схемой, поля названы, коды означают конкретные вещи, проверка автоматическая.

**Контракт** — набор обещаний: какие пути есть, какие поля обязательны, какие типы у значений, что означает каждый код, сколько запросов в минуту разрешено. Обещания публикуются (документация, OpenAPI) и считаются обязательствами: нарушил сервер — это баг сервера.

**Машиночитаемость** — ответ разбирает код. Поэтому `200 OK` с телом `{"success": false}` — ловушка: мониторинг увидит успех, ретраи не сработают. Единственный сигнал, который видит вся инфраструктура по пути (прокси, балансировщик, APM), — код ответа.

**Стабильность** — клиенты выпускаются реже серверов, чужие интеграции живут годами. «Переименуем поле, это же мелочь» в API не работает; работает версия. Практическое следствие: с API нельзя договориться. Сказано «`limit` не больше 100» — при 500 вы получите `400` или молча усечённую страницу.

## Из чего состоит вызов

Вызов — шесть частей, и ошибка в любой даёт свой класс проблем.

| Часть | Пример | Типичная ошибка |
|---|---|---|
| Метод и путь | `GET /v1/tasks/1042` | `GET` вместо `POST` |
| Заголовки | `Authorization`, `Accept` | ключ в query-строке |
| Параметры | `?status=open&limit=50` | `offset` вместо курсора |
| Тело | `{"title": "..."}` | тело у `GET` |
| Код ответа | `200`, `404`, `429` | проверка только на `200` |
| Заголовки ответа | `Retry-After`, `Content-Type` | их не читают |

```http
GET /v1/tasks?status=open&limit=2 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Accept: application/json
X-Request-Id: 7f3c1a9e-2b44-4c01-9a11-5d0e6b8f2c33

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 597

{"items": [{"id": 1042, "title": "Починить CI"}], "has_more": true,
 "next_cursor": "eyJ0cyI6MTc2MTc0NDAwMCwiaWQiOjEwNDJ9"}
```

Ставьте всегда `Accept`, `User-Agent` с версией клиента, `X-Request-Id` и `Content-Type` при теле: без последнего запрос с телом получает `415` на ровном месте.

## Аутентификация: четыре способа

**API-ключ в заголовке** (`X-API-Key: 9f2c...`) опознаёт приложение, а не человека: живёт годами, отзывается в панели. Ключ в query (`?api_key=...`) — плохая практика: query попадает в access-логи, в `Referer`, в историю и в трейсы APM.

**Bearer-токен** — `Authorization: Bearer <token>` (RFC 6750). Токен либо непрозрачный (сервер ищет его в базе), либо JWT (RFC 7519) с подписанными claims. Bearer значит «кто предъявил, тот и есть»: только TLS и короткий TTL.

**Подпись запроса** — секрет не передаётся: клиент считает HMAC от канонизированных частей (метод, путь, дата, хеш тела), так работает AWS Signature Version 4. Подпись привязана к запросу и не переиспользуется; цена — сложная канонизация и чувствительность к расхождению часов (окно 5–15 минут).

**OAuth 2.0 client credentials** — обмен `client_id`/`client_secret` на access-токен (RFC 6749, §4.4). Выигрыш: короткоживущий токен вместо вечного секрета и единый механизм с остальными клиентами провайдера.

| Способ | Что летит в сеть | Ротация | Когда брать |
|---|---|---|---|
| API-ключ | сам ключ | вручную | утилиты, простые SaaS |
| Bearer/JWT | токен | по TTL | сервис уже выдаёт токены |
| Подпись | HMAC, не секрет | мгновенная | платежи, банки, AWS |
| client credentials | токен | 5–60 минут | server-to-server |

```bash
curl -sS --max-time 10 https://auth.example.com/oauth/token \
  -d grant_type=client_credentials -d client_id="$CLIENT_ID" \
  -d client_secret="$CLIENT_SECRET" -d scope="tasks:read tasks:write"
```

В ответ приходит `access_token` и `expires_in`. Токен кэшируют до истечения минус запас в минуту, а не запрашивают на каждый вызов: иначе вы упираетесь в лимит эндпоинта авторизации ещё до первой полезной операции.

## Лимиты и квоты

Лимит ({{L|g91|rate limit}}) — запросов в единицу времени; квота (quota) — всего за период. В лимит упираются на минуту, в квоту — до конца расчётного месяца, и ожиданием это не лечится.

Сервер сообщает три вещи: `429 Too Many Requests`, `Retry-After` (секунды или HTTP-дата, RFC 9110) и `X-RateLimit-Limit` / `Remaining` / `Reset`. Имена `RateLimit-*` без префикса — интернет-драфт IETF, в природе встречаются оба варианта.

Как не быть забаненным: считать `Remaining` до запроса, уважать `Retry-After` буквально, ограничивать параллелизм (двадцать потоков с ретраями — это двадцать запросов в секунду, то есть атака), не ретраить `4xx` кроме `429` и `408`, размазывать фоновые обходы (600 запросов на 10 минут — 1 rps).

```python
import time, httpx

def get_with_budget(client: httpx.Client, url: str, attempts: int = 4) -> httpx.Response:
    for attempt in range(attempts):
        r = client.get(url)
        if r.status_code != 429:
            return r
        wait = float(r.headers.get("Retry-After", 2 ** attempt))
        time.sleep(min(wait, 60))
    return r
```

Задержка берётся из ответа сервера, а не из головы клиента, и ограничена сверху: `Retry-After: 86400` иначе повесит воркер на сутки.

## Пагинация

**Offset/limit** (`?limit=50&offset=100`) позволяет прыгнуть на любую страницу, но позиция нестабильна: пока вы листаете, кто-то создаёт запись в начале — все сдвигаются, и на следующей странице вы видите дубль или пропуск. Плюс `OFFSET 100000` заставляет базу прочитать и выбросить 100 000 строк — это уже про стоимость.

**Cursor** (`?cursor=...`) — «дай 50 записей после этой». Внутри закодированы значение поля сортировки и id; сервер читает по индексу `WHERE (created_at, id) < (:ts, :id)`, вставки его не сдвигают. Минус: нельзя прыгнуть на страницу 7 и показать общее число страниц.

**Link-заголовок** (RFC 8288) сообщает URL следующей страницы, не требуя своего поля в теле:

```http
Link: <https://api.example.com/v1/tasks?limit=50&cursor=eyJ0cyI6MTc2MTc0NDAwMH0>; rel="next"
```

Клиенту достаточно идти по `rel="next"`, пока заголовок есть. Условие выхода — отсутствие `Link` или `has_more: false`, а не пустой `items`: пустая страница при живом курсоре означает, что фильтр съел всё.

Проверяйте, что курсор относится к тем же фильтрам: курсор от `status=open` в запросе `status=done` даст либо `400`, либо тихо неверный результат.

## Идемпотентность и Idempotency-Key

Сеть теряет ответы. Сервер выполнил `POST`, ответ не дошёл, клиент повторил по таймауту — две задачи. Для `PUT` и `DELETE` это не проблема: повтор не меняет результат. Для `POST` вводится `Idempotency-Key: 5b1e0f7a-...` — уникальная строка на **логическую операцию**; сервер помнит ключ с ответом (обычно 24 часа) и на повтор возвращает тот же ответ.

Два частых нарушения. Ключ генерируется внутри функции повтора — тогда каждый ретрай приходит с новым ключом и создаёт новый объект. Ключ не привязан к телу: тот же ключ с другим содержимым сервер вправе отклонить (`422`). Ответы `409` и `425` на знакомый ключ означают «операция ещё идёт»: ждать и повторять с тем же ключом.

## Версионирование и deprecated

Версия в пути (`/v1/`) видна в логах, конфиге и curl. Версия в заголовке (`Accept: application/vnd.api+json;version=2`) чище теоретически, но в отладке хуже: одинаковые URL ведут себя по-разному. Когда эндпоинт объявляют устаревшим:

1. Найти сигнал: `Deprecation`, `Sunset` (RFC 8594) с датой, changelog. Дата в `Sunset` — дедлайн, а не пожелание.
2. Зафиксировать версию в конфиге, а не «брать последнюю».
3. Понять, что ломается: переименование поля, смена типа (`1` → `"1"`), новое обязательное поле, другой код.
4. Сделать миграцию обратимой: обе версии по флагу, пока обе живы, плюс тест на контракт.

## Разбор ответа

Проверять `Content-Type`: `text/html` значит captive-прокси или страницу ошибки балансировщика, и `json.loads` соврёт про синтаксис вместо причины. Смотреть код, потом тело: успех — это `2xx`, даже если в теле `"status": "ok"`. Ошибки `problem+json` (RFC 9457) читать по `type` — он стабилен, `detail` — для лога:

```python
if r.headers.get("content-type", "").startswith("application/problem+json"):
    p = r.json()          # p["type"] — стабильный код класса, p["detail"] — конкретика
```

Ответ чужого API — недоверенные данные: поле, вчера бывшее числом, сегодня может быть строкой, поэтому схема на входе (pydantic, JSON Schema) ловит это на границе.

## Webhooks и подпись тела

Webhook — обратное направление: API зовёт вас. Endpoint публичен, отвечает `2xx` за 5–10 секунд и терпит повторы: доставка «хотя бы один раз» — норма, дубли обязательны к обработке. Порядок: проверить подпись → сохранить сырое событие в очередь → ответить `200` → обработать асинхронно. Дедупликация по id события, а не по содержимому.

Подпись — единственный способ отличить настоящий webhook от запроса любого, кто узнал URL: HMAC-SHA256 от `timestamp + "." + raw_body`, сравнение за постоянное время.

```python
import hashlib, hmac, time

def verify(raw_body: bytes, header: str, secret: bytes, tolerance: int = 300) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    ts, sig = parts.get("t", "0"), parts.get("v1", "")
    expected = hmac.new(secret, f"{ts}.".encode() + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, sig) and abs(time.time() - int(ts)) <= tolerance
```

Два нюанса: подписывается **сырое** тело (распарсить и сериализовать заново нельзя — изменится порядок ключей), и метка времени обязательна, иначе перехваченный запрос повторяют вечно.

## Как читать документацию за 10 минут

Нужны шесть вещей, в этом порядке: аутентификация (заголовок, где взять, TTL), лимиты (сколько и по чему считают), один пример запроса целиком (не работает пример — дальше читать бессмысленно), формат ошибок, пагинация, changelog с ближайшими deprecation. Плюс два вопроса, экономящие дни: есть ли sandbox и есть ли OpenAPI-спецификация — первое даёт прогнать сценарий без риска, второе избавляет от ручных моделей.

## Первый запрос: curl, потом httpx

Начинать с curl: он показывает ровно то, что ушло и пришло, без слоёв библиотеки. Ключ берётся из окружения, чтобы не осесть в истории шелла.

```bash
export TASKSVC_TOKEN="$(cat ~/.config/tasksvc/token)"
curl -sS -i --max-time 10 \
  -H "Authorization: Bearer $TASKSVC_TOKEN" \
  -H "Accept: application/json" \
  "https://api.example.com/v1/tasks?status=open&limit=2"
```

`-i` печатает заголовки (`Retry-After` и `X-RateLimit-Remaining` видно сразу), `--max-time 10` не даёт зависнуть, `-sS` убирает прогресс, но оставляет ошибки.

```python
import os, time, httpx

def fetch_open_tasks() -> list[dict]:
    headers = {"Authorization": f"Bearer {os.environ['TASKSVC_TOKEN']}",
               "Accept": "application/json"}
    tasks, cursor = [], None
    with httpx.Client(base_url="https://api.example.com/v1",
                      headers=headers, timeout=httpx.Timeout(10.0, connect=3.0)) as c:
        for _ in range(1000):                      # предохранитель от зацикливания
            params = {"status": "open", "limit": 50}
            if cursor:
                params["cursor"] = cursor
            r = c.get("/tasks", params=params)
            if r.status_code == 429:
                time.sleep(min(float(r.headers.get("Retry-After", 5)), 60))
                continue
            r.raise_for_status()
            page = r.json()
            tasks.extend(page["items"])
            cursor = page.get("next_cursor")
            if not page.get("has_more") or not cursor:
                break
    return tasks
```

Чего обычно не хватает самописным клиентам: единого `Client` (пул соединений и один TLS-handshake вместо одного на запрос), явного таймаута, предохранителя в цикле и `Retry-After` из ответа. Ретраи на таймауты и `5xx` строятся так же; полная версия с четырьмя таймаутами и джиттером — в главе 21.

## Где хранить ключ

Ключ в коде — это ключ в git, а значит в форке, CI-логе, бэкапе и чьём-то ноутбуке. Ключ живёт в переменной окружения или файле вне репозитория (права `600`), `.env` — только локально и в `.gitignore`, в проде — secret manager. У каждого окружения свой ключ: общий делает ротацию невозможной, а логи бесполезными. Ротация — по расписанию.

```bash
git log -S "sk_live_" --oneline --all        # поиск по истории коммитов
gitleaks detect --source . --no-banner       # рабочее дерево и история
```

Если ключ уже в истории, удалить строку новым коммитом недостаточно: значение остаётся в старых объектах — ключ отзывают.

## Куда двигаться дальше

Потребление и проектирование API — две стороны одного контракта: половина проблем потребления это недоделанный контракт на той стороне. Как его строить — глава 13; как собрать клиент с четырьмя таймаутами, джиттером и лимитом параллелизма — глава 21.

## Типичные ошибки

1. **Ключ в query-строке.** Query — часть URL, а URL логируется везде, где есть HTTP-сервер: access-логи, `Referer`, трейсы APM. Лечится заголовком и ротацией.
2. **Проверка только на `200`.** `201` и `204` — успех, но код падает в ветку ошибки; `500` с телом `{"ok": true}` наоборот проходит. Статус воспринимается как булево, а не как класс.
3. **Ретрай всего подряд.** `401` не исправит ключ, зато попадёт в счётчик брутфорса; `422` детерминирован. Повторяют только временное: таймауты, `502/503/504`, `429`.
4. **Новый `Idempotency-Key` на каждом повторе.** UUID генерируется внутри функции ретрая, а не до неё — и дубли создаются ровно там, где ключ должен был их предотвратить.
5. **Offset на живых данных.** На тестах с 200 записями работает; на проде вставка в начало сдвигает набор, и страница 2 начинается с уже виденной записи.
6. **Игнорирование `Retry-After` и разбор ошибки как текста.** Клиент ждёт «свои» 2 секунды вместо указанных 30, жжёт квоту до блокировки аккаунта, а причину отказа вытаскивает регуляркой из `{"message": "Bad request"}` — тексты меняются каждый релиз.

## Чек-лист

- [ ] Ключ приходит из окружения или secret manager; `gitleaks detect` чист.
- [ ] У каждого запроса явный таймаут.
- [ ] `429` обрабатывается с учётом `Retry-After`, число попыток ограничено.
- [ ] `X-RateLimit-Remaining` читается, батчи разбиты под остаток квоты.
- [ ] Пагинация завершается по `has_more: false` или отсутствию `Link`.
- [ ] Создающие `POST` отправляют `Idempotency-Key`, один на логическую операцию.
- [ ] Ошибки разбираются по `type`, webhook — по подписи сырого тела.
