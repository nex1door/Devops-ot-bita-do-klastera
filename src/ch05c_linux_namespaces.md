# Глава 5c. Linux: namespaces, cgroups, диагностика

Контейнер — не «маленькая виртуалка», а обычный процесс Linux, которому ядро показало урезанную картину мира и ограничило аппетит. Второй ОС внутри нет: тот же планировщик, тот же сетевой стек, то же ядро. Отсюда и странности, которые ломают интуицию: `free` в контейнере показывает память хоста, `sysctl -w` не работает, `docker kill` возвращает код 137, а `top` в поде врёт про CPU. В этой главе — семь видов namespaces, cgroups v2 с реальными файлами, veth и bridge, {{L|g81|overlayfs}} в двух словах, набор диагностических инструментов и разбор двух самых частых вопросов эксплуатации. В конце — прямой мост к Docker (глава 38) и Kubernetes (глава 41).

## Namespaces: что именно изолируется

Namespace (пространство имён) — это подмена глобальной таблицы ядра на локальную для группы процессов. Процесс в своём namespace видит только «свои» объекты и не подозревает о существовании остальных.

| Namespace | Что изолирует | Что видно снаружи |
|---|---|---|
| `pid` | номера процессов | процесс в контейнере — обычный PID на хосте |
| `net` | интерфейсы, адреса, маршруты, порты, iptables | свой `lo`, свой порт 80 |
| `mnt` | точки монтирования | свой корень `/`, свои тома |
| `uts` | hostname и домен NIS | своё имя хоста |
| `ipc` | очереди сообщений, семафоры, разделяемая память | свои очереди POSIX/SysV |
| `user` | uid/gid и capabilities внутри | uid 0 внутри — не uid 0 на хосте |
| `cgroup` | видимая иерархия cgroup | свой `/sys/fs/cgroup` |

Отдельно стоит `user`: он позволяет процессу быть root внутри namespace, оставаясь непривилегированным снаружи. Именно на нём держатся rootless-контейнеры (Podman, Docker в rootless-режиме), и именно без него «root в контейнере» означает настоящий root на хосте. Есть ещё `time` (смещение монотонных часов, с ядра 5.6), но в разговоре о контейнерах он почти не встречается.

Каждый namespace — объект ядра с номером {{L|g55|inode}}. Посмотреть, в каких namespace живёт процесс:

```bash
ls -l /proc/self/ns/
```

```
lrwxrwxrwx 1 nextdoor nextdoor 0 окт 29 20:14 cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 nextdoor nextdoor 0 окт 29 20:14 ipc -> 'ipc:[4026531839]'
lrwxrwxrwx 1 nextdoor nextdoor 0 окт 29 20:14 mnt -> 'mnt:[4026531841]'
lrwxrwxrwx 1 nextdoor nextdoor 0 окт 29 20:14 net -> 'net:[4026531992]'
lrwxrwxrwx 1 nextdoor nextdoor 0 окт 29 20:14 pid -> 'pid:[4026531836]'
lrwxrwxrwx 1 nextdoor nextdoor 0 окт 29 20:14 user -> 'user:[4026531837]'
lrwxrwxrwx 1 nextdoor nextdoor 0 окт 29 20:14 uts -> 'uts:[4026531838]'
```

Совпадающие номера означают общий namespace. Это самый быстрый способ проверить, «в контейнере ли» процесс: если `net` у двух процессов одинаковый — они в одной сети.

## unshare, lsns, nsenter

Создать namespace вручную — `unshare`. Полноценный «контейнер на коленке» выглядит так:

```bash
sudo unshare --pid --net --mount --uts --ipc --fork --mount-proc /bin/bash
```

```
root@host:/# ps aux
    PID TTY          TIME CMD
      1 pts/1    00:00:00 bash
      7 pts/1    00:00:00 ps
```

Внутри — два процесса и `bash` с PID 1. Снаружи это обычные PID хоста. `--fork` обязателен: без него `unshare` меняет namespace себе, а `--mount-proc` перемонтирует `/proc`, иначе `ps` покажет процессы хоста, потому что старый `/proc` остался от родителя.

Обратные инструменты — `lsns` (кто где) и `nsenter` (зайти внутрь):

```bash
lsns -t net -o NS,TYPE,NPROCS,PID,COMMAND
sudo nsenter -t 4213 -n -p ss -tlnp
```

```
        NS TYPE NPROCS   PID COMMAND
4026531840 net      24   742 python /srv/bot/bot.py
```

`nsenter -t PID -n` входит в сетевой namespace процесса и позволяет увидеть его интерфейсы и порты, не заходя в контейнер через `docker exec` — полезно, когда контейнер «почти мёртв», но процесс ещё есть. Так же работают `-m` (корень ФС), `-p`, `-u`.

## cgroups v2: иерархия и лимиты

Контрольные группы (cgroups) отвечают за вторую половину — сколько ресурсов процессу можно. В cgroups v2 иерархия одна, смонтирована в `/sys/fs/cgroup`, а контроллеры (cpu, memory, io, pids) включаются поштучно на каждом уровне через `cgroup.subtree_control`. Посмотреть, что доступно и что включено:

```bash
cat /sys/fs/cgroup/cgroup.controllers
cat /sys/fs/cgroup/cgroup.subtree_control
```

```
cpuset cpu io memory hugetlb pids rdma misc
cpuset cpu io memory pids
```

Лимиты — это файлы, и значение `max` в них означает «без ограничения».

```bash
C=/sys/fs/cgroup/system.slice/docker-0fce964f4258.scope
cat $C/memory.max $C/memory.current $C/cpu.max $C/pids.max
```

```
536870912
418734080
200000 100000
512
```

Читается так: памяти не больше 512 МиБ (536870912 = 512×1024²), занято около 400 МиБ, CPU — 200000/100000, то есть два ядра (квота 200 мс на период 100 мс), процессов не больше 512. `cpu.weight` (по умолчанию 100) задаёт не потолок, а долю при конкуренции — это разница между «не больше двух ядер» и «получить половину при перегрузке».

`memory.low` защищает память от вытеснения, `memory.high` — мягкий порог с торможением, `memory.max` — жёсткий, за которым наступает OOM. `cgroup.procs` — PID группы, `cgroup.freeze=1` — заморозка, `cgroup.kill=1` — убить всю группу разом (ядро 5.14+), что решает проблему «убил родителя — остались внуки».

## OOM: memory.events и код 137

Когда группа упирается в `memory.max`, ядро сначала пытается освободить страницы (reclaim), а если не выходит — вызывает OOM-killer и убивает процесс внутри группы. Счётчики лежат рядом:

```bash
cat $C/memory.events
```

```
low 0
high 0
max 14
oom 2
oom_kill 2
```

`max 14` — сколько раз группа упиралась в потолок, `oom_kill 2` — сколько процессов убито. Это единственный надёжный способ отличить «приложение утекло память» от «приложению не дали памяти»: если `oom_kill` растёт, виноват лимит, а не код.

Снаружи убийство выглядит как код `137` — это `128 + 9` (SIGKILL) по соглашению Unix. В `dmesg` остаётся `Memory cgroup out of memory: Killed process 2417 (python)`. Отсюда практика: `137` в Kubernetes — почти всегда `limits.memory`, `143` (`128+15`) — корректная остановка по {{L|g105|SIGTERM}}.

## Сеть контейнера: veth и bridge

Сетевой namespace сам по себе пуст: внутри только `lo`. Чтобы дать контейнеру сеть, создают пару виртуальных интерфейсов (veth pair): один конец остаётся на хосте, второй переносят в namespace контейнера. Всё, что попадает в один конец, выходит из другого.

```bash
ip -br link | head -5
ip -br addr show docker0
```

```
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
enp3s0           UP             d0:17:c2:93:74:8d <BROADCAST,MULTICAST,UP,LOWER_UP>
docker0          UP             f6:14:2a:c3:f8:9b <BROADCAST,MULTICAST,UP,LOWER_UP>
veth7f46a3a@if2  UP             aa:28:b2:95:54:19 <BROADCAST,MULTICAST,UP,LOWER_UP>
```

```
docker0          UP             172.17.0.1/16 fe80::f414:2aff:fec3:f89b/64
```

`veth7f46a3a@if2` — хостовый конец пары; `@if2` означает «парный интерфейс с индексом 2 в другом namespace». `docker0` — программный мост (bridge): он коммутирует veth-концы между собой, как обычный свитч, и держит адрес шлюза по умолчанию для контейнеров. Выход в мир — через NAT: правило `MASQUERADE` в `iptables`/`nftables` подменяет адрес контейнера на адрес хоста. Публикация порта `-p 8080:80` — это DNAT на хосте плюс запись в цепочке `DOCKER`.

Типичные симптомы: контейнер не видит соседа — разные bridge-сети; `ping` работает, а `curl` нет — MTU или NAT. Диагностика — в namespace контейнера: `nsenter -t PID -n ip addr`, `ss -tlnp`.

## overlayfs в двух словах

Корневая ФС контейнера собрана из слоёв: нижние — read-only (образ), верхний — пустой каталог для записи. overlayfs показывает их как один каталог `merged`. При записи в файл из нижнего слоя ядро сначала копирует его наверх (copy-up) и только потом меняет копию; удаление ставит в верхнем слое «белую метку» (whiteout), чтобы файл не появился снова. Изменения в контейнере живут в верхнем слое и исчезают вместе с ним, а образ остаётся неизменным; поэтому `rm` внутри не уменьшает образ (глава 38).

## Диагностика: что и где смотреть

Набор инструментов делится на три вопроса: кто ест ресурсы, кто держит файл, что говорит ядро.

```bash
cat /proc/loadavg                 # 0.84 1.15 0.64 1/555 553079
cat /proc/meminfo | head -3        # MemTotal, MemFree, MemAvailable
ps -eo pid,ppid,stat,pcpu,pmem,rss,etime,cmd --sort=-rss | head
vmstat 1 3                         # r b swpd free buff cache si so bi bo in cs us sy id wa
iostat -x 1 3                      # %util и await по дискам
ss -tlnp                           # кто слушает порты
lsof -p 2417 | head                # какие файлы и сокеты открыл процесс
strace -f -p 2417 -e trace=openat,connect
dmesg --since "1 hour ago" | tail  # OOM, ошибки драйверов, segfault
```

{{L|g66|Load average}} — самый непонятый показатель. Это среднее число задач в состоянии `R` (выполняется или ждёт CPU) и `D` (uninterruptible sleep — обычно ждёт диск или сеть) за 1, 5 и 15 минут. Поэтому load 8.0 на восьмиядерной машине с `%id` 80 — это не «процессор загружен», а «восемь процессов висят в ожидании I/O». Смотреть надо в паре: `vmstat` показывает колонку `wa` и очередь `b`, и если `wa` растёт вместе с load, а `us`/`sy` низкие — узкое место диск, а не CPU. В контейнере `/proc/loadavg` общий с хостом: load — величина не namespaced, и это одна из причин, почему метрики пода надо брать из {{L|g13|cgroup}} (`cpu.stat`), а не из `top`.

`%st` (steal) в `top` показывает, сколько времени гипервизор отобрал у вашей виртуалки — на «железном» сервере он всегда 0, а в облаке легко объясняет «медленно, хотя CPU свободен».

Три инструмента ломаются в контейнерах предсказуемо: `dmesg` требует `CAP_SYSLOG` и упирается в `kernel.dmesg_restrict=1`; `strace` требует `CAP_SYS_PTRACE` и часто запрещён seccomp; `lsof` показывает пути внутри namespace, а не хоста. Поэтому диагностируют снаружи — через `/proc/PID` и `nsenter`.

## Вопрос 1: почему контейнер видит память хоста

```bash
docker run --rm -m 512m alpine free -m
```

```
              total        used        free      shared  buff/cache   available
Mem:          15887        9214        1174         412        5498        6337
Swap:             0           0           0
```

Лимит 512 МиБ, а `free` показывает 15,5 ГиБ. Причина в том, что `/proc/meminfo` собирается из глобальных счётчиков памяти ядра, а не из cgroup. Namespaces покрывают PID, сеть, монтирования, IPC, UTS, user и cgroup — память в этот список не входит, потому что ядро одно на всех. В cgroup namespaced только дерево `/sys/fs/cgroup`, где лежит настоящий лимит.

Правильный ответ на вопрос «сколько памяти у контейнера»:

```bash
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.current
```

```
536870912
418734080
```

`memory.current` — фактическое потребление группы вместе с {{L|g82|page cache}}, поэтому оно всегда больше «памяти приложения» и уменьшается после записи на диск. В Kubernetes те же цифры приходят в метриках cAdvisor как `container_memory_working_set_bytes`, и именно на них смотрит планировщик и OOM.

Обойти вранье `free` можно через lxcfs (FUSE-слой, подменяющий `/proc/meminfo` и `/proc/cpuinfo` значениями cgroup) — так делают LXC и некоторые managed-кластеры. В Docker/Kubernetes по умолчанию этого нет, и приложение, читающее `/proc/meminfo` для автонастройки (JVM, PostgreSQL, Elasticsearch), берёт память хоста и падает по OOM. Лечится явными лимитами в конфиге (`-Xmx`, `shared_buffers`) или переменными окружения — это одна из самых частых причин «контейнер убит сразу после старта».

## Вопрос 2: почему в контейнере не работают sysctl

```bash
docker run --rm alpine sh -c 'echo 4096 > /proc/sys/net/core/somaxconn'
```

```
sh: can't create /proc/sys/net/core/somaxconn: Read-only file system
```

Причин две, и они разные. Первая: `/proc/sys` в контейнере смонтирован read-only — Docker делает это намеренно, и запись отбивается на уровне монтирования, хотя `net.*` вообще-то namespaced и принадлежит сети контейнера. Вторая: параметры `kernel.*`, `vm.*`, `fs.*` не namespaced вовсе — они относятся к ядру, а ядро у всех общее. Даже с `--privileged` запись в `kernel.shmmax` изменит настройку для всего хоста.

Практика: `net.*` задают при создании контейнера (`docker run --sysctl net.core.somaxconn=4096`) или на уровне пода (`securityContext.sysctls` в Kubernetes, где разрешён только список «безопасных» параметров). Всё остальное меняют на хосте через `/etc/sysctl.d/` и `sysctl --system` — и это, кстати, ещё один аргумент против «контейнер как замена виртуалке»: граница владения ядром проходит по хосту.

## Мост: как из этого получается Docker и зачем это Kubernetes

Сложите два механизма. Namespaces дают процессу иллюзию отдельной машины: свой PID 1, своя сеть, свой корень. Cgroups дают ему бюджет: не больше 512 МиБ, два ядра, 512 процессов. Добавьте overlayfs как корневую ФС из слоёв и `pivot_root` вместо `chroot` — получится ровно то, что делает `runc` по команде Docker: `clone(CLONE_NEWPID|CLONE_NEWNET|...)`, запись лимитов в `/sys/fs/cgroup`, монтирование overlay, `execve`.

Docker в главе 38 — обёртка над этими вызовами: образы и слои, bridge-сети, тома, рестарт-политики. Магии нет, и когда контейнер «не стартует», вопрос почти всегда один из трёх: не тот namespace, упёршийся cgroup-лимит, перекрытый слой.

Kubernetes в главе 41 добавляет оркестрацию, но опирается на то же самое: `limits.memory` — это `memory.max` в cgroup пода, `requests.cpu` — `cpu.weight`, `shareProcessNamespace` — общий pid-namespace, `hostNetwork` — отказ от net-namespace, а `terminationGracePeriodSeconds` — это `TimeoutStopSec` из главы 5b. Инженер, который знает `/sys/fs/cgroup` и `nsenter`, отлаживает поды быстрее того, кто знает только `kubectl describe`.

## Типичные ошибки

1. **Верить `free` и `top` внутри контейнера.** Память и load берутся с хоста. Механизм: `/proc/meminfo` и `/proc/loadavg` не namespaced; лимит живёт в `/sys/fs/cgroup`.
2. **`sysctl -w` в контейнере без `--sysctl`.** Ответ — `Read-only file system`. Механизм: `/proc/sys` смонтирован только для чтения, а `kernel.*`/`vm.*` вообще глобальны.
3. **`strace`/`dmesg` не работают в поде.** Механизм: нет `CAP_SYS_PTRACE`/`CAP_SYSLOG`, срабатывает seccomp.
4. **`unshare --pid` без `--fork`.** Внутри видно процессы хоста. Механизм: namespace применяется к самому `unshare`, а `ps` читает старый `/proc`.
5. **Код 137 трактуют как «упало приложение».** Механизм: `128+9` — это SIGKILL, и чаще всего его прислал OOM-killer по `memory.max`; смотреть `memory.events`.
6. **Лимит CPU как гарантия.** `cpu.max` ограничивает, но не резервирует. Механизм: квота работает только когда есть конкуренция, а `cpu.weight` — это доля, не абсолют.

## Чек-лист

- `ls -l /proc/PID/ns/` показывает, в каких namespace живёт процесс и совпадает ли `net` с ожидаемым.
- Для любого лимита известно имя файла в cgroup v2: `memory.max`, `cpu.max`, `pids.max`.
- `memory.events` прочитан перед выводами об утечке: `oom_kill` отличает лимит от бага.
- Код возврата расшифрован: 137 — SIGKILL, 143 — SIGTERM, 126/127 — про запуск, а не про приложение.
- Сеть проверена изнутри namespace (`nsenter -n ip addr`, `ss -tlnp`), а не только с хоста.
- Для диагностики снаружи доступны `/proc/PID`, `nsenter`, `dmesg` на хосте.

## Упражнения

1. Создайте через `unshare` окружение с собственным PID 1, hostname и пустым сетевым namespace. Докажите, что `ps` внутри показывает один процесс, а снаружи — все.
2. Найдите в `/sys/fs/cgroup` группу работающего контейнера и объясните каждое значение в `memory.max`, `cpu.max`, `pids.max`, `memory.events`.
3. Запустите процесс под лимитом 64 МиБ, который аллоцирует 256 МиБ, и определите по `memory.events` и `dmesg`, что именно произошло.
4. Сравните `free -m` внутри контейнера с `memory.max`/`memory.current` и объясните расхождение в двух предложениях.
5. Остановите сервис внутри контейнера и объясните разницу между `SIGTERM` и `SIGKILL` с точки зрения `terminationGracePeriodSeconds`.
